# 第8章　ACME による証明書

TLS の証明書を用意する方法には、運用者がファイルを置く方法と、コマンド `acme renew` で発行・更新する方法の 2 つがあり、本章では後者を扱います。

ACME の仕組みと必要な設定、初回の発行の手順、更新を毎日実行するタイマー、managed 設定のサイトの証明書、運用で気を付けることを順に説明します。

## 8.1　ACME の仕組み

`acme renew` は HTTP-01 のチャレンジだけを使って、証明書を発行・更新します（RFC 8555）。
CA とやり取りするのは `acme renew` のコマンドで、プロキシは CA から来るチャレンジのリクエストに応答します。

証明書の発行は次の流れで進みます。

1. **設定ファイルを書く**: `acme` と、`acme` を持つ証明書を書きます。
   証明書のファイルはまだ無くてかまいません。
2. **プロキシを起動する**: ファイルの無い証明書はハンドシェイクから外したまま起動します。
3. **`acme renew` を実行する**: サービスの OS ユーザーで実行します。
   コマンドが CA に注文し、チャレンジのファイルを `challenge_dir` に置きます。
   CA がポート 80 へチャレンジのリクエストを送ってくると、プロキシがそのファイルで応答します。
4. **コマンドが証明書と鍵のファイルを書く**
5. **プロキシに SIGUSR2 を送る**: プロキシが新しい証明書を使い始めます。

動作中のプロキシは、コマンドが証明書を書いたことに気付かないので、コマンドの後には必ず SIGUSR2 を送ります。
更新は同じコマンドを毎日実行して行い、そのための systemd のタイマーは 8.4 で説明します。

managed 設定を使う場合は、サイトの証明書を設定ファイルのパスではなく managed ストアに置き、サイトの `certificate` に `acme` を書きます（8.5）。

## 8.2　必要なもの

### ポート 80

CA は証明書のホストのポート 80 へ、平文の HTTP でチャレンジのリクエストを送ってくるので、ポート 80 に通常のリスナーかリダイレクトのリスナーを置く必要があります。
プロキシはポートの番号を検証しません。
TLS のリスナーはチャレンジに応答しません。

通常のリスナーとリダイレクトのリスナーは、次の形のリクエストに、管理画面のルート、ポリシー（全体の設定とホストごとの設定）、ルート、ルートの `access`、検査、転送、リダイレクトのどれよりも先に応答します。

- メソッドが `GET` か `HEAD` です。
- リクエストターゲットが `/.well-known/acme-challenge/<token>` で、その後ろに何もありません。
- `Host` が、`acme` を持つ証明書のホストです。

上の形に当てはまらないリクエストはチャレンジとして扱わず、ほかのリクエストと同じようにルートと検査へ回ります。

チャレンジへの応答は、`challenge_dir` にある `<token>` のファイルをボディにした 200 か、404 です。
このときのリクエストのログは、`class` が `answered` になります（第7章）。
細かい条件は、付録A 運用リファレンスの「ACME」を参照してください。

### 設定

設定ファイルには、`acme` と、`acme` を持つ証明書を書きます。
次の例では、https へのリダイレクトのリスナーと、ACME で発行する証明書を持つ TLS のリスナーを書いています。

```json
{
  "proxy": {
    "listeners": [
      {"address": "0.0.0.0:80", "redirect": {"https_port": 443}},
      {
        "address": "0.0.0.0:443",
        "tls": {
          "min_version": "1.2",
          "certificates": [
            {
              "cert_file": "/var/lib/tukuyomi-core/tls/www.pem",
              "key_file": "/var/lib/tukuyomi-core/tls/www.key",
              "hosts": ["www.example.com"],
              "acme": {"renew_before_days": 30}
            }
          ]
        }
      }
    ]
  },
  "acme": {
    "directory_url": "https://acme-staging-v02.api.letsencrypt.org/directory",
    "contact_email": "admin@example.com",
    "account_key_file": "/var/lib/tukuyomi-core/acme/account.key",
    "challenge_dir": "/var/lib/tukuyomi-core/challenges",
    "ca_file": "/etc/tukuyomi-core/acme-roots.pem",
    "timeout_ms": 300000
  }
}
```

この例は設定ファイルの抜粋で、`proxy` の `listeners` 以外の設定キーと、`forward`、`kernel`、`rules` などは省略しています。
設定の値にはデフォルト値が無いため、省略できると決まっている設定キーを除いて、実際の設定ファイルにはすべて書きます。
設定キーの一覧は、付録A 運用リファレンスの「設定ファイル」を参照してください。

- 証明書の `acme` は `{"renew_before_days"}`（1〜60）の形で、`acme renew` で発行・更新する証明書であることを示します。
  この証明書のホストに `*.` は書けません。
- 最上位の `acme` は、`managed` の無い設定では、`acme` を持つ証明書があるときだけ書きます。
  書くときは次の 6 つの設定キーをすべて書きます。
  - `directory_url`: CA の ACME ディレクトリです。
    試すときは、CA のテスト用の ACME ディレクトリ（Let's Encrypt ならステージング）を書きます。
    例の値はそのステージングです。
  - `contact_email`: CA に届ける連絡先で、形式だけを検証します。
  - `account_key_file`: ACME のアカウントの鍵で、ファイルが無ければコマンドが作成します（0600）。
  - `challenge_dir`: チャレンジのファイルを置くディレクトリです。
  - `ca_file`: CA の API のサーバー証明書を発行したルート証明書だけを入れるファイルです。
    入れられるのは 100 枚までなので、OS のルート証明書のバンドルをそのまま使うことはできません。
  - `timeout_ms`: コマンド全体のタイムアウトです。
- 値の範囲と、ほかの設定キーとの関係は、付録A 運用リファレンスの「`acme`」を参照してください。

### ディレクトリとユーザー

- `acme renew` はプロキシと同じサービスの OS ユーザーで実行します。
  root で作った鍵は、別の OS ユーザーで動作するプロキシが読めないため、root での実行は拒否します。
- `cert_file`・`key_file`・`challenge_dir` を置くディレクトリには、サービスの OS ユーザーが書き込める必要があります。
  コマンドは証明書・鍵・チャレンジのファイルを一時ファイルとして書いてから、置き換えます。
- `challenge_dir` はチャレンジ専用のディレクトリにして、ほかのファイル（`account_key_file`、`ca_file`、証明書と鍵のファイルなど）は置きません。
  ルールストア、ログのディレクトリ、管理データの保存先などと同じディレクトリにすることも、互いの中に置くこともできません。

ディレクトリの一覧と権限は、第3章を参照してください。

## 8.3　初回の発行

初回の発行は、まずテスト用の CA で発行できることを確認し、それから本番の CA に切り替える順に進めます。

1. 設定に `acme` と、`acme` を持つ証明書を書きます。
   証明書のファイルはまだ無くてかまいません。
   - `managed` の無い設定では、リスナーの証明書に `acme` を付けます。
     `managed` のある設定では、管理画面のルートの証明書（`admin.route.certificate`）と、バージョンのサイトに付けます（8.5）。
   - プロキシは `start: tls certificate not issued yet (<place>)` の行を出し、その証明書をハンドシェイクから外したまま起動します。
   - 試すときは、CA のテスト用の ACME ディレクトリ（Let's Encrypt ならステージング）を `directory_url` に書きます。
2. プロキシを起動します。
3. サービスの OS ユーザーで `acme renew` を実行します。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy acme renew /etc/tukuyomi-core/config.json
   ```

   `2.1 renewed`（`managed` のある設定では `admin route renewed` や `site www renewed`）のような行が出ます。
4. `systemctl kill -s SIGUSR2 --kill-whom=main tukuyomi-core.service` で SIGUSR2 を送ると、プロキシが証明書を使い始めます。
5. テスト用の CA で発行できたら、本番の CA に切り替えます。
   - テスト用の CA の証明書は有効期限が来ておらず、そのままでは置き換わらない（`valid`）ので、その証明書のファイルを削除します。
     削除するのは、リスナーと管理画面のルートの証明書では `cert_file` と `key_file`、ACME のサイトでは managed ストアの `acme/<hosts-sha256>/` にある `chain` と `key` です。
   - `directory_url` を本番の CA のものに変更します。
     本番の CA で、API のサーバー証明書を発行したルート証明書が違う場合は、`ca_file` も変更します。
   - もう一度 `acme renew` を実行してから、SIGUSR2 を送ります。
     ファイルを削除してから `acme renew` が終わるまでの間に SIGUSR2 を送ると、その証明書はハンドシェイクから外れます（証明書も読み込み直す設定のリロードでも同じです）。
     この順を守れば、その間もプロキシは読み込み済みの証明書を使い続けます。
   - `directory_url`・`ca_file`・`contact_email` など、`acme` の多くの設定キーはコマンドだけが読むので、プロキシの再起動は必要ありません。
     `challenge_dir` と、`acme` を持つ証明書のホストはプロキシも読むので、変更したときはプロキシに設定をリロードさせます（SIGHUP、`systemctl reload`）。
     ACME のサイトのホストは、バージョンの反映で切り替わります。
6. 毎日実行するタイマーを置きます（8.4）。

## 8.4　`acme renew` と更新のタイマー

### コマンドの動作

`acme renew` は `acme` を持つ証明書を、設定に書かれた順に調べます。
次のどれかに当てはまる証明書は、更新が必要とみなして、新しい鍵で注文し直します。

- 証明書か鍵のファイルが読めない
- 鍵が証明書に合わない
- 証明書がすべてのホストを含まない
- 有効期間の終わりまでが `renew_before_days` 日より短い（ちょうどその日数のときは、短いとみなしません）

更新が必要ない証明書は `valid` です。
結果は、`acme` を持つ証明書ごとに標準出力に 1 行ずつ出ます。
`managed` の無い設定では `<listener>.<certificate> renewed|valid|failed` の形で、リスナーと証明書の番号はどちらも 1 から数えます。
リスナーの番号は `proxy.listeners` での並びの位置で、TLS でないリスナーも数に入れます。
`failed` の証明書は、ファイルを前のまま残します。

終了コードは次のとおりです。

- 0: すべてが `renewed` か `valid`
- 1: 1 つでも `failed` がある、停止された、実行できない、root で実行した
- 2: 引数のエラー、受け付けない設定ファイル、`acme` の無い設定ファイル

コマンド全体にかかる時間は、CA の応答と待ち時間を含めて `timeout_ms` までです。
ほかの条件と、`managed` のある設定での扱いは、付録A 運用リファレンスの「`acme renew`」を参照してください。

### 更新のタイマー

証明書の更新では `acme renew` を毎日実行します。
systemd のユニットの例（サービスの `tukuyomi-core-acme.service` と、タイマーの `tukuyomi-core-acme.timer`）と、SIGUSR2 を `ExecStopPost` で送る理由は、第3章の 3.5「証明書の更新のタイマー」にあります。
ACME の更新で守る点は次の 2 つです。

- **コマンドの後に SIGUSR2 を送る**: コマンドが失敗したとき（証明書が 1 つでも `failed` のとき）でも、更新できたほかの証明書を使い始められるように、`ExecStopPost` で送ります。
  SIGHUP（`systemctl reload`）は設定ファイルの全体を読み込むので、使いません。
- **`ExecStartPost=+` で SIGUSR2 を送っているユニットは変更する**: その行を `ExecStopPost=+` の行に変更し、`systemctl daemon-reload` を実行してください。
  `ExecStartPost` はコマンドが exit 0 で終わったときだけ実行されるので、1 つでも `failed` があると、更新できたほかの証明書も、次に SIGUSR2 か SIGHUP を送るまで使われません。

## 8.5　ACME のサイト（managed 設定）

managed 設定では、バージョンのサイトの `certificate` を `{"acme": {"renew_before_days": 30}}`（1〜60）にすると、`acme renew` がそのサイトの証明書を発行・更新します。
サイトの `hosts` に書けるのは名前だけで、`*.` は書けません。

次の例はバージョンの `sites` の 1 つで、`managed import` の文書にも同じ形で書きます。

```json
{"name": "www", "hosts": ["www.example.com"], "certificate": {"acme": {"renew_before_days": 30}}}
```

ACME のサイトを使うには、設定ファイルに `acme` が必要です。
`managed` のある設定ファイルでは、ACME のサイトがバージョンの中にあるため、`acme` を持つ証明書が設定ファイルに無くても `acme` を書けます。
managed 設定そのものについては、第5章を参照してください。

### 証明書の置き場所

ACME のサイトの証明書チェーンと秘密鍵は、設定ファイルのパスではなく、managed ストアの `acme/<hosts-sha256>/chain` と `key` にあります。

`<hosts-sha256>` は、サイトの `hosts` をバイト順に並べ、それぞれの後ろに改行を付けてつないだバイト列の SHA-256 です。
サイトの名前は入らないので、ホストの組み合わせが同じなら、サイトの名前を変更してもほかのバージョンでも同じディレクトリを使います。
たとえば、次のコマンドで計算できます。

```bash
printf '%s\n' www.example.com app.example.com | LC_ALL=C sort | sha256sum | cut -d' ' -f1
```

`acme/` とその中のディレクトリが無ければ、`acme renew` が作成します（0700）。

### `acme renew` の対象

`acme renew` は `current` のバージョンを読み、`acme` を持つ管理画面のルートとバージョンのサイトを、この順に処理します。
結果の行は、`admin route renewed|valid|failed` と `site <name> renewed|valid|failed` の形です。
タイマーを失敗させないため、`acme` を持つ管理画面のルートも ACME のサイトも無いときは、結果の行を出さずに標準エラーに 1 行を出して exit 0 で終わります。

管理画面のルートの証明書に `acme` を付けた場合、証明書のファイルは設定ファイルの `cert_file`・`key_file` に書きます。
ファイルが無い間は、管理画面のルートのハンドシェイクを拒否します。
初回の発行の手順は 8.3 と同じです。

チャレンジに応答するホストは、`acme` を持つ管理画面のルートのホストと、稼働中のバージョンにある ACME のサイトのホストです。
CA はどのアドレスからも来るため、`admin.route.access` はチャレンジに適用されません。

### 証明書がまだ無いサイト

証明書のファイルが無いサイトは、まだ発行していない証明書として扱います。
起動、設定のリロード、`config check`、`managed activate` は拒否せず、`tls certificate not issued yet (site <name>)` の行を出して、そのサイトのホストに対するハンドシェイクを拒否します。
ファイルができた後に SIGUSR2 を送ると、その証明書を使い始めます。

### バージョンを変更するとき

バージョンを反映する前に、そのバージョンの ACME の証明書を発行することは、実装していません。

ホストの組み合わせを変更したバージョン（サイトにホストを追加した、変更した、`{"chain", "key"}` から `acme` に変更した、など）を反映すると、新しいディレクトリにはまだ証明書が無いため、そのサイトのすべてのホストに TLS で接続できなくなります。
以前から接続できたホストも同じです。

反映の後は、すぐに `acme renew` を実行して SIGUSR2 を送ります。
第3章の 3.5 にある更新のサービスを、`systemctl start tukuyomi-core-acme.service` で実行してください。
タイマーに任せると、次のタイマーまで接続できません。

- 管理画面で「保存して反映する」を押したとき、ACME の証明書が新しく必要なサイトがあれば、確認の画面に次の文が表示されます。
  「{n} 件のサイトで新しい証明書が必要です。acme renew で発行されるまで（タイマーに任せると最大 1 日あまり）、そのサイトのホストには TLS で接続できません。」
  `{n}` はそのサイトの数です。
- 前のバージョンに戻したとき（ロールバック、名前を指定した反映）は、そのホストの組み合わせに当たるディレクトリに前の証明書が残っていれば、発行し直さずにその証明書を使います。
  プロキシは証明書の有効期限を見ないため、有効期限の切れた証明書もそのまま使います。
  戻した後は `acme renew` を実行してください（有効期限が近ければ、発行し直します）。
- コマンドで `managed activate` を実行した後、SIGHUP を送る前に `acme renew` を実行すると、新しいバージョンだけにあるホストは、プロキシがチャレンジに応答しないため `failed` になります。
  `managed activate` の後は、すぐに設定をリロードしてください（第5章、第9章）。

バージョンを削除すると、残ったバージョンのどのサイトにも使われていないホストの組み合わせについては、その `acme/` のディレクトリも削除されます。
後で同じホストの組み合わせを持つ ACME のサイトを使うと証明書を発行し直し、この発行も CA の発行の回数に数えられます。

## 8.6　運用上の注意

最後に、ACME の運用で気を付ける点をまとめます。

- 同時実行を防ぐ仕組みは無いので、同じ設定で `acme renew` を 2 つ同時に実行しないでください（第3章の 3.5）。
- 証明書と鍵は、別のファイルに書いて同期してから、鍵、証明書の順に置き換えます。
  2 つの置き換えの間で止まると、鍵が証明書に対応しない組み合わせが残ります。
  動作中のプロキシは、SIGUSR2 を受けてもその組み合わせを拒否し、今使っているものを使い続けます。
  この組み合わせは次に実行するコマンドが作り直しますが、それまでにプロキシを起動すると、その組み合わせを拒否して起動しません（exit 1）。
- 2 つの置き換えの間に、設定のリロード（SIGHUP、制御ソケットの `reload`）、`managed activate`、`config check`、起動が重なると、証明書の検証で拒否されることがあります（`tls refused`）。
  その場合はもう一度実行してください。
  管理画面と管理 API で反映したときの扱いは、付録B 管理リファレンスの「制御ソケット」を参照してください。
- 鍵は 0600、証明書は 0644 で書きます（umask の分は引かれます）。
- ディレクトリの重なりの検証では書いたままのパスを比較するので、`acme.challenge_dir` と managed ストアにはシンボリックリンクを使わないでください。
- `acme.account_key_file` と、管理画面のルートが使う証明書と秘密鍵のファイルは、ルールストア、`records.dir`、管理データの保存先、managed ストアの中に置かないでください。
  `acme renew` はこれらのファイルを書き換えます。

ここで説明しなかった条件は、付録A 運用リファレンスの「ACME」と「ACME のサイト」にあります。
