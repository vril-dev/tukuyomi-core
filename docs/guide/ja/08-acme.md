# 第8章　ACME による証明書

TLS の証明書は、運用者がファイルを置くか、コマンド `acme renew` で発行・更新します。本章では後者を扱います。ACME の仕組みと必要な設定、初回の発行の手順、更新を毎日実行するタイマー、managed 設定のサイトの証明書、運用で気を付けることが分かります。

## 8.1　ACME の仕組み

`acme renew` は、HTTP-01 のチャレンジだけで、証明書を発行・更新します（RFC 8555）。CA とやり取りするのは `acme renew` のコマンドで、プロキシは、CA から来るチャレンジのリクエストに応答します。

証明書の発行は、次の流れで進みます。

1. 設定ファイルに `acme` と、`acme` を持つ証明書を書きます。証明書のファイルは、まだ無くてかまいません。
2. プロキシを起動します。ファイルの無い証明書は、ハンドシェイクから外したまま起動します。
3. サービスの OS ユーザーで `acme renew` を実行します。コマンドが CA に注文し、チャレンジのファイルを `challenge_dir` に置きます。CA がポート 80 へチャレンジを取りに来ると、プロキシがそのファイルで応答します。
4. コマンドが、証明書と鍵のファイルを書きます。
5. プロキシに SIGUSR2 を送ると、プロキシが新しい証明書を使い始めます。

動作中のプロキシは、コマンドが証明書を書いたことを検知しません。コマンドの後に、必ず SIGUSR2 を送ります。更新は、同じコマンドを毎日実行します。systemd のタイマーは 8.4 で説明します。

managed 設定を使うときは、サイトの証明書を設定ファイルのパスではなく managed ストアに置き、サイトの `certificate` に `acme` を書きます（8.5）。

## 8.2　必要なもの

### ポート 80

CA は、証明書のホストのポート 80 へ、平文の HTTP でチャレンジを取りに来ます。ポート 80 で、通常のリスナーかリダイレクトのリスナーを持つ必要があります。プロキシはポートの番号を検証しません。TLS のリスナーは、チャレンジに応答しません。

通常のリスナーとリダイレクトのリスナーは、次の形のリクエストに、管理画面のルート、ポリシー（全体の設定とホストごとの設定）、ルート、ルートの `access`、検査、転送、リダイレクトより先に応答します。

- メソッドが `GET` か `HEAD` です。
- リクエストターゲットが `/.well-known/acme-challenge/<token>` で、後ろに何もありません。
- `Host` が、`acme` を持つ証明書のホストです。

上の形でないリクエストは、チャレンジとして扱わず、ほかのリクエストと同じようにルートと検査へ回ります。応答は、`challenge_dir` の `<token>` のファイルをボディにした 200 か、404 です。この応答のログは、リクエストのログの `class` が `answered` になります（第7章）。細かい条件は、付録A 運用リファレンスの「ACME」を参照してください。

### 設定

設定ファイルには、`acme` と、`acme` を持つ証明書を書きます。次の例は、https へのリダイレクトのリスナーと、ACME で発行する証明書を持つ TLS のリスナーです。

```json
{
  "proxy": {
    "listeners": [
      {"address": "0.0.0.0:80", "redirect": {"https_port": 443}},
      {
        "address": "0.0.0.0:443",
        "tls": {
          "min_version": "1.2",
          "certificates": [
            {
              "cert_file": "/var/lib/tukuyomi-core/tls/www.pem",
              "key_file": "/var/lib/tukuyomi-core/tls/www.key",
              "hosts": ["www.example.com"],
              "acme": {"renew_before_days": 30}
            }
          ]
        }
      }
    ]
  },
  "acme": {
    "directory_url": "https://acme-staging-v02.api.letsencrypt.org/directory",
    "contact_email": "admin@example.com",
    "account_key_file": "/var/lib/tukuyomi-core/acme/account.key",
    "challenge_dir": "/var/lib/tukuyomi-core/challenges",
    "ca_file": "/etc/tukuyomi-core/acme-roots.pem",
    "timeout_ms": 300000
  }
}
```

例は設定ファイルの抜粋です。`proxy` の `listeners` 以外の設定キーと、`forward`、`kernel`、`rules` などは省略しました。値にデフォルト値は無いので、実際の設定ファイルには、省けると決まっている設定キーのほかは、すべて書きます。設定キーの一覧は、付録A 運用リファレンスの「設定ファイル」を参照してください。

- 証明書の `acme` は `{"renew_before_days"}`（1〜60）で、`acme renew` で発行・更新する証明書であることを示します。ホストに `*.` は書けません。
- 最上位の `acme` は、`managed` の無い設定では、`acme` を持つ証明書があるときだけ書きます。そのときは、6 つの設定キーをすべて書きます。
  - `directory_url`: CA の ACME ディレクトリです。試すときは、CA のテスト用の ACME ディレクトリ（Let's Encrypt ならステージング）を書きます。例の値は、そのステージングです。
  - `contact_email`: CA に届ける連絡先です。形式だけを検証します。
  - `account_key_file`: ACME のアカウントの鍵です。無ければコマンドが作ります（0600）。
  - `challenge_dir`: チャレンジのファイルを置くディレクトリです。
  - `ca_file`: CA の API のサーバー証明書を発行したルート証明書だけを入れます。100 枚までなので、OS のルート証明書のバンドルをそのまま使うことはできません。
  - `timeout_ms`: コマンド全体のタイムアウトです。
- 範囲と、ほかの設定キーとの関係は、付録A 運用リファレンスの「`acme`」を参照してください。

### ディレクトリとユーザー

- `acme renew` は、プロキシと同じサービスの OS ユーザーで実行します。root で実行すると、作った鍵を別の OS ユーザーのプロキシが読めないので、拒否します。
- `cert_file`・`key_file`・`challenge_dir` を置くディレクトリに、サービスの OS ユーザーが書けることが必要です。コマンドは、証明書・鍵・チャレンジのファイルを、一時ファイルとして書いてから置き換えます。
- `challenge_dir` は、チャレンジのためだけのディレクトリにします。ほかのファイル（`account_key_file`、`ca_file`、証明書と鍵のファイルなど）を置きません。ルールストア、ログのディレクトリ、管理データの保存先などと同じにも、互いの中にも置けません。

ディレクトリの一覧と権限は、第3章を参照してください。

## 8.3　初回の発行

初回の発行は、テスト用の CA で通るかを確かめてから、本番の CA に切り替える順に進めます。

1. 設定に `acme` と、`acme` を持つ証明書を書きます。証明書のファイルは、まだ無くてかまいません。
   - `managed` の無い設定では、リスナーの証明書に `acme` を付けます。`managed` のある設定では、管理画面のルートの証明書（`admin.route.certificate`）とバージョンのサイトに付けます（8.5）。
   - プロキシは、`start: tls certificate not issued yet (<place>)` の行を出して、その証明書をハンドシェイクから外したまま起動します。
   - 試すときは、CA のテスト用の ACME ディレクトリ（Let's Encrypt ならステージング）を `directory_url` に書きます。
2. プロキシを起動します。
3. サービスの OS ユーザーで `acme renew` を実行します。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy acme renew /etc/tukuyomi-core/config.json
   ```

   `2.1 renewed` のような行が出ます（`managed` のある設定では `admin route renewed`、`site www renewed` のような行）。
4. `systemctl kill -s SIGUSR2 --kill-whom=main tukuyomi-core.service`（SIGUSR2）で、プロキシが証明書を使い始めます。
5. テスト用の CA で通ったら、本番の CA に切り替えます。
   - テスト用の CA の証明書は、有効期限が来ていないので、そのままでは置き換わりません（`valid`）。その証明書のファイルを削除します。リスナーと管理画面のルートの証明書は `cert_file` と `key_file`、ACME のサイトは managed ストアの `acme/<hosts-sha256>/` の `chain` と `key` です。
   - `directory_url` を本番の CA のものに変更します。CA の API のサーバー証明書のルート証明書が違うなら、`ca_file` も変更します。
   - もう一度 `acme renew` を実行してから、SIGUSR2 を送ります。ファイルを削除してから `acme renew` が終わるまでの間に SIGUSR2 を送ると（証明書も読む設定のリロードも含みます）、その証明書はハンドシェイクから外れます。この順を守れば、その間もプロキシは読み込み済みの証明書を使い続けます。
   - `directory_url`・`ca_file`・`contact_email` など、`acme` の多くの設定キーはコマンドだけが読むので、プロキシの再起動は必要ありません。`challenge_dir` と、`acme` を持つ証明書のホストはプロキシも読むので、変更したときはプロキシに設定をリロードさせます（SIGHUP、`systemctl reload`。ACME のサイトのホストは、バージョンの反映で切り替わります）。
6. 毎日のタイマーを置きます（8.4）。

## 8.4　`acme renew` と更新のタイマー

### コマンドの動作

`acme renew` は、`acme` を持つ証明書を設定の順に調べます。次のどれかに当てはまる証明書は、更新が必要とみなして、新しい鍵で注文し直します。

- 証明書か鍵のファイルが読めない
- 鍵が証明書に合わない
- 証明書がすべてのホストを含まない
- 有効期間の終わりまでが `renew_before_days` 日より短い（ちょうどその日数は短くありません）

更新が必要ない証明書は `valid` です。結果は、`acme` を持つ証明書ごとに標準出力に 1 行出ます。`managed` の無い設定では `<listener>.<certificate> renewed|valid|failed` の形で、どちらの番号も 1 から数えます。リスナーの番号は `proxy.listeners` の並びの位置で、TLS でないリスナーも数えます。`failed` の証明書は、ファイルを前のまま残します。

終了コードは、0（すべてが `renewed` か `valid`）、1（1 つでも `failed` がある、停止された、実行できない、root で実行した）、2（引数のエラー、受け付けない設定ファイル、`acme` の無い設定ファイル）です。コマンド全体（CA の応答と待ち時間を含みます）は `timeout_ms` までです。ほかの条件と `managed` のある設定の扱いは、付録A 運用リファレンスの「`acme renew`」を参照してください。

### 更新のタイマー

更新は、`acme renew` を毎日実行します。systemd のサービスとタイマーのユニットの例（`tukuyomi-core-acme.service` と `tukuyomi-core-acme.timer`）と、SIGUSR2 を `ExecStopPost` で送る理由は、第3章の 3.5「証明書の更新のタイマー」を参照してください。ACME の更新で守る点は、次の 2 つです。

- コマンドの後に、SIGUSR2 を送ります。コマンドが失敗しても（証明書が 1 つでも `failed` のとき）、ほかの更新できた証明書が使われ始めるように、`ExecStopPost` で送ります。SIGHUP（`systemctl reload`）は、設定ファイルの全体を読み込むので、使いません。
- `ExecStartPost=+` で SIGUSR2 を送っているユニットは、その行を `ExecStopPost=+` の行に変更し、`systemctl daemon-reload` を実行してください。`ExecStartPost` はコマンドが exit 0 で終わったときだけ実行されるので、1 つの `failed` で、ほかの更新できた証明書も、次に SIGUSR2 か SIGHUP を送るまで使われません。

## 8.5　ACME のサイト（managed 設定）

managed 設定を使うときは、バージョンのサイトの `certificate` を `{"acme": {"renew_before_days": 30}}`（1〜60）にすると、`acme renew` がそのサイトの証明書を発行し、更新します。サイトの `hosts` は名前だけで、`*.` は書けません。次の例は、バージョンの `sites` の 1 つです（`managed import` の文書にも、同じ形で書きます）。

```json
{"name": "www", "hosts": ["www.example.com"], "certificate": {"acme": {"renew_before_days": 30}}}
```

ACME のサイトを使うには、設定ファイルに `acme` が必要です。`managed` のある設定ファイルは、`acme` を持つ証明書が設定ファイルに無くても `acme` を書けます（ACME のサイトはバージョンの中にあるためです）。managed 設定そのものは、第5章を参照してください。

### 証明書の置き場所

ACME のサイトの証明書チェーンと秘密鍵は、設定ファイルのパスではなく、managed ストアの `acme/<hosts-sha256>/chain` と `key` にあります。`<hosts-sha256>` は、サイトの `hosts` をバイト順に並べ、1 つずつ後ろに改行を付けてつないだバイト列の SHA-256 です。サイトの名前は入らないので、同じホストの組み合わせなら、名前を変更しても、ほかのバージョンでも、同じディレクトリを使います。

```bash
printf '%s\n' www.example.com app.example.com | LC_ALL=C sort | sha256sum | cut -d' ' -f1
```

`acme/` と、その中のディレクトリは、`acme renew` が無ければ作ります（0700）。

### `acme renew` の対象

`acme renew` は、`current` のバージョンを読みます。対象は、`acme` を持つ管理画面のルート、バージョンのサイトの順です。結果の行は `admin route renewed|valid|failed`、`site <name> renewed|valid|failed` になります。`acme` を持つ管理画面のルートも ACME のサイトも無いときは、結果の行を出さず、標準エラーに 1 行出して exit 0 で終わります（タイマーを失敗させないためです）。

管理画面のルートの証明書に `acme` を付けたときは、ファイルは設定ファイルの `cert_file`・`key_file` に書きます。ファイルが無い間は、管理画面のルートのハンドシェイクを拒否します。初回の発行は、8.3 と同じです。チャレンジに応答するホストは、`acme` を持つ管理画面のルートのホストと、稼働中のバージョンの ACME のサイトのホストです。`admin.route.access` はチャレンジに適用されません（CA はどのアドレスからも来るためです）。

### 証明書がまだ無いサイト

ファイルがまだ無いサイトは、まだ発行していない証明書です。起動、設定のリロード、`config check`、`managed activate` は拒否せず、`tls certificate not issued yet (site <name>)` の行を出して、そのサイトのホストに対するハンドシェイクを拒否します。ファイルができた後の SIGUSR2 で使い始めます。

### バージョンを変更するとき

バージョンを反映する前に、そのバージョンの ACME の証明書を発行することは、実装していません。

ホストの組み合わせを変更したバージョン（サイトにホストを追加した、変更した、`{"chain", "key"}` から `acme` に変更した）に反映すると、新しいディレクトリにはまだ証明書がありません。そのサイトのすべてのホスト（以前から接続できたホストも）に、TLS で接続できなくなります。反映の後すぐに、`acme renew` と SIGUSR2 を実行します。第3章の 3.5 の更新のサービスを、`systemctl start tukuyomi-core-acme.service` で実行します。タイマーに任せると、次のタイマーまで接続できません。

- 管理画面で「保存して反映する」を押すと、ACME の証明書が新しく必要なサイトがあるときに、確認の画面に「{n} 件のサイトで新しい証明書が必要です。acme renew で発行されるまで（タイマーに任せると最大 1 日あまり）、そのサイトのホストには TLS で接続できません。」と表示されます（`{n}` はその数です）。
- 前のバージョンに戻す（ロールバック、名前を指定した反映）と、そのホストの組み合わせのディレクトリに前の証明書が残っていれば、発行し直さずに使います。プロキシは証明書の有効期限を見ないので、有効期限の切れた証明書もそのまま使います。戻した後は `acme renew` を実行します（有効期限が近ければ発行し直します）。
- コマンドで `managed activate` した後、SIGHUP の前に `acme renew` を実行すると、新しいバージョンだけにあるホストは、プロキシがチャレンジに応答しないので `failed` になります。`managed activate` の後は、すぐに設定をリロードします（第5章、第9章）。

バージョンを削除すると、残るどのバージョンのサイトでもないホストの組み合わせの `acme/` のディレクトリも削除されます。後で同じホストの組み合わせの ACME のサイトを使うと、発行し直します（CA の発行の回数に数えます）。

## 8.6　運用上の注意

- 同じ設定で `acme renew` を 2 つ同時に実行しないでください。同時実行を防ぐ仕組みはありません（第3章の 3.5）。
- 証明書と鍵は、別のファイルに書いて同期してから、鍵、証明書の順に置き換えます。2 つの置き換えの間で止まると、鍵が証明書に対応しない組み合わせが残ります。動作中のプロキシは、SIGUSR2 でその組み合わせを拒否して現在のものを使い続け、次のコマンドが作り直します。ただし、その間にプロキシを起動すると、その組み合わせを拒否して起動しません（exit 1）。
- 2 つの置き換えの間と、設定のリロード（SIGHUP、制御ソケットの `reload`）、`managed activate`、`config check`、起動が重なると、証明書の検証で拒否されることがあります（`tls refused`）。そのときは、もう一度実行します。管理画面と管理 API の反映での扱いは、付録B 管理リファレンスの「制御ソケット」を参照してください。
- 鍵は 0600、証明書は 0644 で書きます（umask の分は引かれます）。
- `acme.challenge_dir` と managed ストアには、シンボリックリンクを使わないでください。ディレクトリの重なりの検証は、書いたままのパスで比較します。
- `acme.account_key_file` と、管理画面のルートが使う証明書と秘密鍵のファイルは、ルールストア、`records.dir`、管理データの保存先、managed ストアの中に置かないでください。`acme renew` は、これらのファイルを書き換えます。

付録A 運用リファレンスの「ACME」と「ACME のサイト」に、ここに書かなかった条件があります。
