# 第1章　tukuyomi core 入門

本章では、tukuyomi core がどのような製品かを説明します。
どのプロセスで構成されていて、それぞれが何を担い、何を持たないのかを見ていきます。
あわせて、0.2.2 で実装していること、実装していないこと、決まっていないことを整理します。

具体的な設定やコマンドは第2章以降で扱い、ここでは全体像をつかみ、用語の地図を作ることを目的にします。

## 1.1　tukuyomi core とは

tukuyomi core は、WAF を組み込んだ HTTP/HTTPS のリバースプロキシです。
受信したリクエストを Coraza または ModSecurity v3 で検査し、アップストリームへ転送します。
検査には、OWASP Core Rule Set（CRS）などのルールセットを使います。

主な機能は次のとおりです。

- HTTP/1.1 と HTTP/2（TLS）のリクエストの受信と、アップストリームへの転送
- Coraza または ModSecurity v3 によるリクエストの検査（ルールの世代の管理、検知のみのモード）
- IP アドレスと国によるアクセス制御、レート制限（全体とホストごと）
- ACME（HTTP-01）による証明書の発行と更新
- 管理 API と管理画面（managed 設定の編集と、プロキシを止めない反映、ルールの世代の操作、ログの検索、監査ログ）
- ログファイルへの出力と、PostgreSQL/MySQL へのログ送信

動作を確認しているのは、Landlock が有効な Linux x86_64 だけです。
検査プロセスは自分の権限を制限するために Landlock を使います。
製品全体のセキュリティ評価は、まだ行っていません。

## 1.2　構成要素

tukuyomi core は 1 つのプロセスではなく、役割ごとに分けた複数のプロセスで動きます。どれも同じリリースの tarball に入っています。

| 構成要素 | 役割 | 境界 |
|---|---|---|
| プロキシ（`tukuyomi-proxy`） | HTTP/HTTPS のリクエストの受信と転送、検査プロセスの起動・停止・再起動 | プロキシのプロセスは DB に接続せず、managed ストアにも書き込みません |
| 検査プロセス（Coraza、`tukuyomi-inspector`） | Coraza でリクエストを検査します | 待ち受けるポートを持ちません |
| 検査プロセス（ModSecurity v3、`tukuyomi-inspector-modsecurity`） | ModSecurity v3 でリクエストを検査します。ModSecurity を使うときだけ必要です | 待ち受けるポートを持ちません |
| 管理プロセス（`tukuyomi-proxy admin`） | 管理 API と管理画面を提供し、ルールの世代と managed 設定を操作します | ループバックアドレスで待ち受け、外部からはプロキシを通して使います |
| ログ送信プロセス（`tukuyomi-records-ship`） | プロキシのログファイルの行を PostgreSQL か MySQL のテーブルへ送ります。ログを DB へ送るときだけ必要です | 待ち受けるポートを持ちません |

### プロキシ

プロキシはリクエストを受けてアップストリームへ転送する本体です。
リスナーを 1〜8 個持ち、平文の HTTP、TLS（1.2 と 1.3）、https へのリダイレクトの 3 種類を使えます。
TLS のリスナーでは、HTTP/2 も扱えます。
アップストリームへは HTTP/1.1 で接続します。

プロキシには、検査カーネルと呼ぶ部分（Rust のライブラリ）が組み込まれています。
検査プロセスの起動、停止、再起動は、この検査カーネルが受け持ちます。
リクエストが来るたびに、検査カーネルは検査プロセスへ検査を依頼し、許可、ブロック、検査不能のどれかの結果を受け取ります。

同じ実行ファイルには、プロキシのほかに、第2章以降で使う次のコマンドもあります。

- ルールストアのコマンド（`rules`）
- 証明書のコマンド（`acme renew`）
- 設定の検証（`config check`）
- managed 設定のコマンド（`managed`）
- 管理プロセス（`admin`）

### 検査プロセス

検査プロセスはリクエストの検査だけを受け持ちます。
プロキシが子プロセスとして起動し、検査プロセスはプロキシから引き継いだ Unix ドメインソケットのペアで通信します。待ち受けるポートは持ちません。

検査エンジンは 2 つあります。
Coraza の検査プロセスは Go で作られています。
ModSecurity v3 の検査プロセスは Rust と C++ で作られていて、libmodsecurity 3.0.17 を実行ファイルに静的にリンクしています。

ModSecurity の検査プロセスが必要なのは、ModSecurity の世代を使うときと、デフォルトのエンジンやアップストリームのエンジンに `modsecurity` を指定するときだけです。使わないホストでは省略できます。

起動のときにルールの世代を読んだ後、検査プロセスは Landlock で自分を制限し、一時ディレクトリの外のファイルに触れられないようにします。あわせてケーパビリティも破棄します。
この制限の中身と、制限できないものは、第3章で説明します。

### 管理プロセス

管理プロセスはプロキシとは別のプロセスで、管理 API と、実行ファイルに組み込んだ管理画面を提供します。
ループバックアドレスで平文の HTTP の接続を待ち受けます。
外部から使うときは、プロキシの TLS リスナーを通します。

管理プロセスが行うのは、ルールの世代の一覧表示、インポート、選択、前の世代へのロールバック、managed 設定のバージョンの保存と反映などです。
動作中のプロキシへの依頼には、Unix ドメインソケット（制御ソケット）を使います。
このソケットでプロキシが応答するのは、状態の問い合わせ、世代の切り替え、managed 設定のバージョンを指定したリロードの 3 つだけです。

ユーザー、ロール（`viewer`、`operator`、`owner`）、セッション、API トークン、MFA（TOTP）、監査ログも、管理プロセスが持ちます。詳しくは第5章で説明します。

### ログ送信プロセス

ログ送信プロセスは、プロキシが書くログファイルを読み、その行を DB のテーブルへ送ります。
DB に接続するライブラリと DB のパスワードは、このプロセスにだけあり、外部からのリクエストを受けるプロキシには入れていません。
DB に接続できない間は待ち、接続が戻れば続きから送ります。詳しくは第7章で説明します。

### プロセスの境界

どのプロセスもプロキシと同じ OS ユーザーで動き、root では動きません。
ユーザー ID のどれかが 0 のときは、起動もすべてのコマンドも拒否します。

0.2.2 では、検査プロセスとログ送信プロセスを別の OS ユーザーや別のサービスで動かすことは実装していません。
つまり、プロセスは分けていても、OS ユーザーの境界は分けていません。
各プロセスのファイルの置き場と権限は、この前提で決めます（第3章）。

## 1.3　リクエストが通る道筋

ここでは、クライアントから届いたリクエストが処理される主な段階だけを順に示します。
順番の詳しい定義は、付録A 運用リファレンスの「リクエストの検証の順序」にあります。

1. **ヘッダー部の検証**: HTTP の解析の前に、ヘッダー部の形式と上限を厳格に検証します。
   違反したリクエストは、アップストリームへ何も送らずに、ボディの無い決まった応答（400、408、413、414、415、417、431）で拒否します。
2. **アクセス制御とレート制限**: IP アドレスと国によるアクセス制御で拒否したときは 403、レート制限を超えたときは 429 で応答します。どちらもルートを選ぶ前に行います。
   ホストごとの設定（`host_policies`）があるときは、全体の設定の代わりにそれを適用します。ホストごとの設定では、全体の設定を引き継ぐこともできます。
3. **ルートの選択**: リクエストの `Host` とパスから、アップストリームを選びます。
   どのルートにも一致せず、デフォルトのアップストリームも無いときは 404 です。
4. **検査**: 検査するルートでは、リクエストの URI、ヘッダー、ボディの先頭を検査します。
   検査を受け持つのは、行き先のアップストリームが使うエンジンの検査プロセスです。
   結果は、許可、ブロック、検査不能の 3 つです。
   検査除外のルートに一致したリクエストは、検査せずに転送します。
5. **転送**: 許可したリクエストと、検知のみのモードでルールに一致したリクエストは、アップストリームへ転送します。
   ブロックしたリクエストは転送せず、ルールのステータスコードで応答します。

運用では、次の点を押さえておいてください。

- **検査を完了できないリクエストは、許可になりません**: 検査プロセスが使えないときや検査の待ち行列が満杯になったときなど、技術的な理由で検査できなかったリクエストには 503 で応答し、転送しません。
  検査除外のルートのように意図して検査しないことと、検査できなかったことは、区別して扱います。
- **検査するのは、ボディの先頭だけです**: ボディのうち、設定したバイト数（1 MiB まで）を検査し、許可した後の残りは検査せずにアップストリームへ流します。
  検査できるボディの型も限られます。
  詳しくは、付録A 運用リファレンスの「リクエストボディの上限と検査する長さ」と「ボディの型」を参照してください。
- **応答は検査しません**: 0.2.2 では、アップストリームから返ってきた応答を検査する機能を実装していません。
- **アップストリームの失敗は 502 です**: 接続できないときや応答が不正なとき、タイムアウトしたときなどは、プロキシが 502 で応答します。

## 1.4　設定ファイルと各プロセス

プロキシ、管理プロセス、ログ送信プロセスは、同じ 1 つの設定ファイルを読みます。
設定ファイルは UTF-8 で書いた JSON のオブジェクト 1 つで、大きさは 256 KiB までです。
最上位の設定キーは次のとおりです。

```text
{"proxy": {..}, "forward": {..}, "kernel": {..}, "rules": {"store": {..}}, "acme": {..}, "status": {..}, "records": {..}, "access": {..}, "rate_limit": {..}, "host_policies": [..], "geo": {..}, "admin": {..}, "managed": {..}}
```

このうち `acme`、`status`、`records`、`access`、`rate_limit`、`host_policies`、`geo`、`admin`、`managed` は省略できます。
省略できると決まっている設定キーのほかは、すべて書く必要があります。
**設定の値にデフォルト値はありません。**
最初の設定ファイルが長くなるのは、このためです（第2章）。

設定ファイルについて、運用で押さえておく点は次のとおりです。

- 未知の設定キー、同じ設定キーの重複、型が違う値は受け付けません。
  値の範囲と、値どうしの関係は、起動のときに検証します。
  起動の前に同じ検証をするのが、`config check` のコマンドです。
- 3 つのプロセスは同じ設定ファイルを読み、どれも未知の設定キーを受け付けません。
  新しい設定キーは、実行ファイルを入れ替えて同じリリースにそろえてから書いてください（第9章）。
- `admin` の中には、プロキシが使う設定キー（`listen`、`control`、`route`）と、管理プロセスが使う設定キーがあります。
  ほかの設定キーについては、プロキシは値を検証するだけです。
- ログ送信プロセスは managed 設定のバージョンを読みません。

設定キーの全体は、付録A 運用リファレンスの「設定ファイル」にある「全体の構成」と「例」で確認できます。

## 1.5　ルールセットの世代と managed 設定

本書を通して出てくる仕組みが 2 つあり、名前が似ているので、最初に区別しておきます。

### ルールセットの世代

ルールの世代は、`rules import` が作るルールセットの一式で、ある時点で有効なルールと設定の組み合わせを表します。
世代を指すときは、内容のフィンガープリント（マニフェストの SHA-256）を使います。
一度作った世代は変わらず、更新するたびに新しい世代になります。

- 世代には、検査するエンジン（Coraza か ModSecurity）とモードがあります。
  モードは、ブロックする「遮断」か、ルールに一致しても通してログに残す「検知のみ」のどちらかです。
  検査除外のルート（Host とパス）を持たせることもできます。
- インポートでは、検査プロセスを 1 つ起動して決まったリクエストを検査し（事前検証）、通ったものだけが世代になります。
  インポートしただけでは使われず、`rules activate` でエンジンごとに 1 つ選択します。
- コマンドで世代を選択しただけでは、動作中のプロキシは切り替わりません。
  SIGUSR1 を受けたときに、プロキシは止まらずに切り替わります。
  管理画面と管理 API からは、選択に続けて、制御ソケットで切り替えを依頼します。
- 検査するエンジンは、アップストリームごとに選べます。
  アップストリームの `engine` で指定します。省略すると、デフォルトのエンジンになります。

CRS は同梱していないので、バージョンとチェックサムを固定したスクリプトでダウンロードします（第2章）。
世代の扱いは第4章で説明します。

### managed 設定

managed 設定は、設定の一部を設定ファイルから切り離し、管理画面と管理 API から変更できるようにする仕組みです。
対象は、サイトと証明書、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定です。
これらを managed ストア（設定の `managed.dir` のディレクトリ）にバージョンとして保存します。

- バージョンの名前は内容の SHA-256 で、一度保存したバージョンの内容は変わりません。
  ルールの世代とは別のものです。
- 管理画面と管理 API から、検証して保存し、動作中のプロキシを止めずに反映できます。
  保存したバージョンは残るので、前のバージョンへ戻せます。
- managed 設定を使うには、設定ファイルに `managed` を書きます。書かなければ、設定ファイルだけで動きます。
  使うかどうかを切り替えるには、プロキシと管理プロセスの再起動が必要です。
  `managed` を使うと、設定ファイルに書けなくなる設定キーがあります。

managed 設定を使うか、設定ファイルだけで動かすかを決めるときは、第5章と付録A 運用リファレンスの「managed 設定を使うかどうか」を参照してください。

## 1.6　上流の tukuyomi との関係

tukuyomi core は、tukuyomi（tukuyomi WAF）から派生し、WAF の機能に特化した製品を目指しています。
主な実装言語は Rust です。

ただし、tukuyomi のどの機能を残し、どの機能を除くかの基準は、ドキュメントで未決定とされています。
基準が決まるまでは、個々の機能を残すか除くかは決めていません。
移植元にする tukuyomi のバージョンも未決定です。

tukuyomi の機能や設定が tukuyomi core にあるかどうかは、1.7 と、ドキュメントのシステム概要にある「現在の状態」で確認してください。
製品のコードにあるのは、1.7 に挙げた範囲だけです。

## 1.7　実装しているものと、していないもの

ドキュメントのシステム概要にある「現在の状態」の項目に沿って、0.2.2 で実装している範囲をまとめます。
なお、ドキュメントは各部分の実装について、「WAF としての完成を意味しません」と注記しています。

### 実装しているもの

| 項目 | 内容 |
|---|---|
| リクエストの検査 | 受信したリクエストの URI、ヘッダー、ボディの先頭を検査カーネルで検査します。検査できるボディの型は限られます |
| ルールの世代 | ルールセットのインポート、エンジンごとの世代の選択と切り替え、アップストリームごとの検査エンジンの選択、検知のみのモード、検査除外のルート。管理 API と管理画面からも、インポート、選択、切り替え、ロールバックができます |
| HTTP/HTTPS の受信と転送 | 平文の HTTP、TLS、https へのリダイレクトのリスナー。アップストリームごとの TLS 接続、重みによるサーバーの選択、ダウン判定、WebSocket の転送（フレームは検査しません） |
| アクセス制御とレート制限 | IP アドレスと国による全体の許可・拒否と、クライアントごとのレート制限。どちらもホストごとの設定で変えられます。国のデータベースは同梱せず、運用者が置きます |
| managed 設定 | サイトと証明書、アップストリーム、ルートなどをバージョンとして保存します。管理画面と管理 API から変更し、プロキシを止めずに反映します |
| ログ | 1 行 1 件の JSON を標準エラーに出し、設定すればログファイルにも書きます。ログ送信プロセスで PostgreSQL か MySQL へ送れます。管理 API と管理画面で、ログファイルを検索できます |
| 監視 | 監視用のリスナーの `/healthz`・`/readyz`・`/metrics`（Prometheus のテキスト形式）と、systemd の `Type=notify` への通知 |
| 証明書 | ファイルを置くか、`acme renew`（ACME の HTTP-01）で発行・更新します。SIGUSR2 で再読み込みします |
| 管理プロセス | 管理 API と管理画面（日本語と英語）。ユーザー、ロール、セッション、API トークン、MFA（TOTP）、ログインの試行回数の制限、監査ログ |
| OS 上の権限の制限 | root では動きません。検査プロセスは起動時に Landlock とケーパビリティの破棄で自分を制限します |
| 配布 | 0.1.0 から、Linux x86_64 用の 4 つの実行ファイルを 1 つの tarball にまとめ、GitHub のリリースで配布しています。ソースからもビルドできます |

0.1.0 からの変更は、付録C リリースノートを参照してください。

### 実装していないもの

- HTTP の受信と転送のうち、上の範囲に入らないもの: HTTP/3、平文の HTTP/2、アップストリームへの HTTP/2、リクエストのトレーラー、1xx の応答の中継（WebSocket の 101 を除きます）、PROXY protocol、応答のキャッシュ
- 次のボディの検査: XML のボディ、`application/json` と `application/<name>+json` 以外の JSON の型（`text/json` など）、`gzip` 以外の Content-Encoding を持つボディ
- 応答の検査
- 設定ファイルそのものを管理 API や管理画面で編集すること。
  管理画面で編集できるのは managed 設定で、設定ファイルは値を表示するだけです
- 管理プロセスとログ送信プロセスが、動作中に自分の設定の値を変更すること
- 接続を切らずに実行ファイルを入れ替えること
- managed 設定のバージョンを反映する前に、そのバージョンの ACME の証明書を発行すること
- TLS の秘密鍵をプロキシとは別のプロセスで扱うこと
- 署名付きの監査ログとトレーシング
- ユーザー、API トークン、履歴をファイル以外に保存すること
- PostgreSQL と MySQL 以外へのログの保存。
  管理 API と管理画面で、DB からログを検索すること
- Linux x86_64 以外の環境向けの、ビルド済みの実行ファイル
- 検査プロセスとログ送信プロセスを別の OS ユーザーや別のサービスで動かすこと

### 決まっていないこと

ドキュメントで未決定とされているものです。0.2.2 の実装はこれらを決めたものではありません。

- どの機能を残し、どの機能を除くかの基準。
  移植元とする tukuyomi のバージョン
- 応答の検査を行うかどうか、行う場合の範囲
- 対応する HTTP のバージョンと通信の種類
- 管理画面の再利用・改善の範囲と、元にするバージョン
- 配布形態、対応する環境、デプロイ構成
- 設定、ルール、ログの保存の方式。
  ログの保存の期間と容量の方針
- 全体としての安全性の評価（評価していません）

現在の実装は 1 台の Linux ホストで動くもので、systemd の例があります（第3章）。

## 1.8　次章への橋渡し

ここまでで、tukuyomi core の全体像が見えてきました。
中心にあるのは、リクエストを検査プロセスで検査してアップストリームへ転送するプロキシで、管理プロセスとログ送信プロセスはプロキシとは別のプロセスです。
そして運用の軸になるのが、ルールの世代と managed 設定という 2 つの仕組みです。

次の第2章では、本番の構成を組む前に、1 台の Linux ホストで tukuyomi core を手で起動します。
通常のリクエストが通ることと、SQL インジェクションのリクエストがブロックされることをログで確認します。
tukuyomi core に触れたことがない方は、第2章で手を動かしてから第3章以降へ進むと、設定キーの意味をつかみやすくなります。
