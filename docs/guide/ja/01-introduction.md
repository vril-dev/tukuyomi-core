# 第1章　tukuyomi core 入門

本章では、tukuyomi core がどのような製品か、どのプロセスで構成され、それぞれが何を担い、何を持たないのかを説明します。あわせて、0.2.0 で実装していることと、実装していないこと、決まっていないことを整理します。具体的な設定やコマンドは第2章以降で扱うので、ここでは全体像と用語の地図づくりを目的とします。

## 1.1　tukuyomi core とは

tukuyomi core は、WAF を組み込んだ HTTP／HTTPS のリバースプロキシです。受信したリクエストを Coraza または ModSecurity v3 で検査し、アップストリームへ転送します。検査には、OWASP Core Rule Set（CRS）などのルールセットを使います。

主な機能は次のとおりです。

- HTTP/1.1 と HTTP/2（TLS）のリクエストの受信と、アップストリームへの転送
- Coraza または ModSecurity v3 によるリクエストの検査（ルールセットの世代の管理、検知のみのモード）
- IP アドレスと国によるアクセス制御、レート制限（全体とホストごと）
- ACME（HTTP-01）による証明書の発行と更新
- 管理 API と管理画面（managed 設定の編集と、プロキシを止めない反映、ルールセットの世代の操作、ログの検索、監査ログ）
- ログファイルへの出力と、PostgreSQL／MySQL へのログ送信

動作を確認しているのは、Landlock が有効な Linux x86_64 だけです。Landlock は、検査プロセスが自分の権限を制限するために使います。製品全体のセキュリティ評価は、まだ行っていません。

## 1.2　構成要素

tukuyomi core は、1 つのプロセスではなく、役割ごとに分けた複数のプロセスで動きます。どれも同じリリースの tarball に入っています。

| 構成要素 | 役割 | 境界 |
|---|---|---|
| プロキシ（`tukuyomi-proxy`） | HTTP／HTTPS のリクエストの受信と転送、検査プロセスの起動・停止・再起動 | プロキシのプロセスは、DB に接続しません。managed ストアにも書き込みません |
| 検査プロセス（Coraza、`tukuyomi-inspector`） | Coraza でリクエストを検査します | 待ち受けるポートを持ちません |
| 検査プロセス（ModSecurity v3、`tukuyomi-inspector-modsecurity`） | ModSecurity v3 でリクエストを検査します。ModSecurity を使うときだけ必要です | 待ち受けるポートを持ちません |
| 管理プロセス（`tukuyomi-proxy admin`） | 管理 API と管理画面を提供し、ルールの世代と managed 設定を操作します | ループバックアドレスで待ち受けます。外部からは、プロキシを通して使います |
| ログ送信プロセス（`tukuyomi-records-ship`） | プロキシのログファイルの行を、PostgreSQL か MySQL のテーブルへ送ります。ログを DB へ送るときだけ必要です | 待ち受けるポートを持ちません |

### プロキシ

プロキシは、リクエストを受けて、アップストリームへ転送する本体です。リスナーを 1〜8 個持ち、平文の HTTP、TLS（1.2 と 1.3）、https へのリダイレクトの 3 種類を使えます。TLS のリスナーでは HTTP/2 も扱えます。アップストリームへは HTTP/1.1 で接続します。

プロキシは、検査カーネルと呼ぶ部分（Rust のライブラリ）を組み込んでいます。検査カーネルが、検査プロセスの起動、停止、再起動を受け持ちます。リクエストが来るたびに、検査カーネルが検査プロセスへ検査を依頼し、許可、ブロック、検査不能のどれかの結果を受け取ります。

同じ実行ファイルが、ルールストアのコマンド（`rules`）、証明書のコマンド（`acme renew`）、設定の検証（`config check`）、managed 設定のコマンド（`managed`）、管理プロセス（`admin`）も持ちます。コマンドの使い方は第2章以降で出てきます。

### 検査プロセス

検査プロセスは、リクエストの検査だけを担います。プロキシが子プロセスとして起動し、プロキシから引き継いだ Unix ドメインソケットのペアで通信します。待ち受けるポートは持ちません。

検査エンジンは 2 つあります。Coraza の検査プロセスは Go で、ModSecurity v3 の検査プロセスは Rust と C++ で作られています（libmodsecurity 3.0.17 を実行ファイルに静的にリンクしています）。ModSecurity の検査プロセスは、ModSecurity の世代を使うときと、デフォルトのエンジンやアップストリームのエンジンに `modsecurity` を指定するときだけ必要で、使わないホストでは省けます。

検査プロセスは、起動のときにルールセットの世代を読んだ後、Landlock で、一時ディレクトリの外のファイルに触れられないよう自分を制限します。あわせてケーパビリティを破棄します。この制限の中身と、制限できないものは、第3章で説明します。

### 管理プロセス

管理プロセスは、プロキシとは別のプロセスで、管理 API と、実行ファイルに組み込んだ管理画面を提供します。ループバックアドレスで、平文の HTTP の接続を待ち受けます。外部から使うときは、プロキシの TLS リスナーを通します。

管理プロセスは、ルールの世代の一覧表示、インポート、選択、前の世代へのロールバック、managed 設定のバージョンの保存と反映などを行います。動作中のプロキシへの依頼は、Unix ドメインソケット（制御ソケット）で行います。プロキシはこのソケットでは、状態の問い合わせ、世代の切り替え、managed 設定のバージョンを指定したリロードの 3 つにだけ応答します。ユーザー、ロール（`viewer`、`operator`、`owner`）、セッション、API トークン、MFA（TOTP）、監査ログも管理プロセスが持ちます。第5章で説明します。

### ログ送信プロセス

ログ送信プロセスは、プロキシが書くログファイルを読み、行を DB のテーブルへ送ります。DB に接続するライブラリと DB のパスワードは、このプロセスにだけあり、外部からのリクエストを受けるプロキシには入れていません。DB に接続できない間は待ち、接続が戻れば続きから送ります。第7章で説明します。

### プロセスの境界

どのプロセスも、プロキシと同じ OS ユーザーで動きます。root では動きません。起動もすべてのコマンドも、ユーザー ID のどれかが 0 なら拒否します。検査プロセスとログ送信プロセスを、別の OS ユーザーや別のサービスで動かすことは、0.2.0 では実装していません。つまり、プロセスを分けても、OS ユーザーの境界は分けていません。この前提で、各プロセスのファイルの置き場と権限を決めます（第3章）。

## 1.3　リクエストが通る道筋

クライアントから届いたリクエストは、次の順に処理されます。ここに示すのは主な段階です。順番の詳しい定義は、付録A 運用リファレンスの「リクエストの検証の順序」にあります。

1. **ヘッダー部の検証。** HTTP の解析の前に、ヘッダー部の形式と上限を厳格に検証します。違反したリクエストは、アップストリームへ何も送らずに、ボディの無い決まった応答（400、408、413、414、415、417、431）で拒否します。
2. **アクセス制御とレート制限。** IP アドレスと国による許可・拒否は 403 で、レート制限の超過は 429 で、ルートを選ぶ前に拒否します。ホストごとの設定（`host_policies`）があれば、全体の設定の代わりにそれを適用します（全体の設定を引き継ぐこともできます）。
3. **ルートの選択。** リクエストの `Host` とパスから、アップストリームを選びます。どのルートにも一致せず、デフォルトのアップストリームも無いときは 404 です。
4. **検査。** 検査するルートでは、リクエストの URI、ヘッダー、ボディの先頭を、行き先のアップストリームが使うエンジンの検査プロセスで検査します。結果は、許可、ブロック、検査不能の 3 つです。検査除外のルートに一致したリクエストは、検査せずに転送します。
5. **転送。** 許可したリクエストと、検知のみのモードでルールに一致したリクエストは、アップストリームへ転送します。ブロックしたリクエストは、ルールのステータスコードで応答し、転送しません。

次の点は、運用で押さえておいてください。

- **検査を完了できないリクエストは、許可になりません。** 検査プロセスが使えない、検査の待ちが満杯になった、といった技術的な理由で検査できないリクエストは、503 で応答し、転送しません。検査除外のルートのように、意図して検査しないことと、検査できなかったことは、区別して扱います。
- **検査するのは、ボディの先頭だけです。** ボディは、設定したバイト数（1 MiB まで）を検査します。許可した後の残りは、検査せずにアップストリームへ流します。検査できるボディの型も限られます。詳しくは、付録A 運用リファレンスの「リクエストボディの上限と検査する長さ」と「ボディの型」を参照してください。
- **応答は検査しません。** アップストリームから返ってきた応答の検査は、0.2.0 では実装していません。
- **アップストリームの失敗は 502 です。** 接続できない、応答が不正、タイムアウトしたといった場合に、プロキシが 502 で応答します。

## 1.4　設定ファイルと各プロセス

プロキシ、管理プロセス、ログ送信プロセスは、同じ 1 つの設定ファイルを読みます。設定ファイルは、UTF-8 の JSON の 1 つのオブジェクトで、256 KiB までです。最上位の設定キーは次のとおりです。

```text
{"proxy": {..}, "forward": {..}, "kernel": {..}, "rules": {"store": {..}}, "acme": {..}, "status": {..}, "records": {..}, "access": {..}, "rate_limit": {..}, "host_policies": [..], "geo": {..}, "admin": {..}, "managed": {..}}
```

`acme`、`status`、`records`、`access`、`rate_limit`、`host_policies`、`geo`、`admin`、`managed` は省けます。省けると決まっている設定キーのほかは、すべて書きます。**設定の値にデフォルト値はありません。** 最初の設定ファイルが長くなるのは、このためです（第2章）。

設定ファイルについて、運用上の要点は次のとおりです。

- 未知の設定キー、同じ設定キーの重複、型が違う値は受け付けません。範囲と値どうしの関係は、起動のときに検証します。起動の前に同じ検証を実行するのが、`config check` のコマンドです。
- 3 つのプロセスは同じ設定ファイルを読み、どれも未知の設定キーを受け付けません。新しい設定キーを書くときは、実行ファイルをそろえて入れ替えてから書きます（第9章）。
- `admin` は、プロキシが使う設定キー（`listen`、`control`、`route`）と、管理プロセスが使う設定キーを持ちます。プロキシは、ほかの設定キーの値を検証するだけです。
- ログ送信プロセスは、managed 設定のバージョンを読みません。

設定キーの全体は、付録A 運用リファレンスの「設定ファイル」の「全体の構成」と「例」にあります。

## 1.5　ルールセットの世代と managed 設定

本書を通して出てくる仕組みが 2 つあります。名前が似ているので、最初に区別しておきます。

### ルールセットの世代

ルールセットの世代は、`rules import` が作るルールセットの一式で、ある時点で有効なルールと設定の組み合わせです。内容のフィンガープリント（マニフェストの SHA-256）で呼びます。いったん作った世代は変わりません。更新するたびに、新しい世代になります。

- 世代は、検査するエンジン（Coraza か ModSecurity）と、モード（ブロックする「遮断」か、ルールに一致しても通してログに残す「検知のみ」か）を持ちます。検査除外のルート（Host とパス）を持たせることもできます。
- インポートでは、検査プロセスを 1 つ起動して決まったリクエストを検査します（事前検証）。通ったものだけが世代になります。インポートしただけでは使われず、`rules activate` でエンジンごとに 1 つ「選択」します。
- コマンドで選択した世代へ、動作中のプロキシが切り替わるのは、SIGUSR1 を受けたときです。プロキシは止まりません。管理画面と管理 API からは、選択に続けて、制御ソケットで切り替えを依頼します。
- アップストリームごとに、検査するエンジンを選べます（アップストリームの `engine`。省けばデフォルトのエンジン）。

CRS は同梱していません。バージョンとチェックサムを固定した取得スクリプトで取得します（第2章）。世代の扱いは第4章で説明します。

### managed 設定

managed 設定は、設定の一部を設定ファイルから分け、管理画面と管理 API から変更する仕組みです。サイトと証明書、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定が対象です。これらを、managed ストア（設定の `managed.dir` のディレクトリ）に「バージョン」として保存します。

- バージョンの名前は内容の SHA-256 で、一度保存したバージョンの内容は変わりません。ルールの世代とは別のものです。
- 管理画面と管理 API から、検証して保存し、動作中のプロキシに反映できます。反映でプロキシは止まりません。保存したバージョンは残り、前のバージョンへ戻せます。
- 設定ファイルに `managed` を書いたときに使い始めます。書かなければ、設定ファイルだけで動きます。使うかどうかの切り替えには、プロキシと管理プロセスの再起動が要ります。`managed` を使うと、設定ファイルに書けなくなる設定キーがあります。

どちらを選ぶかの判断は、第5章と、付録A 運用リファレンスの「managed 設定を使うかどうか」を参照してください。

## 1.6　上流の tukuyomi との関係

tukuyomi core は、tukuyomi（tukuyomi WAF）から派生し、WAF の機能に特化した製品を目指しています。主な実装言語は Rust です。

ただし、tukuyomi のどの機能を残し、どの機能を除くかの基準は、ドキュメントでは未決定としています。基準が決まるまで、個々の機能を残すか除くかは決めていません。移植元とする tukuyomi のバージョンも、未決定です。

運用では、tukuyomi の機能や設定が tukuyomi core にあるかどうかを、1.7 と、ドキュメントのシステム概要の「現在の状態」で確かめてください。製品のコードとして、1.7 に挙げた範囲のほかはありません。

## 1.7　実装しているものと、していないもの

0.2.0 で実装している範囲を、ドキュメントのシステム概要の「現在の状態」の項目に沿ってまとめます。ドキュメントは、各部分の実装について「WAF としての完成を意味しません」と注記しています。

### 実装しているもの

| 項目 | 内容 |
|---|---|
| リクエストの検査 | 受信したリクエストの URI、ヘッダー、ボディの先頭を、検査カーネルで検査します。検査できるボディの型は限られます |
| ルールの世代 | ルールセットのインポート、エンジンごとの世代の選択と切り替え、アップストリームごとの検査エンジンの選択、検知のみのモード、検査除外のルート。管理 API と管理画面からも、インポート、選択、切り替え、ロールバックができます |
| HTTP／HTTPS の受信と転送 | 平文の HTTP、TLS、https へのリダイレクトのリスナー。アップストリームごとの TLS 接続、重みによるサーバーの選択、ダウン判定、WebSocket の転送（フレームは検査しません） |
| アクセス制御とレート制限 | 全体の IP アドレスと国による許可・拒否と、クライアントごとのレート制限。どちらも、ホストごとの設定でホストごとに変えられます。国のデータベースは同梱せず、運用者が置きます |
| managed 設定 | サイトと証明書、アップストリーム、ルートなどを、バージョンとして保存し、管理画面と管理 API から変更して、プロキシを止めずに反映します |
| ログ | 1 行 1 件の JSON を標準エラーに出し、設定すれば、ログファイルにも書きます。ログ送信プロセスが PostgreSQL か MySQL へ送れます。管理 API と管理画面で、ログファイルを検索できます |
| 監視 | 監視用のリスナーの `/healthz`・`/readyz`・`/metrics`（Prometheus のテキスト形式）と、systemd の `Type=notify` への通知 |
| 証明書 | ファイルを置くか、`acme renew`（ACME の HTTP-01）で発行・更新します。SIGUSR2 で再読み込みします |
| 管理プロセス | 管理 API と管理画面（日本語と英語）。ユーザー、ロール、セッション、API トークン、MFA（TOTP）、ログインの試行回数の制限、監査ログ |
| OS 上の権限の制限 | root では動きません。検査プロセスは、起動時に Landlock とケーパビリティの破棄で自分を制限します |
| 配布 | 0.1.0 から、Linux x86_64 用の 4 つの実行ファイルを 1 つの tarball にまとめ、GitHub のリリースで配布しています。ソースからもビルドできます |

0.1.0 からの変更は、付録C リリースノートを参照してください。

### 実装していないもの

- HTTP の受信と転送のうち、上の範囲の外のもの（HTTP/3、平文の HTTP/2、アップストリームへの HTTP/2、リクエストのトレーラー、1xx の応答の中継（WebSocket の 101 を除きます）、PROXY protocol、応答のキャッシュ）
- XML のボディ、`application/json` と `application/<name>+json` 以外の JSON の型（`text/json` など）、`gzip` 以外の Content-Encoding を持つボディの検査
- 応答の検査
- 設定ファイルそのものを、管理 API や管理画面で編集すること。管理画面で編集できるのは managed 設定で、設定ファイルは値を表示するだけです
- 管理プロセスとログ送信プロセスが、動作中に自分の設定の値を変更すること
- 実行ファイルを、接続を切らずに入れ替えること
- managed 設定のバージョンを反映する前に、そのバージョンの ACME の証明書を発行すること
- TLS の秘密鍵を、プロキシとは別のプロセスで扱うこと
- 署名付きの監査ログとトレーシング
- ユーザー、API トークン、履歴の、ファイル以外への保存
- ログの、PostgreSQL と MySQL 以外への保存。管理 API と管理画面で、DB からログを検索すること
- Linux x86_64 以外の環境用の、ビルド済みの実行ファイル
- 検査プロセスとログ送信プロセスを、別の OS ユーザーや別のサービスで動かすこと

### 決まっていないこと

ドキュメントが「未決定」としているものです。0.2.0 の実装は、これらを決めたものではありません。

- どの機能を残し、どの機能を除くかの基準。移植元とする tukuyomi のバージョン
- 応答の検査を行うかどうか、行う場合の範囲
- 対応する HTTP のバージョンと通信の種類
- 管理画面の再利用・改善の範囲と、元にするバージョン
- 配布形態、対応する環境、デプロイ構成
- 設定、ルール、ログの保存の方式。ログの保存の期間と容量の方針
- 全体としての安全性の評価（評価していません）

現在の実装は、1 台の Linux ホストで動き、systemd の例があります（第3章）。

### ドキュメントの位置づけ

## 1.8　次章への橋渡し

ここまでで、tukuyomi core が、リクエストを検査プロセスで検査してアップストリームへ転送するプロキシを中心に、管理プロセスとログ送信プロセスを別のプロセスとして持つ構成であること、ルールセットの世代と managed 設定という 2 つの仕組みが運用の軸になることが分かりました。

第2章では、本番の構成を組む前に、1 台の Linux ホストで手で起動し、通常のリクエストが通ることと、SQL インジェクションのリクエストがブロックされることを、ログで確かめます。tukuyomi core に触れたことがない方は、第2章で手を動かしてから第3章以降へ進むと、設定キーの意味をつかみやすくなります。
