# はじめに

本書は、WAF（Web Application Firewall）を組み込んだ HTTP／HTTPS のリバースプロキシ **tukuyomi core** を、自分の手で導入し、運用していくための日本語ガイドです。

tukuyomi core は、受信したリクエストを Coraza または ModSecurity v3 で検査し、アップストリームへ転送します。検査には、OWASP Core Rule Set（CRS）などのルールセットを使います。本書では、リリースの入手と最初の起動から、ルールセットの管理、管理画面、ログ、証明書、日々の運用までを、上から順に読み通せる形で説明します。

## 本書の範囲

本書が扱うのは、tukuyomi core 0.2.0 で実装している機能だけです。実装していない機能や、決まっていないことは、そうと分かるように書きます（第1章の「1.7　実装しているものと、していないもの」にまとめています）。

製品全体のセキュリティ評価は、まだ行っていません。これはリポジトリの README にある注記です。

## 本書の対象読者

- Web サービスの前段に、WAF を組み込んだリバースプロキシを導入し、運用する立場のエンジニア（インフラ、SRE、プラットフォームの担当）

Linux、HTTP/HTTPS、TLS、systemd の基本的な概念は既知のものとして話を進めます。

## 本書の前提となる tukuyomi core のバージョン

本書は **tukuyomi core 0.2.0** を起点に書いています。手順に出てくるリリースのファイル名も、`v0.2.0` のものです。

以後のリリースで、設定キー、コマンド、ログの文などが変わった場合は、リポジトリのドキュメントと、GitHub のリリースに置かれている各バージョンのリリースノートを、本書より優先して確かめてください。

## 本書の読み方

最初から順に読み進めれば、入手と最初の起動、本番向けの配置、日々の運用までの流れを通り抜けられる構成にしています。

- **第1章** では、tukuyomi core が何をする製品か、どのプロセスで構成されているか、0.2.0 で実装していることと、していないことを説明します。
- **第2章** では、リリースの tarball から、手で起動して SQL インジェクションのリクエストがブロックされることを確かめるところまでを、順に示します。
- **第3章** では、systemd を使った本番向けの配置を説明します。
- **第4章から第9章** は、ルールセットと世代、managed 設定と管理画面、アクセス制御とレート制限、ログとログ送信、ACME による証明書、日々の運用を、トピックごとに説明します。すでに tukuyomi core を動かしている方は、目次から必要な章へ直接進んでかまいません。
- 巻末の **付録A 運用リファレンス** と **付録B 管理リファレンス** は、リポジトリのドキュメント（運用リファレンスと管理リファレンス）の本文を収めたものです。見出しの段と、文書の間のリンクだけを、本書の形に替えています。
- **付録C リリースノート** には、0.2.0 と 0.1.0 のリリースノートを収めています。

各章は、概要、仕組み、設定例、運用上の注意の流れにそろえ、章の頭に、その章で分かることを書いています。章単位で読み切れます。

本文は道案内として書いています。なぜその手順を踏むのか、何から始めるのか、どこで迷いやすいのかを説明し、設定キーの一覧、値の範囲、細かい断りは付録に任せます。具体的な設定キーや振る舞いを確かめたいときは、本文から案内する付録の節を引いてください。本文の中の「付録A 運用リファレンスの「…」を参照してください」は、付録Aにある、その見出しの節を指します。

## 表記について

- 「です・ます」調で統一しています。
- 設定キー、コマンド、ログの文、管理画面の語は、ドキュメントと同じ綴りをそのまま使います。ログの文は英語のままです。`proxy.max_body` や `rules import`、`start: listening` のように、`code` の書式で書きます。
- 技術用語は、ドキュメントと同じ語を使います。分野で一般に使われるカタカナ語（リクエスト、ログ、ブロック、アップストリーム、ルート、リスナーなど）は、そのまま使います。
- 製品名は、本文では tukuyomi core と書きます。実行ファイルの名前（`tukuyomi-proxy` など）、ディレクトリ名、ファイル名は、`tukuyomi-core` を含めて綴りのまま書きます。tukuyomi core の元になった製品は、「上流の tukuyomi」と書きます。
- コマンドは、次のようなコードブロックで示します。tukuyomi core は root では動きません。コマンドは、サービス用の OS ユーザー `tukuyomi` で実行する形（`sudo -u tukuyomi ...`）で書きます。

  ```bash
  sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy config check /etc/tukuyomi-core/config.json
  ```

- `<` と `>` で囲んだ語は、実際の値に置き換える場所の名前です。たとえば、`<config>` は設定ファイルのパス、`<fingerprint>` はルールセットの世代のフィンガープリント、`<version>` は managed 設定のバージョン、`<engine>` は検査エンジンの名前（`coraza` か `modsecurity`）です。
- パスと名前は、ドキュメントの例に合わせています。実行ファイルは `/opt/tukuyomi-core/bin/`、設定ファイルは `/etc/tukuyomi-core/config.json`、状態を置くディレクトリは `/var/lib/tukuyomi-core` の下、OS ユーザーは `tukuyomi`、ホスト名は `example.com`、ネットワークは `192.0.2.0/24` です。どれも例なので、環境に合わせて替えてください。設定に書くパスは、どれも絶対パスです。

## ドキュメントとの関係

tukuyomi core のリポジトリのドキュメント（`docs/`。英語は `foo.md`、日本語は `foo.ja.md`）が、設定キー、コマンド、シグナル、ログの形式、管理 API の定義と振る舞いの正です。ドキュメントは、システム概要、アーキテクチャ概要、設計方針・制約、ビルドと配置、運用リファレンス、管理リファレンスの文書からなります（`docs/README.ja.md` の「文書の一覧」）。このうち、システム概要、アーキテクチャ概要、設計方針・制約は初期草案で、目標、前提、候補、未決事項を記録しています（第1章 1.7）。

本書は、ドキュメントを順に読み通せるように組み直した道案内で、ドキュメントにない事実は書きません。付録A と付録B は、運用リファレンスと管理リファレンスの本文を収めたものです。本文からドキュメントの別の文書を引くときは、「ビルドと配置」の「ソースからのビルド」のように、文書の名前と見出しで書きます。

本書とドキュメントの内容が食い違うように見えるときは、ドキュメントを優先してください。また、リリースが替わったときは、本書より先に、そのリリースのドキュメントとリリースノートを確認してください。

それでは本編へ進みます。最初の第1章では、tukuyomi core が何をする製品で、どのようなプロセスで構成されているのかを概観します。
