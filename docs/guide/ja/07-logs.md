# 第7章　ログとログ送信

本章では、tukuyomi core が出すログの形式、ログファイル（`records`）、ログを残せないときの扱い、管理画面でのログの検索、ログを PostgreSQL か MySQL へ送るログ送信プロセスを説明します。ログをどこまで残すかは、使い方で決まります。章の順に、必要な段階まで進めてください。

## 7.1　ログの全体像

ログは、次の 3 つの段階で残せます。

- 標準エラー（systemd ではジャーナル）: いつも出ます。1 行 1 件の JSON です。
- ログファイル: 設定に `records` があれば、同じ行をファイルにも書きます。管理プロセスは、このファイルを読んで、管理画面と管理 API でログを検索します（7.6）。ファイルはサイズと本数でローテーションするので、古いものから消えます。ただし、起動の最初の行のうち、ログファイルを開く前に出る行（`start: configuration accepted` や `start: rules …` の行）は、標準エラーだけに出ます。
- ログ送信プロセス: 設定に `records.ship` があれば、別のプロセスが、ファイルの行を PostgreSQL か MySQL へ送ります。DB に残す日数は `retention_days` で決めます（7.7）。

`records` を省くと、ログは標準エラーだけに出て、管理画面と管理 API のログの検索は使えません。どの段階まで使うかは、運用で決めます。

ログには、種類を示す `type` があります。`request`、`connection`、`tunnel`、`line`、`audit`、`dropped` のどれかです。どのログも、記録した時刻の `ts` と `type` で始まります。`ts` は UTC の RFC 3339 形式でミリ秒までです（例: `2026-10-27T03:53:27.123Z`）。値の無い項目は書きません（`null` にしません）。

短いコマンド（`config check`・`rules`・`managed`・`acme`・`admin bootstrap`・`admin reset`）の出力は、ログではなく、人が読む文の行です。

## 7.2　リクエストのログとほかのログ

### リクエストのログ（`request`）

クライアントへ応答を書いたリクエストごとに 1 件出ます。ヘッダー部の拒否、リダイレクト、ACME のチャレンジへの応答も含みます。応答を送り終えたとき（または切れたとき）に書くので、ストリーミング応答のログは、応答の終わりに出ます。

```text
{"ts":"2026-10-27T03:53:27.123Z","type":"request","id":"0186af5443bddbd9-1","conn":1,"listener":0,"proto":"h1","tls":false,"client":"192.0.2.10","method":"GET","host":"example.com","path":"/q","class":"blocked","status":403,"reason":"blocked by a rule","ms":3,"mode":"block","engine":"coraza","generation":"2f3bda9b9ca7db60","rule":949110,"rules":[941100,941110],"severity":2,"score":10,"sent":0}
```

この例は、`192.0.2.10` からの `GET` リクエスト（パスは `/q`）を、Coraza の遮断の世代（`engine` が `coraza`、`mode` が `block`）がルール 949110 でブロックし、403 を返した行です。最初に見る項目は、次のとおりです。

- `id`: リクエスト ID です。応答の `X-Request-ID` と、アップストリームへ送る `X-Request-ID` と同じです。リクエストとログを結び付けるときに使います。
- `client`、`method`、`host`、`path`: クライアントのアドレス、メソッド、`Host`、リクエストターゲットの `?` より前です。
- `class`、`status`、`reason`: リクエストの結果です。
- `rule`、`rules`、`severity`、`score`: ブロックしたルール（検知のみのモードでは、一致したルール）の ID、ほかに一致したルールの ID、重大度、CRS の anomaly score です。
- `mode`、`engine`、`generation`: 判定した世代のモード（`block` か `detect`）、そのエンジン、世代のフィンガープリントの先頭 16 桁です。検査しなかったリクエスト（検査除外のルートで通したリクエストを含みます）にはありません。
- `ms`、`sent`: かかった時間（ミリ秒）と、クライアントへ送った応答のボディのバイト数です。

`class` は、リクエストの結果の分類で、7 つのどれかです。

- `forwarded`: アップストリームの応答を返した
- `blocked`: ルールがブロックした
- `rejected`: ヘッダー部かボディが拒否された（アクセス制御とレート制限の拒否も含みます）
- `redirected`: https へリダイレクトした
- `answered`: ACME のチャレンジに応答した
- `failed`: こちらの理由で応答できなかった（混んでいる、検査できない、アップストリームの失敗）
- `closed`: 何も応答しなかった

`forwarded` の `reason` が `detected by a rule` の行は、検知のみのモードでルールに一致して、通したリクエストです。`bypassed by a route` は、検査除外のルートで通したリクエストです。

リクエストから来る文字（`method`、`host`、`path`）は、0x21〜0x7e の外のバイトと `"`・`\` を `%XX`（大文字の 16 進数）にして、`method` は 32、`host` は 255、`path` は 1024 バイトで切ります。クエリ、ボディ、`Host` 以外のヘッダー（`User-Agent`、`Cookie` など）、ルールに一致した値と変数の名前、ルールの `msg` は、記録しません。パスに秘密の値を入れる作りのサイトでは、その値がログに残ります。

全部の項目と `class` ごとの場合は、付録A 運用リファレンスの「リクエストのログ（`request`）」を参照してください。

### ほかのログ

- `connection`: 応答を書かずに終わった接続（リクエストの前に閉じた、TLS のハンドシェイクに失敗したなど）と、HTTP/2 の接続の終わりです。
- `tunnel`: WebSocket のトンネルが終わったときです。
- `line`: 動作を示す文です。512 バイトまでで、長い文は切ります。ログ送信プロセスの文は、`records-ship:` で始まります（7.7）。
- `audit`: 管理プロセスの監査ログです。管理プロセスだけが出し、プロキシのログファイルには入りません（第5章）。
- `dropped`: 書けずに捨てたログの数です（`count`）。

`line` の文は、先頭の語で種類が分かります。起動と停止、設定のリロードを確かめるときに使います。

- `start:`: 起動の各段階（`start: the kernel is ready`、`start: listening` など）と、起動の拒否です。
- `reload:`: 設定のリロードと世代の切り替えの依頼を受けたことと、その結果です（`reload: configuration replaced <sha256>` など）。
- `stop:`: 停止の理由と、最後の停止の結果です。

ほかに、`control:`（制御ソケットの依頼への応答）、`driver:`（検査プロセスの再起動と、停止の始め）、`notify:`（systemd への通知を送れなかった場合）、`conn <number>: internal fault: <reason>`（プロキシの内部の不整合）があります。すべての文は、付録A 運用リファレンスの「ほかのログ」を参照してください。

### ログを書けないとき

- ログは 1024 件の待ち行列に入れ、書くのは 1 つのスレッドだけです。リクエストの処理と停止は、書き込みを待ちません。
- 待ち行列が満杯になったときは、そのログを捨てて数え、書けるようになってから `dropped` のログを 1 件出します。標準エラーを読む側が止まると、こうなります。書き込みの失敗は、そのログを失い、別に数えます。
- どちらの数も、`/metrics` の `tukuyomi_records_dropped_total` と `tukuyomi_record_write_errors_total` で見られます。標準エラーが詰まっている間は、ログでは通知できません。
- ログを残せなくてもリクエストを通すのが、デフォルトの扱い（`best_effort`）です。残せないときにリクエストを拒否するルートも選べます（7.4）。

## 7.3　ログファイル（`records`）

設定に `records` を書くと、標準エラーに出すログを、ディレクトリのファイルにも書きます（ログファイルを開く前に出る起動の行を除きます。7.1）。省けば、ログは標準エラーだけに出ます。

```json
"records": {
  "dir": "/var/lib/tukuyomi-core/records",
  "file_bytes": 16777216,
  "files": 8
}
```

`dir`、`file_bytes`、`files` は必ず書きます。ほかに、ログの残し方の `keep`（7.4）、同期の間隔の `sync_ms`、ログ送信プロセスの設定の `ship`（7.7）があります。

### ディレクトリを用意する

`dir` は、ファイルを置くディレクトリの絶対パスです。プロキシは作らないので、先に作ります。条件は、シンボリックリンクでないディレクトリであること、所有者がプロキシの OS ユーザーであること、グループとその他のユーザーの権限が無いことです。

```bash
sudo install -d -m 0700 -o tukuyomi -g tukuyomi /var/lib/tukuyomi-core/records
```

ログのディレクトリは、ルールストアなどのほかのディレクトリと、同じにも、互いの中にも置けません（第3章の 3.4）。

### サイズと本数

- `file_bytes` は 1 つのファイルのサイズ（1 MiB〜1 GiB）、`files` は残すファイルの数（2〜64。使用中のものを含みます）です。使うディスクは、多くても `file_bytes × files` です。例の値なら、16 MiB × 8 本で、128 MiB までです。
- 使用中のファイルは `records.log` です。古いファイルは、`records.1.log`、`records.2.log` と続き、`records.<files - 1>.log` が最も古いファイルです。
- 行を追加すると `file_bytes` を超えるときは、先に次のファイルへローテーションします。いちばん古いファイルは、置き換えられて無くなります。どのファイルも、行の途中では切れません。ローテーションは、プロキシが自分で行います。

### 書き方と同期

- `records.log` は、無ければ 0600 で作り、追記で開きます。起動のときに開けなければ、`start: record file refused: <reason>` の文を出し、検査プロセスを起動せずに止まります（exit 1）。
- `sync_ms` が無ければ、ディスクへの同期（`fsync`）はしません。電源が落ちると、OS がまだディスクに書いていない行は失われます。`sync_ms`（1〜60000）があれば、同期していない行のうち最も古いものが `sync_ms` だけ待ったときに、ファイルを同期します。電源が落ちて失うのは、最後の同期より後の行です。
- 書き込み、`open`、リネームが失敗すると、その行はファイルに入らず、`tukuyomi_record_file_errors_total` に数えます。標準エラーには出ます。リクエストの処理は待ちません。失敗から 1 秒以上後に来た最初の行が、ファイルを開き直します。
- ログ送信プロセスを使うときは、同じディレクトリに `ship.state`（送った位置）が置かれます。プロキシは `ship.state` を読むだけです。

`records` は、動作中に変更できない設定キーです（`keep` を除きます）。変更するときは、プロキシと、同じ設定ファイルを読む管理プロセスとログ送信プロセスを再起動します（第9章）。ファイルの開き方、ファイルが外部から動かされたときの扱い、`files` を小さくしたときの扱いは、付録A 運用リファレンスの「ログファイル（`records`）」を参照してください。

## 7.4　ログの残し方

ログを残せないときの扱いと、残すログを、ルートごとに選べます。選べるのは、次の 3 つです。

| 値 | ログを残せないとき | 書くログ |
|---|---|---|
| `best_effort` | ログを捨てて数え、リクエストは通します | すべて |
| `required` | そのルートの新しいリクエストを 503 で拒否します | すべて |
| `security` | `best_effort` と同じです | 下の 4 つのリクエストだけ。通常どおり通したリクエストのログは書きません |

`security` が書くのは、ルールが判定したリクエスト（ブロックと、検知のみのモードで一致したもの）、検査できなかったリクエスト、全体の `access`・`rate_limit` とホストごとの設定で拒否したリクエスト、受け付けた後に応答の前に切れたリクエストです。

ルートの `records` に書きます。書かなければ、全体の `records.keep`（`best_effort` か `required`）に従い、`records.keep` も書かなければ `best_effort` です。デフォルトのアップストリームには `records` が無いので、そこへ回るリクエストには `records.keep` が使われます。

```json
{"host": "www.example.com", "upstream": "app", "records": "required"}
```

### `required`

`required` のルートは、次の 3 つがそろうときだけ、リクエストを受け付けます。

1. ログファイルへの最後の書き込み（と同期）が通っていて、ログを書くスレッドが動いている。
2. ログ送信プロセス（`ship`）があるなら、ログ送信プロセスがまだ送っていないバイト数が、ファイル `files − 2` 個分（`file_bytes × (files − 2)`）より少ない。送っていないログがローテーションで消える前に、拒否するためです。ログ送信プロセスの遅れが分からないときも拒否します。
3. ログの待ち行列に枠が空いている。

拒否したリクエストには 503 で応答し、`tukuyomi_records_refused_total` に数えます。拒否したリクエストのログ（`reason` は `records cannot be kept`）は、「できる限り」で書きます。ただし、ログ送信プロセスの遅れで拒否したときは、そのログは書かずに数えるだけです。送っていないログがローテーションで消えるまでの余白を、拒否したリクエストのログで使わないためです。受け付けたリクエストのログは、待ち行列が満杯でも捨てません。

- ログは応答を送り終えた後に書くので、`required` は、クライアントに応答する前にログがあることは約束しません。書き込みが失敗し始めたときに受け付け済みだったリクエストのログと、電源が落ちたときの、最後の同期より後のログは、抜けることがあります。
- `required` を使うには `records` が必要です。`ship` と `required` を両方使うときは、`files` を 3 以上にします。
- ルートを決める前、またはボディを読まずに応答するリクエスト（全体の `access`・`rate_limit` の 403 と 429、ヘッダー部の検証で拒否したリクエスト、接続のログなど）は、ルートの値にかかわらず、ログを「できる限り」で書きます。

受け付ける 3 つの条件の細かい決まりと、「できる限り」で書くリクエストの一覧は、付録A 運用リファレンスの「ログの残し方（`keep` とルートの `records`）」を参照してください。

## 7.5　ログを読めるユーザー

ログには、クライアントのアドレスとパスが入ります。誰がログを読めるかは、次のとおりです。

- ジャーナル: ジャーナルを読めるユーザー（root と、Ubuntu では `adm`・`systemd-journal` のグループのユーザー）が読めます。グループに入れる OS ユーザーは最小限にします。保存の期間と容量は、journald の設定で決めます（第3章の 3.5）。
- ログファイル（`records`）: 0600 で、0700 のディレクトリにあります。読めるのは、プロキシの OS ユーザーと root です。管理プロセスは、同じ OS ユーザーとしてこのファイルを読み、管理画面と管理 API のユーザーに見せます。
- 管理 API: ログの検索（`GET /api/records`）は viewer 以上が読めるので、viewer のロールを渡すユーザーを検討したうえで決めます（第5章）。
- DB のテーブル: ログ送信プロセスを使うときは、DB のテーブルにも同じログが入ります。テーブルを読める DB のユーザーも、最小限にします。

## 7.6　管理画面のアクセスログ

`records` を書くと、管理画面の「ログ」の「アクセスログ」（viewer 以上）と、管理 API の `GET /api/records` で、ログを検索できます。管理プロセスが、`records.dir` のファイルを新しい行から読み、条件に合う行を返します。「ログ」には、「監査ログ」（operator 以上）もあります（画面の一覧は第5章）。

- 条件は、時刻（`from`・`to`）、`type`、`class`、`status`、`rule`、`id`（リクエスト ID）、`client`、`generation`、`engine`（検査したエンジン）です。
- 行は、書かれたままの JSON です。リクエストから来た文字（`path` など）は、`%XX` の形のまま表示します。画面の「すべての欄」で「URL デコードした文字も表示する」を選ぶと、デコードした文字も表示します。
- 1 回に返すのは 500 行まで、読み込むのは 256 MiB までです。どちらかに達して、まだログが残っているときは、応答に続きの位置（`next`）が入ります。画面は、最後のページの「次へ」で、続きの古いログを読み込みます。
- 応答に `error` の文が無い失敗（手前に置いたプロキシがルールでブロックしたリクエストの 403、プロキシが管理プロセスに接続できなかった 502 など）では、画面は失敗の文の後に、応答の `X-Request-ID` のリクエスト ID を表示します。その ID で「アクセスログ」の画面を検索すると、ブロックしたルールなどが分かります。ID は、プロキシと管理プロセスが付与する形式のときだけ表示します。
- 監査ログは、プロキシのログファイルに入りません。`type=audit` で検索しても見つからないので、監査ログの画面（か `GET /api/audit`）で読みます。
- 設定に `records` が無いと、この API は 404（`records are not configured`）になります。ログのディレクトリが所有者と権限の検証に通らないときは、503 になります。
- DB に送ったログを、管理 API と管理画面で検索することは、実装していません。

条件の形式、続きの読み方、失敗の応答は、付録B 管理リファレンスの「ログの読み出し」を参照してください。

## 7.7　ログ送信プロセス

ログ送信プロセス（`tukuyomi-records-ship`）は、プロキシのログファイルを読み、行を PostgreSQL か MySQL のテーブルへ順に入れる、別のプロセスです。プロキシはログ送信プロセスを動かさず、DB にも接続しません。DB に接続するライブラリと DB のパスワードは、ログ送信プロセスの実行ファイルとプロセスにだけあります。動作を確認しているのは PostgreSQL 16・18 と MySQL 8.0 です。使うのは、ログを DB へ送る場合だけです。

準備は、次の順に進めます。

1. DB のユーザーと DB を用意します。
2. 接続文字列のファイルを、所有者をサービスの OS ユーザーにして 0600 で置きます（下の「接続文字列」）。
3. 設定に `records.ship` を書きます（`ship` と `required` を両方使うときは、`files` を 3 以上にします）。動作中のプロキシの設定に足すときは、`records` が動作中に変更できない設定キーなので、プロキシを再起動します（第9章）。
4. ログ送信プロセスのユニットを起動します（第3章の 3.5「ログ送信プロセスのユニット」）。
5. ログ送信プロセスのログに `records-ship: configuration accepted` の行が出ることを確かめます。テーブルは、最初に接続したときに作ります。

### 起動

```text
tukuyomi-records-ship <config>
```

- `<config>` は、プロキシと同じ設定ファイルで、絶対パスで書きます。`records.ship` が必要です。無ければ、`records-ship: configuration refused: there is no records.ship object` の行を出して終わります。
- 読むのは設定ファイルだけで、managed ストアのバージョンと国のデータベースは読みません。未知の設定キーのある設定ファイルは受け付けないので、設定に新しい設定キー（`managed`、`host_policies`、`kernel.default_engine`、アップストリームの `engine` など）を書く前に、ログ送信プロセスをプロキシと同じビルドに入れ替えます。
- プロキシと同じ OS ユーザーで動かします。root では動きません。
- ログのディレクトリのファイルシステムは、ファイルの作成時刻（`statx` の btime）を返す必要があります。動作を確認しているのは ext4 だけです。返さないファイルシステムでは、ログ送信プロセスは起動せず、プロキシは遅れを「分からない」として、`required` のリクエストを拒否します。
- 終了コードは、0（SIGTERM、SIGINT、SIGHUP で停止）、1（接続文字列が読めない、DB がログインを拒否したなど）、2（引数のエラー、設定が受け付けられなかった）です。

設定ファイルと接続文字列のファイルは、起動時に 1 回だけ読みます。SIGHUP は停止のシグナルなので、設定を変更したら、再起動します。

### `records.ship`

5 つとも書きます。

- `db_driver`: `pgsql` か `mysql`
- `db_dsn_file`: 接続文字列のファイルの絶対パス。プロキシはこのファイルを開きません
- `batch`: 1 つのトランザクションに入れる行の数の上限（1〜10000）
- `interval_ms`: 送る行が無かったときに、次の回まで待つ時間（100〜60000）。失敗の後に待つ時間の初期値でもあります
- `retention_days`: DB に残す日数（0〜3650）。0 なら削除しません

```json
"records": {
  "dir": "/var/lib/tukuyomi-core/records",
  "file_bytes": 16777216,
  "files": 8,
  "sync_ms": 1000,
  "ship": {
    "db_driver": "pgsql",
    "db_dsn_file": "/etc/tukuyomi-core/records-db.dsn",
    "batch": 500,
    "interval_ms": 1000,
    "retention_days": 90
  }
}
```

### 接続文字列

接続文字列はパスワードを含むので、設定ファイルには書かず、別のファイルに置きます。ファイルの条件は、通常のファイルであること、所有者がログ送信プロセスの OS ユーザーであること、グループとその他のユーザーの権限が無いこと（0600）です。16 KiB まで、UTF-8 の文字です。

ファイルには、使う DB に合わせて、次のどれか 1 つを書きます。

PostgreSQL の例です。`postgresql://` の URL（`tokio-postgres` の形式）でも書けます。テーブルは、接続の `search_path` の最初のスキーマに作ります。

```text
host=db.example.com port=5432 user=tukuyomi_ship password=<password> dbname=records
```

同じホストの PostgreSQL に、Unix ドメインソケットと peer 認証（OS ユーザーの名前と同じ名前のロール）で接続する例です。パスワードは必要ありません。

```text
host=/var/run/postgresql user=tukuyomi dbname=tukuyomi_records sslmode=disable
```

MySQL の例です。URL の形式は `mysql_async` 0.37 のものです。DB の名前が必要で、テーブルはその DB に作ります。URL の中で記号を使う値は、パーセントエンコーディングで書きます。

```text
mysql://<user>:<password>@<host>:<port>/<db-name>
```

TLS は、何も書かなければ使い、証明書とホスト名を検証します（PostgreSQL も MySQL も同じです）。平文にできるのは、PostgreSQL は `sslmode=disable`、MySQL は `require_ssl=false` と書いたときだけです。証明書を検証する認証局は、システムのものです。DB サーバーの証明書を独自の認証局で発行したときは、その証明書のファイルを、ユニットの `Environment=SSL_CERT_FILE=<path>` で渡します。受け付けない指定を含む一覧は、付録A 運用リファレンスの「接続文字列（`db_dsn_file`）」を参照してください。

### ログのテーブル

ログ送信プロセスは、DB に接続したときにテーブルを探し、無いテーブルだけを作ります。テーブルは 3 つです。

- `tukuyomi_records`: ログの行ごとに 1 つ。`ts`、`type`、`request_id`、`client`、`class`、`status`、`rule` などの列と、行そのものを入れる `raw`、行の SHA-256 の `line_hash`（UNIQUE）を持ちます。
- `tukuyomi_records_state`: ログのディレクトリごとの、送った位置。
- `tukuyomi_records_schema`: スキーマのバージョン（現在は 1）。

テーブルがそろっていてバージョンの行があれば、ログ送信プロセスは何も作らないので、DB のユーザーにテーブルを作る権限は必要ありません。作る権限を渡したくないときは、作る権限のあるユーザーでログ送信プロセスを一度動かしてテーブルを作らせ、その後で、ログ送信プロセスのユーザーを変更します。

1 つのログのディレクトリには、ログ送信プロセスを 1 つだけ動かします。位置は `records.dir` のパスで分けるので、別のホストのプロキシを同じテーブルへ送るときは、`records.dir` のパスを変えるか、別のスキーマや DB にします。MySQL では、サーバーの `max_allowed_packet` を 2 MiB 以上にします。列、インデックス、MySQL と PostgreSQL の違いは、付録A 運用リファレンスの「ログのテーブル」を参照してください。

### 送信の仕組み

- 1 回の処理で、ログファイルの行を `batch` 個まで読み、1 つのトランザクションで、行を入れて位置のテーブルを進めます。コミットの後に `ship.state` を書きます。ログ送信プロセスが落ちても、次の回は DB の位置から続けます。
- 失敗の後は、待つ時間を `interval_ms` から倍にして 1 分まで延ばし、うまくいった回の後に戻します。
- DB に接続できない間と、送る行が無い間も、`ship.state` を 1 秒に 1 回は書き直します。プロキシは、これでログ送信プロセスが動作中であることを判断します。
- ログファイルは、名前ではなく inode と作成時刻で追跡します。ローテーションでリネームされても、続きから読みます。
- すべての `type` の行を送ります。行そのものは、いつも `raw` に残ります。`line_hash` が UNIQUE なので、二重に送った行は 1 つになります。
- `retention_days` があれば、1 分に 1 回、それより古い行を 1000 行まで削除します。古さはログの `ts`（プロキシの時計）で決めます。

### 送れないログ

- ログ送信プロセスが読む前に、ローテーションで消えたログファイルの行は失われます。ログ送信プロセスが開いていたファイルなら、失われた行を数えて位置の `lost_lines` に足し、`records-ship: a record file was removed before it was shipped, <count> lines lost` の行を出します。開く前に消えたファイル（DB に長く接続できない間に、プロキシが `files` より多くローテーションしたときなど）の行は、数えられません。`lines may be lost` を含む行だけを出します。この行は、何も失われていないときにも出ることがあります。
- プロキシの `required` のルートは、そうなる前にリクエストを拒否します（7.4）。`best_effort` と `security` のルートは拒否しません。
- ログファイルは切り詰めないでください（logrotate の `copytruncate` など）。ログ送信プロセスは、切り詰めたファイルを同じファイルと見て、その先頭の行を送らないことがあります。ローテーションは、プロキシが自分で行います。

### エラー

ログ送信プロセスのログは、プロキシと同じ 1 行 1 件の JSON（`type` が `line`、文は `records-ship:` で始まる）で、標準エラーに出ます。文には、接続文字列、ログ、サーバーが返した文の値を入れません。DB のエラーは、決まった文と、サーバーが返した SQLSTATE です（例: `records-ship: the database refused or failed a request (SQLSTATE 42000)`）。

- DB がログインを拒否したとき（PostgreSQL の SQLSTATE が 28 で始まるもの、MySQL の 1045）は、待っても直らないので、`records-ship: stop: the login is refused, which waiting does not mend` の行を出して終わります（exit 1）。ユニットの `Restart=on-failure` で再起動を繰り返すので、接続文字列を直します。
- ほかの拒否は、上の待ち時間を置いて再試行し、そのたびに行を出します。

ここまでに書かなかった決まりは、付録A 運用リファレンスの「ログ送信プロセス」を参照してください。

## 7.8　運用上の注意

- ログには、クライアントのアドレスとパスが入ります。パスに秘密の値を入れる作りのサイトでは、その値もログに残ります。ジャーナル、ログファイル、DB のテーブルの読める範囲を、最小限にします。
- ログを残せないときの扱いは、ルートごとに選びます。`required` は、そのルートの新しいリクエストを 503 で拒否します。`best_effort` と `security` は、リクエストを通して、ログを失います。
- ログファイルは、プロキシが書き、ローテーションします。切り詰めないでください（logrotate の `copytruncate` など）。
- ログ送信プロセスと `required` のルートを両方使うときは、`files` を 3 以上にします。ログ送信プロセスが遅れたり止まったりしたときに、ログがローテーションで消える前に、`required` のルートがリクエストを拒否します。
- `/metrics` の `tukuyomi_records_dropped_total`、`tukuyomi_record_write_errors_total`、`tukuyomi_record_file_errors_total`、`tukuyomi_records_unshipped_bytes` などで、ログが書けているか、送れているかを確かめます（第9章）。
- `records.keep` 以外の `records` を変更したときは、プロキシ、管理プロセス、ログ送信プロセスを再起動します。接続文字列のファイルを変更したときは、ログ送信プロセスを再起動します。
