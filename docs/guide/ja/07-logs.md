# 第7章　ログとログ送信

本章では、tukuyomi core が出すログの形式、ログファイル（`records`）、ログを残せないときの扱い、管理画面でのログの検索と、ログを PostgreSQL か MySQL へ送るログ送信プロセスについて説明します。

ログをどこまで残すかは使い方によって決まるので、章の順に、必要な段階まで読み進めてください。

## 7.1　ログの全体像

まず、ログがどこに残るのかを見ておきます。ログは次の 3 つの段階で残せます。

- **標準エラー（systemd ではジャーナル）**: 1 行 1 件の JSON で、いつも出ます。
- **ログファイル**: 設定に `records` があれば、同じ行をファイルにも書きます。
  管理画面と管理 API でのログの検索は、管理プロセスがこのファイルを読んで行います（7.6）。
  ファイルはサイズと本数でローテーションするため、古いものから消えていきます。
  ただし、ログファイルを開く前に出る起動の最初の行は、標準エラーにだけ出ます。たとえば、`start: configuration accepted` や `start: rules …` の行です。
- **ログ送信プロセス**: 設定に `records.ship` があれば、別のプロセスがファイルの行を PostgreSQL か MySQL へ送ります。
  DB に残す日数は `retention_days` で決めます（7.7）。

`records` を省略すると、ログは標準エラーにだけ出て、管理画面と管理 API のログの検索は使えません。
どの段階まで使うかは、運用に合わせて決めてください。

ログには種類を示す `type` があり、値は `request`、`connection`、`tunnel`、`line`、`audit`、`dropped` のどれかです。
どのログも、記録した時刻を示す `ts` と `type` で始まります。
`ts` は UTC の RFC 3339 形式で、ミリ秒まで入ります（例: `2026-10-27T03:53:27.123Z`）。
値の無い項目は `null` にせず、項目ごと書きません。

なお、短時間で終わるコマンド（`config check`・`rules`・`managed`・`acme`・`admin bootstrap`・`admin reset`）の出力はログではなく、人が読むための文の行です。

## 7.2　リクエストのログとほかのログ

### リクエストのログ（`request`）

リクエストのログは、クライアントへ応答を書いたリクエストごとに 1 件出ます。ヘッダー部の拒否やリダイレクト、ACME のチャレンジへの応答でも出ます。
ログは応答を送り終えたときか切れたときに書くので、ストリーミング応答のログは応答の終わりに出ます。

```text
{"ts":"2026-10-27T03:53:27.123Z","type":"request","id":"0186af5443bddbd9-1","conn":1,"listener":0,"proto":"h1","tls":false,"client":"192.0.2.10","method":"GET","host":"example.com","path":"/q","class":"blocked","status":403,"reason":"blocked by a rule","ms":3,"mode":"block","engine":"coraza","generation":"2f3bda9b9ca7db60","rule":949110,"rules":[941100,941110],"severity":2,"score":10,"sent":0}
```

この例は `192.0.2.10` から来た `GET` リクエストの行で、パスは `/q` です。
Coraza の世代（`engine` が `coraza`、`mode` が `block`）が、このリクエストをルール 949110 でブロックし、403 を返しました。

まず見るとよい項目は次のとおりです。

- `id`: リクエスト ID で、応答の `X-Request-ID` とも、アップストリームへ送る `X-Request-ID` とも同じ値です。リクエストとログを結び付けるときに使います。
- `client`、`method`、`host`、`path`: 順に、クライアントのアドレス、メソッド、`Host`、リクエストターゲットのうち `?` より前の部分です。
- `class`、`status`、`reason`: リクエストの結果です。
- `rule`、`rules`、`severity`、`score`: 順に、ブロックしたルールの ID、ほかに一致したルールの ID、重大度、CRS の anomaly score です。
  検知のみのモードでは、`rule` は一致したルールの ID です。
- `mode`、`engine`、`generation`: 順に、判定した世代のモード（`block` か `detect`）、その世代のエンジン、世代のフィンガープリントの先頭 16 桁です。
  検査除外のルートで通したリクエストも含め、検査しなかったリクエストには、この 3 つの項目はありません。
- `ms`、`sent`: かかった時間（ミリ秒）と、クライアントへ送った応答のボディのバイト数です。

`class` はリクエストの結果を分類したもので、次の 7 つのどれかになります。

- `forwarded`: アップストリームの応答を返した
- `blocked`: ルールがブロックした
- `rejected`: ヘッダー部かボディが拒否された（アクセス制御とレート制限の拒否も含みます）
- `redirected`: https へリダイレクトした
- `answered`: ACME のチャレンジに応答した
- `failed`: プロキシ側の理由で応答できなかった（混んでいる、検査できない、アップストリームの失敗）
- `closed`: 何も応答しなかった

`class` が `forwarded` でも、`reason` が `detected by a rule` の行は、検知のみのモードでルールに一致したうえで通したリクエストです。
`reason` が `bypassed by a route` の行は、検査除外のルートで通したリクエストです。

リクエストから来る文字（`method`、`host`、`path`）では、0x21〜0x7e の範囲に入らないバイトと `"`・`\` を `%XX`（大文字の 16 進数）に置き換えます。
置き換えた後、`method` は 32 バイト、`host` は 255 バイト、`path` は 1024 バイトで切ります。

クエリ、ボディ、`Host` 以外のヘッダー（`User-Agent`、`Cookie` など）、ルールに一致した値と変数の名前、ルールの `msg` は記録しません。
ただし、パスに秘密の値を入れる作りのサイトでは、その値がログに残ります。

すべての項目と、`class` ごとにどのような場合に当たるかは、付録A 運用リファレンスの「リクエストのログ（`request`）」を参照してください。

### ほかのログ

リクエストのログのほかに、次のログがあります。

- `connection`: 応答を書かずに終わった接続（リクエストの前に閉じた、TLS のハンドシェイクに失敗した、など）と、HTTP/2 の接続が終わったときのログです。
- `tunnel`: WebSocket のトンネルが終わったときのログです。
- `line`: 動作を示す文のログです。
  文は 512 バイトまでで、それより長い文は切ります。
  ログ送信プロセスが出す文は `records-ship:` で始まります（7.7）。
- `audit`: 管理プロセスだけが出す監査ログで、プロキシのログファイルには入りません（第5章）。
- `dropped`: 書けずに捨てたログの数（`count`）を示すログです。

`line` の文は先頭の語で種類が分かります。
起動と停止、設定のリロードを確認するときは、次の文を見ます。

- `start:`: 起動の各段階（`start: the kernel is ready`、`start: listening` など）と、起動を拒否したときの文です。
- `reload:`: 設定のリロードと世代の切り替えについて、依頼を受けたことと、その結果を示す文です（`reload: configuration replaced <sha256>` など）。
- `stop:`: 停止の理由と、最後に出す停止の結果の文です。

ほかに、次の文があります。

- `control:`: 制御ソケットの依頼への応答
- `driver:`: 検査プロセスの再起動と、停止の始まり
- `notify:`: systemd への通知を送れなかった場合
- `conn <number>: internal fault: <reason>`: プロキシの内部の不整合

すべての文の一覧は、付録A 運用リファレンスの「ほかのログ」を参照してください。

### ログを書けないとき

ログの書き込みが追いつかないときや、失敗したときの動作は次のとおりです。

- ログは 1024 件まで入る待ち行列に入れてから、1 つのスレッドだけが書きます。リクエストの処理と停止は書き込みを待ちません。
- 待ち行列が満杯になると、そのログは捨てて数え、書けるようになってから `dropped` のログを 1 件出します。
  標準エラーを読む側が止まると、この状態になります。
- 書き込みに失敗したときは、そのログが失われます。
  その数は満杯で捨てた数とは別に数えます。
- どちらの数も、`/metrics` の `tukuyomi_records_dropped_total` と `tukuyomi_record_write_errors_total` で確認できます。
  標準エラーが詰まっている間は、このことをログでは知らせられません。
- デフォルトの扱い（`best_effort`）では、ログを残せなくてもリクエストを通します。
  ログを残せないときにリクエストを拒否する扱いも、ルートごとに選べます（7.4）。

## 7.3　ログファイル（`records`）

設定に `records` を書くと、指定したディレクトリのファイルにも、標準エラーに出すログを書きます。ただし、ログファイルを開く前に出る起動の最初の行は除きます（7.1）。
`records` を省略した場合、ログは標準エラーにだけ出ます。

```json
"records": {
  "dir": "/var/lib/tukuyomi-core/records",
  "file_bytes": 16777216,
  "files": 8
}
```

`dir`、`file_bytes`、`files` の 3 つは必ず書きます。
ほかに書ける設定キーは、ログの残し方を決める `keep`（7.4）、同期の間隔を決める `sync_ms`、ログ送信プロセスの設定を書く `ship`（7.7）です。

### ディレクトリを用意する

`dir` にはログファイルを置くディレクトリを絶対パスで指定します。
このディレクトリはプロキシが作らないので、先に作成しておきます。
ディレクトリの条件は次のとおりです。

- シンボリックリンクではないディレクトリであること
- 所有者がプロキシの OS ユーザーであること
- グループとその他のユーザーに権限が無いこと

```bash
sudo install -d -m 0700 -o tukuyomi -g tukuyomi /var/lib/tukuyomi-core/records
```

ログのディレクトリは、ルールストアなどのほかのディレクトリと同じにすることも、互いの中に置くこともできません（第3章の 3.4）。

### サイズと本数

- `file_bytes` は 1 つのファイルのサイズ（1 MiB〜1 GiB）です。
  `files` は残すファイルの数（2〜64）で、使用中のファイルも含みます。
- 使うディスクの量は多くても `file_bytes × files` です。例の値なら、16 MiB × 8 本で 128 MiB までです。
- 使用中のファイルは `records.log` です。
  それより古いファイルは `records.1.log`、`records.2.log` と続き、`records.<files - 1>.log` が最も古いファイルになります。
- 行を追加すると `file_bytes` を超える場合は、先に次のファイルへローテーションし、最も古いファイルは置き換えられて無くなります。どのファイルも行の途中で切れることはありません。
- ローテーションはプロキシが自分で行います。

### 書き方と同期

- `records.log` が無ければ 0600 で作成し、追記で開きます。
  起動のときにこのファイルを開けない場合は、`start: record file refused: <reason>` の文を出し、検査プロセスを起動せずに止まります（exit 1）。
- `sync_ms` が無い場合は、ディスクへの同期（`fsync`）をしません。
  同期しないので、電源が落ちると、OS がまだディスクに書いていない行は失われます。
- `sync_ms`（1〜60000）を書いた場合は、同期していない行のうち最も古いものが `sync_ms` だけ待った時点で、ファイルを同期します。
  電源が落ちたときに失われるのは、最後の同期より後の行です。
- 書き込み、`open`、リネームのどれかが失敗すると、その行はファイルに入らず、`tukuyomi_record_file_errors_total` に数えます。
  その行も標準エラーには出ます。リクエストの処理はこれを待ちません。
  失敗から 1 秒以上たった後に来た最初の行で、ファイルを開き直します。
- ログ送信プロセスを使う場合は、同じディレクトリに `ship.state`（どこまで送ったかの位置）が置かれます。プロキシは `ship.state` を読むだけです。

`records` のうち `keep` 以外は、動作中に変更できない設定キーです。
変更するときは、プロキシと、同じ設定ファイルを読む管理プロセスとログ送信プロセスを再起動します（第9章）。

ファイルの開き方、外部からファイルを動かされたときの扱い、`files` を小さくしたときの扱いは、付録A 運用リファレンスの「ログファイル（`records`）」を参照してください。

## 7.4　ログの残し方

ログを残せないときにどうするかと、どのログを残すかは、ルートごとに次の 3 つの値から選べます。

| 値 | ログを残せないとき | 書くログ |
|---|---|---|
| `best_effort` | ログを捨てて数え、リクエストは通します | すべて |
| `required` | そのルートの新しいリクエストを 503 で拒否します | すべて |
| `security` | `best_effort` と同じです | 下に挙げる 4 つのリクエストだけで、通常どおり通したリクエストのログは書きません |

`security` が書くのは、次の 4 つのリクエストのログです。

- ルールが判定したリクエスト（ブロックしたものと、検知のみのモードで一致したもの）
- 検査できなかったリクエスト
- 全体の `access`・`rate_limit` と、ホストごとの設定で拒否したリクエスト
- 受け付けた後、応答の前に切れたリクエスト

値はルートの `records` に書きます。
ルートに書かなければ、全体の `records.keep` に従います。`records.keep` も書かなければ、`best_effort` になります。
`records.keep` に書けるのは `best_effort` か `required` です。
デフォルトのアップストリームには `records` が無いため、そこへ回るリクエストには `records.keep` が使われます。

```json
{"host": "www.example.com", "upstream": "app", "records": "required"}
```

### `required`

`required` のルートは、次の 3 つの条件がすべてそろったときだけ、リクエストを受け付けます。

1. ログファイルへの最後の書き込み（と同期）が成功していて、ログを書くスレッドが動作中である。
2. ログ送信プロセス（`ship`）を使う場合は、ログ送信プロセスがまだ送っていないバイト数が、ファイル `files − 2` 個分（`file_bytes × (files − 2)`）より少ない。
   送っていないログがローテーションで消える前に拒否するための条件です。
   ログ送信プロセスの遅れが分からないときも拒否します。
3. ログの待ち行列に枠が空いている。

拒否したリクエストには 503 で応答し、`tukuyomi_records_refused_total` に数えます。
拒否したリクエストのログは `best_effort` の扱いで書き、書けなければ捨てて数えます。このログの `reason` は `records cannot be kept` です。
ログ送信プロセスの遅れで拒否したときは、そのログを書かずに数えるだけです。
拒否したリクエストのログで、送っていないログがローテーションで消えるまでの余裕を使ってしまわないためです。
一方、受け付けたリクエストのログは、待ち行列が満杯でも捨てません。

- ログは応答を送り終えた後に書くので、`required` でも、クライアントに応答する前にログがあることまでは約束しません。
  抜けることがあるのは、書き込みが失敗し始めた時点で受け付け済みだったリクエストのログと、電源が落ちたときに最後の同期より後にあったログです。
- `required` を使うには `records` が必要です。
  `ship` と `required` を両方使うときは、`files` を 3 以上にします。
- ルートを決める前に応答するリクエストや、ボディを読まずに応答するリクエストのログは、ルートの値にかかわらず `best_effort` の扱いで書きます。書けなければ捨てて数えます。
  全体の `access`・`rate_limit` の 403 と 429、ヘッダー部の検証で拒否したリクエスト、接続のログなどが、これに当たります。

受け付ける 3 つの条件の細かい決まりと、`best_effort` の扱いで書くリクエストの一覧は、付録A 運用リファレンスの「ログの残し方（`keep` とルートの `records`）」を参照してください。

## 7.5　ログを読めるユーザー

ログにはクライアントのアドレスとパスが入ります。
誰がログを読めるかは、置き場所ごとに次のとおりです。

- **ジャーナル**: root が読めます。Ubuntu では、`adm`・`systemd-journal` のグループのユーザーも読めます。
  これらのグループに入れる OS ユーザーは最小限にしてください。
  保存の期間と容量は journald の設定で決めます（第3章の 3.5）。
- **ログファイル（`records`）**: 0600 のファイルが 0700 のディレクトリにあり、読めるのはプロキシの OS ユーザーと root です。
  管理プロセスは同じ OS ユーザーとしてこのファイルを読み、管理画面と管理 API のユーザーに見せます。
- **管理 API**: ログの検索（`GET /api/records`）は viewer 以上のロールで読めます。
  viewer のロールを渡すユーザーは、このことを踏まえて決めてください（第5章）。
- **DB のテーブル**: ログ送信プロセスを使う場合は、DB のテーブルにも同じログが入ります。
  テーブルを読める DB のユーザーも最小限にしてください。

## 7.6　管理画面のアクセスログ

`records` を書くと、管理画面では「ログ」の「アクセスログ」、管理 API では `GET /api/records` でログを検索できます。「アクセスログ」は viewer 以上のロールで使えます。
管理プロセスが `records.dir` のファイルを新しい行から読み、条件に合う行を返します。
なお、「ログ」には operator 以上のロールで使える「監査ログ」もあります（画面の一覧は第5章）。

- 検索の条件に使えるのは、時刻（`from`・`to`）、`type`、`class`、`status`、`rule`、`id`（リクエスト ID）、`client`、`generation`、`engine`（検査したエンジン）です。
- 返す行は書かれたままの JSON なので、リクエストから来た文字（`path` など）は `%XX` の形のまま表示します。
  画面の「すべての欄」で「URL デコードした文字も表示する」を選ぶと、デコードした文字もあわせて表示します。
- 1 回に返すのは 500 行まで、読み込むのは 256 MiB までです。
  どちらかの上限に達した時点でまだログが残っている場合は、応答に続きの位置（`next`）が入ります。
  画面では、最後のページの「次へ」で続きの古いログを読み込みます。
- 応答に `error` の文が無い失敗では、画面は失敗の文の後に、応答の `X-Request-ID` にあるリクエスト ID を表示します。
  手前に置いたプロキシがルールでブロックしたリクエストの 403 や、プロキシが管理プロセスに接続できなかった 502 などが、この失敗に当たります。
  その ID で「アクセスログ」の画面を検索すると、ブロックしたルールなどが分かります。
  ID を表示するのは、プロキシと管理プロセスが付与する形式のときだけです。
- 監査ログはプロキシのログファイルには入らないので、`type=audit` で検索しても見つかりません。
  「監査ログ」の画面か `GET /api/audit` で読みます。
- 設定に `records` が無いと、この API は 404（`records are not configured`）になります。
  ログのディレクトリが所有者と権限の検証に通らない場合は、503 になります。
- DB に送ったログを管理 API と管理画面で検索することは、実装していません。

条件の形式、続きの読み方、失敗の応答は、付録B 管理リファレンスの「ログの読み出し」を参照してください。

## 7.7　ログ送信プロセス

ログ送信プロセス（`tukuyomi-records-ship`）は、プロキシのログファイルを読み、行を順に PostgreSQL か MySQL のテーブルへ入れる、プロキシとは別のプロセスです。使うのは、ログを DB へ送る場合だけです。

プロキシはログ送信プロセスを動かさず、DB にも接続しません。
DB に接続するライブラリと DB のパスワードは、ログ送信プロセスの実行ファイルとプロセスにだけあります。
動作を確認しているのは、PostgreSQL 16・18 と MySQL 8.0 です。

準備は次の順に進めます。

1. **DB のユーザーと DB を用意する**
2. **接続文字列のファイルを置く**: 所有者をサービスの OS ユーザーにして、0600 で置きます（下の「接続文字列」）。
3. **設定に `records.ship` を書く**: `ship` と `required` を両方使うときは、`files` を 3 以上にします。
   `records` は動作中に変更できない設定キーです。動作中のプロキシの設定に追加する場合は、プロキシを再起動します（第9章）。
4. **ログ送信プロセスのユニットを起動する**: ユニットは、第3章の 3.5「ログ送信プロセスのユニット」にあります。
5. **ログを確認する**: ログ送信プロセスのログに `records-ship: configuration accepted` の行が出ることを確認します。テーブルは最初に接続したときに作ります。

### 起動

```text
tukuyomi-records-ship <config>
```

- `<config>` にはプロキシと同じ設定ファイルを絶対パスで指定します。
  設定ファイルには `records.ship` が必要です。
  無い場合は、`records-ship: configuration refused: there is no records.ship object` の行を出して終了します。
- 読むのは設定ファイルだけで、managed ストアのバージョンと国のデータベースは読みません。
  未知の設定キーがある設定ファイルは受け付けません。
  設定に新しい設定キー（`managed`、`host_policies`、`kernel.default_engine`、アップストリームの `engine` など）を書く前に、ログ送信プロセスをプロキシと同じビルドに入れ替えてください。
- プロキシと同じ OS ユーザーで動かします。root では動きません。
- ログのディレクトリを置くファイルシステムは、ファイルの作成時刻（`statx` の btime）を返す必要があります。動作を確認しているのは ext4 だけです。
  作成時刻を返さないファイルシステムでは、ログ送信プロセスは起動しません。
  このときプロキシは、ログ送信プロセスの遅れが分からないものとして `required` のリクエストを拒否します。
- 終了コードは次のとおりです。
  - 0: SIGTERM、SIGINT、SIGHUP で停止した
  - 1: 接続文字列が読めない、DB がログインを拒否した、など
  - 2: 引数のエラー、設定が受け付けられなかった

設定ファイルと接続文字列のファイルを読むのは、起動時の 1 回だけです。
SIGHUP は停止のシグナルです。設定を変更したときは、再起動します。

### `records.ship`

`records.ship` には、次の 5 つの設定キーをすべて書きます。

- `db_driver`: `pgsql` か `mysql` です。
- `db_dsn_file`: 接続文字列のファイルの絶対パスです。プロキシはこのファイルを開きません。
- `batch`: 1 つのトランザクションに入れる行の数の上限（1〜10000）です。
- `interval_ms`: 送る行が無かったときに次の回まで待つ時間（100〜60000）です。失敗の後に待つ時間の初期値でもあります。
- `retention_days`: DB に残す日数（0〜3650）です。0 なら削除しません。

```json
"records": {
  "dir": "/var/lib/tukuyomi-core/records",
  "file_bytes": 16777216,
  "files": 8,
  "sync_ms": 1000,
  "ship": {
    "db_driver": "pgsql",
    "db_dsn_file": "/etc/tukuyomi-core/records-db.dsn",
    "batch": 500,
    "interval_ms": 1000,
    "retention_days": 90
  }
}
```

### 接続文字列

接続文字列にはパスワードが含まれるため、設定ファイルには書かず、別のファイルに置きます。
このファイルの条件は次のとおりです。

- 通常のファイルであること
- 所有者がログ送信プロセスの OS ユーザーであること
- グループとその他のユーザーに権限が無いこと（0600）
- 16 KiB までの、UTF-8 の文字であること

ファイルには、使う DB に合わせて、下の例のどれか 1 つの形で書きます。

まず、PostgreSQL の例です。
`postgresql://` で始まる URL（`tokio-postgres` の形式）でも書けます。
テーブルは接続の `search_path` にある最初のスキーマに作ります。

```text
host=db.example.com port=5432 user=tukuyomi_ship password=<password> dbname=records
```

次は、同じホストの PostgreSQL に、Unix ドメインソケットと peer 認証で接続する例です。
peer 認証では、OS ユーザーの名前と同じ名前のロールで接続します。パスワードは必要ありません。

```text
host=/var/run/postgresql user=tukuyomi dbname=tukuyomi_records sslmode=disable
```

最後は MySQL の例で、URL は `mysql_async` 0.37 の形式です。
DB の名前は必ず書き、テーブルはその DB に作ります。
URL の中で記号を使う値は、パーセントエンコーディングで書きます。

```text
mysql://<user>:<password>@<host>:<port>/<db-name>
```

TLS について何も書かなければ、TLS を使い、証明書とホスト名を検証します。PostgreSQL も MySQL も同じです。
平文で接続できるのは、PostgreSQL では `sslmode=disable`、MySQL では `require_ssl=false` と書いたときだけです。

証明書の検証にはシステムの認証局を使います。
DB サーバーの証明書を独自の認証局で発行した場合は、その認証局の証明書を入れたファイルをユニットの `Environment=SSL_CERT_FILE=<path>` で渡します。
受け付けない指定も含めた一覧は、付録A 運用リファレンスの「接続文字列（`db_dsn_file`）」を参照してください。

### ログのテーブル

DB に接続したとき、ログ送信プロセスはテーブルを探し、無いテーブルだけを作ります。
テーブルは次の 3 つです。

- `tukuyomi_records`: ログの 1 行ごとに、テーブルの 1 行が入ります。
  `ts`、`type`、`request_id`、`client`、`class`、`status`、`rule` などの列と、ログの行そのものを入れる `raw`、行の SHA-256 を入れる `line_hash`（UNIQUE）の列があります。
- `tukuyomi_records_state`: ログのディレクトリごとに、どこまで送ったかの位置を入れます。
- `tukuyomi_records_schema`: スキーマのバージョンを入れます（現在は 1）。

テーブルがそろっていてバージョンの行もあれば、ログ送信プロセスは何も作らないので、DB のユーザーにテーブルを作る権限は必要ありません。
作る権限を渡したくないときは、まず作る権限のあるユーザーでログ送信プロセスを一度動かし、テーブルを作らせます。
その後で、ログ送信プロセスが接続に使う DB のユーザーを変更します。

ログ送信プロセスは 1 つのログのディレクトリに 1 つだけ動かします。
送った位置は `records.dir` のパスで区別します。
別のホストにあるプロキシのログを同じテーブルへ送るときは、`records.dir` のパスを変えるか、別のスキーマや DB にします。

MySQL では、サーバーの `max_allowed_packet` を 2 MiB 以上にしてください。
列、インデックス、MySQL と PostgreSQL の違いは、付録A 運用リファレンスの「ログのテーブル」を参照してください。

### 送信の仕組み

- 1 回の処理では、ログファイルの行を `batch` 個まで読みます。
  1 つのトランザクションの中で、読んだ行を入れて位置のテーブルを進めます。
  コミットの後に `ship.state` を書きます。
  ログ送信プロセスが落ちても、次の回は DB にある位置から続けます。
- 失敗した後は、待つ時間を `interval_ms` から倍にして 1 分まで延ばします。うまくいった回の後は、元に戻します。
- DB に接続できない間も、送る行が無い間も、`ship.state` は 1 秒に 1 回は書き直します。
  プロキシはこれを見て、ログ送信プロセスが動作中であると判断します。
- ログファイルは名前ではなく inode と作成時刻で追跡するので、ローテーションでリネームされても続きから読みます。
- 送るのはすべての `type` の行で、行そのものはいつも `raw` に残ります。
  `line_hash` が UNIQUE なので、同じ行を二重に送っても 1 行になります。
- `retention_days` が 0 でなければ、1 分に 1 回、それより古い行を 1000 行まで削除します。
  古いかどうかは、ログの `ts`（プロキシの時計）で決めます。

### 送れないログ

- ログ送信プロセスが読む前にローテーションで消えたログファイルの行は、失われます。
- ログ送信プロセスが開いていたファイルなら、失われた行を数えて位置の `lost_lines` に加え、`records-ship: a record file was removed before it was shipped, <count> lines lost` の行を出します。
- 開く前に消えたファイルの行は数えられず、`lines may be lost` を含む行だけを出します。この行は何も失われていないときにも出ることがあります。
  ログ送信プロセスが開く前にファイルが消えるのは、DB に長く接続できない間に、プロキシが `files` より多くローテーションしたときなどです。
- プロキシの `required` のルートは、こうなる前にリクエストを拒否します（7.4）。`best_effort` と `security` のルートは拒否しません。
- ログ送信プロセスは切り詰めたファイルを同じファイルとみなし、その先頭の行を送らないことがあります。
  ログファイルは切り詰めないでください（logrotate の `copytruncate` など）。ローテーションはプロキシが自分で行います。

### エラー

ログ送信プロセスのログは、プロキシと同じ 1 行 1 件の JSON で、標準エラーに出ます。
`type` は `line` で、文は `records-ship:` で始まります。
文には、接続文字列、ログ、サーバーが返した文の値を入れません。
DB のエラーは、決まった文と、サーバーが返した SQLSTATE で示します（例: `records-ship: the database refused or failed a request (SQLSTATE 42000)`）。

- DB がログインを拒否したときは、待っても直らないので、`records-ship: stop: the login is refused, which waiting does not mend` の行を出して終了します（exit 1）。
  その後はユニットの `Restart=on-failure` で再起動を繰り返します。接続文字列を直してください。
  ログインの拒否に当たるのは、PostgreSQL では SQLSTATE が 28 で始まるもの、MySQL では 1045 です。
- ほかの拒否のときは、上で説明した待ち時間を置いて再試行し、そのたびに行を出します。

ここで説明しなかった決まりは、付録A 運用リファレンスの「ログ送信プロセス」を参照してください。

## 7.8　運用上の注意

最後に、ログの運用で気を付ける点をまとめます。

- ログにはクライアントのアドレスとパスが入ります。
  パスに秘密の値を入れる作りのサイトでは、その値もログに残ります。
  ジャーナル、ログファイル、DB のテーブルを読める範囲は、最小限にしてください。
- ログを残せないときの扱いは、ルートごとに選びます。
  `required` はそのルートの新しいリクエストを 503 で拒否します。
  `best_effort` と `security` はリクエストを通し、ログを失います。
- ログファイルへの書き込みとローテーションはプロキシが行います。
  ファイルを切り詰めないでください（logrotate の `copytruncate` など）。
- ログ送信プロセスと `required` のルートを両方使うときは、`files` を 3 以上にします。
  こうしておくと、ログ送信プロセスが遅れたり止まったりしても、ログがローテーションで消える前に `required` のルートがリクエストを拒否します。
- `/metrics` の `tukuyomi_records_dropped_total`、`tukuyomi_record_write_errors_total`、`tukuyomi_record_file_errors_total`、`tukuyomi_records_unshipped_bytes` などで、ログが書けているか、送れているかを確認します（第9章）。
- `records.keep` 以外の `records` を変更したときは、プロキシ、管理プロセス、ログ送信プロセスを再起動してください。
  接続文字列のファイルを変更したときは、ログ送信プロセスを再起動してください。
