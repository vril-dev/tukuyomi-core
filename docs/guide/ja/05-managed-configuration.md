# 第5章　managed 設定と管理画面

本章では、まず管理プロセスを用意します。
続いて、ユーザーとロール、ログインと二要素認証、API トークン、監査ログを順に説明します。

後半で扱う managed 設定は、設定の一部を設定ファイルの外に置き、管理画面から変更して動作中のプロキシに反映できるようにする仕組みです。
使うかどうかの判断、初回起動、反映の順に見ていきます。
最後に、管理画面の各画面を紹介します。

API の細かい形と画面ごとの説明は、付録B 管理リファレンスにあるので、本章ではそちらを案内します。

## 5.1　管理プロセスと managed 設定

この節では、管理プロセスの役割と、使うかどうかの判断を見ておきます。

管理プロセスは、`tukuyomi-proxy admin <config>` で動く、プロキシとは別のプロセスです。
ブラウザーで開く管理画面と、プログラムから使う管理 API に応答します。
プロキシと同じ実行ファイルと設定ファイルを使い、同じ OS ユーザーで動きます。

リスナーは `admin.listen` のループバックのアドレスです。
TLS は使わず、HTTP/1.1 で応答します。
1 つの接続ではリクエストを 1 つ受け付け、応答したら接続を閉じます。
同時接続数は 32 で、超えた接続は受け付けてすぐに閉じます。

管理プロセスは、管理データの保存先（設定の `admin.store.dir`）に、ユーザー、API トークン、監査ログ、切り替えの履歴、設定の変更履歴を置きます。
managed 設定のバージョンは、managed ストア（設定の `managed.dir`）に置きます。

プロキシへの依頼には、プロキシが作る Unix ドメインソケット（制御ソケット。設定の `admin.control`）を使います。
管理プロセスはこのソケットで、プロキシの状態を問い合わせたり、世代の切り替えや設定のリロードを依頼したりします。

管理プロセスでできることは、次のとおりです。

- ルールの世代の操作（第4章）
- ログの検索（第7章）
- ユーザー、API トークン、監査ログの管理
- managed 設定の編集と反映

設定ファイルそのものは管理画面からも管理 API からも編集できません。画面には値を表示するだけです。

使うかどうかを決めておくことが 2 つあります。

- **管理プロセスを使うか**: 設定ファイルに `admin` を書くと使います。
  `admin` が無いと、管理プロセスは起動せず（exit 2）、プロキシは制御ソケットを作りません。
  管理プロセスはプロキシが停止していても動作しますが、プロキシに依頼する世代の切り替えと managed 設定の反映は拒否します。
- **managed 設定を使うか**: 設定ファイルに `managed` を書くと使います（5.9）。
  管理プロセスだけを使い、managed 設定は使わない構成もできます。

## 5.2　管理プロセスを用意する

まず、次の例のように、設定ファイルの最上位に `admin` を書きます。

```json
"admin": {
  "listen": "127.0.0.1:9100",
  "control": "/var/lib/tukuyomi-core/control/proxy.sock",
  "store": {"kind": "file", "dir": "/var/lib/tukuyomi-core/admin"},
  "origin": "https://admin.example.com",
  "trusted_proxies": ["127.0.0.1/32"],
  "mfa": "required",
  "session_idle_ms": 1800000,
  "session_total_ms": 43200000,
  "crs_dir": "/var/lib/tukuyomi-core/crs-4.23.0"
},
"records": {"dir": "/var/lib/tukuyomi-core/records", "file_bytes": 16777216, "files": 8}
```

`admin` を書くときは、`crs_dir` と `route` 以外のすべての設定キーを書きます。
主な設定キーの意味は次のとおりです。

- `listen`: ループバックのアドレスです。`proxy.listeners` や `status.listen` と重ねることはできません。
- `control`: 制御ソケットのパスです。ソケットはプロキシが作ります。
- `origin`: 管理画面を開く URL のオリジンです。
- `crs_dir`: 管理画面のインポートで CRS を使うときのディレクトリです。
- `route`: 管理画面のルートです。`managed` のある設定では必ず書き、`managed` の無い設定では書けません（5.3）。

各設定キーの範囲は、付録B 管理リファレンスの「設定キー `admin`」を参照してください。

`admin.store.dir` と、`admin.control` を置くディレクトリは、シンボリックリンクでないディレクトリとして先に作っておきます。
所有者はプロキシの OS ユーザーにし、グループとその他のユーザーには権限を与えません（0700）。
ルールストア、`records.dir`、`managed.dir` などとは、同じディレクトリにすることも、互いの中に置くこともできません。
付録A 運用リファレンスの「値どうしの関係」を参照してください。

第3章の例のように、管理プロセスはプロキシとは別のユニットで動かします。
ユニットでは、`Type=notify`、`KillMode=mixed`、`LogRateLimitIntervalSec=0` を指定します。

- `KillMode=mixed` にするのは、ルールのインポートの事前検証で起動した検査プロセスを管理プロセスが順に停止できるようにするためです。
- `LogRateLimitIntervalSec=0` にするのは、標準エラー（ジャーナル）にも出力される監査ログの行が、journald のレート制限で失われないようにするためです。

管理プロセスにとって SIGHUP は停止のシグナルなので、`ExecReload` は置きません。

管理プロセスは `admin` などの値を起動時に 1 回だけ読みます。
`admin` の設定キーを変更したときは、`config check` で検証してから、管理プロセスとプロキシを再起動します。

最初のユーザーは `admin bootstrap` で作成します。このユーザーのロールは `owner` です。
パスワードは引数では渡さず、標準入力の最初の 1 行から読み込みます。

```bash
read -r -s -p 'password: ' PW; echo
printf '%s\n' "$PW" | sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy admin bootstrap /etc/tukuyomi-core/config.json alice
unset PW
```

- **名前とパスワード**: 名前は小文字の英字・数字・`.`・`_`・`-` からなる 1〜32 バイトの文字列で、パスワードは 12〜128 バイトの UTF-8 です。
- **結果**: 成功すると、標準出力に `created owner <name>` が出て、exit 0 で終了します。
  ユーザーが 1 人でもいると、作成できません（exit 1）。
  管理プロセスが動作していなくても、このコマンドは実行できます。
- **ロックアウトされたとき**: 唯一の owner がパスワードと二要素認証の両方を失った場合などは、`admin reset` を使います。
  `admin reset` は、パスワードを決め直し、二要素認証と API トークンを無効にします。
  次のログインでは、パスワードの変更を求めます。

## 5.3　外部から利用する

管理プロセスは TLS を使わないので、プロキシの TLS のリスナーを通して使います。
クッキーは `Secure` 付きで出力されるため、管理画面は https でしか使えません。

プロキシを通す方法は、設定ファイルに `managed` があるかどうかで変わります。

`managed` の無い設定では、次の例のように、管理用の Host のルートを `forward.routes` に書きます。

```json
"forward": {
  "upstreams": {
    "app": {"servers": [{"address": "127.0.0.1:8080", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]},
    "admin": {"servers": [{"address": "127.0.0.1:9100", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]}
  },
  "routes": [
    {"host": "admin.example.com", "upstream": "admin", "access": {"allow_cidrs": ["192.0.2.0/24"]}}
  ],
  "default_upstream": "app"
}
```

この例では、`forward` のほかの設定キーを省略し、`admin.listen` を `127.0.0.1:9100` としています。

- **証明書と許可するアドレス**: TLS のリスナーには、`admin.example.com` を `hosts` に持つ証明書を置きます。
  `access` の `allow_cidrs` では、管理画面を使うユーザーのアドレスだけを許可します。
- **平文のリスナー**: この Host を平文のリスナーに通さないでください。
  ルートはリスナーに関係なく選択されるので、`redirect` でない平文のリスナーがあると、パスワードが暗号化されずに流れるおそれがあります。
- **適用されるポリシー**: 全体の設定（全体のアクセス制御とレート制限）とホストごとの設定は、この Host へのリクエストにも適用されます（第6章）。

`managed` のある設定では、管理画面のルートを `admin.route` に書きます。
このルートはプロキシが自分で作成するもので、`host`（管理画面のホスト名）、`certificate`、`access` を持ちます。
`access` の `allow_cidrs` は必ず書き、空にはできません。
このルートには、全体の設定もホストごとの設定も適用されません（5.9。例は 5.11）。

次の 2 つは、どちらの設定でも書きます。

- **`admin.trusted_proxies`**: プロキシが管理プロセスに接続するときの、接続元のアドレスです。同じホストのときは `127.0.0.1/32` にします。
  書かないと、すべてのクライアントのアドレスがプロキシのアドレスとして扱われます。
  クライアントごとにかかるログインの試行回数の制限は、全員で共有されることになります。
  監査ログの `client` も、すべての行でプロキシのアドレスになります。
- **`admin.origin`**: ブラウザーで開く URL のオリジンと、一字一句同じにします。ポートが 443 のときは、ポートを書きません。
  違うと、ログインを含む変更が 403 になります。

詳しくは、付録B 管理リファレンスの「外部からの利用」を参照してください。

## 5.4　管理画面へのリクエストと WAF の検査

管理画面へのリクエストも、WAF の検査を通ります。
どのエンジンで検査するかは、設定によって次のように変わります。

- `managed` のある設定: デフォルトのエンジンです。
  デフォルトのエンジンは設定ファイルの `kernel.default_engine` に書いたエンジンです。`kernel.default_engine` を書かないときは `coraza` になります。
- `managed` の無い設定: 管理プロセスへ転送するアップストリームのエンジンです。

ここで気を付けたいのが、大きなリクエストボディです。
ルールのインポートや managed 設定の検証・保存で送るリクエストのボディは、ルールのファイルや証明書の PEM が入った大きな JSON で、最大で 12 MiB になります。
このボディを検査の対象にすると、ルールにブロックされることがあります。
これらのリクエストのパスは世代の検査除外のルート（第4章）にしてください。

次の例は、`managed` のある設定で、1 つの `--routes` のファイルに書いたものです。

```json
[
  {"host": "admin.example.com", "path": "/api/generations", "action": "bypass"},
  {"host": "admin.example.com", "path": "/api/managed/check", "action": "bypass"},
  {"host": "admin.example.com", "path": "/api/managed/apply", "action": "bypass"}
]
```

- **パスの一致**: `path` は `/` で終わらないので、そのパスだけに一致します。
- **世代ごとのルート**: 検査除外のルートは世代の一部です。
  管理画面のリクエストを検査するエンジンでは、どの世代にも同じルートを入れ続けてください。
  入れ忘れた世代を選択すると、その世代からは、これらのリクエストが検査されます。
- **最初の世代**: このルートが効くのは、ルートを入れた世代が使われてからです。
  最初にこのルートを入れる世代は、コマンドでインポートします（`rules import ... --routes <file>`）。
- **`proxy.max_body`**: 管理画面のルートには `max_body` が無く、`proxy.max_body` が上限になります。
  値は 12 MiB（12582912）以上にしてください。
- **ブロックされたときの表示**: 検査除外のルートが無い世代で、ルールが `check` か `apply` のリクエストを 403 でブロックすると、管理画面は「プロキシか WAF がリクエストを拒否しました。PEM のファイルや多くのルートを含むリクエストボディは、WAF にブロックされることがあります。/api/managed/check と /api/managed/apply を検査の対象から除外する設定を確認してください。」と表示します。

管理画面の Host を CRS で検査するときは、PUT と DELETE のメソッドと、パスワードの欄についても調整が必要です。
調整しないと、新しいユーザーが最初のパスワードを変更できず、ログインを終えられません。
付録B 管理リファレンスの「管理画面の Host での CRS の調整」を参照してください。

## 5.5　ユーザーとロール

ロールは `viewer`、`operator`、`owner` の 3 つで、この順にできることが増えます。

- **`viewer`**: 状態、世代の一覧と内容、切り替えの履歴、ログを読めます。
  managed 設定の状態、バージョンの一覧、設定の変更履歴も読めます。
  自分のパスワード、二要素認証、API トークンを扱えます。
- **`operator`**: viewer ができることはすべてでき、加えて監査ログを読めます。
  ルールのインポート、世代の選択、ロールバック、削除ができます。
  managed 設定では、検証、保存して反映、名前で反映、ロールバック、削除ができます。
- **`owner`**: operator ができることはすべてでき、加えてユーザーを作成し、ロールと有効・無効を変更できます。
  ほかのユーザーのパスワードと二要素認証を初期化でき、全員の API トークンを閲覧して削除できます。

ユーザーの扱いは次のとおりです。

- **ユーザーの作成**: 最初の owner は `admin bootstrap` で作成します。
  それ以降のユーザーは、owner が管理画面の「ユーザー」で作成します。
  owner が作成したユーザーと、owner がパスワードを決めたユーザーは、次のログインで自分のパスワードに変更するまでほかの API を使えません。
- **ユーザーの削除**: ユーザーを削除する API はありません。使わなくなったユーザーは無効にします。
  有効にし直しても、削除された API トークンは戻りません。
- **拒否される変更**: owner が自分自身に対して行う操作（自分のロールを下げる、自分を無効にする、自分のパスワードと二要素認証を初期化する）は拒否します。
  有効な owner が 1 人もいなくなる変更も拒否します。

## 5.6　ログインと二要素認証

ログインに成功すると、管理プロセスはセッションを作成し、クッキー `tukuyomi_admin` を返します。
セッションは次のようなときに終了します。

- `admin.session_idle_ms` の間、使われなかったとき
- 作成してから `admin.session_total_ms` が過ぎたとき
- ログアウトしたとき

二要素認証（MFA）には、時刻に基づくワンタイムパスワード（RFC 6238）を使います。
コードは HMAC-SHA1、6 桁、30 秒ごとの時間枠で作成します。
`admin.mfa` が `required` のとき、二要素認証を設定していないユーザーは、設定するまでほかの操作ができません。

- **設定の流れ**: 管理画面の「アカウント」から設定すると、管理プロセスがセットアップキーを返します。
  設定は、認証アプリの認証コードで確定します。
  確定のときに、リカバリーコードを 10 個、1 回だけ返します。
  リカバリーコードは 1 個 16 文字で、それぞれ 1 回だけ使えます。
- **`required` のときの無効化**: 自分では二要素認証を無効にできません。owner に無効にしてもらいます。
  owner 自身の分は、ほかの owner に無効にしてもらうか、`admin reset` を使います。
- **ロックアウトと試行回数**: ユーザーごとに、続けて 5 回失敗すると、15 分間ロックアウトします。
  クライアントごとには、1 分間に 30 回まで試行できます。

変更のリクエストでは、次の 2 つを検証します。

- `Origin` ヘッダーがあれば、`admin.origin` と一字一句同じであること
- セッションのリクエストでは、`X-CSRF-Token` が正しいこと

1 つのリクエストに、セッションのクッキーと `Authorization` ヘッダーの両方があると、400 になります。
管理画面の前に Basic 認証などの HTTP 認証をかけた場合は、ログイン後のリクエストに両方が付くので、400 になります。

詳しくは、付録B 管理リファレンスの「ログインと二要素認証」「ロックアウトと試行回数の制限」「セッション」「CSRF と Origin」を参照してください。

## 5.7　API トークン

API トークンは、プログラムから管理 API を使うためのトークンです。
作成と削除は、管理画面の「アカウント」で行います。

- **形式と保存**: `tkc_<16-hex-digits>_<43-characters>` の形式です。
  トークンの全体は作成したときに 1 回だけ返し、管理データの保存先には秘密の SHA-256 だけを置きます。
- **作成するとき**: 名前、ロール、有効な日数（1〜365）、現在のパスワードを指定します。
  指定できるロールは、自分のロール以下です。
  1 人が持てるのは 50 個までで、期限が切れたトークンも数に入ります。
- **使うとき**: `Authorization: Bearer <token>` で送ります。セッションのクッキーとは一緒に送れません。
  アカウントの API と、ユーザーの管理の API には使えません。
- **所有者の状態が変わったとき**: 所有者が無効になったとき、ロールが下がったとき、パスワードが変更されたときにも、トークンは無効になります。

たとえば、`$TOKEN` にトークンを入れて `curl -sS -H "Authorization: Bearer $TOKEN" https://admin.example.com/api/status` を実行します。
使える API の一覧は、付録B 管理リファレンスの「API のパスの一覧」を参照してください。

## 5.8　監査ログ

管理プロセスは、ログイン、変更、拒否したリクエストを監査ログの行として残します。
パスワード、API トークン、認証コード、リカバリーコード、二要素認証のセットアップキー、クッキーは、監査ログに書きません。

- **変更との順序**: 監査ログの行を先に書いてから、変更を行います。
  ディスクが満杯の場合などで行を書けないときは、変更せずに 503 `unavailable` で拒否します。
  例外はログアウトで、行を書けなくてもセッションを終了します。
- **`ok` の行**: 世代の選択とロールバック、managed 設定の変更では、`ok` の行を変更の前に書くので、この行は成功を示すものではありません。
  どう終わったかは、後に続く行と、切り替えの履歴や設定の変更履歴で確認します。
- **保存先**: `admin.store.dir` の `audit/audit.log` に、1 行 1 件の JSON で書きます。
  1 つのファイルが 16 MiB を超えると次のファイルに移り、8 ファイルを残します。
  同じ行を標準エラー（ジャーナル）にも出力します。
- **読み方**: 管理画面の「監査ログ」（operator 以上）か `GET /api/audit` で、最新の 200 行を新しい順に読めます。
  `audit` のログはプロキシのログファイル（`records.dir`）には入らないので、`type=audit` でログを検索しても見つかりません。

行の項目と `action` の一覧は、付録B 管理リファレンスの「監査ログ」を参照してください。

## 5.9　managed 設定を使うかどうか

managed 設定は、設定の一部を設定ファイルの外にある managed ストアに、バージョンとして保存する仕組みです。
対象になるのは、次の設定です。

- サイト（ホストと証明書）
- アップストリーム
- ルート
- デフォルトのアップストリーム
- 全体のアクセス制御とレート制限
- ホストごとの設定

使い始めるには、設定ファイルに `managed` を書きます。
`managed` の無い設定ファイルは、これまでと同じように読みます。
この節では、使うとできることと、その代わりに必要になることを並べます。

使うと、次のことができます。

- **管理画面からの編集と反映**: 上の設定を管理画面と管理 API で編集し、検証してから保存して、動作中のプロキシに反映できます。
  反映では、プロキシがそのバージョンで設定のリロードを通した後にだけ、選択中のバージョンを進めます。
  反映でプロキシが拒否したバージョンが、次の起動で使われることはありません。
- **前のバージョン**: 保存したバージョンは残るので、前のバージョンに戻せます（ロールバック、名前を指定した反映）。
- **履歴**: 管理画面と管理 API からの反映は管理プロセスの変更履歴に、操作は監査ログに残ります。
  コマンドでの変更はどちらにも残りません。

その代わり、次のことが必要になります。

- **設定ファイルに書けなくなる設定キーがある**: `forward` は `resolve_timeout_ms` だけになります。
  TLS のリスナーの `certificates`、全体の `access`・`rate_limit`、`host_policies` も書けません。これらはバージョンに書きます。
- **管理画面のルート**: 設定に `admin` があれば、管理画面のルート（`admin.route`）が必須です。
  このルートに適用されるネットワークの制限は、`admin.route.access` の `allow_cidrs` だけです。
- **`managed` を追加するときと外すとき**: `managed` の有無と `managed.dir` は、動作中に変更できません。
  設定のリロードで変更しようとすると、リロードは拒否されます。
  変更するときは、プロキシと管理プロセスを再起動します。
- **検査除外のルートを入れた世代が必要になる**: 管理画面のルートも、デフォルトのエンジンによる WAF の検査を通ります。
  デフォルトのエンジンの世代には、5.4 の検査除外のルートを入れた世代を使います。
  デフォルトのエンジンを変更するときは、新しいデフォルトのエンジンの世代にも、同じルートを入れます。
- **ACME の証明書**: ACME で発行するサイトの証明書は、managed ストアの `acme/` に置きます（第8章）。
- **ログ送信プロセスのビルド**: `managed` を知らない前のビルドは、未知の設定キーのある設定ファイルを受け付けず、起動しません。
  ログ送信プロセスを使うなら、プロキシと同じビルドに入れ替えてから、設定ファイルに `managed` を書いてください。

設定をファイルだけで管理し、管理画面から変更しないなら、`managed` は必要ありません。

## 5.10　managed ストアとバージョン

設定キー `managed` が持つのは、`{"dir"}` だけです。
`dir` は managed ストアのディレクトリです。
このディレクトリはプロキシもコマンドも作らないので、先に作っておきます。
シンボリックリンクでないディレクトリにし、所有者はプロキシの OS ユーザー、権限は 0700 にします。

managed ストアには、次のものがあります。

- バージョン（`versions/<version>.json`）
- バージョンが指す証明書チェーン・秘密鍵・アップストリームの CA のファイル（`files/<sha256>`）
- ACME のサイトの証明書（`acme/`）
- 選択中のバージョンを示す `current`

バージョンとファイルの名前は内容の SHA-256 で、作った後は変えません。
バージョンは手で書かず、`managed import` か管理画面で作成します。

バージョンは JSON で、`sites`、`upstreams`、`routes`、`default_upstream` を持ちます。
省略できる `access`、`rate_limit`、`host_policies` も持てます。

`upstreams`、`routes`、`default_upstream`、`access`、`rate_limit`、`host_policies` は、`managed` の無い設定ファイルの `forward` や、第6章と同じ形で書きます。
違うのはアップストリームの `tls` の `ca` だけで、ここには managed ストアの `files/` にあるファイルの SHA-256 を書きます。

`sites` のサイトは、`{"name", "hosts", "certificate"}` と書きます。
`certificate` は、`{"chain", "key"}` か `{"acme": {"renew_before_days"}}` のどちらかです。
形と決まりの全体は、付録A 運用リファレンスの「managed ストアとバージョン」を参照してください。

`managed` コマンドは動作中のプロキシには依頼しません。

- `managed import <config> <document>` は、文書からバージョンを作成して managed ストアに置き、選択はしません。
- `managed activate <config> <version>` は、起動と同じ検証を実行します。
  通ったときだけ、`current` を変更してバージョンを選択します。
- ほかに、`managed remove` と `managed list` があります。

文書はバージョンと同じ形で書きますが、ファイルは SHA-256 ではなくパスで書きます（`chain_file`・`key_file`・`ca_file`）。
インポートした後は、文書が指すファイルを使いません。
付録A 運用リファレンスの「`managed`」を参照してください。

## 5.11　managed 設定での初回起動

`managed` のある設定では、選択中のバージョンが無いと、起動も `config check` も拒否します（`config check: managed store refused: no managed version is chosen`、exit 1）。
最初のバージョンは、起動の前にコマンド（`managed import` と `managed activate`）で作成して選択しておきます。
ほかの手順は第2章の初回起動の手順と同じです。

ここでは、次の構成を例にします。

- リダイレクトのリスナーと TLS のリスナー
- ファイルの証明書を持つサイト 1 つ
- アップストリーム 1 つ
- 管理画面のルート

1. ディレクトリを作ります。
   第3章のディレクトリに加えて、managed ストアのディレクトリを 0700 で作ります。

   ```bash
   sudo install -d -m 0700 -o tukuyomi -g tukuyomi /var/lib/tukuyomi-core/managed
   ```

2. 証明書のファイルを置きます。
   置くのは、管理画面のルートの証明書と秘密鍵（例: `/var/lib/tukuyomi-core/tls/admin.pem`・`admin.key`）と、サイトの証明書チェーンと秘密鍵（例: `/var/lib/tukuyomi-core/import/www.pem`・`www.key`）です。
   サイトのファイルはインポートの入力になるので、サービスの OS ユーザーが読める場所に置きます。
3. 設定ファイルを書きます。
   次の抜粋は、`managed` の無い設定ファイルとの違いを示したものです。

   ```json
   "proxy": {
     "listeners": [
       {"address": "0.0.0.0:80", "redirect": {"https_port": 443}},
       {"address": "0.0.0.0:443", "tls": {"min_version": "1.2"}}
     ]
   },
   "forward": {"resolve_timeout_ms": 5000},
   "managed": {"dir": "/var/lib/tukuyomi-core/managed"},
   "admin": {
     "route": {
       "host": "admin.example.com",
       "certificate": {
         "cert_file": "/var/lib/tukuyomi-core/tls/admin.pem",
         "key_file": "/var/lib/tukuyomi-core/tls/admin.key"
       },
       "access": {"allow_cidrs": ["203.0.113.0/24"]}
     }
   }
   ```

   `proxy` は `listeners` 以外の設定キーを、`admin` は `route` 以外の設定キーを省略しています。
   省略した設定キーは、5.2 の例と、付録A 運用リファレンスの「例」に従って書きます。
   TLS のリスナーには、`certificates` を書きません。

4. バージョンの文書を書きます（例: `/etc/tukuyomi-core/managed-import.json`）。
   文書はサービスの OS ユーザーが読めるように置きます。

   ```json
   {
     "sites": [
       {
         "name": "www",
         "hosts": ["www.example.com"],
         "certificate": {
           "chain_file": "/var/lib/tukuyomi-core/import/www.pem",
           "key_file": "/var/lib/tukuyomi-core/import/www.key"
         }
       }
     ],
     "upstreams": {
       "web": {"servers": [{"address": "127.0.0.1:8080", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]}
     },
     "routes": [],
     "default_upstream": "web"
   }
   ```

5. ルールセットをインポートし、世代を選択します（第2章、第4章）。
   バージョンを選択する `managed activate` は、バージョンのアップストリームが使うエンジンに選択中の世代があることを確認します。
   この手順は 7 より前に行います。
6. バージョンをインポートします。
   `<version> created` が出ます。
   このコマンドはバージョンを置くだけで、選択はしません。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy managed import /etc/tukuyomi-core/config.json /etc/tukuyomi-core/managed-import.json
   ```

7. バージョンを選択します。
   起動と同じ検証を実行し、通ったときだけ選択します。
   `<version> current` が出ます。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy managed activate /etc/tukuyomi-core/config.json <version>
   ```

8. 設定を検証します。
   通れば、標準出力に `accepted` が、標準エラーに `config check: managed version <version>` の行が出ます。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy config check /etc/tukuyomi-core/config.json
   ```

9. サービスを起動します（第3章）。
   ログに `start: managed version <version>` の行が出ます。
10. 管理プロセスを起動し、最初のユーザーを作成します（5.2）。
    管理画面には、`admin.route.access` が許すネットワークから、`admin.route.host` のホスト名でアクセスします。
    これ以降の変更は管理画面か管理 API で行います（5.13）。

ACME のサイトを使う場合は、付録A 運用リファレンスの「ACME のサイト」を参照してください。

## 5.12　managed 設定への移行

`managed` の無い設定ファイルで動作しているプロキシと管理プロセスは、managed 設定に移行できます。
変換のコマンドは無いので、設定ファイルとバージョンの文書は手で書きます。
何がどこへ移るかの表と手順は、付録A 運用リファレンスの「managed 設定への移行」にあります。
ここでは、迷いやすい点だけを挙げます。

- **管理画面のルート**: 管理画面のホストのルートは `forward.routes` から外し、そのルートの `access` は `admin.route.access` にコピーします。
  管理画面のルートには全体の設定が適用されないので、コピーし損ねると、管理画面に到達できる相手が変わります。
- **ACME のサイト**: 現在の証明書チェーンと秘密鍵は、managed ストアの `acme/<hosts-sha256>/` にコピーします。
  コピーしないと、`acme renew` と SIGUSR2 の後まで、そのサイトのホストに TLS で接続できません。
- **移行前の構成**: 元の設定ファイル、実行ファイル、ユニットを残してから、新しい設定ファイルを元のパスに置きます。
- **再起動の順序**: 管理プロセス、プロキシ、ログ送信プロセスの順に再起動します（`systemctl restart`）。
  `admin.route.host` と `managed` は動作中に変更できないので、`systemctl reload` は拒否されます。
  管理プロセスを再起動してからプロキシを再起動するまでの間は、managed 設定の変更の依頼を 409 で拒否し、何も変更しません。

## 5.13　バージョンを反映する

動作中のプロキシに別のバージョンを使わせる方法は、管理画面と管理 API から反映する方法と、コマンドと SIGHUP を使う方法の 2 つです。

### 管理画面と管理 API の反映

管理画面と管理 API からは、次の操作で反映します。

- **保存して反映**: 画面の下書きから作ったバージョンを保存し、反映します。
- **名前を指定した反映**: managed ストアにあるバージョンを名前（SHA-256）で指定して反映します。
- **ロールバック**: 前のバージョンへ戻します。
  ロールバック先は、設定の変更履歴で結果が `applied` かつ `from` と `to` が違う行のうち、最も新しい行の `from` です。
  ロールバックできるのは、その行の `to` が現在選択中のバージョンのときだけです。
  反映が `applied` に終わらなかった後や、コマンドでバージョンを選択した後は、ロールバックできません（409 `the history does not end at the chosen version`）。
  続けてもう一度ロールバックすると、元のバージョンに戻ります。

どの操作でも、管理プロセスは制御ソケットで `reload` を依頼して、プロキシにそのバージョンで設定をリロードさせます。
`current` をそのバージョンにするのは、プロキシの設定が切り替わった後だけです。
プロキシが拒否したバージョンは `current` になりません。

- **古い画面からの上書きを防ぐ**: 画面で見た選択中のバージョンは、`expect` として送ります。
  画面を見た後にほかのユーザーかコマンドが選択し直していた場合は、409 で拒否します。
- **反映の処理**: 反映は 202 で応答し、その後は管理プロセスの中で反映の処理として続きます。
  管理画面は終わるまで「反映中」と表示し、終わると結果（「反映済み」「拒否」「使用中」など）を表示します。
  反映の処理はキャンセルできません。
- **managed ストアのロック**: 反映の間は管理プロセスがこのロックを持ち、その間の `managed import`・`managed activate`・`managed remove` は拒否されます（`the managed store is in use by another command`）。
- **ACME のサイトを追加・変更したとき**: ACME のサイトを追加したバージョンや、サイトのホストを変更したバージョンを反映した時点では、新しいホストの組み合わせの証明書はまだ managed ストアにありません。
  `acme renew` で発行するまで、そのサイトのすべてのホストに TLS で接続できなくなります。
  反映の後は、すぐに `acme renew` を実行して SIGUSR2 を送ってください（第8章）。
  「保存して反映する」の確認にも、この注意が表示されます。
- **設定ファイルの書き換え**: リロードでは、バージョンと一緒に設定ファイルも読み込みます。
  設定ファイルを書き換えて、まだ SIGHUP を送っていない場合は、管理画面からの反映でその書き換えも効きます。
  設定ファイルにエラーがあれば、反映も拒否します。

### コマンドと SIGHUP

`managed activate` は、起動と同じ検証を実行して `current` を変更します。
このコマンドはプロキシに依頼しません。
動作中のプロキシが `current` のバージョンを読むのは、次の SIGHUP（`systemctl reload`）か起動のときです（第9章）。

SIGHUP が拒否されると、`current` は動作中のプロキシが拒否したバージョンのまま残ります。
次に起動するときは、そのバージョンが使われます。

動作中のプロキシのバージョンを変更するには、管理画面か管理 API を使います。
コマンドで変更したときは、すぐに `systemctl reload` を実行し、`reload: configuration replaced <sha256> managed <version>` の行を確認してください。

### 途中で止まったとき

反映が途中で止まると、選択中のバージョン（`current`）と、稼働中のバージョンが違うことがあります。
稼働中のバージョンは `GET /api/managed` の `serving` で、選択中のバージョンは `current` で分かります。

管理画面の「設定のバージョン」でも、2 つが違うときは通知を表示します。
あわせて、2 つをそろえる操作（「選択中のバージョンをもう一度反映する」と「稼働中のバージョンを選択し直す」）も表示します。
プロキシと管理プロセスは、この不一致を自動では修正しません。
状態と直し方の表は、付録A 運用リファレンスの「反映」を参照してください。

## 5.14　管理画面の各画面

管理画面は、ブラウザーで `https://admin.example.com/`（`admin.origin`）を開いて使います。
画面のファイルは実行ファイルに組み込まれているので、管理プロセスと管理画面はいつも同じバージョンです。

画面上部の帯では、次の表示を切り替えられます。

- 言語（日本語と英語）
- テーマ（自動、ライト、ダーク）
- 時刻の表示方法（ローカルか UTC）

使える画面はロールで決まり、メニューには、そのロールが使える画面だけが並びます。

| メニュー | 画面（ロール） | 内容 |
|---|---|---|
| （名前なし） | 概要（viewer 以上） | プロキシの数と状態、エンジンごとの世代の状態、設定ファイルの SHA-256。managed 設定を使っているときは、選択中と稼働中のバージョン |
| WAF | ルールの世代（viewer 以上）、ルールのインポート（operator 以上）、切り替え履歴（viewer 以上） | 世代の一覧と詳細、インポート、選択、プロキシの切り替え、エンジンの起動、削除、ロールバック（operator 以上） |
| ログ | アクセスログ（viewer 以上）、監査ログ（operator 以上） | 条件を指定したログの検索。監査ログの最新の 200 件 |
| プロキシ | サイト、アップストリーム、ルート（operator 以上） | managed 設定の下書きの編集 |
| ポリシー | アクセス制御とレート制限（operator 以上） | 下書きの、全体の設定とホストごとの設定の編集（第6章） |
| 設定 | 設定のバージョン、設定の変更履歴（viewer 以上）、設定ファイル（operator 以上） | 選択中と稼働中のバージョン、バージョンの内容、名前で反映、削除。設定の変更履歴とロールバック。設定ファイルの値の表示（変更はできません） |
| 管理 | アカウント（viewer 以上）、ユーザー（owner） | パスワード、二要素認証、API トークン。ユーザーの作成と管理 |

各画面の表示内容は、付録B 管理リファレンスの「管理画面」を参照してください。

「サイト」「アップストリーム」「ルート」「アクセス制御とレート制限」の 4 つの画面では、managed 設定の 1 つの下書きを編集します。

- **下書きの元**: 下書きは選択中のバージョンから作成します。
  「設定のバージョン」の画面からは、ほかのバージョンから作成することもできます。
  ここでの変更は、「保存して反映する」を押すまで有効になりません。
- **ページのメモリ**: 下書きはこのページのメモリにだけあり、ログアウトしたとき、セッションが切れたとき、タブを閉じたときに失われます。
- **検証と保存**: 帯の「検証する」は、保存せずに検証します。
  拒否されたときは、エラーをその欄に表示します。
  「保存して反映する」は、検証、確認、保存と反映の順に進みます。
  「変更なし」の下書きは保存できません。
- **確認の表示**: 確認には、保存する変更が名前で並びます。
  ルートの書き換えには秘密の値を書けるため、値は表示しません。

次の操作では、先に確認を表示します。

- 世代の選択、ロールバック、削除
- バージョンの名前での反映、ロールバック、削除

管理プロセスが managed 設定なしで起動しているときは、「設定のバージョン」の画面と編集の画面に、managed 設定でできることと、使い始めるまでの手順の要点を表示します。

## 5.15　運用上の注意

最後に、管理プロセスと managed 設定の運用で気を付ける点をまとめます。

- **管理プロセスとプロキシのビルド**: 同じビルドにそろえてください。
  プロキシがエンジンごとの状態を返さない前のビルドだと、管理画面は世代の選択、プロキシへの反映、エンジンの起動、ロールバックのボタンを表示しません。
- **管理プロセスの再起動**: 再起動すると、セッション、ロックアウトの状態、設定中の二要素認証のセットアップキー、反映の処理が失われます。全員がログインし直すことになります。
  API トークン、ユーザー、監査ログ、履歴は、保存先に残ります。
- **ログを読めるユーザー**: ログファイルにはクライアントのアドレスとパスが入ります。
  管理 API では、viewer 以上がログを読めます。
  viewer のロールを渡すユーザーは、検討したうえで決めてください。
- **不要なバージョン**: `managed remove` か、管理画面の「設定のバージョン」で削除します。
  選択中のバージョンと、使用中のバージョンは削除できません。
