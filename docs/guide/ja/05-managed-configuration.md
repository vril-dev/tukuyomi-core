# 第5章　managed 設定と管理画面

本章では、管理プロセスの用意から、ユーザーとロール、ログインと二要素認証、API トークン、監査ログまでを順に説明します。続いて、設定の一部を設定ファイルの外に置き、管理画面から変更して動作中のプロキシに反映する managed 設定を、使うかどうかの判断、初回起動、反映の順に扱います。最後に、管理画面の画面を紹介します。API の細かい形と画面ごとの説明は付録B 管理リファレンスにあり、本章はそこへ案内します。

## 5.1　管理プロセスと managed 設定

管理プロセスは、`tukuyomi-proxy admin <config>` で動く、プロキシとは別のプロセスです。ブラウザーで開く管理画面と、プログラムが使う管理 API に応答します。プロキシと同じ実行ファイル、同じ設定ファイル、同じ OS ユーザーで動きます。リスナーは `admin.listen` のループバックのアドレスで、TLS を使わずに HTTP/1.1 に応答します。1 つの接続でリクエストを 1 つ受け付けて応答し、閉じます。同時接続数は 32 で、超えた接続は、受け付けてすぐに閉じます。

管理プロセスは、ユーザー、API トークン、監査ログ、切り替えの履歴、設定の変更履歴を、管理データの保存先（設定の `admin.store.dir`）に置きます。プロキシへの依頼には、プロキシが作る Unix ドメインソケット（制御ソケット、設定の `admin.control`）を使い、プロキシの状態の問い合わせと、世代の切り替えや設定のリロードを依頼します。managed 設定のバージョンは、managed ストア（設定の `managed.dir`）に置きます。

管理プロセスでできるのは、ルールの世代の操作（第4章）、ログの検索（第7章）、ユーザーと API トークンと監査ログの管理、managed 設定の編集と反映です。設定ファイルそのものを管理画面や管理 API で編集することはできません。設定ファイルは、画面に値を表示するだけです。

使うかどうかを決めることは、2 つあります。

- 管理プロセスを使うか。設定ファイルに `admin` を書くと使います。`admin` が無ければ、管理プロセスは起動せず（exit 2）、プロキシは制御ソケットを作りません。プロキシが停止していても管理プロセスは動作しますが、プロキシに依頼する世代の切り替えと managed 設定の反映は拒否します。
- managed 設定を使うか。設定ファイルに `managed` を書くと使います（5.9）。管理プロセスだけを使い、managed 設定を使わない構成もできます。

## 5.2　管理プロセスの用意

設定ファイルの最上位に `admin` を書きます。例を示します。

```json
"admin": {
  "listen": "127.0.0.1:9100",
  "control": "/var/lib/tukuyomi-core/control/proxy.sock",
  "store": {"kind": "file", "dir": "/var/lib/tukuyomi-core/admin"},
  "origin": "https://admin.example.com",
  "trusted_proxies": ["127.0.0.1/32"],
  "mfa": "required",
  "session_idle_ms": 1800000,
  "session_total_ms": 43200000,
  "crs_dir": "/var/lib/tukuyomi-core/crs-4.23.0"
},
"records": {"dir": "/var/lib/tukuyomi-core/records", "file_bytes": 16777216, "files": 8}
```

`admin` を書くときは、`crs_dir` と `route` 以外のすべての設定キーを書きます。`listen` は `proxy.listeners` や `status.listen` と重ねられないループバックのアドレス、`control` は制御ソケットのパス（ソケットはプロキシが作ります）、`origin` は管理画面を開く URL のオリジン、`crs_dir` は管理画面のインポートで CRS を使うときのディレクトリです。`route` は管理画面のルートで、`managed` のある設定では必ず書き、`managed` の無い設定では書けません（5.3）。各設定キーの範囲は、付録B 管理リファレンスの「設定キー `admin`」を参照してください。

`admin.store.dir` と、`admin.control` を置くディレクトリは、先に作ります。所有者がプロキシの OS ユーザーで、グループとその他のユーザーの権限が無い（0700）、シンボリックリンクでないディレクトリにします。ルールストア、`records.dir`、`managed.dir` などとは、同じディレクトリにも、互いの中にも置けません。付録A 運用リファレンスの「値どうしの関係」を参照してください。

管理プロセスは、プロキシとは別のユニットで動かします。ユニットの例は第3章にあります。`Type=notify` と `KillMode=mixed`（ルールのインポートの事前検証で起動した検査プロセスを、管理プロセスが順に停止できるようにするため）、`LogRateLimitIntervalSec=0`（監査ログの行が標準エラー（ジャーナル）にも出力されるので、journald のレート制限で失われないようにするため）にします。`ExecReload` は置きません。管理プロセスにとって SIGHUP は停止のシグナルです。管理プロセスは、`admin` などの値を起動時に 1 回だけ読みます。`admin` の設定キーを変更したら、`config check` で検証してから、管理プロセスとプロキシを再起動します。

最初のユーザーは `admin bootstrap` で作ります。ロールは `owner` です。パスワードは標準入力の最初の 1 行から読み込み、引数には渡しません。

```bash
read -r -s -p 'password: ' PW; echo
printf '%s\n' "$PW" | sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy admin bootstrap /etc/tukuyomi-core/config.json alice
unset PW
```

- 名前は 1〜32 バイトの小文字の英字・数字・`.`・`_`・`-`、パスワードは 12〜128 バイトの UTF-8 です。
- 成功すると、標準出力に `created owner <name>` が出力され、exit 0 で終了します。ユーザーが 1 人でもいれば、作成できません（exit 1）。管理プロセスが動作していなくても実行できます。
- パスワードと二要素認証を両方失った唯一の owner のように、ロックアウトされたユーザーには `admin reset` を使います。パスワードを決め直し、二要素認証と API トークンを無効にして、次のログインでパスワードを変更させます。

## 5.3　外部からの利用

管理プロセスは TLS を使わないので、プロキシの TLS のリスナーを通して使います。クッキーは `Secure` 付きで出力されるので、管理画面は https でしか使えません。通し方は、設定ファイルに `managed` があるかどうかで違います。`managed` の無い設定では、管理用の Host のルートを `forward.routes` に書きます。例を示します。

```json
"forward": {
  "upstreams": {
    "app": {"servers": [{"address": "127.0.0.1:8080", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]},
    "admin": {"servers": [{"address": "127.0.0.1:9100", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]}
  },
  "routes": [
    {"host": "admin.example.com", "upstream": "admin", "access": {"allow_cidrs": ["192.0.2.0/24"]}}
  ],
  "default_upstream": "app"
}
```

（`forward` のほかの設定キーは省略しています。`admin.listen` が `127.0.0.1:9100` の例です。）

- `admin.example.com` を `hosts` に持つ証明書を、TLS のリスナーに置きます。`access` の `allow_cidrs` で、管理画面を使うユーザーのアドレスだけを許可します。
- 平文のリスナーに、この Host を通さないでください。ルートはリスナーを問わずに選択されるので、`redirect` でない平文のリスナーがあると、パスワードが暗号化されずに流れる可能性があります。
- 全体の設定（全体のアクセス制御とレート制限）とホストごとの設定は、この Host のリクエストにも適用されます（第6章）。

`managed` のある設定では、管理画面のルートを `admin.route` に書きます。プロキシがこのルートを自分で作成し、`host`（管理画面のホスト名）、`certificate`、`access` を持ちます。`access` の `allow_cidrs` は必ず書き、空にできません。全体の設定もホストごとの設定も適用されません（5.9、例は 5.11）。次の 2 つは、どちらの設定でも書きます。

- `admin.trusted_proxies`: プロキシが管理プロセスに接続する元のアドレス（同じホストなら `127.0.0.1/32`）。書かないと、すべてのクライアントがプロキシのアドレスになり、ログインの試行回数の制限（クライアントごと）が全員で共有され、監査ログの `client` がどれもプロキシのアドレスになります。
- `admin.origin`: ブラウザーで開く URL のオリジンと一字一句同じにします（ポートが 443 のときは書きません）。違うと、ログインを含む変更が 403 になります。

詳しくは、付録B 管理リファレンスの「外部からの利用」を参照してください。

## 5.4　管理画面へのリクエストと WAF の検査

管理画面へのリクエストも、WAF の検査を通ります。検査するエンジンは、`managed` のある設定ではデフォルトのエンジン（設定ファイルの `kernel.default_engine`。書かなければ Coraza）、`managed` の無い設定では、管理プロセスへ転送するアップストリームのエンジンです。

ルールのインポートと managed 設定の検証・保存のリクエストのボディは、ルールのファイルや証明書の PEM を含む大きな JSON で、最大 12 MiB になります。検査の対象にすると、ルールがブロックすることがあります。そのため、次のパスを世代の検査除外のルート（第4章）にします。`managed` のある設定で、1 つの `--routes` のファイルに書く例です。

```json
[
  {"host": "admin.example.com", "path": "/api/generations", "action": "bypass"},
  {"host": "admin.example.com", "path": "/api/managed/check", "action": "bypass"},
  {"host": "admin.example.com", "path": "/api/managed/apply", "action": "bypass"}
]
```

- `path` は `/` で終わらないので、そのパスだけに一致します。
- 検査除外のルートは世代の一部です。管理画面のリクエストを検査するエンジンのどの世代にも、同じルートを入れ続けてください。入れ忘れた世代を選択すると、その世代からは該当のリクエストが検査されます。
- このルートが効くのは、入れた世代が使われてからです。最初にこのルートを入れる世代は、コマンドでインポートします（`rules import ... --routes <file>`）。
- `proxy.max_body` は、12 MiB（12582912）以上にします。管理画面のルートには `max_body` が無いので、`proxy.max_body` が上限になります。
- 検査除外のルートが無い世代で、ルールが `check` か `apply` のリクエストを 403 でブロックすると、管理画面は「プロキシか WAF がリクエストを拒否しました。PEM のファイルや多くのルートを含むリクエストボディは、WAF にブロックされることがあります。/api/managed/check と /api/managed/apply を検査の対象から除外する設定を確認してください。」と表示します。

管理画面の Host を CRS で検査するときは、PUT と DELETE のメソッドと、パスワードの欄にも調整が要ります。調整が無いと、新しいユーザーが最初のパスワードの変更をできず、ログインを終えられません。付録B 管理リファレンスの「管理画面の Host での CRS の調整」を参照してください。

## 5.5　ユーザーとロール

ロールは `viewer`、`operator`、`owner` の 3 つで、権限は順に増えます。

- `viewer`: 状態、世代の一覧と内容、切り替えの履歴、ログを読めます。managed 設定の状態、バージョンの一覧、設定の変更履歴も読めます。自分のパスワード、二要素認証、API トークンを扱えます。
- `operator`: viewer のすべて。加えて、監査ログを読めます。ルールのインポート、世代の選択、ロールバック、削除と、managed 設定の検証、保存して反映、名前で反映、ロールバック、削除ができます。
- `owner`: operator のすべて。加えて、ユーザーを作成し、ロールと有効・無効を変更し、ほかのユーザーのパスワードと二要素認証を初期化し、全員の API トークンを閲覧して削除できます。

ユーザーの扱いは次のとおりです。

- 最初の owner は `admin bootstrap` で作成します。以降のユーザーは、owner が管理画面の「ユーザー」で作成します。owner が作成したユーザーと、owner がパスワードを決めたユーザーは、次のログインで、自分のパスワードに変更するまで、ほかの API を使えません。
- ユーザーを削除する API はありません。使わなくなったユーザーは無効にします。有効にし直しても、削除された API トークンは戻りません。
- owner の自分自身に対する操作（自分のロールを下げる、自分を無効にする、自分のパスワードと二要素認証の初期化）と、有効な owner が 1 人もいなくなる変更は拒否します。

## 5.6　ログインと二要素認証

ログインが通ると、管理プロセスはセッションを作成し、クッキー `tukuyomi_admin` を返します。`admin.session_idle_ms` の間使われなかったとき、作成してから `admin.session_total_ms` が過ぎたとき、ログアウトしたときなどに、セッションは終了します。

二要素認証（MFA）は、時刻に基づくワンタイムパスワード（RFC 6238）で、HMAC-SHA1、6 桁、30 秒ごとの時間枠で作成します。`admin.mfa` が `required` のときは、二要素認証を設定していないユーザーは、設定だけをさせます。

- 設定は、管理画面の「アカウント」から行います。管理プロセスがセットアップキーを返し、認証アプリの認証コードで確定します。確定のとき、リカバリーコードを 10 個、1 回だけ返します。1 個は 16 文字で、1 回だけ使えます。
- `required` のときは、自分では二要素認証を無効にできません。owner に無効にしてもらいます（owner 自身の分は、ほかの owner に無効にしてもらうか、`admin reset` を使います）。
- ユーザーごとに、続けて 5 回失敗すると 15 分間ロックアウトします。クライアントごとには、1 分間に 30 回まで試行できます。

変更のリクエストでは、`Origin` ヘッダーがあれば `admin.origin` と一字一句同じであること、セッションのリクエストでは `X-CSRF-Token` が正しいことを検証します。1 つのリクエストがセッションのクッキーと `Authorization` ヘッダーの両方を持つと 400 になります。管理画面の前に Basic 認証などの HTTP 認証をかけると、ログイン後のリクエストは 400 になります。付録B 管理リファレンスの「ログインと二要素認証」、「ロックアウトと試行回数の制限」、「セッション」、「CSRF と Origin」を参照してください。

## 5.7　API トークン

API トークンは、プログラムが管理 API を使うためのトークンです。管理画面の「アカウント」で作成と削除ができます。

- 形式は `tkc_<16-hex-digits>_<43-characters>` です。作成したときに 1 回だけ全体を返します。管理データの保存先には、秘密の SHA-256 だけを置きます。
- 作成するときは、名前、ロール、有効な日数（1〜365）、現在のパスワードを指定します。ロールは、自分のロール以下です。1 人が持てるのは 50 個までで、期限が切れたトークンも数えます。
- `Authorization: Bearer <token>` で送ります。セッションのクッキーとは一緒に送れません。アカウントの API と、ユーザーの管理の API には使えません。所有者が無効になったとき、ロールが下がったとき、パスワードが変更されたときにも、無効になります。

使い方の例は `curl -sS -H "Authorization: Bearer $TOKEN" https://admin.example.com/api/status` です（`$TOKEN` にトークンを入れます）。使える API の一覧は、付録B 管理リファレンスの「API のパスの一覧」を参照してください。

## 5.8　監査ログ

管理プロセスは、ログイン、変更、拒否したリクエストを、監査ログの行として残します。パスワード、API トークン、認証コード、リカバリーコード、二要素認証のセットアップキー、クッキーは書きません。

- 変更は、監査ログの行を先に書いてから行います。行を書けない（ディスクが満杯の場合など）ときは、変更せずに 503 `unavailable` で拒否します。例外はログアウトで、行を書けなくてもセッションを終了します。
- 世代の選択とロールバック、managed 設定の変更の `ok` の行は、変更の前に書くので、成功を示す行ではありません。終わり方は、後に続く行と、切り替えの履歴や設定の変更履歴で確認します。
- 保存先は `admin.store.dir` の `audit/audit.log` で、1 行 1 件の JSON です。1 つのファイルが 16 MiB を超えると次のファイルに移り、8 ファイルを残します。同じ行を標準エラー（ジャーナル）にも出力します。
- 管理画面の「監査ログ」（operator 以上）か `GET /api/audit` で、最新の 200 行を新しい順に読めます。`audit` のログは、プロキシのログファイル（`records.dir`）には入らないので、`type=audit` でログを検索しても見つかりません。

行の項目と `action` の一覧は、付録B 管理リファレンスの「監査ログ」を参照してください。

## 5.9　managed 設定を使うかどうか

managed 設定は、サイト（ホストと証明書）、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定を、設定ファイルの外の managed ストアにバージョンとして保存する仕組みです。設定ファイルの `managed` で使い始めます。`managed` の無い設定ファイルは、これまでと同じように読みます。

使うと、次のことができます。

- 上の設定を、管理画面と管理 API で編集し、検証してから保存して、動作中のプロキシに反映できます。反映では、プロキシがそのバージョンで設定のリロードを通した後にだけ、選択中のバージョンを進めます。そのため、プロキシが拒否したバージョンが、次の起動で使われることはありません。
- 保存したバージョンは残り、前のバージョンに戻せます（ロールバック、名前を指定した反映）。
- 管理画面と管理 API からの反映は管理プロセスの変更履歴に、操作は監査ログに残ります。コマンドでの変更は、どちらにも残りません。

代わりに、次のことが必要です。

- 設定ファイルに書けなくなる設定キーがあります。`forward` は `resolve_timeout_ms` だけになり、TLS のリスナーの `certificates`、全体の `access`・`rate_limit`、`host_policies` も書けません。これらはバージョンに書きます。
- 設定に `admin` があれば、管理画面のルート（`admin.route`）が必須です。適用されるネットワークの制限は、`admin.route.access` の `allow_cidrs` だけです。
- `managed` の有無と `managed.dir` は、動作中に変更できません。`managed` を追加するときと外すときは、プロキシと管理プロセスを再起動します（設定のリロードは拒否します）。
- 管理画面のルートも、デフォルトのエンジンの WAF の検査を通ります。5.4 の検査除外のルートを入れた世代を、デフォルトのエンジンの世代として使います。デフォルトのエンジンを変更するときは、新しいデフォルトのエンジンの世代にも、同じルートを入れます。
- ACME で発行するサイトの証明書は、managed ストアの `acme/` に置きます（第8章）。
- ログ送信プロセスを使うなら、プロキシと同じビルドに入れ替えてから、設定ファイルに `managed` を書きます。`managed` を知らない前のビルドは、未知の設定キーのある設定ファイルを受け付けずに起動しません。

設定をファイルだけで管理し、管理画面から変更しないなら、`managed` は必要ありません。

## 5.10　managed ストアとバージョン

設定キー `managed` は `{"dir"}` だけを持ちます。`dir` は managed ストアのディレクトリで、プロキシもコマンドも作らないので、先に作ります。シンボリックリンクでないディレクトリで、所有者がプロキシの OS ユーザー、権限は 0700 にします。

managed ストアには、バージョン（`versions/<version>.json`）、バージョンが指す証明書チェーン・秘密鍵・アップストリームの CA のファイル（`files/<sha256>`）、ACME のサイトの証明書（`acme/`）、選択中のバージョンを示す `current` があります。バージョンとファイルの名前は、内容の SHA-256 で、作った後は変えません。バージョンは手で書かず、`managed import` か管理画面で作ります。

バージョンは、`sites`、`upstreams`、`routes`、`default_upstream` と、省ける `access`、`rate_limit`、`host_policies` を持つ JSON です。`upstreams`、`routes`、`default_upstream`、`access`、`rate_limit`、`host_policies` は、`managed` の無い設定ファイルの `forward` や、第6章と同じ形で書きます。違うのは、アップストリームの `tls` の `ca` が、managed ストアの `files/` のファイルの SHA-256 であることだけです。`sites` のサイトは `{"name", "hosts", "certificate"}` と書き、`certificate` は、`{"chain", "key"}` か `{"acme": {"renew_before_days"}}` のどちらかです。形と決まりの全体は、付録A 運用リファレンスの「managed ストアとバージョン」を参照してください。

`managed` コマンドは、動作中のプロキシには依頼しません。`managed import <config> <document>` は、文書からバージョンを作って managed ストアに置き（選択しません）、`managed activate <config> <version>` は、起動と同じ検証を実行して、通ったときだけバージョンを選択します（`current` を変更します）。`managed remove` と `managed list` もあります。文書は、バージョンと同じ形で、ファイルを SHA-256 ではなくパスで書きます（`chain_file`・`key_file`・`ca_file`）。インポートの後は、文書が指すファイルを使いません。付録A 運用リファレンスの「`managed`」を参照してください。

## 5.11　managed 設定での初回起動

`managed` のある設定では、選択中のバージョンが無いと、起動も `config check` も拒否します（`config check: managed store refused: no managed version is chosen`、exit 1）。最初のバージョンは、コマンド（`managed import` と `managed activate`）で作成して選択します。そのため、起動の前にバージョンをインポートして選択します。ほかの手順は、第2章の初回起動の手順と同じです。

例は、リダイレクトのリスナーと TLS のリスナー、ファイルの証明書を持つサイト 1 つ、アップストリーム 1 つ、管理画面のルートを持つ形です。

1. ディレクトリを作ります。第3章のディレクトリに加えて、managed ストアのディレクトリを 0700 で作ります。

   ```bash
   sudo install -d -m 0700 -o tukuyomi -g tukuyomi /var/lib/tukuyomi-core/managed
   ```

2. 証明書のファイルを置きます。管理画面のルートの証明書と秘密鍵（例: `/var/lib/tukuyomi-core/tls/admin.pem`・`admin.key`）と、サイトの証明書チェーンと秘密鍵（例: `/var/lib/tukuyomi-core/import/www.pem`・`www.key`）です。サイトのファイルはインポートの入力になるので、サービスの OS ユーザーが読める場所に置きます。
3. 設定ファイルを書きます。`managed` の無い設定ファイルとの違いは次のとおりです。次は抜粋です。`proxy` は `listeners` 以外の設定キーを、`admin` は `route` 以外の設定キーを省略しています。省略した設定キーは、5.2 の例と、付録A 運用リファレンスの「例」に従って書きます。TLS のリスナーには `certificates` を書きません。

   ```json
   "proxy": {
     "listeners": [
       {"address": "0.0.0.0:80", "redirect": {"https_port": 443}},
       {"address": "0.0.0.0:443", "tls": {"min_version": "1.2"}}
     ]
   },
   "forward": {"resolve_timeout_ms": 5000},
   "managed": {"dir": "/var/lib/tukuyomi-core/managed"},
   "admin": {
     "route": {
       "host": "admin.example.com",
       "certificate": {
         "cert_file": "/var/lib/tukuyomi-core/tls/admin.pem",
         "key_file": "/var/lib/tukuyomi-core/tls/admin.key"
       },
       "access": {"allow_cidrs": ["203.0.113.0/24"]}
     }
   }
   ```

4. バージョンの文書を書きます（例: `/etc/tukuyomi-core/managed-import.json`）。サービスの OS ユーザーが読めるように置きます。

   ```json
   {
     "sites": [
       {
         "name": "www",
         "hosts": ["www.example.com"],
         "certificate": {
           "chain_file": "/var/lib/tukuyomi-core/import/www.pem",
           "key_file": "/var/lib/tukuyomi-core/import/www.key"
         }
       }
     ],
     "upstreams": {
       "web": {"servers": [{"address": "127.0.0.1:8080", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]}
     },
     "routes": [],
     "default_upstream": "web"
   }
   ```

5. ルールセットをインポートし、世代を選択します（第2章、第4章）。バージョンを選択する `managed activate` は、バージョンのアップストリームが使うエンジンに、選択中の世代があることを確認します。そのため、この手順は 7 より前に行います。
6. バージョンをインポートします。`<version> created` が出ます。バージョンを置くだけで、選択しません。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy managed import /etc/tukuyomi-core/config.json /etc/tukuyomi-core/managed-import.json
   ```

7. バージョンを選択します。起動と同じ検証を実行し、通ったときだけ選択します。`<version> current` が出ます。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy managed activate /etc/tukuyomi-core/config.json <version>
   ```

8. 設定を検証します。通れば、標準出力に `accepted` が出ます。標準エラーに `config check: managed version <version>` の行が出ます。

   ```bash
   sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy config check /etc/tukuyomi-core/config.json
   ```

9. サービスを起動します（第3章）。ログに `start: managed version <version>` の行が出ます。
10. 管理プロセスを起動し、最初のユーザーを作ります（5.2）。管理画面には、`admin.route.access` が許すネットワークから、`admin.route.host` のホスト名で入ります。この後の変更は、管理画面か管理 API で行います（5.13）。

ACME のサイトを使う場合は、付録A 運用リファレンスの「ACME のサイト」を参照してください。

## 5.12　managed 設定への移行

`managed` の無い設定ファイルで動作しているプロキシと管理プロセスを、managed 設定に移行できます。変換のコマンドは無いので、設定ファイルとバージョンの文書は手で書きます。何がどこへ移るかの表と手順は、付録A 運用リファレンスの「managed 設定への移行」にあります。ここでは、迷いやすい点だけを挙げます。

- 管理画面のホストのルートは `forward.routes` から外し、その `access` を `admin.route.access` にコピーします。管理画面のルートには全体の設定が適用されないので、コピーし損ねると、管理画面に到達できる相手が変わります。
- ACME のサイトは、現在の証明書チェーンと秘密鍵を、managed ストアの `acme/<hosts-sha256>/` にコピーします。コピーしないと、`acme renew` と SIGUSR2 の後まで、そのサイトのホストに TLS で接続できません。
- 移行前の構成（元の設定ファイル、実行ファイル、ユニット）を残してから、新しい設定ファイルを元のパスに置きます。
- 管理プロセス、プロキシ、ログ送信プロセスの順に再起動します（`systemctl restart`）。`admin.route.host` と `managed` は動作中に変更できないので、`systemctl reload` は拒否します。管理プロセスを再起動してからプロキシを再起動するまでの間、managed 設定の変更の依頼は 409 で拒否します（何も変更されません）。

## 5.13　反映

動作中のプロキシに別のバージョンを使わせる方法は 2 つあります。

### 管理画面と管理 API の反映

- 保存して反映: 画面の下書きから作ったバージョンを保存し、反映します。
- 名前を指定した反映: managed ストアにあるバージョンを、名前（SHA-256）で指定して反映します。
- ロールバック: 前のバージョンへ戻します。ロールバック先は、設定の変更履歴の中で、結果が `applied` で、`from` と `to` が違う、最も新しい行の `from` です。ただし、その行の `to` が現在選択中のバージョンのときだけです。反映が `applied` に終わらなかった後や、コマンドでバージョンを選択した後は、ロールバックできません（409 `the history does not end at the chosen version`）。続けてもう一度ロールバックすると、元のバージョンに戻ります。

どの操作でも、管理プロセスが、制御ソケットの `reload` の依頼で、プロキシにそのバージョンで設定をリロードさせます。プロキシの設定が切り替わった後にだけ、`current` をそのバージョンにします。プロキシが拒否したバージョンは `current` になりません。

- 画面で見た選択中のバージョンを `expect` として送ります。画面を見た後にほかのユーザーかコマンドが選択し直していれば、古い画面から上書きしないよう、409 で拒否します。
- 反映は 202 で応答し、管理プロセスの中の反映の処理として続きます。管理画面は、終わるまで「反映中」と表示し、終わると結果（「反映済み」「拒否」「使用中」など）を表示します。反映の処理はキャンセルできません。
- 反映の間、管理プロセスは managed ストアのロックを持ちます。その間の `managed import`・`managed activate`・`managed remove` は拒否します（`the managed store is in use by another command`）。
- ACME のサイトを追加するか、サイトのホストを変更したバージョンを反映すると、新しいホストの組み合わせの証明書は、まだ managed ストアにありません。そのサイトのすべてのホストに、`acme renew` で発行するまで TLS で接続できなくなります。反映の後すぐに、`acme renew` と SIGUSR2 を実行します（第8章）。「保存して反映する」の確認にも、この旨の注意が表示されます。
- リロードは、バージョンと一緒に設定ファイルも読み込みます。設定ファイルを書き換えて、まだ SIGHUP を送っていなければ、管理画面からの反映でその書き換えも効きます。設定ファイルにエラーがあれば、反映も拒否します。

### コマンドと SIGHUP

`managed activate` は、起動と同じ検証を実行して `current` を変更します。コマンドはプロキシに依頼しないので、動作中のプロキシは、次の SIGHUP（`systemctl reload`）か起動で `current` のバージョンを読みます（第9章）。SIGHUP が拒否されると、`current` は、動作中のプロキシが拒否したバージョンのまま残り、次に起動するときは、そのバージョンが使われます。動作中のプロキシのバージョンを変更するには、管理画面か管理 API を使います。コマンドで変更したときは、すぐに `systemctl reload` を実行し、`reload: configuration replaced <sha256> managed <version>` の行を確認します。

### 途中で止まったとき

反映が途中で止まると、選択中のバージョン（`current`）と稼働中のバージョンが違うことがあります。稼働中のバージョンは `GET /api/managed` の `serving`、選択中のバージョンは `current` で分かります。管理画面の「設定のバージョン」も、違うときに通知と、そろえる 2 つの操作（「選択中のバージョンをもう一度反映する」と「稼働中のバージョンを選択し直す」）を表示します。プロキシと管理プロセスは、この不一致を自動では修正しません。状態と直し方の表は、付録A 運用リファレンスの「反映」を参照してください。

## 5.14　管理画面の画面

管理画面は、ブラウザーで `https://admin.example.com/`（`admin.origin`）を開いて使います。画面のファイルは実行ファイルに組み込まれているので、管理プロセスと管理画面は、いつも同じバージョンです。画面上部の帯で、言語（日本語と英語）、テーマ（自動、ライト、ダーク）、時刻の表示方法（ローカルか UTC）を切り替えられます。使える画面はロールで決まり、メニューには、ロールが使える画面だけが並びます。

| メニュー | 画面（ロール） | 内容 |
|---|---|---|
| （名前なし） | 概要（viewer 以上） | プロキシの数と状態、エンジンごとの世代の状態、設定ファイルの SHA-256。managed 設定を使っているときは、選択中と稼働中のバージョン |
| WAF | ルールの世代（viewer 以上）、ルールのインポート（operator 以上）、切り替え履歴（viewer 以上） | 世代の一覧と詳細、インポート、選択、プロキシの切り替え、エンジンの起動、削除、ロールバック（operator 以上） |
| ログ | アクセスログ（viewer 以上）、監査ログ（operator 以上） | 条件を指定したログの検索。監査ログの最新の 200 件 |
| プロキシ | サイト、アップストリーム、ルート（operator 以上） | managed 設定の下書きの編集 |
| ポリシー | アクセス制御とレート制限（operator 以上） | 下書きの、全体の設定とホストごとの設定の編集（第6章） |
| 設定 | 設定のバージョン、設定の変更履歴（viewer 以上）、設定ファイル（operator 以上） | 選択中と稼働中のバージョン、バージョンの内容、名前で反映、削除。設定の変更履歴とロールバック。設定ファイルの値の表示（変更はできません） |
| 管理 | アカウント（viewer 以上）、ユーザー（owner） | パスワード、二要素認証、API トークン。ユーザーの作成と管理 |

各画面の表示内容は、付録B 管理リファレンスの「管理画面」を参照してください。

「サイト」「アップストリーム」「ルート」「アクセス制御とレート制限」の 4 つの画面は、managed 設定の 1 つの下書きを編集します。

- 下書きは、選択中のバージョンから作成します（「設定のバージョン」の画面から、ほかのバージョンからも作成できます）。ここでの変更は、「保存して反映する」を押すまで有効になりません。
- 下書きは、このページのメモリにだけあり、ログアウトしたとき、セッションが切れたとき、タブを閉じたときに失われます。帯の「検証する」は、保存せずに検証して、拒否されたらエラーをその欄に表示します。「保存して反映する」は、検証、確認、保存と反映の順に進みます。「変更なし」の下書きは保存できません。確認には、保存する変更が名前で並び、値は表示しません（書き換えに秘密を書けるためです）。

世代の選択、ロールバック、削除と、バージョンの名前での反映、ロールバック、削除は、先に確認を表示します。管理プロセスが managed 設定なしで起動しているときは、「設定のバージョン」の画面と編集の画面に、managed 設定でできることと、使い始めるまでの手順の要点を表示します。

## 5.15　運用上の注意

- 管理プロセスとプロキシは、同じビルドにそろえます。前のビルドのプロキシ（エンジンごとの状態を返さないもの）には、管理画面は世代の選択、プロキシへの反映、エンジンの起動、ロールバックのボタンを表示しません。
- 管理プロセスを再起動すると、セッション、ロックアウトの状態、設定中の二要素認証のセットアップキー、反映の処理は失われ、全員がログインし直します。API トークン、ユーザー、監査ログ、履歴は保存先に残ります。
- ログファイルにはクライアントのアドレスとパスが入ります。管理 API では viewer 以上が読めるので、viewer のロールを渡すユーザーを検討したうえで決めてください。
- 不要になったバージョンは、`managed remove` か、管理画面の「設定のバージョン」で削除します。選択中のバージョンと、使用中のバージョンは削除できません。
