# 管理リファレンス

この文書では、管理プロセス、設定キー `admin`、管理 API、管理画面について、現在の実装の動作をまとめています。
必要な項目を調べながら使えるように書いています。
プロキシの設定キーとコマンドは、[運用リファレンス](operator-reference.ja.md) を、配置と systemd のユニットの例は [ビルドと配置](../build/binary-deployment.ja.md) を参照してください。

この文書に出てくるパスや名前（`/etc/tukuyomi-core/config.json`、OS ユーザー `tukuyomi`、`admin.example.com`、`192.0.2.0/24` など）は、どれも例です。

## 構成

管理プロセスは、プロキシとは別のプロセスです。
`tukuyomi-proxy` と同じ実行ファイルを `admin` コマンドで起動して動かします。
ブラウザーで開く管理画面と、プログラムから使う管理 API の両方に応答します。

| 構成要素 | 内容 |
|---|---|
| 管理プロセス | `tukuyomi-proxy admin <config>` で起動します。ループバックのリスナーで待ち受け、TLS を使わずに管理画面と管理 API に応答します |
| 管理画面 | 実行ファイルに組み込まれた画面（日本語と英語）です。管理プロセスが提供します |
| 管理データの保存先 | 設定の `admin.store.dir` で指定するディレクトリです。ユーザー、API トークン、監査ログ、切り替えの履歴、設定の変更履歴を置きます |
| 制御ソケット | 設定の `admin.control` で指定する、プロキシが作る Unix ドメインソケットです。管理プロセスはこのソケットを使ってプロキシの状態を問い合わせ、エンジンごとの世代の切り替えや、managed 設定のバージョンによる設定のリロードを依頼します（プロキシ側の動作は [運用リファレンス](operator-reference.ja.md) の「制御ソケット」） |
| ログファイル | 設定の `records.dir` で指定するディレクトリです。プロキシがログのコピーを置き、管理プロセスがそれを読み出します（[運用リファレンス](operator-reference.ja.md) の「ログファイル（`records`）」） |
| managed ストア | 設定の `managed.dir` で指定するディレクトリです。`managed` のある設定だけにあります。managed 設定のバージョンと、バージョンが使う証明書などのファイルを置きます。バージョンの保存と削除は管理プロセスが行い、プロキシは読むだけです（[運用リファレンス](operator-reference.ja.md) の「managed ストアとバージョン」） |

- 管理プロセスとプロキシは同じ設定ファイルを読みます。
  管理プロセスが `admin` などの値を読むのは起動時の 1 回だけで、後から再読み込みはしません。
  ただし、設定ファイルの値を読み出す `GET /api/config` と、managed 設定の検証と変更では、そのたびに設定ファイルを再読み込みします（下の「managed 設定の操作」）。
  プロキシは SIGHUP で設定をリロードしますが、`admin` は動作中には変更できない設定キーです（[運用リファレンス](operator-reference.ja.md) の「SIGHUP（設定のリロード）」）。
  - プロキシが `admin` の中で使う設定キーは `listen` と `control` で、managed のある設定では `route` も使います。
    `route` を使うのはプロキシだけで、管理プロセスは使いません。
    ほかの設定キーは、プロキシも範囲を検証するだけです。
    管理プロセスとプロキシが同じ設定ファイルをそろって受け付けるか、そろって受け付けないようにするためです。
  - `admin` の設定キーを変更したら、管理プロセスを再起動します。
    プロキシは `admin` が違う設定のリロードを拒否するため、プロキシも再起動します。
    `admin.route` を変更したときのプロキシの扱いは、[運用リファレンス](operator-reference.ja.md) の「`admin`」と「SIGHUP（設定のリロード）」を参照してください。
- プロキシが停止していても、管理プロセスは動作します。
  プロキシが止まっている間も、世代とログの読み出し、インポート、ユーザーの管理、managed 設定のバージョンの読み出し・検証・削除は使えます。
  一方、世代の切り替えとロールバック、managed 設定の反映はプロキシに依頼する操作です。
  プロキシに接続できないときは、これらの操作を拒否します。
  managed 設定の「保存して反映」の操作では、このときバージョンの保存もしません（下の「世代の操作」と「managed 設定の操作」）。
- 設定に `admin` が無いときは、管理プロセスは起動せず（exit 2）、プロキシは制御ソケットを作りません。

## 管理プロセス

### `admin`

```text
tukuyomi-proxy admin <config>
```

- 設定ファイルは絶対パスで渡します（[運用リファレンス](operator-reference.ja.md) の「コマンド」と同じ決まりです）。
- 起動は次の順に進みます。
  1. 起動前の検証を行います。
     root でないこと、SIGCHLD、ファイルディスクリプターを検証します。
     内容はプロキシと同じで、[ビルドと配置](../build/binary-deployment.ja.md) の「起動前の検証」にあります。
  2. 設定ファイルを読み込みます。
  3. 管理データの保存先を開き、`process.lock` のロックを取得します。
  4. 監査ログを開きます。
  5. リスナーをバインドします。
- リスナーをバインドすると、`admin: listening` の行を出力します。
  環境に `NOTIFY_SOCKET` があれば、`READY=1` を送ります。
- 1 つの管理データの保存先で動作できる管理プロセスは、1 つだけです。
  あるプロセスが `process.lock` を保持している間、ほかの管理プロセスは同じ保存先では起動できません（exit 1）。
  同じ時間枠の認証コードや同じリカバリーコードを 2 つのプロセスがそれぞれ 1 回ずつ受け入れてしまうのを防ぐためです。
- 管理プロセスはプロキシと同じ OS ユーザーで実行します。
  ルールストア、管理データの保存先、ログファイルを置くディレクトリ、managed ストア（`managed.dir`）は、所有者がその OS ユーザーで、グループとその他のユーザーに権限が無いディレクトリでなければ使いません。
  制御ソケットを置くディレクトリについては、プロキシがソケットを作るときに同じ検証をします。
  インポートの事前検証では検査プロセスを起動するため、設定の `kernel`（検査プロセスの実行ファイルと作業ディレクトリ）もプロキシと同じ値を使います。
- 終了コードは次のとおりです。

| 終了コード | 意味 |
|---|---|
| 0 | シグナルを受けて停止しました |
| 1 | それ以外の終了です。root での起動、起動前の検証の失敗、管理データの保存先が使えない（別の管理プロセスが使用している場合を含む）、監査ログを開けない、`admin.listen` をバインドできない |
| 2 | 引数のエラー、設定ファイルが受け付けられなかった、設定ファイルに `admin` が無い |

### `admin bootstrap`

```text
tukuyomi-proxy admin bootstrap <config> <name>
```

最初のユーザーをロール `owner` で作成します。
作成できるのは、管理データの保存先にユーザーが 1 人もいないときだけです。

- パスワードは標準入力の最初の 1 行から読み込み、引数では渡しません。
  例:

  ```bash
  read -r -s -p 'password: ' PW; echo
  printf '%s\n' "$PW" | sudo -u tukuyomi /opt/tukuyomi-core/bin/tukuyomi-proxy admin bootstrap /etc/tukuyomi-core/config.json alice
  unset PW
  ```

- 名前に使えるのは小文字の英字・数字・`.`・`_`・`-` で、長さは 1〜32 バイトです。
  パスワードは 12〜128 バイトの UTF-8 です。
- 成功すると、標準出力に `created owner <name>` を出力して、exit 0 で終了します。
  ほかの行は標準エラーに出力します。
  監査ログの行（下）のほかは、`admin bootstrap:` で始まります。
- ユーザーを作成する前に、監査ログの行を書きます。
  この行は `action` が `create`、`auth` が `bootstrap` で、操作者とクライアントのアドレスはありません。
  行を書けなければ、ユーザーは作成しません。
  この行は標準エラーに JSON のまま出力されます。
- 管理プロセスが動作していなくても実行できます。

### `admin reset`

```text
tukuyomi-proxy admin reset <config> <name>
```

ロックアウトされたユーザーのために、パスワードを設定し直します。
たとえば、唯一の owner がパスワードと二要素認証の両方を失ったときに使います。

- パスワードの読み込み方、名前とパスワードの決まり、標準エラーの行、監査ログの行の書き方は、`admin bootstrap` と同じです。
  監査ログの行は、`action` と `auth` がどちらも `reset` で、対象はユーザーの名前です。
- 成功すると、標準出力に `reset password of <name>` を出力して、exit 0 で終了します。
- 対象のユーザーについて、次のことを行います。
  - パスワードを入力した値にし、次のログインでパスワードの変更を求めます。
  - 二要素認証とリカバリーコードを無効にします。
  - このユーザーのセッションを終了し、API トークンをすべて無効にします。
    トークンのファイルを削除できなかったときは、その旨の行を標準エラーに出力します。
    その場合もトークンは無効のままで、exit 0 で終了します。
  - ロックアウトを解除し、失敗回数を 0 から数え直します。
- 無効にされたユーザーを有効に戻すことはしません。
  無効のユーザーを使えるようにするには、owner が `PUT /api/users/<name>` で有効にします。
- 管理プロセスが動作している間も実行できます。
  保存先のロックの中で変更を書き込みます。
  書き込むのは、読み込んだときからユーザーが変わっていない場合だけです。
  別の書き込みと重なったときは、`the admin store is in use by another process` か `the user was changed since it was read` で拒否されます（exit 1）。その場合は、もう一度実行してください。

`bootstrap` と `reset` の終了コードと、標準エラーの主な行は次のとおりです。

| 終了コード | 場合 | 標準エラーの行（`admin bootstrap:` か `admin reset:` の後） |
|---|---|---|
| 0 | 成功 | （標準出力に上の行） |
| 1 | root での実行、起動前の検証の失敗 | `host check refused: ...` |
| 1 | パスワードを読み込めない | `the password is not 12 to 128 bytes`、`the password line is too long`、`the password is not UTF-8` |
| 1 | 管理データの保存先が使えない、監査ログに書き込めない | `admin store refused: ...`、`audit log refused: ...`、`the audit log cannot be written` |
| 1 | ユーザーがすでにいる（`bootstrap`）、ユーザーがいない（`reset`） | `the store has a user already`、`the user is not in the store` |
| 2 | 設定が受け付けられなかった、`admin` が無い | `configuration refused: ...` |
| 2 | 名前のエラー | `the name is not 1 to 32 bytes of a-z, 0-9, '.', '_' and '-'` |
| 2 | 引数のエラー | （`admin:` で始まる行に、使い方の行が続きます） |

### リスナー

管理プロセスは `admin.listen` のループバックアドレスで待ち受けます。
TLS は使わず、HTTP/1.1 で応答します。
外部から使うときは、プロキシの TLS のリスナーを通します（下の「外部からの利用」）。

| 項目 | 値 |
|---|---|
| 同時接続数 | 32。超えた接続は受け付けた直後に閉じます |
| 1 つの接続 | リクエストを 1 つ受け付けて応答したら接続を閉じ（`Connection: close`）、次のリクエストは待ちません |
| ヘッダー部 | 8 KiB まで、ヘッダーフィールドは 64 個までです。読み込みにかけられる時間は 10 秒です |
| ボディ | 64 KiB までです。読み込みにかけられる時間は 30 秒です |
| インポート、`POST /api/managed/check`、`POST /api/managed/apply` のボディ | 12 MiB までです。ボディを読み込むのは、その API を使えるユーザーのリクエストだけです。その API を使えるのは、operator 以上で、セッションかトークンが有効で、状態による制限を受けていないユーザーです。それ以外のリクエストは、ボディを読み込まずに検証の 400・401・403・429・503 で拒否します。クッキーとトークンの両方がある場合は 400、トークンの回数を使い切ったクライアントは 429、保存先を読めないときは 503 です |
| 応答を作る時間 | 30 秒です。インポート、世代の選択、ロールバックでは、下の「時間のかかる応答」の時間になります |
| 接続の存続時間 | ヘッダー部、ボディ、応答のそれぞれの時間を合計した時間までです |

- `Content-Length` が上限を超えるリクエストには、認証情報を検証する前に 413 で応答し、ボディは読み込みません。
  ヘッダー部のエラーや上限超過では、HTTP ライブラリが自身の応答を返すか、何も返しません。
- ボディを読み込む API では、`Content-Type` が `application/json` でなければ 415 になります。
  JSON の形式が違うボディや、その API が認識しないキーを含むボディは、400 になります。
- `HEAD` は `GET` として扱います。
  表に無いパスは 404 になります。
  表にあるパスでも、メソッドが違えば 405 になります（`Allow` を付けます）。

時間のかかる応答: インポート（事前検証を含む）、世代の選択、ロールバックは、時間がかかります。
これらの応答を作る時間は、次の 2 つのうち長い方に 7 秒を加えた時間です（`proxy` の時間の設定キーを使います）。

- インポート: `ready_wait_ms + 3 × inspect_wait_ms + stop_inspect_ms`
- 選択とロールバック: `ready_wait_ms + stop_inspect_ms + 14 秒`

時間切れになったリクエストは、503 `unavailable` になります。
運用リファレンスの例の値（`ready_wait_ms` 30000、`inspect_wait_ms` 55000、`stop_inspect_ms` 10000）では、上限は約 212 秒になります。
問題なく終わるインポートなら、これよりずっと短い時間で済みます。

### 停止と systemd

- SIGTERM、SIGINT、SIGHUP を受けると停止します。
  `admin: stop: <signal>` の行を出力します。
  `NOTIFY_SOCKET` があれば、`STOPPING=1` を送ります。
  停止は次の順に進みます。
  1. 実行中のインポートの事前検証を失敗として終わらせ、検査プロセスと作業ディレクトリは片付けます。
  2. リスナーを閉じます。
  3. 処理中のリクエストを最長 10 秒待ち、残った接続は打ち切ります。
  4. exit 0 で終了します。
- `NOTIFY_SOCKET` の決まりは、プロキシと同じです（[運用リファレンス](operator-reference.ja.md) の「systemd への通知」）。
  扱うシグナルはこの 3 つだけで、SIGUSR1 と SIGUSR2 は扱いません。
  SIGUSR1 か SIGUSR2 を送ると、デフォルトの動作でプロセスが終了します。
- セッション、ユーザーごとの失敗回数とロックアウトの状態、設定中の二要素認証のセットアップキー、managed 設定の反映の処理は、メモリにだけあります。
  再起動すると、全員がログインし直すことになり、反映の処理も残りません。
  API トークン、ユーザー、監査ログ、切り替えの履歴、設定の変更履歴は保存先に残ります。

管理プロセスの systemd のユニットは、プロキシのユニット（[ビルドと配置](../build/binary-deployment.ja.md) の「systemd」）に合わせて作成します。
プロキシのユニットとの違いは次のとおりです。

- `ExecStart` は `tukuyomi-proxy admin <config>` にし、`User` と `Group` はプロキシと同じにします。
- `Type=notify` にします。
  管理プロセスはリスナーをバインドした後に `READY=1` を送ります。
- `KillMode=mixed` にします。
  デフォルトの `control-group` では、インポートの事前検証で起動した検査プロセスにも SIGTERM が届き、管理プロセスが検査プロセスを順に停止できなくなります（理由はプロキシと同じです）。
- `TimeoutStopSec` は停止時に待つ 10 秒より長くします。
  停止のときにインポートの事前検証が実行中の場合に備えて、その検査プロセスを停止する時間（`proxy.stop_inspect_ms` と `kernel.kill_grace_ms`）も加えておきます。
- `admin.listen` のポートが 1024 以上なら、`AmbientCapabilities` は不要です。
  `ReadWritePaths` には、ルールストア、管理データの保存先、`kernel.tmp_root`、制御ソケットを置くディレクトリ、managed ストア（`managed.dir` があるとき）を含めます。
- `LogRateLimitIntervalSec=0` を指定します。
  監査ログの行は標準エラー（ジャーナル）にも出力されるので、journald のレート制限で失われないようにします。
- プロキシのユニットとの間に、順序を付ける必要はありません。

管理プロセスのログは、プロキシと同じく、標準エラーに 1 行 1 件の JSON で出力されます（[運用リファレンス](operator-reference.ja.md) の「ログ」）。
出力するのは、`admin:` で始まる文の `line` と、監査ログの行の `audit` です。
`audit` はプロキシのログファイル（`records.dir`）には入りません。

## 設定キー `admin`

```json
"admin": {
  "listen": "127.0.0.1:9100",
  "control": "/var/lib/tukuyomi-core/control/proxy.sock",
  "store": {"kind": "file", "dir": "/var/lib/tukuyomi-core/admin"},
  "origin": "https://admin.example.com",
  "trusted_proxies": ["127.0.0.1/32"],
  "mfa": "required",
  "session_idle_ms": 1800000,
  "session_total_ms": 43200000,
  "crs_dir": "/var/lib/tukuyomi-core/crs-4.23.0"
},
"records": {"dir": "/var/lib/tukuyomi-core/records", "file_bytes": 16777216, "files": 8}
```

`admin` と `records` は、設定ファイルの最上位に置くオブジェクトで、`proxy`、`forward`、`kernel` などと並びます。どちらも省略できます。
`admin` を書くときは、`crs_dir` と `route` 以外の設定キーをすべて書きます。
`route` は、`managed` のある設定では必ず書き、`managed` の無い設定では書けません。
未知の設定キー、重複、型の違いを受け付けない決まりは、[運用リファレンス](operator-reference.ja.md) の「設定ファイル」と同じです。

| 設定キー | 範囲 | 意味 |
|---|---|---|
| `listen` | ループバックの IP（`127.0.0.0/8` か `::1`）とポート（0 は不可） | 管理プロセスのリスナーのアドレスです。`::ffff:127.0.0.1` の形はループバックとみなしません |
| `control` | 絶対パス、107 バイトまで | 制御ソケットのファイルです |
| `store` | `{"kind": "file", "dir"}` | 管理データの保存先です。`kind` に書けるのは、現在は `file` だけです。`dir` は 3840 バイトまでの絶対パスです |
| `origin` | `https://` とホスト（任意で `:port`） | 管理画面を開く URL のオリジンです。ルートの `host` と同じ形（小文字の名前）で書き、ワイルドカード、パス、クエリ、末尾の `/` は書けません。`POST` などの変更のリクエストで、`Origin` と比較します |
| `trusted_proxies` | 0〜256 個のネットワーク | クライアントのアドレスを `X-Forwarded-For` から決めるときに、管理プロセスが信頼する相手です。ホスト部が 0 の `address/prefix` の形で書きます。読み方はプロキシと同じです（[運用リファレンス](operator-reference.ja.md) の「クライアントのアドレス」） |
| `mfa` | `"optional"`、`"required"` | 二要素認証を求めるかどうかです。`required` では、二要素認証を設定していないユーザーに、二要素認証の設定だけをさせます（下の「ログインと二要素認証」） |
| `session_idle_ms` | 1 分〜24 時間 | 使われないままセッションが続く時間です |
| `session_total_ms` | `session_idle_ms` 〜 7 日 | セッションが続く時間の上限です |
| `crs_dir` | 絶対パス、3840 バイトまで。省略できます | インポートで使える CRS のディレクトリです。`scripts/fetch-crs.sh` でダウンロードしたものを指定します（[ビルドと配置](../build/binary-deployment.ja.md) の「CRS の取得」）。省略すると、インポートで CRS を使えません |
| `route` | `managed` のある設定だけ。そのときは必須 | 管理画面のルート（ホスト、証明書、`access`）です。使うのはプロキシだけです。形式と決まりは、[運用リファレンス](operator-reference.ja.md) の「`admin`」を、使い方は下の「managed 設定を使う場合の管理画面のルート」を参照してください |

- `listen` はリスナー（`proxy.listeners`）とも `status.listen` とも重ならないようにします。
  重なりの決まりはリスナーどうしと同じです。
  アドレスとポートが同じもの、または片方が `0.0.0.0` や `::` でポートが同じものが重なりになります。
- アップストリームのサーバーのアドレスには、プロキシのルートを通して外部から使うために `admin.listen` を書けます（下の「外部からの利用」）。
  リスナーと `status.listen` は書けません。
- ディレクトリはそれぞれ別の場所にします。
  ルールストア（`rules.store.dir`）、`records.dir`（あるとき）、`admin.store.dir`、`admin.control` を置くディレクトリ、`managed.dir`（あるとき）、`acme.challenge_dir`（あるとき）は、どれも同じディレクトリにすることも、互いの中に置くこともできません。
  `admin.control` そのものも、ルールストア、`records.dir`、`admin.store.dir` の中には置けません。
- `admin.route.host` を変更すると、ブラウザーで開く URL も変わります。
  `admin.origin` も新しいホストに合わせて（下の「外部からの利用」）、管理プロセスを再起動してください。
  管理プロセスが `admin.origin` を読むのは起動時だけです。
  プロキシ側の扱いは、[運用リファレンス](operator-reference.ja.md) の「`admin`」を参照してください。
- `admin.store.dir` と、`admin.control` を置くディレクトリは、先に作っておきます。
  シンボリックリンクでないディレクトリにして、所有者をプロキシの OS ユーザーにし、グループとその他のユーザーには権限を与えません（0700）。
  管理プロセスは管理データの保存先の中に `users/`、`tokens/`、`audit/` を作ります。
- `config check` は `admin` と `records` について、設定キーと値の関係を検証します。
  管理データの保存先、制御ソケット、ログファイルを開けるかどうかは検証しません。

管理データの保存先の内容（ファイルは 0600、ディレクトリは 0700）:

| パス | 内容 |
|---|---|
| `users/<name>.json` | ユーザーです。パスワードのハッシュ、二要素認証のセットアップキー、リカバリーコードのハッシュを含みます。最大 1000 人です |
| `tokens/<id>.json` | API トークンです。トークンの秘密の SHA-256 だけを持ちます。所有者ごとに 50 個までです |
| `audit/` | 監査ログ（`audit.log` と、ローテーションした古いファイル） |
| `activations.log` | 切り替えの履歴 |
| `managed.log` | 設定の変更履歴（下の「設定の変更履歴」） |
| `lock`、`process.lock` | 書き込みのロックと、管理プロセスのロック |

### 制御ソケット

設定に `admin` があると、プロキシは起動時に `admin.control` の制御ソケットを作ります。
作り方、使えるユーザー、依頼と応答の形式は、[運用リファレンス](operator-reference.ja.md) の「制御ソケット」を参照してください。
管理プロセス側の扱いは次のとおりです。

- 状態の問い合わせでは、接続を 2 秒、応答を 2 秒まで待ちます。
  プロキシが同時接続数の上限に達しているときは、接続を受け付けたのに、何も応答せずに閉じることがあります。
  そのときは 250 ms 後に 1 回だけ問い合わせ直し、それでも同じなら「プロキシが処理中」とします。
  `GET /api/status` では、`reachable` が `true` で `proxy` が `null` になります。
- 状態の問い合わせと世代の切り替えの依頼では、次のどれかに当たると「プロキシに接続できない」になります。
  - ソケットが無い
  - 接続を受け付けるプロセスが無い
  - 応答が決まった形式でない
  - 時間内に応答が無い
- 世代の切り替えはエンジンごとに依頼します。
  依頼には、切り替えるエンジン（`engine`）と、ルールストアでそのエンジンに選択中の世代（`expect`）を書きます。
  状態の `engines`（プロキシで稼働しているエンジンごとの世代、モード、段階）を返さないプロキシには、管理プロセスは依頼しません。
  これはエンジンごとの選択に対応していない、以前のバージョンのプロキシです（下の「選択とロールバック」）。
- 世代の切り替えを依頼したときは、`ready_wait_ms + 7 秒` まで待ちます。
  プロキシ自身が応答を待つ時間は `ready_wait_ms + 5 秒` なので、管理プロセスはそれより 2 秒長く待ちます。
- プロキシが切り替えの依頼に `busy` と応答したとき、または依頼を読まずに閉じたときは、管理プロセスが 250 ms ごとに状態を問い合わせます。
  結果は次のように判断します。
  - 依頼したエンジンで、プロキシが依頼した世代を使い始めれば、`switched` とします。
    使い始めたかどうかは、状態の `engines` にある、そのエンジンの世代で判断します。
  - 切り替えの途中ではなく、世代も依頼したものではない状態が 2 回続けば、`failed` とします。
  - `stop_inspect_ms + 7 秒` が過ぎた場合も `failed` とします。
  - 途中で接続できなくなれば `unconfirmed` とします。
- managed 設定のバージョンによるリロードの依頼（`reload`）では、アップストリームのサーバーの名前解決にかかる可能性のある時間に、7 秒を加えた時間まで待ちます。
  名前解決の時間には、プロキシが状態で返す `forward.resolve_timeout_ms` を使います。
  この値を返さない古いプロキシでは、管理プロセスが読み込んだ設定ファイルの値を使います。
  待つ時間は、プロキシ自身が待つ時間より 2 秒長くなっています。
- プロキシが証明書（`tls`）で拒否したときは、1 秒後に 1 回だけ依頼し直します。
  証明書の更新（`acme renew`）がファイルを書き換えている瞬間に証明書を読み込むと、その瞬間だけ拒否されるためです。
- `reload` の依頼では、依頼が届いていてリロードが続いていることがあるため、次のどの場合も結果が分からないものとして扱います。
  - ソケットが無い
  - 接続を受け付けるプロセスが無い
  - 応答が決まった形式でない
  - 時間内に応答が無い
  - 何も応答せずに閉じられた
  - プロキシが `busy`（`reload under way`）と応答した

  管理プロセスはそれまで待った時間と同じ時間だけ、250 ms ごとにプロキシの状態を問い合わせて、リロード中でなくなるのを待ちます。
  結果は次のように判断します。
  - プロキシが依頼したバージョンを使っていて、設定を切り替えたリロードの数（`config_reloads` の `replaced`）が依頼の前より増えていれば、反映済みとします。
  - そうでなければ `failed` とします。
  - 途中で接続できなくなったときは、`unconfirmed` とします。
    待つ時間が終わったときに、まだリロード中か、まだ問い合わせに応答できない場合も、`unconfirmed` とします。

結果の扱いは、下の「世代の操作」と「managed 設定の操作」を参照してください。
反映の順序と、反映が途中で停止したときの扱いは、[運用リファレンス](operator-reference.ja.md) の「反映」を参照してください。

### ログファイル

`GET /api/records` は、プロキシが書き込むログファイル（`records.dir`）を読み込みます。
ファイルの名前、サイズ、ローテーションは、[運用リファレンス](operator-reference.ja.md) の「ログファイル（`records`）」を参照してください。

- 設定に `records` が無いと、この API は 404 になります。
- 管理プロセスはプロキシと同じ OS ユーザーでファイルを読み込みます。
  ディレクトリが次のどれかに当たるときは読み込まず、503 になります。
  - 所有者が違う
  - グループかその他のユーザーに権限がある
  - ディレクトリでない（シンボリックリンクは使えません）
- ログファイルにはクライアントのアドレスとパスが入ります。
  管理 API では、viewer 以上がログファイルを読めます。
  viewer のロールを誰に渡すかは、検討したうえで決めてください。

## 外部からの利用

管理プロセスは TLS を使わないため、外部からはプロキシの TLS のリスナーを通して使います。
クッキーには `Secure` が付くので、管理画面は https でしか使えません。
プロキシを通す方法は、設定ファイルに `managed` があるかどうかで変わります。

- **`managed` の無い設定**: 管理用の Host のルートを `forward.routes` に書きます（下の例）。
- **`managed` のある設定**: 管理画面のルートを `admin.route` に書きます（[運用リファレンス](operator-reference.ja.md) の「全体の構成」と「`admin`」、下の「managed 設定を使う場合の管理画面のルート」）。

`managed` の無い設定の例:

```json
"forward": {
  "upstreams": {
    "app": {"servers": [{"address": "127.0.0.1:8080", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]},
    "admin": {"servers": [{"address": "127.0.0.1:9100", "weight": 1, "max_fails": 0, "fail_timeout_ms": 10000, "backup": false}]}
  },
  "routes": [
    {"host": "admin.example.com", "upstream": "admin", "access": {"allow_cidrs": ["192.0.2.0/24"]}}
  ],
  "default_upstream": "app"
}
```

この例では、`forward` のほかの設定キーを省略しています。
`admin.listen` が `127.0.0.1:9100` の場合の例です。

- **証明書**: `hosts` に `admin.example.com` を持つ証明書を TLS のリスナーに置きます。
  証明書に無い名前では、ハンドシェイクが失敗します。
- **アップストリーム**: サーバーのアドレスに `admin.listen` を書きます。
- **`engine`**: 管理プロセスへ転送するアップストリームにも、ほかのアップストリームと同じように `engine` を書けます。
  書かなければ、デフォルトのエンジンで検査します。
  書き方は、[運用リファレンス](operator-reference.ja.md) の「`forward`」を、エンジンの選択は同じ文書の「検査エンジンの選択」を参照してください。
  インポートのための検査除外のルート（下の「インポートのルートを検査除外にする」）は、このアップストリームを検査するエンジンの世代に入れます。
- **`access`**: `allow_cidrs` で、管理画面を使うユーザーのアドレスだけを許可します。
  クライアントのアドレスの決め方と、`access` を使うときの注意は、[運用リファレンス](operator-reference.ja.md) の「クライアントのアドレス」と「`access` を使うときの注意」を参照してください。
  どれかのルートが `access` を持つと、どのルートの `host` にもポートを書けません。
- **全体の設定とホストごとの設定**: どちらも、ルートを選択する前にこの Host のリクエストにも適用されます。
  全体の設定とは、全体のアクセス制御とレート制限です（[運用リファレンス](operator-reference.ja.md) の「アクセス制御とレート制限」）。
  値は管理画面を使うユーザーの数と速さに合わせて決めてください。
- **平文のリスナー**: この Host を通さないでください。
  ルートはリスナーに関係なく選択されます。
  `redirect` でない平文のリスナーがあると、パスワードが暗号化されずに流れる可能性があります。
  平文のリスナーは `redirect` にしてください。

次の 2 つは、`managed` があってもなくても書きます。

- **`admin.trusted_proxies`**: プロキシが管理プロセスに接続するときの接続元のアドレスを書きます。同じホストのときは `127.0.0.1/32` にします。
  書かないと、どのクライアントのアドレスもプロキシのアドレスになります。
  クライアントごとにかかるログインの試行回数の制限は、全員で共有されることになります。
  監査ログの `client` も、すべてプロキシのアドレスになります。
- **`admin.origin`**: ブラウザーで開く URL のオリジンと、一字一句同じにします。ポートが 443 のときは、ポートを書きません。
  違うと、ログインを含む変更のリクエストが 403 になります。

### managed 設定を使う場合の管理画面のルート

`managed` のある設定では、管理画面のルートを設定ファイルの `admin.route` に書きます。
このルートはプロキシが自分で作成します。
設定キーの形式、証明書と `access`、全体の設定とホストごとの設定が適用されないこと、managed 設定のバージョンに書けないホストについては、[運用リファレンス](operator-reference.ja.md) の「`admin`」を参照してください。
リクエストを受信してからの処理は、同じ文書の「リクエストの検証の順序」を、ボディの上限は下の「ボディのサイズ」を参照してください。

管理画面のルートのリクエストは、デフォルトのエンジンの稼働中の世代で検査されます。
デフォルトのエンジンは設定ファイルの `kernel.default_engine` に書いたエンジンです。`kernel.default_engine` を書かないときは `coraza` になります。
管理画面で managed 設定を編集するときは、`POST /api/managed/check`（検証）と `POST /api/managed/apply`（「保存して反映」の操作）を検査除外のルートにしてください。
この 2 つのリクエストのボディは、証明書チェーンと秘密鍵の PEM や多くのルートを含む、最大 12 MiB の JSON です。
これを検査の対象にすると、ルールがブロックすることがあります。
この 2 つのパスは、ルールのインポートのパス（下の「インポートのルートを検査除外にする」）と一緒に、1 つの `--routes` のファイルに書けます。

```json
[
  {"host": "admin.example.com", "path": "/api/generations", "action": "bypass"},
  {"host": "admin.example.com", "path": "/api/managed/check", "action": "bypass"},
  {"host": "admin.example.com", "path": "/api/managed/apply", "action": "bypass"}
]
```

- `path` は `/` で終わらないので、そのパスだけに一致します。
  `/api/managed` のほかのパスは検査されます。
- 検査除外のルートは世代の一部です。
  デフォルトのエンジンのどの世代にも、同じルートを入れ続けてください。
  入れ忘れた世代を選択すると、その世代からは `check` と `apply` のボディが検査されます。
  デフォルトのエンジンを替えるときは、新しいデフォルトのエンジンの世代にも同じルートを入れ、その世代を選択してから替えます。
  手順は、[運用リファレンス](operator-reference.ja.md) の「検査エンジンの選択」を参照してください。
- 検査除外のルートが無い世代で、ルールが `check` か `apply` のリクエストを 403 でブロックすると、管理画面は「プロキシか WAF がリクエストを拒否しました。PEM のファイルや多くのルートを含むリクエストボディは、WAF にブロックされることがあります。/api/managed/check と /api/managed/apply を検査の対象から除外する設定を確認してください。」と表示します。

### インポートのルートを検査除外にする

`POST /api/generations`（インポート）のボディは、ルールのファイルを含む大きな JSON です。
これを検査の対象にすると、ルールの検査がインポートをブロックすることがあります。
このパスは世代の検査除外のルート（[運用リファレンス](operator-reference.ja.md) の「検査除外のルート」）にしてください。

```json
[
  {"host": "admin.example.com", "path": "/api/generations", "action": "bypass"}
]
```

- `path` は `/` で終わらないので、このパスだけに一致します。
  `/api/generations/<fingerprint>`（世代の読み出しと削除）は検査されます。
- 検査除外のルートは世代の一部です。
  管理画面のリクエストを検査するエンジンのどの世代にも、同じルートを入れ続けてください。
  検査するエンジンは、`managed` のある設定ではデフォルトのエンジン、`managed` の無い設定では管理プロセスへ転送するアップストリームのエンジンです（上の「外部からの利用」）。
  入れ忘れた世代を選択すると、その世代からはインポートが検査されます。
  デフォルトのエンジンを替えるときなど、検査するエンジンが替わるときは、新しいエンジンの世代に同じルートを移してから替えます（[運用リファレンス](operator-reference.ja.md) の「検査エンジンの選択」）。
- このルートが効くのは、ルートを入れた世代が使われ始めてからです。
  最初にこのルートを入れる世代は、コマンドでインポートします（`rules import ... --routes <file>`）。
  管理画面のインポートでも、ホストとパスを表の行に書けば入れられます（送るボディは同じ形の JSON です）。

### 管理画面の Host での CRS の調整

管理画面の Host を CRS で検査すると、CRS のデフォルトの設定では、管理画面の次のリクエストがブロックされます。

- **PUT と DELETE**: CRS がデフォルトで許可するメソッドは `GET`・`HEAD`・`POST`・`OPTIONS` だけです。
  ほかのメソッドはルール 911100 でブロックされます。
  管理 API は、パスワードの変更、ロールと有効・無効の変更、二要素認証の無効化、API トークンと世代の削除に PUT と DELETE を使います。
  調整が無いと、新しいユーザーは最初のパスワードを変更できないので、ログインを終えられません。
- **パスワードの欄**: CRS は JSON のボディの値も検査します。
  記号の並びによっては、正しいパスワードが SQL インジェクションと判定され、ログインやパスワードの変更がブロックされます（ルール 942100 など）。

どちらも、管理画面の Host にだけ効く調整を入れて通します。
調整を入れても、ほかの Host の検査は変わりません。

2 つの調整は、管理画面の Host を検査するエンジンの世代に入れます。
検査するエンジンは、`managed` のある設定ではデフォルトのエンジン、`managed` の無い設定では管理プロセスへ転送するアップストリームのエンジンです（上の「外部からの利用」）。

デフォルトのエンジンを ModSecurity にした場合も、この節の 2 つの調整を入れた世代で動作を確認しています。
通ることを確認したのは、ログイン、ユーザーと API トークンの作成、`GET /api/status`、ルールのインポート、管理画面の「概要」「アップストリーム」「ルールのインポート」の表示です。
PUT と DELETE は、ModSecurity では確認していません。
この節の最後の項目のとおり、世代を選択する前に試してください。

メソッドの調整は、CRS のディレクトリにある `crs-setup.conf` の終わりに追加してから、世代をインポートします。
運用者のルールのファイルに書いても効きません。
運用者のルールのファイルは CRS のルールの後に読み込まれ（[運用リファレンス](operator-reference.ja.md) の「`rules`」）、メソッドのルールより後になるためです。
管理画面のインポートで CRS を使うときは、`admin.crs_dir` にある `crs-setup.conf` に追加します。

```text
SecRule REQUEST_HEADERS:Host "@rx ^admin\.example\.com(?::[0-9]{1,5})?$" \
    "id:1000100,phase:1,pass,nolog,t:none,t:lowercase,setvar:'tx.allowed_methods=GET HEAD POST OPTIONS PUT DELETE'"
```

パスワードの欄の調整は、運用者のルールのファイルに書き、インポートのときに `--rules`（管理画面では「ルールファイル」）で渡します。
フェーズ 1 のルールなので、CRS の後に読み込まれても、ボディを検査する CRS のルールより先に効きます。

```text
SecRule REQUEST_HEADERS:Host "@rx ^admin\.example\.com(?::[0-9]{1,5})?$" \
    "id:1000101,phase:1,pass,nolog,t:none,t:lowercase,\
    ctl:ruleRemoveTargetByTag=OWASP_CRS;ARGS:json.password,\
    ctl:ruleRemoveTargetByTag=OWASP_CRS;ARGS:json.current,\
    ctl:ruleRemoveTargetByTag=OWASP_CRS;ARGS:json.new"
```

- `admin\.example\.com` は `admin.origin` のホストに置き換え、`.` は `\.` と書きます。
- 検査の対象から外すのは、パスワードの 3 つの欄（`password`、`current`、`new`）だけです。
  名前の欄、トークンの名前、クエリなどは、調整の後も検査されます。
  攻撃に似た名前はブロックされます。別の名前にしてください。
- ルール ID はほかのルールと重ならない値にします。
  検査プロセスが使う ID は、[運用リファレンス](operator-reference.ja.md) の「検査プロセスが追加する設定とルール」を参照してください。
- 調整を入れた世代は、管理画面の Host での PUT と DELETE と、記号を含むパスワードでのログインを試してから選択してください。
  リクエストがブロックされたときは、画面に表示されるリクエスト ID でログを検索すると、ログの `rules` でルール ID が分かります。

### ボディのサイズ

- ルールのインポート（`POST /api/generations`）と、managed 設定の `POST /api/managed/check`・`POST /api/managed/apply` のリクエストボディは、最大 12 MiB になります。
  `proxy.max_body` は 12 MiB（12582912）以上にしてください。
  ルートの `max_body` は `proxy.max_body` を下げることしかできません。
  ほかのルートを制限したい場合は、そのルートに小さい `max_body` を書きます。
  管理画面のルート（`admin.route`）には `max_body` が無いので、`proxy.max_body` が上限になります。
- 検査除外のルートでは長いボディをバッファリングせずに流すので、12 MiB のボディが `max_buffered_bytes` を使い切ることはありません（[運用リファレンス](operator-reference.ja.md) の「リクエストボディの上限と検査する長さ」）。
- 検証のリクエストボディが 12 MiB を超えるとき、またはファイルが 192 件を超えるときは、管理画面は送信せずにその旨を表示します。
  設定ファイルの `proxy.max_body`（`GET /api/config` で読み出します）より大きいだけのときは、送信したうえで、検証の結果と一緒に「送信するリクエストボディが、設定ファイルの proxy.max_body より大きくなります。プロキシを経由して接続しているときは拒否されます。」と表示します。
  プロキシがボディの上限で拒否した 413 には、「リクエストボディがプロキシの上限（proxy.max_body）を超えました。」と表示します。

### 時間のかかる応答とタイムアウト

- インポート、世代の選択、ロールバックは、数十秒以上かかることがあります（時間の上限は「リスナー」の「時間のかかる応答」）。
  プロキシの時間の設定キーはルートごとには変更できません。
  応答のヘッダー部を待つ時間は、`upstream_header_ms`、`response_idle_ms`、`request_total_ms` のうち、先に尽きたもので切れます（[運用リファレンス](operator-reference.ja.md) の「`proxy`: 時間」と「値どうしの関係」）。
  ボディを流すリクエスト（検査除外のルートのインポートなど）では、応答のヘッダー部が届くまで `response_idle_ms` は効きません。
- 時間が切れると、プロキシはクライアントに 502 を返します。`request_total_ms` で切れたときは 503 を返します。
  プロキシが接続を切っても、管理プロセスは処理を続けます。
  インポート、選択、ロールバックは、止まらずに最後まで進みます。
- 管理画面はボディに `result` を持たない 502 と 504 を「結果不明」として扱います。
  結果不明のときは、画面ごとに、状態と履歴、または世代の一覧を再読み込みして表示します。
  `result` を持つ応答（`failed` の 502、`unreachable` と `unconfirmed` の 503 を含む）は、その値で結果を判断します。
  `result` を持たない 503 は、変更が拒否されたものとして扱います。
  `request_total_ms` は、ボディを受信する時間と検査の時間に `upstream_header_ms` を加えた時間より十分に長くしておいてください。
  API を直接使う場合も、同じ応答を受けたときは `GET /api/status` と `GET /api/history` で確認します。
  インポートのときは、`GET /api/generations` で確認します。
- 時間の設定キーは、インポートと切り替えに必要な時間を測ってから決めてください。
  `upstream_header_ms` を長くすると、ほかの Host のアップストリームが遅いときも長く待つことになります。

## ユーザーとロール

ユーザーは、名前、ロール、パスワードを持ちます。
名前に使えるのは小文字の英字・数字・`.`・`_`・`-` で、長さは 1〜32 バイトです。
パスワードは 12〜128 バイトの UTF-8 です（日本語の文字は 1 文字が 3 バイトです）。
パスワードは PBKDF2-HMAC-SHA256（600000 回、ソルト 16 バイト）のハッシュにして保存します。

| ロール | できること |
|---|---|
| `viewer` | 状態、世代の一覧と内容、切り替えの履歴、ログを読めます。managed 設定については、状態、バージョンの一覧、反映の処理、設定の変更履歴を読めます。自分のパスワード、二要素認証、API トークンを扱えます |
| `operator` | viewer のすべてに加えて、監査ログを読めます。ルールのインポート、世代の選択、ロールバック、削除ができます。managed 設定については、バージョンの内容と証明書の情報、設定ファイルの値を読めるほか、検証、保存して反映、名前で反映、ロールバック、削除ができます |
| `owner` | operator のすべてに加えて、ユーザーの作成、ロールと有効・無効の変更、ほかのユーザーのパスワードと二要素認証の初期化、全員の API トークンの閲覧と削除ができます |

- 最初の owner は `admin bootstrap` で作成します。
  それ以降のユーザーは、owner が `POST /api/users` で作成します。
  作成できるのは 1000 人までです。
  1000 人に達すると、作成は 409 `the store has too many users` で拒否されます。
  ユーザーは削除できないので、上限の人数には無効にしたユーザーも含まれます。
- ユーザーを削除する API はありません。使わなくなったユーザーは無効にします。
  無効にしたユーザーはログインできず、セッションと API トークンも使えなくなります。
  有効にし直しても、削除された API トークンは戻りません。
- owner が作成したユーザーと、owner が `POST /api/users/<name>/password` でパスワードを設定したユーザーは、次のログインで自分のパスワードに変更するまで、ほかの API を使えません。
- owner が自分自身に対して行う次の操作と、owner がいなくなる操作は拒否します。
  - 自分のロールを下げる、自分を無効にする: 403
  - 自分のパスワードと二要素認証の初期化: 403（アカウントの API で変更します）
  - 有効な owner が 1 人もいなくなる変更: 409
- ユーザーの管理は、管理プロセスの中で 1 つずつ順に進みます。
  2 人の owner が同時に互いのロールを下げて、owner がいなくなることはありません。
- ロールと状態の変更（ロールの変更、無効にする、有効にする、パスワードの設定、二要素認証の無効化）を行うと、そのユーザーのセッションは終了します。
  ロールを下げたとき、無効にしたとき、パスワードを設定したときは、API トークンも無効になります。
- ロールも有効・無効も変わらない `PUT /api/users/<name>` では、何も変更せずに、200 でそのユーザーを返します。
  セッションは終了せず、監査ログにも書きません。

## ログインと二要素認証

ログインは `POST /api/login`（`{"name", "password"}`）から始めます。
応答の `mfa` が次の段階を示します。

| `mfa` | 意味 | 次の操作 |
|---|---|---|
| `off` | セッションが使えます | API を使います。`must_change` が `true` なら、パスワードを変更します |
| `verify` | 二要素認証の認証コードが必要です | `POST /api/login/mfa` |
| `setup` | `admin.mfa` が `required` で、二要素認証が未設定です | 二要素認証を設定します |

セッションで使える API は、セッションの状態によって決まります。
状態に合わない API は、403 と次の決まった文で拒否します。

| 状態 | 場合 | 使える API | 拒否するときの `error` |
|---|---|---|---|
| 認証コード待ち | パスワードが合った、二要素認証を設定しているユーザー。この状態は 5 分で終了します | `POST /api/login/mfa`、`POST /api/logout` | `second factor required` |
| パスワード変更待ち | owner が作成したユーザー、または owner か `admin reset` でパスワードを設定されたユーザー | `PUT /api/account/password`、`GET /api/session`、`POST /api/logout` | `password change required` |
| 二要素認証の設定待ち | `admin.mfa` が `required` で、二要素認証が未設定のユーザー | `POST /api/account/mfa/setup`、`POST /api/account/mfa/confirm`、`GET /api/session`、`POST /api/logout` | `second factor setup required` |
| 通常 | 上のどれでもない場合 | ロールが許可するすべての API | |

- パスワード変更待ちと二要素認証の設定待ちが重なるときは、両方の API を使えます。
- `GET /api/session` は、状態（`state`: `active`、`must_change`、`mfa_setup`）、残りの時間、残りのリカバリーコードの数を返します。
  認証コード待ちのセッションでは、403 になります。

二要素認証（MFA）:

- **方式**: 時刻に基づくワンタイムパスワード（RFC 6238）を使います。
  認証コードは HMAC-SHA1、6 桁、30 秒ごとの時間枠で作成します。
  現在の枠に加えて、前後 1 つずつの枠の認証コードも受け入れます。
  使った枠は記録しておき、その枠と、それより前の枠の認証コードは拒否します。
- **設定**
  1. `POST /api/account/mfa/setup`（`{"password"}`）は、セットアップキー（20 バイトの乱数）を base32 の文字列（`secret`）と `otpauth://` のアドレス（`uri`）の形で返します。
     セットアップキーはセッションのメモリに 10 分だけ置きます。
  2. `POST /api/account/mfa/confirm`（`{"code"}`）は、認証アプリの認証コードを検証し、二要素認証を有効にして、リカバリーコードを返します。
     このユーザーのほかのセッションは終了し、新しいセッションと CSRF トークンが返されます。
- **設定の開始と確定を拒否する場合**: すでに二要素認証を設定しているユーザーは、開始も確定も 409 `mfa is set already` で拒否されます。
  確定は、設定を始めていないとき、または 10 分を過ぎたときも、409 `mfa setup was not started or has run out` で拒否されます。
  認証コードが合わないときは、403 `the code is wrong` になります。
- **リカバリーコード**: 10 個で、1 個は 16 文字（大文字の `A`〜`Z` と `2`〜`7`）です。どれも 1 回だけ使えます。
  リカバリーコードを返すのは設定したときの 1 回だけで、保存先には SHA-256 だけを置きます。
  使い切る前に作り直すには、二要素認証を無効にしてから設定し直します。
  `admin.mfa` が `required` のときは、自分では無効にできません。
  owner に `DELETE /api/users/<name>/mfa` で無効にしてもらいます。
  owner 自身の分は、ほかの owner に無効にしてもらうか、`admin reset` を使います。
- **ログインでの確認**: `POST /api/login/mfa` に、`{"code"}`（6 桁）か `{"recovery"}`（リカバリーコード。大文字で送ります）のどちらか一方を送ります。
  合うと、認証コード待ちのセッションは終了し、新しいセッション（新しい ID と CSRF トークン）が返されます。
- **無効にする**: `DELETE /api/account/mfa`（`{"password", "code"}`）を使います。
  `code` には、認証コードかリカバリーコードを書きます。
  `admin.mfa` が `required` のときは、403 `mfa is required` で拒否されます。
  owner はほかのユーザーの二要素認証を `DELETE /api/users/<name>/mfa` で無効にできます。
- **`required` のときの API トークン**: 二要素認証を設定していないユーザーの API トークンは使えません。
- **セットアップキーの保存**: 認証コードを計算するにはセットアップキーそのものが必要なため、ユーザーのファイルにそのまま置きます。
  保存先のディレクトリを 0700 にして保護します。

## ロックアウトと試行回数の制限

| 対象 | 決まり |
|---|---|
| ユーザーごと | 続けて 5 回失敗すると、15 分間ロックアウトします。ロックアウト中の試行も失敗に数え、15 分を数え直します。成功すると、失敗回数をリセットします |
| クライアントごと | 1 分間に 30 回まで試行できます。超えた試行は、ハッシュを計算する前に 429 `too many tries` で拒否し、ユーザーの失敗には数えません |

- ユーザーごとの失敗に数えるのは、次の場合です。
  - ログインで、パスワードが合わなかった
  - ログインの認証コード（`POST /api/login/mfa`）が合わなかった
  - 二要素認証の無効化で、認証コードが合わなかった
  - パスワードを検証する API（パスワードの変更、二要素認証の設定と無効化、トークンの作成）で、パスワードが合わなかった
  - 無効のユーザーやロックアウト中のユーザーで、ログインを試みた
- 二要素認証を設定しているユーザーは、パスワードが合っても失敗回数をリセットせず、認証コードが合ったときにリセットします。
  パスワードを知っている人が、ログインのたびに失敗回数をリセットして、認証コードを試し続けられないようにするためです。
- 二要素認証の設定の確定（`POST /api/account/mfa/confirm`）で認証コードが合わなかった場合は、ユーザーの失敗にもクライアントの回数にも数えず、監査ログにも書きません。
  応答は 403 `the code is wrong` です。
- クライアントごとの回数に数えるのは、ログイン、ログインの認証コード、パスワードを検証する API（上と同じ）、合わない API トークンです。
  ログインは成功した試行も数えます。
  正しい API トークンのリクエストと、二要素認証の設定の確定は数えません。
  回数を使い切ったクライアントの API トークンのリクエストは、トークンが正しくても、トークンを検証する前に 429 `too many tries` で拒否します。
- 追跡するクライアントは最大 4096 です。
  1 分以内に試行したクライアントで満杯のときは、ほかのクライアントを受け付けません。
- ログインは、存在しない名前、無効なユーザー、ロックアウト中のユーザー、パスワードの不一致のどれでも、同じ応答（401 `invalid credentials`）にします。
  存在しない名前やロックアウト中のときもハッシュを 1 回計算するので、かかる時間でも見分けられません。
  ログインの認証コードが合わないときも、同じ 401 `invalid credentials` で応答します。
  ほかの API でのエラーは 403 です。
  文は、パスワードでは `the password is wrong`、認証コードでは `the code is wrong` です。
  パスワードの変更でパスワードが合わないときは、`the current password is wrong` になります。
- 失敗の理由は監査ログにだけ書きます（`unknown user`、`disabled`、`locked`、`wrong password`、`wrong code`）。
  名前の欄に入力されたパスワードがログに出ないように、存在しない名前は書きません。
- ユーザーごとの失敗回数とロックアウトの状態、クライアントごとの試行回数は管理プロセスのメモリにだけあるので、再起動すると消えます。
- ユーザーが変更されると（`admin reset`、owner の操作、パスワードの変更、二要素認証の設定と無効化）、ロックアウトは解除され、失敗回数は次の失敗から数え直します。

## セッション

- ログインが通ると、セッションを作成して、クッキー `tukuyomi_admin` を返します。
  クッキーの値は 32 バイトの乱数を base64url にした 43 文字です。

  ```text
  Set-Cookie: tukuyomi_admin=<43-characters>; Secure; HttpOnly; SameSite=Strict; Path=/
  ```

  クッキーに有効期限は付けないので、ブラウザーを閉じると消えます。
  ログアウトでは `Max-Age=0` のクッキーを返して削除します。
- 管理プロセスはセッションを ID の SHA-256 で保持し、ID そのものは持ちません。
  監査ログの `session` には、その SHA-256 の先頭 8 桁だけを書きます。
- セッションごとに、CSRF トークン（別の 32 バイトの乱数で、43 文字）を持ちます。
  CSRF トークンはログインの応答と `GET /api/session` で返します。
- セッションが終了するのは次の場合です。
  - `admin.session_idle_ms` の間、使われなかった場合（リクエストのたびに数え直します）
  - 作成してから `admin.session_total_ms` が過ぎた場合
  - ログアウトした場合
  - そのユーザーのパスワード、ロール、有効・無効、二要素認証が変更された場合（`admin reset` と、別の管理プロセスの操作を含みます）。
    パスワードと二要素認証を自分で変更したときは、そのリクエストに新しいセッションを返し、ほかのセッションを終了します
  - ユーザーが無効になった場合
  - 管理プロセスを再起動した場合
- 1 人のユーザーが持てるセッションは、認証コード待ちと通常のそれぞれで 16 個までです。
  17 個目を作成すると、いちばん古いものを終了して、監査ログに `logout`（`reason` は `too many sessions`）を書きます。
  認証コード待ちを繰り返しても、通常のセッションは終了しません。
  全体で持てるセッションは 1024 個までです。
  満杯になると新しいセッションを作成できず、ログインは 503 になります。
- 1 つのリクエストが持てるのは、セッションのクッキーか API トークンのどちらか一方で、両方あると 400 になります。
  `Authorization` ヘッダーが Bearer でなくても、セッションのクッキーと一緒にあると 400 になります。
  管理画面の前に Basic 認証などの HTTP 認証をかけた場合は、ログイン後のリクエストが 400 になります。
  クッキーが 2 回含まれるリクエストは、セッションを持たないものとして扱い、401 にします。

## CSRF と Origin

`GET` と `HEAD` 以外のリクエスト（変更）では、次の 2 つを検証します。

- **`Origin`**: ヘッダーがあるときは、1 つだけで、`admin.origin` と一字一句同じであること。
  違うと 403 `forbidden` になります。
  `Origin` ヘッダーが無いリクエスト（プログラムからのリクエスト）は通ります。
  この検証はログインのリクエストにも適用します。
- **`X-CSRF-Token`**: セッションのリクエストでは、そのセッションの CSRF トークンと同じ値を 1 つだけ付けること。
  比較は一定の時間で行います。
  違うか無いと 403 `forbidden` になります。
  API トークンのリクエストには不要です。クッキーを使わないためです。

検証の順序は、「応答の形式」の「管理 API の検証の順序」を参照してください。

- 管理画面は CSRF トークンをメモリにだけ置き、変更のリクエストのたびに付けます。
  ページを開き直したときは `GET /api/session` で受け取り直します。
  認証コード待ちのセッションでは、`GET /api/session` が 403 になり、CSRF トークンを受け取れません。
  このセッションでページを開き直すと、ログインからやり直しになります。
- `Origin` の不一致と CSRF の不一致で拒否したリクエストは、ユーザーが分かっているときに監査ログに書きます（`reason` は `origin`、`csrf`）。

## API トークン

API トークンは、プログラムから管理 API を使うためのトークンです。

- **形式**: `tkc_<16-hex-digits>_<43-characters>` です。
  前の部分がトークンの ID、後ろの部分が秘密（32 バイトの乱数の base64url）です。
  トークン全体を返すのは作成したときの 1 回だけで、管理データの保存先には秘密の SHA-256 だけを置きます。
- **送り方**: `Authorization: Bearer <token>` で送ります。セッションのクッキーとは一緒に送れません（400）。
- **作成**: `POST /api/account/tokens`（`{"name", "role", "days", "password"}`）で、セッションのユーザーが自分のためのトークンを作成します。
  現在のパスワードが必要です。
  - `name`: 1〜64 バイトの印字可能な ASCII
  - `role`: 自分のロール以下。
    それより上のロールは 403 `the role is above the role of the user` で拒否します。
  - `days`: 1〜365。
    作成した時刻からこの日数で有効期限が切れます。
  - 1 人が持てるのは 50 個までです。超えると、409 `the user has too many tokens` で拒否します。
    50 個の数には、期限が切れたトークンも含まれます。
    期限が切れたトークンは自動では削除されないので、`DELETE /api/account/tokens/<id>` で削除します。
  - 応答は、トークンの情報（`id`、`owner`、`name`、`role`、`created`、`expires`、`expired`、`last_used`。時刻はミリ秒のエポック）に、`token`（全体の文字列）を加えたものです。
- **使える API**: 状態、世代、インポート、選択、ロールバック、削除、履歴、ログ、監査ログ、managed 設定と設定ファイルの値の API です（下の「API のパスの一覧」で「トークン」が ○ のもの）。
  アカウントの API と、ユーザーの管理の API には使えません（403）。
  owner のトークンで、ほかのユーザーのパスワードや二要素認証を初期化し、そのユーザーとしてログインできてしまうのを防ぐためです。
- **リクエストのロール**: トークンのロールです（所有者のロール以下）。
  CSRF トークンは不要です。
  変更のリクエストに `Origin` があるときは、`admin.origin` と同じであること。
- **使うたびの検証**: 次のことを検証します。
  - 形式が正しく、保存先にその ID があり、秘密の SHA-256 が合うこと
  - 所有者がいて、無効でなく、ロールがトークンのロール以上であること
  - トークンが、所有者ごとに持つ無効化の時刻より後に作成されていること（この時刻より前に作ったトークンは無効です）
  - 有効期限が過ぎていないこと
  - `admin.mfa` が `required` なら、所有者が二要素認証を設定していること
- **無効になる場合**: トークンのファイルを削除できなくても、上の検証で通らなくなります。
  - 有効期限が来た場合、または削除した場合（`DELETE /api/account/tokens/<id>`、owner は `DELETE /api/tokens/<id>`）
  - 所有者が無効になった場合
  - 所有者のロールが下がった場合（所有者のすべてのトークンが無効になります）
  - 所有者のパスワードが変更された場合（自分で変更したとき、owner が設定したとき、`admin reset`）
- **合わないトークン**: クライアントごとの試行回数（上の「ロックアウトと試行回数の制限」）に数えますが、監査ログには書きません。
  誰でも送れるリクエストで、監査ログが埋め尽くされないようにするためです。
- **最後に使った時刻**: `last_used` は 10 分に 1 回までしか書き込みません。
  書き込めなくても、リクエストは通ります。
- **使い方の例**: `$TOKEN` にトークンを入れて使います。

  ```bash
  curl -sS -H "Authorization: Bearer $TOKEN" https://admin.example.com/api/status
  curl -sS -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d '{"generation":"<target-fingerprint>","expect":"<current-fingerprint>"}' \
    https://admin.example.com/api/activate
  ```

## 監査ログ

管理プロセスは、ログイン、変更、拒否したリクエストを監査ログの行として残します。

| 項目 | 内容 |
|---|---|
| `ts`、`type` | ログと同じで、`type` は `audit` です |
| `id` | リクエスト ID（`X-Request-ID`）。コマンド（`admin bootstrap`、`admin reset`）の行にはありません |
| `actor` | 検証できたユーザーの名前。検証できなかったときはありません。リクエストヘッダーからは取得しません |
| `session` | セッション ID の SHA-256 の先頭 8 桁。ID そのものは書きません |
| `auth` | セッション以外で認証したときの認証方法。`token:<id>`、`bootstrap`、`reset` |
| `client` | クライアントのアドレス。コマンドの行にはありません |
| `action` | 操作（下の表） |
| `target` | 操作の対象（ユーザーの名前、API トークンの ID、世代のフィンガープリント、managed 設定のバージョンの名前）。存在しない名前のログインにはありません |
| `result` | `ok`、`denied`（拒否）、`failed`（実行を試みたが失敗） |
| `reason` | 決まった語（`wrong password`、`locked`、`expect`、`store` など） |
| `before`、`after` | 変更の前と後の値。ロール、有効・無効、世代のフィンガープリント、managed 設定のバージョンの名前 |

パスワード、API トークン、認証コード、リカバリーコード、二要素認証のセットアップキー、クッキーは、監査ログに書きません。

| `action` | 場合 |
|---|---|
| `login` | ログインの成功（`ok`）と失敗（`denied`。`reason` は `unknown user`、`wrong password`、`locked`、`disabled`）。セッションを作成できないとき（`failed`、`no session`）。二要素認証を設定したユーザーのパスワードが合ったときは、`reason` が `second factor pending` になります |
| `mfa` | 認証コードの成功と失敗（`wrong code`、`locked`）。リカバリーコードでの成功は、`reason` が `recovery code` になります |
| `lock` | ユーザーのロックアウト（`reason` は `too many failures`） |
| `logout` | ログアウト。セッションが多すぎて終了させたときは、`reason` が `too many sessions` になります |
| `password`、`mfa_setup`、`mfa_confirm`、`mfa_disable` | 自分のパスワードの変更と、二要素認証の設定の開始・確定・無効化。パスワードや認証コードのエラーは、`denied`（`wrong password`、`wrong code`、`locked`）になりますが、`mfa_confirm` で認証コードが合わなかったときは行を書きません |
| `token_create`、`token_revoke` | API トークンの作成（`after` がロール）と削除 |
| `user_create`、`role`、`disable`、`enable`、`user_password`、`user_mfa` | owner が行うユーザーの管理 |
| `import`、`activate`、`rollback`、`remove` | 世代の操作（下の「世代の操作」） |
| `managed-import` | `POST /api/managed/apply`（「保存して反映」の操作）で、バージョンを保存する前に書く行（下の「managed 設定の操作」の「保存して反映」） |
| `managed-apply`、`managed-activate`、`managed-rollback` | managed 設定の「保存して反映」「名前で反映」「ロールバック」の操作（下の「managed 設定の操作」） |
| `managed-remove` | managed 設定のバージョンの削除 |
| `create`、`reset` | コマンド `admin bootstrap`、`admin reset` |
| API ごとの `action` | 拒否した API の名前で、`denied` の行を書きます（下の注）。名前は、上の世代の操作と managed 設定の `action` のほかに、`status`、`generations`、`generation`（世代 1 つの読み出し）、`history`、`records`、`audit`、`session`、`users`、`user_update`（`PUT /api/users/<name>`）、`tokens`、`managed`（`GET /api/managed`）、`managed-versions`、`managed-version`（バージョン 1 つの読み出し）、`managed-job`、`managed-history`、`managed-check`、`managed-certificates`、`config`（`GET /api/config`）です |

- API ごとの検証で拒否したリクエストは、ユーザーが分かっていれば `denied` の行を書きます。
  `reason` は、`origin`、`csrf`、`token`（API トークンが使えない API）、`role`、`state`、`second factor pending`、`password change`、`second factor setup` です。
- ユーザーが分からない段階で拒否したリクエストは、書きません。
  セッションも API トークンも無い、API トークンが合わない、クライアントの回数を超えたログイン、`Origin` が違うログイン、パスが無い、などです。
  誰でも送れるリクエストで、古い行が押し出されないようにするためです。
- 世代の操作の行では、`target` に対象の世代のフィンガープリントを書きます。
  `activate` と `rollback` の `ok` の行には、`before` に選択中だった世代、`after` に依頼した世代も書きます。
  - `ok` の行は変更の前に書くので、成功を示す行ではありません。
    どう終わったかは、後に続く `failed` の行と、切り替えの履歴で確認します。
  - `failed` の `reason` は、`expect`、`store`、`refused`、`failed`、`unconfirmed`、`history`（履歴の行を書き込めなかった）です。インポートでは `store` と `trial` です。
  - 変更の前に拒否したときは `denied` で、`reason` は `expect`、`engine`、`version`（エンジンごとの状態を返さないプロキシ）、`busy`、`unreachable` です。
  - 削除の `reason` は、選択中の世代のときは `chosen`、ロールバック先のときは `rollback target` です。
- managed 設定の行では、`target` に対象のバージョンの名前を書きます。
  `managed-apply`、`managed-activate`、`managed-rollback` の `ok` の行は、反映の処理がプロキシに依頼する前に書きます。
  `before` には変更前のバージョン、`after` には変更後のバージョンを書きます。
  この行も成功を示す行ではありません。
  どう終わったかは、後に続く行と設定の変更履歴で確認します。
  - 変更の前に拒否したときは `denied` で、`reason` は `managed`、`configuration`、`expect`、`unreachable`、`busy`、`unmanaged`、`engine` と、反映の処理の結果を表す語（`current changed`、`no version`、`store`）です。
    `engine` は、`managed-activate` と `managed-rollback` で、バージョンのアップストリームのエンジンに、ルールストアで選択中の世代が無いときです。
  - 変更の前の行を書いた後に失敗したときは `failed` で、`reason` は反映の処理の結果を表す語（`refused`、`busy`、`error`、`failed`、`unconfirmed`、`not recorded`）と、`history`（設定の変更履歴の行を書き込めなかった）です。
    反映の処理を始められなかったときも `failed` で、`reason` は `time`、`stopping`、`thread` です。
  - `managed-import` の失敗の `reason` は、`store`、`version`、`configuration` です。
    削除の `reason` は、拒否では `managed`、`configuration`、`chosen`（選択中のバージョン）、`rollback target`（ロールバック先）、失敗では `store` です。
  - 検証の API と読み出しだけの API は変更ではないので、入口で拒否したとき以外は行を書きません。

書き込みの方法:

- 監査ログの行を先に書いてから、変更を行います。
  ディスクが満杯の場合などで行を書けないときは、変更せずに 503 `unavailable` で拒否します。
  行はディスクに同期してから標準エラーにも出力します。
- 例外はログアウトです。
  ログアウトは権限を取り消す操作なので、行を書けなくてもセッションを終了します。
- 変更が失敗したときは、後から `failed` の行を書きます（書けなくても、応答は変えません）。
- 保存先は `admin.store.dir` の `audit/audit.log` で、1 行 1 件の JSON です。
  1 つのファイルが 16 MiB を超えると次のファイルに移り、8 つのファイル（`audit.log`、`audit.1.log` から `audit.7.log`）を残します。
  同じ行は標準エラー（ジャーナル）にも出力します。
- `GET /api/audit`（operator 以上、API トークン可）は、最新の 200 行を新しい順に `{"entries": [...]}` で返します。
  ファイルの終わりから読み、足りなければ古いファイルも読みます。
  1 つのファイルは終わりの 1 MiB までを読み、ファイルがそれより大きいときは、古いファイルを読まずにそこで終了します。
  読めない行は飛ばします。

## 世代の操作

世代の一覧と内容は viewer が読めます。
インポート、選択、ロールバック、削除は operator 以上が行えます。

### 一覧と内容

- `GET /api/status` は、次の値を返します。
  - `current`: デフォルトのエンジンについて、ルールストアで選択中の世代のフィンガープリント（無ければ `null`）
  - `reachable`: プロキシに接続できるかどうか。
    同時接続数の上限のために応答できないプロキシは、接続できるものとして扱います
  - `proxy`: プロキシの状態（`generation`、`mode`、`engine`、`phase`、`switching`、`engines`、`reloading`、`ready`）と数（`uptime_ms`、`requests`、`blocked`、`policy_refused`、`upstream_failures`、`config`、`managed`、`resolve_timeout_ms`、`config_reloads`）。
    プロキシの応答をそのまま返し、読めなければ `null` です。
    `generation`、`mode`、`engine`、`phase` は、デフォルトのエンジンについてプロキシが応答した値です。
    `engines` は、プロキシで稼働しているエンジンごとの `{"engine", "generation", "mode", "phase"}` の配列です（エンジンの名前順）。
    `ready` は、`/readyz` が準備済みと答える状態かどうかです。
    `reloading` は、設定のリロードの途中かどうかです。
    以前のバージョンのプロキシは `engines`、`reloading` と数を送らないので、送られなかったものはそれぞれ `null` になります（応答は拒否しません）。
    数の内容は次のとおりです（[運用リファレンス](operator-reference.ja.md) の「制御ソケット」）。
    - `uptime_ms`: プロキシが起動してからのミリ秒
    - `requests`: リクエストの数（ログの 7 つの `class` のすべて）
    - `blocked`: ルールがブロックしたリクエストの数
    - `policy_refused`: 全体の `access` と `rate_limit`、ホストごとの設定が拒否したリクエストの数
    - `upstream_failures`: 稼働中の設定での、アップストリームのサーバーの失敗回数。
      設定のリロードで設定が切り替わると、0 から数え直します
    - `config`: 稼働中の設定ファイルの SHA-256（64 桁の小文字の 16 進数）
    - `managed`: 稼働中の managed 設定のバージョンの名前（64 桁の小文字の 16 進数）。`managed` の無い設定では `null`
    - `resolve_timeout_ms`: 稼働中の設定の `forward.resolve_timeout_ms`
    - `config_reloads`: SIGHUP と制御ソケットの `reload` による、設定のリロードの数。
      `{"replaced", "refused"}`（切り替えた数と拒否した数）
  - `rollback_to`: 今、デフォルトのエンジンのロールバックを依頼したら選択される世代（無ければ `null`）
  - `default_engine`: 管理プロセスが起動したときの `kernel.default_engine`（`coraza` か `modsecurity`）。`kernel.default_engine` を書かないときは `coraza` になります。
    管理プロセスとプロキシの一方だけを再起動したときは、`proxy` の `engine` と違うことがあります
  - `engines`: エンジンごとの `{"engine", "current", "rollback_to"}` の配列（`coraza`、`modsecurity` の順）。
    それぞれ、ルールストアでそのエンジンに選択中の世代と、そのエンジンのロールバック先です。
    上の `current` と `rollback_to` は、この配列のうち `default_engine` のエンジンの値です
  - `crs`: `{"available", "files"}`。
    `admin.crs_dir` があるかどうかと、インポートで除外できる CRS の `.conf` の名前
- `GET /api/generations` は、`{"reachable", "generations"}` を返します。
  `generations` には、新しい順に、各世代の次の値が入ります。
  - `fingerprint`: 世代のフィンガープリント
  - `made`: 作成した時刻（エポックからの秒数）
  - `mode`: `block`、`detect`。マニフェストが読めなければ `unknown`
  - `engine`: `coraza`、`modsecurity`。マニフェストが読めなければ `unknown`
  - `routes`: 検査除外のルートの数
  - `current`: どれかのエンジンで、ルールストアで選択中かどうか
  - `serving`: どれかのエンジンで、プロキシで稼働中かどうか
- `GET /api/generations/<fingerprint>` は、上の値に加えて、`load`（読み込む順）と `files`（`path`、`size`、`sha256`）を返します。
  ここでは、`routes` は数ではなく、ルートの配列（`host`、`path`、`action`）です。
  `host` を持たないルートには、`host` は付きません。
  ルールストアに無い世代は 404 になります。

「選択中」の世代と「稼働中」の世代は別のもので、どちらもエンジンごとに 1 つずつあります。
プロキシが切り替えに失敗しているときや、世代のエンジンが稼働していないときは、ルールストアで選択中の世代でも稼働していません。
管理画面は次のどちらかのときに警告を表示します。

- 切り替えの途中ではないのに、どれかのエンジンで 2 つの世代が違うとき
- 選択中の世代があるのに、そのエンジンが稼働していないとき

### インポート

`POST /api/generations`（operator 以上、API トークン可）は、`rules import` と同じ順序で世代を作成します。
ファイルを集めてルールストアに仮に置き、検査プロセスで事前検証して、通れば世代にします。
作成した世代は選択しません。

ボディは JSON のオブジェクトで、キーはすべて省略できます。

| キー | 内容 |
|---|---|
| `rules` | ルールのファイルです。`{"name", "data"}` の配列で、書いた順に読み込みます。`name` はディレクトリを除いた名前（`--rules` と同じ決まり）、`data` は標準の base64（パディング付き）です |
| `data` | データのファイルで、形式は `rules` と同じです（`--data` に対応します） |
| `crs` | `true` で、`admin.crs_dir` の CRS を使います。リクエストではパスを指定できません。`admin.crs_dir` が無いと 400 になります |
| `crs_off` | 読み込まない CRS の `.conf` の名前の配列です（`--crs-off` に対応します） |
| `routes` | 検査除外のルートの配列です（`--routes` のファイルと同じ形式） |
| `engine` | 検査エンジンの名前です（`--engine` に対応します）。`coraza` か `modsecurity` を小文字で書きます。省略すると、管理プロセスのデフォルトのエンジン（`GET /api/status` の `default_engine` と同じ値）になります |
| `detect_only` | `true` で、検知のみの世代にします |
| `accept_block` | `true` で、事前検証のリクエストがブロックされても失敗にしません |

- 上限と名前の決まりは `rules import` と同じです（[運用リファレンス](operator-reference.ja.md) の「`rules`」）。
  ファイルは 128 個まで、1 つ 2 MiB まで、全体で 8 MiB までです。
  2 MiB を超えるファイルは、デコードする前に拒否します。
- `engine` がエンジンの名前でないときと、そのエンジンが使えないときは、ファイルを集める前に 400 で拒否します。
  何も仮に置かず、事前検証も実行しません。
  文は次のどちらかです。
  - `engine is not the name of an engine (coraza or modsecurity)`
  - `kernel.engines has no inspector for the engine of the generation`（設定に、そのエンジンの検査プロセスが無い）
- 事前検証は `rules import` と同じです。
  管理プロセスが検査プロセスを 1 つ起動し、決まった 3 つのリクエスト（`GET /`、フォームの `POST /`、JSON の `POST /`）を検査します。
  起動するのは、`engine` のエンジンの検査プロセスです（`coraza` は `kernel.inspector`、`modsecurity` は `kernel.engines`）。
  `kernel` の値と、`proxy` の `ready_wait_ms`・`inspect_wait_ms`・`stop_inspect_ms`・`drive_slice_ms` を使います。
- インポート、選択、ロールバック、削除は、管理プロセスの中で 1 つずつ順に進みます。
  ほかの変更が進んでいるときは、待たずに 409 `a change of the rules is under way` になります。
  コマンドや別のプロセスがルールストアのロックを保持しているときは、409 `the rules store is in use by another command` になります。

応答:

| ステータスコード | 場合 | ボディ |
|---|---|---|
| 200 | 世代を作成できたとき | `{"fingerprint", "result", "trial"}`。`result` は `created`、`existing`（同じ世代がすでにあった）、`repaired`（壊れていた同じフィンガープリントの世代を作り直した） |
| 400 | 入力が拒否されたとき（使えないエンジンも含みます） | `{"error"}`。入力のファイルの名前があれば、`subject` に付きます（0x20〜0x7e 以外のバイトは `\xNN`、128 バイトまで） |
| 409 | ルールストアで拒否されたとき、ほかの変更が進んでいるとき | `{"error"}` |
| 422 | 事前検証が失敗したとき。世代は作成しません | `{"error": "the trial failed", "trial": {..}}` |
| 500 | 事前検証を実行できないとき | `{"error"}` |
| 503 | 監査ログの行を書けないとき | `{"error": "unavailable"}` |

`trial` は、通ったときは `{"passed": true, "accepted": [..]}`、失敗したときは `{"passed": false, "failure": <message>}` です。
検査プロセスの出力があれば、`passed` の値に関わらず `detail`（512 バイトまで）が付きます。

事前検証のリクエストがすべて通っても、検査プロセスか作業ディレクトリが片付かなかったときは、`passed` が `false`、`failure` が `the inspector did not stop cleanly; a process or a directory may be left behind` になります。
このときも 422 で、世代は作成しません。
ホストにプロセスやディレクトリが残っていないか、確認してください。

`accepted` は、事前検証で受け入れたブロック（`{"kind": "block", "probe", "rule", "phase", "status"}`）と検知（`{"kind": "detected", "probe", "rule", "status"}`）です。
`probe` は、事前検証のリクエストの名前（`GET /`、`POST / with a urlencoded body`、`POST / with a JSON body`）です。

### 選択とロールバック

`POST /api/activate`（`{"generation", "expect"}`）と `POST /api/rollback`（`{"engine", "expect"}`。`engine` は省略できます）は、ルールストアで選択中の世代を変更し、プロキシに切り替えさせます。
operator 以上が使え、API トークンでも使えます。
切り替えは 1 つのエンジンについて行います。
対象のエンジンは、`activate` では世代のエンジン、`rollback` では `engine` のエンジンです。`engine` を省略すると、管理プロセスのデフォルトのエンジンになります。
選択中の世代とロールバック先は、エンジンごとにあります（[運用リファレンス](operator-reference.ja.md) の「エンジンごとの選択中の世代」）。

- フィンガープリントは 64 桁の小文字の 16 進数で、違うと 400 `a generation is not 64 lowercase hexadecimal digits` になります。
- `rollback` の `engine` が小文字の `coraza` か `modsecurity` でないときは、400 `engine is not the name of an engine (coraza or modsecurity)` になります。
- `expect` には、画面で見た、そのエンジンの「選択中の世代」を書きます。
  画面を見た後に、ほかのユーザーかコマンドが選択し直していれば、409 で拒否します。
  古い画面のまま選択し直して、上書きするのを防ぐためです。
  - `activate` の `expect` には、`generation` の世代のエンジンについて、選択中の世代を書きます。
    そのエンジンに選択中の世代が無いときは、`null` を書きます。
    `null` を書いたのに選択中の世代があれば、409 で拒否します。
  - `activate` では `expect` のキーを必ず書き、省略すると 400 です。
    `rollback` の `expect` は 64 桁の文字列です。
- そのエンジンに選択中の世代が無いときは、`expect` を `null` にして選択できます。
  画面でも、選択中の世代が無いエンジンの世代には、選択の操作を表示します。
  デフォルトのエンジンの最初の世代は、プロキシが起動するために必要です。
  この世代はコマンド（`rules activate`）で選択します（[運用リファレンス](operator-reference.ja.md) の「検査エンジンの選択」）。
- `generation` に今選択中の世代を指定すると、ルールストアで選択中の世代は変わらず、プロキシだけを切り替えさせます（管理画面の「プロキシに反映する」）。
  プロキシでそのエンジンが稼働していないときは、そのエンジンを起動します（管理画面の「エンジンを起動する」）。
  まだ選択していない世代を指定したときも、プロキシで稼働していないエンジンは、その世代で起動します。
  `rollback` でも、プロキシでそのエンジンが稼働していなければ、ロールバック先の世代でそのエンジンを起動します。

進み方:

1. `activate` では、世代がルールストアにあることを確認します。
   無ければ 404 `no such generation` になります。
   ロールバックでは、ロールバック先を決めます（下を参照）。
2. ルールストアで、そのエンジンに選択中の世代が `expect` と同じであることを確認します。
   選択中の世代が無いときは、`expect` が `null` であることを確認します。
   違えば 409 で、何も変更せず、履歴にも書きません（監査ログには `denied` で、`reason` は `expect`）。
3. 切り替え先の世代のエンジンが使えることを確認します。
   使えなければ `{"error": <message>}` の 409 で、何も変更せず、履歴にも書きません（監査ログには `denied` で、`reason` は `engine`）。
   文は上の「インポート」の 400 の `kernel.engines has no inspector for the engine of the generation` と同じです。
   マニフェストが読めない世代は、ここでは拒否せず、ルールストアで世代を選択する段階で拒否されます。
4. プロキシの状態を問い合わせます。
   - 接続できない: 503 `the proxy cannot be reached`。
     ルールストアは変更せず、履歴に `unreachable` を書きます（監査ログにも `denied` で、`reason` は `unreachable`）。
   - 接続を受け付けて何も応答せずに閉じる（同時接続数の上限）: 503 `the proxy is busy`。
     ルールストアは変更せず、履歴には書きません（監査ログには `denied` で、`reason` は `busy`）。
   - 状態に `engines` が無い（エンジンごとの選択に対応していない、以前のバージョンのプロキシ）: 409 `the proxy does not report its engines`。
     ルールストアは変更せず、履歴には書きません（監査ログには `denied` で、`reason` は `version`）。
     管理プロセスとプロキシは、同じビルドにそろえてください（[運用リファレンス](operator-reference.ja.md) の「バージョンの更新」）。
5. 監査ログの行を書きます。
   書けなければ 503 `unavailable` で、変更しません。
6. ルールストアで世代を選択します。
   選択はロックの中で行い、`expect` をもう一度検証します。
   この間に別のプロセスが選択していれば、上書きせずに 409 とします。
7. プロキシに切り替えを依頼し、終わるのを待ちます（上の「制御ソケット」）。
8. 履歴に 1 行書き、応答します。

応答（ボディは `{"result", "engine", "from", "generation", "chosen"}`。失敗では `error` も付きます）:

| `result` | ステータスコード | 意味 | `chosen` |
|---|---|---|---|
| `switched` | 200 | プロキシは現在その世代を使っています | `true` |
| `unchanged` | 200 | プロキシはすでにその世代を使っていました | `true` |
| `refused` | 409 | プロキシが拒否しました（`the proxy refused the switch`）。プロキシが `expect` の不一致を検出したときも含みます | `true` |
| `failed` | 502 | プロキシは切り替えませんでした（`the proxy did not switch`）。時間内に切り替わらなかったときも含みます | `true` |
| `unreachable` | 503 | プロキシに接続できません。ルールストアは変更していません | `false` |
| `unconfirmed` | 503 | ルールストアは変更しましたが、プロキシが結果を応答しませんでした（`the proxy did not say how the switch ended`） | `true` |

- `chosen` は、ルールストアで現在その世代が選択中かどうかを示します。
- 切り替えが `refused`、`failed`、`unconfirmed` に終わっても、ルールストアは元に戻しません。
  `refused` と `failed` では、プロキシは前の世代を使い続けます。
  `unconfirmed` では、プロキシがどちらの世代を使っているか分かりません。
  プロキシが使っている世代は、`GET /api/status` の `proxy.engines` にある、そのエンジンの `generation` で確認してください。
  プロキシを再起動すると、エンジンごとに、ルールストアで選択中の世代で始まります。
  その世代を使わない場合は、前の世代を選択し直します。
- 履歴に行を書けなかったときは、応答に `"history": "not written"` が付きます。
- `result` と `chosen` を持つのは上の表の 6 つの場合だけで、ほかの失敗のボディは `{"error": <message>}` だけです。
  これに当たるのは次の失敗です。
  - `expect` が合わない 409（`the chosen generation is not the one that was expected`）
  - `the proxy is busy` の 503
  - ロールバック先が決まらない 409
  - 世代のエンジンが使えない 409
  - エンジンごとの状態を返さないプロキシへの 409
  - ルールストア自体で選択が拒否された 409

  この中で履歴に行（`refused`）を書くのは、ルールストア自体で選択が拒否されたときだけです。

ロールバック先:

- ロールバック先は、履歴にあるそのエンジンの行のうち、結果が `switched` で、`from` と `to` が違う、最も新しい行の `from` です。
  `engine` の無い行（以前のバージョンの管理プロセスが書いた行）は、`from` と `to` の世代のエンジンがどちらもそのエンジンのときだけ、そのエンジンの行として使います。
  世代のエンジンを読めないときは使いません。
- ロールバックできるのは、その行の `to` がルールストアでそのエンジンに今選択中の世代のときだけです。
  切り替えが失敗した後や、コマンドで世代を選択した後は、履歴の終わりが選択中の世代と合わないため、ロールバックできません。
  応答は 409 `the history does not end at the chosen generation` になります。
  `switched` の行が無いときは、409 `there is no switch to go back from` になります。
- ロールバック先の世代がルールストアに無ければ、409 `the generation to go back to is not in the store` になります。
- ロールバックも履歴に `rollback` として入ります。
  続けてもう一度ロールバックすると、元の世代に戻ります。

### 削除

`DELETE /api/generations/<fingerprint>`（operator 以上、API トークン可）は、世代をルールストアから削除します。
削除は元に戻せません。
次の世代は削除せず、409 で拒否します。

| 世代 | `error` |
|---|---|
| ルールストアで選択中の世代（どのエンジンでも） | `the generation is the one the rules store chooses` |
| ロールバック先の世代（どのエンジンでも） | `the generation is the target of a rollback` |
| プロキシで稼働中の世代（どのエンジンでも） | `the generation is used by a running proxy` |

ルールストアに無い世代は 404 です。
この管理プロセスの中でほかの変更が進んでいるときは、409 `a change of the rules is under way` で拒否します。
コマンドや別のプロセスがルールストアのロックを保持しているときは、409 `the rules store is in use by another command` で拒否します。
削除の検証の後にコマンドが世代を選択したときは、409 `the generation is the current one` になります。
成功すると、`{"removed": <fingerprint>}` を返します。

## managed 設定の操作

managed 設定は、設定ファイルとは別の managed ストアにバージョンとして置き、管理画面と管理 API から変更する設定です。
対象は、サイトと証明書、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定です。
managed 設定を使うかどうか、managed ストアとバージョンの形式、コマンド、反映の順序については、[運用リファレンス](operator-reference.ja.md) の「managed 設定」を参照してください。
ここでは、管理 API の操作を説明します。

- 状態、バージョンの一覧、反映の処理、設定の変更履歴は、viewer が読めます。
  バージョンの内容、証明書の情報、設定ファイルの値、検証、保存して反映、名前で反映、ロールバック、削除は、operator 以上が行えます。
  どれも API トークンで使えます。
- バージョンの内容と設定ファイルの値を operator 以上に限るのは、ルートの書き換え（`rewrite`）に、アップストリームの認証の値などの秘密を書けるためです。
- この API を使えるのは、管理プロセスが起動したときに、設定ファイルに `managed` があった場合だけです。
  無かった場合、`GET /api/managed` は `{"managed": false}` を返します。
  `GET /api/config` は、あった場合と同じように使えます。
  ほかの API は 409 `the configuration has no managed object` で拒否します。
- 管理プロセスが使う managed ストアは、起動時に `managed.dir` が指していたディレクトリです。
  リクエストのたびに開き、開けないときは、500 と managed ストアの文で応答します。
  検証と変更では設定ファイルを再読み込みし、`managed.dir` が起動時と違えば、409 `the managed object of the configuration names another directory than at the start` で拒否します。
  `managed` の有無や `managed.dir` を変更したら、管理プロセスを再起動してください。

### 状態と一覧

- `GET /api/managed` は、次の値を返します。
  - `managed`: `true`
  - `current`: managed ストアで選択中のバージョン（無ければ `null`）
  - `serving`: プロキシが制御ソケットで応答した、稼働中のバージョン（状態を読めないときと、プロキシが `managed` の無い設定で動作しているときは `null`）
  - `reachable`: プロキシに接続できるかどうか。
    同時接続数の上限のために問い合わせに応答できないプロキシは、接続できるものとして扱います
  - `reloading`: プロキシが設定をリロード中かどうか（分からなければ `null`）
  - `rollback_to`: 今ロールバックを依頼したら反映するバージョン（無ければ `null`。下の「名前を指定した反映とロールバック」）
  - `job`: 最後の反映の処理（無ければ `null`。下の「反映の処理」）

  設定の変更履歴を読めないときは 503 になります。
- `GET /api/managed/versions` は、`{"reachable", "versions"}` を返します。
  `versions` には、新しい順に、各バージョンの次の値が入ります。
  - `name`: バージョンの名前（SHA-256 の 64 桁の小文字の 16 進数）
  - `made`: バージョンのファイルの更新時刻（エポックからの秒数）
  - `current`: 選択中かどうか
  - `serving`: 稼働中かどうか
- `GET /api/managed/versions/<version>`（operator 以上）は、上の 4 つに加えて、`version`（managed ストアにあるとおりのバージョンの JSON）を返します。
  バージョンはファイルを SHA-256 だけで指定します。
  どの応答にもファイルの内容は入りません。
  managed ストアに無いバージョンは 404、内容が名前と合わないバージョンは 500 になります。

「選択中」のバージョンと「稼働中」のバージョンは別のものです。
反映が途中で停止したときや、コマンドでバージョンを選択したときは、2 つが違うことがあります。
どちらかのバージョンをもう一度反映すると、2 つはそろいます。
2 つが違うときは、管理画面が通知を表示し、2 つをそろえるための操作を 2 つ示します（下の「管理画面」）。

### 証明書の情報

`GET /api/managed/certificates/<version>`（operator 以上）は、managed ストアにある証明書の状態をバージョンのサイトごとに返します。
サイトの順序はバージョンでの順序です。
応答は `{"name", "sites"}` で、サイトごとに次のキーを持ちます。

| キー | 内容 |
|---|---|
| `name` | サイトの名前 |
| `kind` | `files`（証明書チェーンと秘密鍵のファイル）か `acme`。どちらの形式でもなければ `null` |
| `chain`、`key` | `files` のサイトでの、証明書チェーンと秘密鍵のファイルの名前（SHA-256）。内容は返しません |
| `hosts` | `acme` のサイトのホスト。読める形式のときだけ |
| `state` | 下の表 |
| `not_after`、`expired` | 証明書チェーンの最初の証明書が持つ有効期限（エポックからの秒数）と、サーバーの時計で期限切れかどうか。有効期限を読み取れたときだけ |
| `names`、`more` | 証明書に含まれるホスト名（DNS 名、100 個まで）と、ほかの名前の数。名前も読み取れたときだけ。`[]` は、証明書に DNS 名が無いことを示します |

`state` は、次の表で上から見て、最初に当てはまるものになります。

| `state` | 意味 |
|---|---|
| `unreadable` | 証明書チェーンか秘密鍵のファイルを読めません（シンボリックリンク、1 MiB 以下の通常のファイルでない、`files` のサイトで内容が名前と合わない、など）。どちらの形式でもない証明書も、これになります |
| `missing` | `files` のサイトで、証明書チェーンか秘密鍵のファイルが managed ストアに無いとき |
| `waiting` | `acme` のサイトで、まだ発行されていないとき（`acme renew` が書く証明書チェーンか秘密鍵が無い） |
| `unparsed` | 証明書チェーンの最初の証明書から、名前か有効期限を読み取れないとき |
| `present` | `files` のサイトで、証明書チェーンを読め、秘密鍵のファイルがあるとき |
| `issued` | `acme` のサイトで、証明書チェーンを読め、秘密鍵のファイルがあるとき |

- 応答はディスクにある証明書の状態で、プロキシがメモリに持つ証明書の状態ではありません。
  `acme renew` の後は、プロキシが証明書を再読み込みする（SIGUSR2）まで、2 つは違います。
  指定するバージョンは稼働中のものでなくてもかまいません。
- `present` と `issued` は、ファイルがあり、証明書チェーンを読めることだけを示します。
  秘密鍵の内容、証明書チェーンと秘密鍵が対応しているかどうか、証明書がサイトのホストを含むかどうかは検証しません。
  どのサイトも `present` のバージョンでも、プロキシが拒否することはあります。
- プロキシは証明書の有効期限を確認せず、期限切れの証明書もそのまま使います。
  `check` と `apply` の検証でも、有効期限は確認しません。
- この API は、変更の実行権もロックも取得せず、プロキシへの問い合わせも監査ログへの書き込みもしません。

### 設定ファイルの値

`GET /api/config`（operator 以上）は、設定ファイルの現在の値を返し、設定ファイルに `managed` があっても無くても使えます。

- リクエストのたびに設定ファイルを再読み込みし、設定ファイルの検証にすべて通ったときだけ応答します。
  読めないときと受け付けられないときは、409 と決まった文で応答します。
- 応答は `{"sha256", "managed", ...}` です。
  `sha256` はファイルの SHA-256 で、プロキシがこのファイルを読み込むと `/api/status` の `proxy.config` に出る値です。
  `managed` は、設定ファイルに `managed` があるかどうかです。
  残りは、設定ファイルの設定キーです。名前と形式は設定ファイルと同じです。
- 出力するのは決まった一覧にある設定キーだけです。
  パスの値（証明書、秘密鍵、CA のファイル、ディレクトリ、検査プロセス、ソケット、データベースのファイル）は、書かれていれば `true`、無ければ `null` を返します。パスの文字列は返しません。
- operator 以上に限るのは、ルートの書き換えに秘密を書けるうえに、サーバーとリスナーのアドレスも含まれるためです。

### 検証

`POST /api/managed/check`（operator 以上）は、バージョンを `POST /api/managed/apply` と同じように検証し、何も保存しません。
保存する前に、画面がエラーをその欄に表示するための API です。

- ボディは `{"version", "files", "expect"}` で、`POST /api/managed/apply` と同じ形式です（下の「保存して反映」）。
  `expect` は省略でき、あっても形式は検証しません。
- 進み方（最初に拒否した段階で応答します）:
  1. 検証の実行枠を取得します。
     ほかのリクエストが保持していれば、503 `a check of a managed version is under way` です。
     管理プロセスが起動したときに `managed` が無かった場合は、すぐに 409 になります。
  2. ボディ、ファイル、バージョンの形式を検証します。
     拒否は 400 で、文と場所を返します。
  3. 設定ファイルを再読み込みします。
     `managed` が無いとき、`managed.dir` が起動時と違うとき、受け付けられないときは 409 です。
  4. managed ストアを開きます。
     開けなければ 500 です。
  5. バージョンとファイルを、設定ファイル、リクエストのファイル、managed ストアのファイルで検証します。
     拒否は 400 で、文と場所を返します。
     バージョンのアップストリームのエンジンに、ルールストアで選択中の世代が無いときも 400 です。
     文は `no generation is chosen for the engine of an upstream` で、`at` は最初に当たったアップストリームの `upstreams.<name>.engine` です。
     ルールストアを読めなければ 500 です。
- 応答は 200 `{"version", "detect"}` です。
  `version` は、保存した場合のバージョンの名前です。
  `detect` は、`[{"upstream", "engine"}, ..]` の形の配列です（アップストリームの並びの順。無ければ `[]`）。
  選択中の世代が検知のみのモードであるエンジンで検査するアップストリームが入ります。
  そのアップストリームでは、ルールに一致したリクエストもブロックされません。
- この API は、変更の実行権を取得しません。
  プロキシに問い合わせず、managed ストアに何も置かず、監査ログにも書きません。
  選択中のバージョンが無い managed ストア（コマンドで最初のバージョンを作成する前）でも、検証できます。
- 検証の実行枠: `check` と `apply` のバージョンの検証は、管理プロセスの中で同時に 1 つだけ実行します。
  12 MiB のボディと、managed ストアのファイルをもう一度読み込み、メモリを多く使うためです。

### 保存して反映

`POST /api/managed/apply`（operator 以上）は、バージョンを managed ストアに保存し、稼働中のプロキシに反映します。
ボディは JSON のオブジェクトで、次の 3 つのキーがどれも必要です。

| キー | 内容 |
|---|---|
| `expect` | 画面で見た選択中のバージョン（64 桁の小文字の 16 進数） |
| `version` | 保存するバージョンです。managed ストアのバージョンの形式（ファイルを SHA-256 で指定し、パスを持たない）で、書き方は問いません。保存するときは 1 つの決まった書き方にそろえ、その SHA-256 がバージョンの名前になります |
| `files` | バージョンと一緒に保存するファイル（証明書チェーン、秘密鍵、CA のファイルの PEM の文字列）の配列 |

- `files` は 192 個まで、1 つ 1 MiB までです。
  同じファイルを 2 回送ることはできません。
  送るファイルは、どれもバージョンが指定するものでなければなりません。
  バージョンが指定していて、リクエストに含まれないファイルは、managed ストアにすでにある必要があります。
- ファイルの内容は、応答、監査ログ、設定の変更履歴に書きません。

進み方（最初に拒否した段階で応答します）:

1. 検証の実行枠を取得します。
   ほかのリクエストが保持していれば 503 で、監査ログには書きません。
2. ボディを検証します。
   次のときは 400 で、監査ログには書きません。
   - JSON の形式が違うとき
   - ファイルが多すぎるか大きすぎるとき
   - バージョンの形式が違うとき（設定キーの重複、未知の設定キー、不足している設定キー、型の違い）
   - `expect` が 64 桁の小文字の 16 進数でないとき
3. 変更の実行権、設定ファイルの再読み込み、managed ストアと `expect`、プロキシの状態を順に確認します（下の「名前を指定した反映とロールバック」の 1〜4 と同じ）。
   プロキシがバージョンを受け付けられないときは、何も保存しません。
4. バージョンを、設定ファイルとファイルで検証します。`managed import` と同じ検証です。
   国のデータベースは読み込まず、反映のときにプロキシが読み込みます。
   バージョンのアップストリームのエンジンに、ルールストアで選択中の世代があることも検証します（「検証」の 5 と同じです）。
   拒否は 400 で、文と場所を返し、監査ログには書きません。
5. 監査ログに、`managed-import` の行（対象はバージョンの名前）を書きます。
   書けなければ 503 で、何も保存しません。
6. managed ストアのロックの中で、ファイルとバージョンを置きます。
   コマンドがロックを保持していれば、409 `the managed store is in use by another command` です。
   managed ストアのほかの拒否も 409 です。
   managed ストアのファイルと合わせて読み込んだバージョンが拒否されれば 400（場所なし）、設定ファイルが拒否されれば 409 です。
   どの場合も、監査ログに失敗（`store`、`version`、`configuration`）を書きます。
7. 反映の処理を始めます（下の「名前を指定した反映とロールバック」の 6）。
   保存したものの、反映の処理を始められなかったバージョンは managed ストアに残りますが、害はありません。

応答は 202 で、`version`（バージョンの名前）、`placed`（保存の結果）、`job`（始めた反映の処理）を持ちます。
`placed` は、`created`、`existing`（同じバージョンがすでにあった）、`recreated`（壊れたコピーを置き換えた）のどれかです。

### 名前を指定した反映とロールバック

`POST /api/managed/activate`（`{"expect", "version"}`）は、managed ストアのバージョンを名前で指定して、稼働中のプロキシに反映します。
`POST /api/managed/rollback`（`{"expect"}`）は、ロールバック先のバージョンを稼働中のプロキシに反映します。
どちらも operator 以上が使え、API トークンでも使えます。

- `expect` と `version` は 64 桁の小文字の 16 進数で、違うと 400 `a version is not 64 lowercase hexadecimal digits` になります。
- `expect` には、画面で見た選択中のバージョンを書きます。
  画面を見た後に、ほかのユーザーかコマンドが選択し直していれば、409 で拒否します。
  古い画面から上書きしないようにするためです。
- 選択中のバージョンが無い managed ストアでは、`expect` が合わないので反映できません。
  最初のバージョンは、コマンド（`managed import` と `managed activate`）で作成して選択します（[運用リファレンス](operator-reference.ja.md) の「managed 設定での初回起動」）。

進み方（上の「保存して反映」の 3 も同じです。最初に拒否した段階で応答します）:

1. 変更の実行権を取得します。
   管理プロセスの中で、変更は反映の処理の終わりまでを含めて 1 つずつ順に進みます。
   ほかの変更（バージョンの削除を含みます）が進んでいれば 409 `a change of the managed configuration is under way`、管理プロセスが停止中なら 503 です。
   監査ログには書きません。
2. 設定ファイルを再読み込みします。
   `managed` が無いとき（管理プロセスの起動時に無かったときも）、`managed.dir` が起動時と違うとき、受け付けられないときは 409 です。
   監査ログに拒否（`managed`、`configuration`）を書きます。
3. managed ストアを確認します。
   開けないときと、選択中のバージョンを示すファイル（`current`）を読めないときは 500 です。
   選択中のバージョンが `expect` でないとき（選択中のバージョンが無いときも）は、409 `the chosen managed version is not the one that was expected` です（監査ログに拒否、`expect`）。
   ロールバックでは、ここでロールバック先を決めます。
   ロールバック先が無ければ 409、設定の変更履歴を読めなければ 503 です（どちらも監査ログには書きません）。
4. プロキシの状態を制御ソケットで問い合わせます。
   - 接続できない: 503 `the proxy cannot be reached`。
     設定の変更履歴に `unreachable` の行を書きます（監査ログに拒否、`unreachable`）。
   - 接続を受け付けて何も応答せずに閉じる（同時接続数の上限）: 503 `the proxy is busy`（監査ログに拒否、`busy`）。
   - 稼働中の設定に `managed` が無い: 409 `the configuration in force has no managed object`（監査ログに拒否、`unmanaged`）。
5. 名前で反映とロールバックでは、バージョンが managed ストアにあることを確認します。
   無ければ、名前で反映は 404、ロールバックは 409 `the version to go back to is not in the store` です。
   あれば、バージョンのアップストリームのエンジンに、ルールストアで選択中の世代があることを確認します。
   無ければ、409 `no generation is chosen for the engine of an upstream` と `at`（最初に当たったアップストリームの `upstreams.<name>.engine`）を返し、監査ログに拒否（`engine`）を書きます。
   ルールストアを読めなければ 500 です。
   `POST /api/managed/apply` では、この段階でバージョンを保存します（上の「保存して反映」の 4〜6）。
6. 反映の処理を始めます。
   応答の時間（30 秒）の残りが 5 秒以下のときと、1 の後に管理プロセスが停止し始めたときは、503 です（監査ログに失敗、`time`、`stopping`）。
   スレッドを作成できなければ 503 です（監査ログに失敗、`thread`）。

応答は 202 で、`version`（反映するバージョン）と `job` を持ちます。

ロールバック先:

- ロールバック先は、設定の変更履歴の中で、結果が `applied` で、`from` と `to` が違う、最も新しい行の `from` です。
- ロールバックできるのは、その行の `to` が現在選択中のバージョンのときだけです。
  反映が `applied` に終わらなかった後や、コマンドでバージョンを選択した後は、履歴の終わりが選択中のバージョンと合わないため、ロールバックできません。
  応答は 409 `the history does not end at the chosen version` になります。
  `applied` の行が無いときは、409 `there is no change to go back from` になります。
- ロールバックも履歴に `rollback` として入ります。
  続けてもう一度ロールバックすると、元のバージョンに戻ります。

### 反映の処理

変更（「保存して反映」「名前で反映」「ロールバック」）は、上の段階を通るとすぐに 202 で応答します。
反映そのものは、管理プロセスの中で反映の処理（`job`）として続きます。
反映には、1 つの応答を待てる時間より長くかかることがあるためです。
どう終わったかは、`GET /api/managed/job`（viewer 以上。`{"job"}` を返し、無ければ `null`）か、`GET /api/managed` の `job` で確認します。

- 管理プロセスが保持する反映の処理は、最後の 1 つだけです。
  メモリにだけあるので、管理プロセスを再起動すると失われます。
  動作中の反映の処理は、管理プロセスと一緒に終了し、managed ストアのロックもプロセスと一緒に解放されます。
- 反映の処理はキャンセルできず、依頼したユーザーのロールが変わっても止まりません。
- 反映の処理は終わるまで変更の実行権を保持するので、その間、ほかの変更とバージョンの削除は 409 になります。
- 反映の順序（managed ストアのロック、プロキシへのリロードの依頼、選択中のバージョンを進める順序）と、途中で停止したときの扱いは、[運用リファレンス](operator-reference.ja.md) の「反映」を参照してください。
  管理プロセスが制御ソケットで待つ時間は、上の「制御ソケット」を参照してください。

| キー | 内容 |
|---|---|
| `kind` | `apply`（保存して反映）、`activate`（名前で反映）、`rollback` |
| `actor` | 依頼したユーザーの名前 |
| `from`、`to` | 変更前（`expect`）と変更後のバージョン |
| `started`、`ended` | 始めた時刻と終わった時刻（エポックからの秒数）。動作中は `ended` が `null` です |
| `state` | `running`（反映中）か `ended` |
| `result` | 終わり方（下の表）。動作中は `null` です |
| `reason` | 決まった語です。プロキシのどの部分が拒否したか（`configuration`、`version`、`store`、`upstream`、`tls`、`fixed`、`listener`、`thread`）、`busy` の理由（`store in use`、`proxy busy`、`reload under way`、`starting`、`too many orders`、`stopping`）、`error` の理由、`not recorded` の理由（`current changed`、`store`）が入ります |
| `detail` | プロキシが拒否したときの文か、managed ストアの文 |
| `config_before`、`config_after` | 反映の前と後に使われていた設定ファイルの SHA-256。分かるときだけ |
| `history` | 設定の変更履歴に行が書き込まれたかどうか。行を書かない終わり方では `null` |

| `result` | 意味 | 監査ログ | 設定の変更履歴 |
|---|---|---|---|
| `applied` | プロキシが変更後のバージョンで稼働し、managed ストアで変更後のバージョンが選択されました | 変更の前に書いた `ok` の行 | 行を書きます |
| `refused` | プロキシが拒否し、何も変更されていません | 失敗 | 行を書きます |
| `busy` | managed ストアかプロキシが使用中で、何も変更されていません | 変更の前の行より前なら拒否、後なら失敗 | 後なら行を書きます |
| `current changed` | 選択中のバージョンが `expect` ではなくなっていました | 拒否 | 書きません |
| `no version` | バージョンが managed ストアにありません | 拒否 | 書きません |
| `unmanaged` | 稼働中のプロキシの設定に `managed` がありません | 拒否 | 書きません |
| `store` | managed ストアのロックを取得できない、選択中のバージョンを示すファイル（`current`）が無いか読めない、など | 拒否 | 書きません |
| `audit` | 変更前の監査ログの行を書けず、何も変更されていません | − | 書きません |
| `error` | プロキシが依頼を受け付けませんでした（`unknown op` は、制御ソケットの `reload` に対応していない古いプロキシ） | 失敗 | 行を書きます |
| `unreachable` | プロキシに接続できませんでした | 拒否 | 行を書きます |
| `failed` | プロキシは変更後のバージョンに切り替わりませんでした | 失敗 | 行を書きます |
| `unconfirmed` | 結果を確認できませんでした | 失敗 | 行を書きます |
| `not recorded` | プロキシは変更後のバージョンに切り替わりましたが、managed ストアで選択されませんでした（`current changed`: 選択中のバージョンが手作業で変更された、`store`: 選択中のバージョンを示すファイル（`current`）を書けない） | 失敗 | 行を書きます |

- `refused` の `reason` が `fixed` になるのは、次の 2 つの場合です。
  - 動作中に変更できない設定キーが違うとき。
    `detail` は `<key> cannot change while running` です。
  - バージョンのアップストリームのエンジンが、プロキシで稼働していないとき（起動中を含みます）。
    `detail` は `the engine of an upstream is not ready (upstream <name>)` です。

  稼働していないエンジンは、先に起動してからもう一度反映します。
  起動には、「ルールの世代」の画面の「エンジンを起動する」か、SIGUSR1 を使います（[運用リファレンス](operator-reference.ja.md) の「エンジンごとの選択中の世代」）。
- 監査ログの `ok` の行は、変更の前に書きます。
  `from` と `to` は `before` と `after` に書きます。
  設定ファイルの SHA-256 は、監査ログではなく、設定の変更履歴に書きます。
  `ok` の行は成功を示す行ではありません。
  どう終わったかは、後に続く行と設定の変更履歴で確認します。
- 設定の変更履歴に行を書き込めなかったときは、監査ログに失敗（`history`）を書きます。
- 反映の処理が途中で異常終了したときは `unconfirmed` になり、管理プロセスがログに 1 行を書きます。
- `unconfirmed` と `not recorded` の後は、選択中のバージョンと稼働中のバージョンが違うことがあります。
  `GET /api/managed` の `current` と `serving` で確認し、違っていれば、どちらかのバージョンをもう一度反映します。

### バージョンの削除

`DELETE /api/managed/versions/<version>`（operator 以上、API トークン可、ボディなし）は、バージョンを managed ストアから削除します。
削除は元に戻せません。
どのバージョンからも指定されなくなったファイルと ACME の証明書も、一緒に片付けます（片付けで削除されるものは、[運用リファレンス](operator-reference.ja.md) の「バージョンの削除」）。

進み方（最初に拒否した段階で応答します）:

1. 名前が 64 桁の小文字の 16 進数でなければ、404 です。
2. 変更の実行権を取得します（反映の処理も、この実行権を保持します）。
   ほかの変更が進んでいれば 409、管理プロセスが停止中なら 503 で、監査ログには書きません。
3. 設定ファイルを再読み込みします。
   `managed` が無いとき、`managed.dir` が起動時と違うとき、受け付けられないときは 409 です（監査ログに拒否、`managed`、`configuration`）。
4. managed ストアを開けなければ 500 です。
5. managed ストアの一覧に無いバージョンは 404 です。
6. 選択中のバージョンは削除しません（409、監査ログに拒否、`chosen`）。
7. ロールバック先のバージョンは削除しません（409、監査ログに拒否、`rollback target`）。
   設定の変更履歴を読めなければ 503 です。
8. 監査ログに、`managed-remove` の行（対象はバージョンの名前）を書きます。
   書けなければ 503 で、削除しません。
9. managed ストアから削除します。
   拒否されたときは、409 と managed ストアの文を返します（監査ログに失敗、`store`）。

| バージョン | `error` |
|---|---|
| 選択中のバージョン | `the version is the one the managed store chooses` |
| ロールバック先のバージョン | `the version is the target of a rollback` |
| 使用中のバージョン（どれが使用中かは [運用リファレンス](operator-reference.ja.md) の「バージョンの削除」） | `the managed version is in use` |

- 成功すると、200 `{"removed", "cleaned"}` を返します。
  `removed` は削除したバージョンの名前、`cleaned` は片付けを終えたかどうかの真偽値です。
  `cleaned` が `false` なら、片付けを終えられなかったことを示します（ほかのバージョンを読めなかった、など）。
  その場合も削除は取り消さず、次の削除のときに、もう一度片付けます。
- プロキシには問い合わせません。
  使用中のバージョンは managed ストアで拒否されます。
- 削除では、ほかのバージョンを 1 つずつ読み込むので、バージョンが多いほど時間がかかります。
  応答が間に合わないと 503 になりますが、削除はそのまま完了することがあります。
- 設定の変更履歴には行を書きません。
  削除したバージョンを指定している行は、そのまま残ります。

## 切り替えの履歴

`GET /api/history`（viewer 以上、API トークン可）は、世代の選択とロールバックの履歴を新しい順に 200 行まで `{"entries": [...]}` で返します。

| 項目 | 内容 |
|---|---|
| `ts` | 時刻（UTC の RFC 3339 で、ms まで） |
| `actor` | 切り替えを依頼したユーザーの名前 |
| `from` | 依頼の前に、`to` の世代が属するエンジンで、ルールストアが選択していた世代（無かったときは `to` と同じ） |
| `to` | 依頼した世代（ロールバックでは、ロールバック先） |
| `kind` | `activate`、`rollback` |
| `result` | 結果の語（下の注） |
| `engine` | `to` の世代のエンジン（`coraza` か `modsecurity`）。以前のバージョンの管理プロセスが書いた行では `null` |

`result` は、「選択とロールバック」の応答の `result`（`switched`、`unchanged`、`refused`、`failed`、`unreachable`、`unconfirmed`）と同じ 6 つで、意味も同じです。

- 履歴は `admin.store.dir` の `activations.log` に追記します。
  エンジンごとには分けず、1 つのファイルです。
  1 行を書き終えて同期してから応答します。
  ローテーションはせず、削除もされません。
  読み戻すのは終わりの 1 MiB（約 4000 行）までで、それより古い行は、ロールバック先を決めるのにも使われません。
- 入るのは管理画面と管理 API で依頼した切り替えだけで、コマンド（`rules activate`）と SIGUSR1 による選択と切り替えは入りません。
- 履歴に書くのは、プロキシに接続できなかったときと、監査ログの行を書いた後の結果（ルールストアで選択が拒否されたときと、プロキシの応答）だけです。
  次のときは書きません。
  - 入力のエラー
  - 世代が無い
  - ロールバック先が決まらない
  - ほかの変更が進んでいる
  - `expect` が古い
  - プロキシが同時接続数の上限のために状態の問い合わせに応答しなかった
  - 監査ログの行を書けなかった

## 設定の変更履歴

`GET /api/managed/history`（viewer 以上、API トークン可）は、managed 設定の変更（「保存して反映」「名前で反映」「ロールバック」）の履歴を新しい順に 200 行まで `{"entries": [...]}` で返します。

| 項目 | 内容 |
|---|---|
| `ts` | 時刻（UTC の RFC 3339 で、ms まで） |
| `actor` | 変更を依頼したユーザーの名前 |
| `kind` | `apply`、`activate`、`rollback` |
| `from` | 依頼のときに、managed ストアで選択中だったバージョン |
| `to` | 依頼したバージョン（ロールバックでは、ロールバック先） |
| `result` | 結果の語（下の注） |
| `reason` | 決まった語。無ければ `null` |
| `config_before`、`config_after` | 反映の前と後に使われていた設定ファイルの SHA-256。無ければ `null` |

`result` は、`applied`、`refused`、`busy`、`error`、`failed`、`unconfirmed`、`not recorded`、`unreachable` の 8 つで、意味は「managed 設定の操作」の「反映の処理」の表と同じです。
`reason` も、反映の処理の `reason` と同じ語です。

- 履歴は `admin.store.dir` の `managed.log` に、1 行 1 件の JSON で追記します。
  1 行を書き終えて同期します。
  ローテーションはせず、削除もされません。
  読み戻すのは終わりの 1 MiB までで、それより古い行は、ロールバック先を決めるのにも使われません。
  決まった形式に合わない行は除きます。
- 入るのは管理画面と管理 API で依頼した変更だけで、コマンド（`managed activate`）による選択と、SIGHUP による反映は入りません。
- 行を書くのは、プロキシに接続できなかったとき（`unreachable`）と、変更前の監査ログの行を書いた後の終わり方だけです（「反映の処理」の表）。
  次のときは書きません。
  - 入力のエラー
  - ほかの変更が進んでいる
  - `expect` が古い
  - ロールバック先が決まらない
  - プロキシが同時接続数の上限のために問い合わせに応答しなかった
  - 監査ログの行を書けなかった
- プロキシと managed ストアの文は履歴には書かず、反映の処理の `detail` にだけあります。
- 行を書けなかったときは、反映の処理の `history` が `false` になり、監査ログに失敗（`history`）を書きます。
- 管理プロセスが起動したときに `managed` が無かった場合は 409、履歴を読めない場合は 503 になります。

## ログの読み出し

`GET /api/records`（viewer 以上、API トークン可）は、`records.dir` のファイルを新しい行から順に読み、条件に合う行を返します。
行は書かれたままの JSON のオブジェクトです。
リクエストから来た文字（`path` など）は、`%XX` の形のままです（[運用リファレンス](operator-reference.ja.md) の「ログ」）。
キーの順序は変わることがあります。

条件はクエリで指定します。
どの条件も 1 回までで、値は `%XX` で書けます（デコードした後で 128 バイトまで）。
条件の形式は次のとおりです。

| 条件 | 形式 |
|---|---|
| `from`、`to` | 開始と終了の時刻。UTC の RFC 3339 で、`Z` で終わります。秒の小数は 9 桁まで（ミリ秒に切り捨てます）か、なし |
| `type` | `request`、`connection`、`tunnel`、`line`、`audit`、`dropped` |
| `class` | リクエストのログの結果（1〜32 文字の小文字・数字・`_`・`-`） |
| `status` | ステータスコード（1〜3 桁の数字） |
| `rule` | ルール ID。判定したルールか、ほかに一致したルールの中にあるもの |
| `id` | リクエスト ID |
| `client` | IP アドレス |
| `generation` | 世代のフィンガープリント。先頭 16 桁か 64 桁（ログには先頭 16 桁だけがあります） |
| `engine` | リクエストを検査したエンジン。`coraza` か `modsecurity`（小文字だけ）。`engine` を持たないログ（検査除外のルートを通ったリクエストなど）は、この条件に合いません |
| `file`、`offset`、`inode` | 続きの位置。3 つがそろったときだけ使えます |

- `audit` のログは、管理プロセスの標準エラーと、監査ログの保存先に出力されます。
  プロキシのログファイルには入らないので、`type=audit` で検索しても、このファイルからは見つかりません。
  監査ログは `GET /api/audit` で読みます。
- 1 回に返すのは 500 行まで、読み込むのは 256 MiB までです。
  どちらかに達したときにまだログが残っていれば、応答の `next` に続きの位置が入ります。
  条件に合う行を見つける前に、読み込む量の上限で止まったときは、`records` が空でも `next` が入ります。
  `next` が `null` になるまで、続けて読んでください。
- 応答は `{"records": [..], "next": null か {"file", "offset", "inode"}}` です。`inode` は文字列で返します。
  続きを読むには、同じ条件に `next` の 3 つの値を加えます。
- 続きの位置は、ファイルの番号、ファイルの中の位置、ファイルの inode で決まります。
  ログファイルのローテーションで番号が変わっても、inode でファイルを探します。
  ファイルがローテーションで削除されたとき、または位置が行の終わりでなくなったときは、409 `the continuation names no place in the record files any more` になります。
  その場合は、最初から読み直します。
- 新しい行から順に読み、`from` より古い行に当たったところで読み込みを終えます。
  書き込みの途中で改行が無い最後の行、`ts` を持たない行、長すぎる行は返しません。
- 失敗:
  - 設定に `records` が無い: 404 `records are not configured`
  - 条件のエラー（未知の条件、同じ条件が 2 回、値の形式のエラー、続きの位置の 3 つがそろわない）: 400。文は決まった英語の 1 文
  - ログファイルのディレクトリが、所有者と権限の検証に通らない: 503。文は検証の文
  - ファイルを読めない: 503 `unavailable`

## 管理画面

管理画面は管理プロセスが提供します。
ブラウザーで `https://admin.example.com/`（`admin.origin`）を開きます。

- 画面のファイルは `proxy/admin-ui/` にあり、実行ファイルに組み込むので、管理プロセスと管理画面はいつも同じバージョンです。
  ホストのファイルは読み込みません。
- 提供するパスは、`GET /`（ページ）と `GET /ui/<ui-version>/<name>` だけです。
  後者で提供するファイルは、スタイルシート、アイコン、34 個のスクリプトの、合わせて 36 個です。
  スクリプトの名前は、`proxy/admin-ui/js/` からのパスです（`js/app.js` は `/ui/<ui-version>/app.js`、`js/waf/waf.js` は `/ui/<ui-version>/waf/waf.js`）。
  ファイルに秘密は含まれないので、セッションは不要です。
- パスの `<ui-version>` は、36 個のファイルの名前と内容から作る、16 桁の小文字の 16 進数です。
  ファイルごとに名前と SHA-256 を並べた一覧を作り、その一覧の SHA-256 の先頭 16 桁を使います。
  `<ui-version>` はページかファイルへの最初のリクエストが来たときに 1 回だけ作ります。
  ページを提供するときは、ページの中の `/ui/` を `/ui/<ui-version>/` に置き換えます。
  ファイルの内容が変わらなければ、`<ui-version>` も変わりません。
- `<ui-version>` の無い `/ui/<name>`、`<ui-version>` が違うパス、36 個に無い名前は、どれも API の表に回って 404 になります。
  ページと、`<ui-version>` の下のファイルに、`GET` と `HEAD` 以外のメソッドを送ると、405（`Allow: GET, HEAD`）になります。
- ページとファイルの応答のヘッダー:

| ヘッダー | 値 |
|---|---|
| `Cache-Control` | ページは `no-store`。`<ui-version>` の下のファイルは `public, max-age=31536000, immutable` |
| `X-Content-Type-Options` | `nosniff` |
| `Content-Security-Policy` | `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'` |
| `Referrer-Policy` | `same-origin` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Cross-Origin-Resource-Policy` | `same-origin` |
| `Permissions-Policy` | `accelerometer=(), camera=(), geolocation=(), gyroscope=(), magnetometer=(), microphone=(), payment=(), usb=()` |

- ページは毎回読み込まれ、その時点の `<ui-version>` のパスでファイルを指定します。
  `<ui-version>` の下のファイルは内容が変わらないので、ブラウザーは 1 年までキャッシュを使います。
  画面のファイルが変わった実行ファイルで管理プロセスを再起動すると、`<ui-version>` が変わります。
  ブラウザーが新しいパスのファイルを読み込むのは、そのときだけです。
- 画面のスクリプトは、文字列からマークアップを作成できません（Trusted Types）。
  画面ができるのは、自分のスクリプト、スタイル、アイコンを読み込むことと、自分の API を呼び出すことだけです。
- API の応答の `Referrer-Policy` は `no-referrer`、画面のファイルの応答は `same-origin` です。

言語と保存:

- 言語は日本語と英語です。
  選択した言語が保存されていれば、その言語を使います。
  無ければブラウザーの言語を使い、`ja` で始まれば日本語、`en` で始まれば英語です。
  どちらでもなければ、英語を使います。
  言語は画面上部の帯で切り替えられます。
- テーマ（自動、ライト、ダーク）と、時刻の表示方法（ローカルか UTC）も、画面上部の帯で選べます。
  ブラウザーのストレージ（`localStorage`）に保存するのは、言語、テーマ、時刻の表示方法の 3 つだけです。
- パスワード、認証コード、リカバリーコード、API トークン、CSRF トークン、二要素認証のセットアップキー、managed 設定の下書き（下の「下書き」）は、どれも画面のメモリにだけ置きます。
  一度しか返さないもの（リカバリーコード、API トークン、設定中のセットアップキー）も、画面を離れると破棄します。
  ただし、二要素認証の設定を確定した応答が画面を離れた後に届いたときは、そのリカバリーコードを次の画面に表示するまで保持します。
  ログアウトしたときやセッションが終了したときは、どれも破棄します。
  URL と履歴にも入れません。
- 言語、テーマ、時刻の表示方法を切り替えても、画面は再描画せず、文字だけを置き換えます。
  入力した文字、選択したファイル、絞り込みは、そのまま残ります。
- 二要素認証の QR コードは、画面の中で描画します（外部には何も送信しません）。

使える画面はロールで決まります。
メニューは画面を 7 つのまとまり（下の表の「メニュー」の列）に分けて並べ、ロールで使える画面だけを表示します。

| メニュー | 画面 | ロール | 内容 |
|---|---|---|---|
| （名前なし） | 概要 | viewer 以上 | プロキシの数、プロキシの状態（全部のエンジンの準備ができているか、世代の切り替え中か）、エンジンごとの世代の状態、現在の設定ファイルの SHA-256 を表示します。プロキシの数は「リクエスト」「ブロック」「ポリシーで拒否」「アップストリームのエラー」「設定のリロード」の 5 つです。数の内容は、上の「一覧と内容」の `GET /api/status` を参照してください。「リクエスト」の下には起動からの時間を添えます。エンジンごとの枠には、エンジンの名前（デフォルトのエンジンにはラベル「デフォルト」）、検査カーネルの段階、選択中の世代、稼働中の世代、モード、ロールバック先と、2 つの世代がどうなっているかの文を表示します。選択中の世代があるのにプロキシで稼働していないエンジンには、ラベル「未起動」と、ルールの世代の画面でエンジンを起動するよう促す文（「このエンジンには選択中の世代がありますが、プロキシで稼働していません。ルールの世代の画面で、エンジンを起動してください。」）を表示します。選択中の世代も稼働中の世代も無く、デフォルトのエンジンでもないエンジンは、表示しません。切り替えの途中ではないのに、どれかのエンジンで 2 つの世代が違うときと、選択中の世代があるのにそのエンジンが稼働していないときは、画面上部の帯に警告を表示します。切り替えの途中のときは、概要の画面にその旨だけを表示します。managed 設定を使っているときは、「managed 設定」の枠に、選択中のバージョンと稼働中のバージョン、2 つが「一致」か「不一致」かを表示します。反映の処理の間は、「一致」「不一致」の代わりに「反映中」と表示します。「設定のバージョンを開く」で、設定のバージョンの画面へ移れます |
| WAF | ルールの世代 | viewer 以上 | 世代の一覧と詳細（ファイル、読み込む順、検査除外のルート）を表示します。operator 以上は、世代のエンジンごとに、選択、プロキシの切り替え、エンジンの起動、削除ができます。選択は「この世代に切り替える」で行います。選択中の世代にプロキシが追い付いていないときは、「プロキシに反映する」で切り替えます。選択中の世代があるエンジンがプロキシで稼働していないときは、「エンジンを起動する」で起動します。マニフェストが読めず、エンジンが分からない世代には、選択と起動のボタンを表示しません。どのエンジンでも、選択中の世代、稼働中の世代、ロールバック先は削除できません |
| WAF | ルールのインポート | operator 以上 | ブラウザーでファイルを選択し、検査エンジン（Coraza か ModSecurity）、CRS の使用と使わないファイル、検査除外のルート、検知のみを指定してインポートします。検査エンジンの初期値はデフォルトのエンジンで、デフォルトのエンジンが分からないときは Coraza です。検査除外のルートは、1 行に 1 つずつ、ホスト（省略できます）とパスを書きます。説明には、「管理画面へのリクエストは、managed のある設定ファイルではデフォルトのエンジンで検査されます。managed の無い設定ファイルでは、管理プロセスへ転送するアップストリームのエンジンで検査されます。インポートのリクエストが検査でブロックされるときは、そのエンジンの世代に、検査除外のルートを入れてください。」と表示します。アクションはいつも `bypass` で、送信するボディの `routes` は、`--routes` のファイルと同じ形式の JSON です。ホストだけの行はエラーとして表示し、何も書かない行は送信しません。上限はブラウザーでも数えます。事前検証でブロックされたときは、確認を経て「ブロックを受け入れてインポートする」ができます。新しい世代は選択されません |
| WAF | 切り替え履歴 | viewer 以上 | 切り替えの履歴と、エンジンごとのロールバック先を表示します。履歴は新しい順に 200 件までで、画面にもそう書かれています。列「エンジン」は、`engine` の無い古い行では「—」です。operator 以上は、ロールバック先があるエンジンごとに、「前の世代にロールバックする」ができます |
| ログ | アクセスログ | viewer 以上 | 条件を指定して、ログを検索します。条件「エンジン」（指定しない、Coraza、ModSecurity）で、検査したエンジンを絞り込めます。リクエストから来た文字は、`%XX` の形のまま表示します。リクエスト ID を持つログは、行の内容（メソッドとホストとパスなど）を押すと、詳細が開きます。リクエスト ID は、内容の `title` 属性と、詳細の「すべての欄」と「JSON」に出ます。リクエスト ID を持たないログ（接続や、プロキシの文の行など）は、行の「詳細」で開きます。詳細では、まず要点（結果の `class`・`status`・`reason`、ルール、`score`、時刻、クライアント、メソッドとホストとパス、世代、エンジン）を表示し、その下に、折りたたんだ「すべての欄」と「JSON」を置きます。「すべての欄」で「URL デコードした文字も表示する」を選択すると、デコードした文字も表示します |
| ログ | 監査ログ | operator 以上 | 最新の 200 件を新しい順に表示します（画面にもそう書かれています）。リクエスト ID が、プロキシと管理プロセスが付与する形式のときは、その ID からアクセスログを開けます |
| プロキシ | サイト | operator 以上 | managed 設定の下書きで、サイトの一覧を表示し、編集します（名前、ホスト、証明書）。証明書は、証明書チェーンと秘密鍵のファイルか ACME です。一覧と編集の枠には、managed ストアにある証明書の有効期限、状態、証明書に含まれるホスト名を表示します（上の「証明書の情報」） |
| プロキシ | アップストリーム | operator 以上 | 下書きで、デフォルトのアップストリームを編集し、アップストリームの一覧を表示して編集します（エンジン、サーバー、TLS と CA のファイル）。エンジンは、「デフォルトのエンジン（Coraza）」（かっこの中は、デフォルトのエンジンの名前）、「Coraza」、「ModSecurity」から選びます。選択肢の説明は、[運用リファレンス](operator-reference.ja.md) の「ModSecurity の世代」を案内しています。一覧の列「エンジン」には、検査するエンジンを表示します。デフォルトのエンジンに従うアップストリームには、「（デフォルトのエンジン）」を添えます。保存の前に、選んだエンジンに選択中の世代が無いとき、プロキシで稼働していないとき、起動中のとき、ModSecurity の検査プロセスが設定ファイルの `kernel.engines` に無いときは、その旨の注意を表示します |
| プロキシ | ルート | operator 以上 | 下書きで、ルートの一覧を表示し、編集します（ホスト、パスか正規表現、優先度、アップストリーム。下の「ルートの画面」を参照してください）。アクセス制御、ストリーミング応答、書き換えは、折りたたんだ部分にあります。読み込むのは 1024 本までです |
| ポリシー | アクセス制御とレート制限 | operator 以上 | 下書きで、全体のアクセス制御とレート制限を編集し、ホストごとの設定の一覧を表示して編集します（下の「ホストごとの設定の画面」） |
| 設定 | 設定のバージョン | viewer 以上 | 選択中のバージョンと稼働中のバージョン、プロキシの状態、反映の状況、バージョンの一覧を表示します（下の「managed 設定の画面」）。operator 以上は、バージョンの内容（JSON と証明書）を表示でき、名前で反映、削除、下書きの作成もできます。選択中のバージョン、稼働中のバージョン、ロールバック先は削除できません |
| 設定 | 設定の変更履歴 | viewer 以上 | 設定の変更履歴とロールバック先を表示します。履歴は新しい順に 200 件までで、画面にもそう書かれています。反映の前と後で設定ファイルが違う行には、「変更あり」を表示します。operator 以上は、「前のバージョンにロールバックする」ができます |
| 設定 | 設定ファイル | operator 以上 | 設定ファイルの現在の値（上の「設定ファイルの値」）を表示します。この画面では変更できません。パスは表示せず、書かれていれば true、書かれていなければ「—」と表示します。稼働中のプロキシとの比較も、「一致」か「不一致（リロード待ち）」で表示します |
| 管理 | アカウント | viewer 以上 | パスワードの変更、二要素認証の設定と無効化、API トークンの作成と削除 |
| 管理 | ユーザー | owner | ユーザーの一覧、作成、ロールの変更、無効・有効、パスワードと二要素認証の初期化、全員の API トークンの一覧と削除 |

- 概要の数をプロキシから得られないときは、数の代わりに「—」と短い語を表示し、0 と区別します。
  その理由は次のどれかで、プロキシの枠に 1 回だけ表示します。
  - プロキシに接続できない（`reachable` が `false`）
  - プロキシが処理中（`proxy` が `null`）
  - そのプロキシが数を返さない（以前のバージョンのプロキシで、値が `null`）

  設定ファイルの SHA-256 も同じです。
- エンジンごとの表示では次の注意を表示します。
  - 管理プロセスとプロキシで、デフォルトのエンジンが違うとき（片方だけを再起動したとき）は、デフォルトのラベルを出しません。
    概要、ルールのインポート、アップストリームの画面に、「管理プロセスとプロキシで、デフォルトのエンジンが違います。両方を再起動してそろえてください。」と表示します。
  - 以前のバージョンのプロキシ（`engines` を返さないもの）では、概要、ルールの世代、切り替え履歴の画面に「このプロキシはエンジンごとの状態を返しません。管理プロセスとプロキシを同じビルドにそろえてください。」と表示します。
    世代の選択、プロキシへの反映、エンジンの起動、ロールバックのボタンは表示しません（[運用リファレンス](operator-reference.ja.md) の「バージョンの更新」）。
- 世代の選択、ロールバック、削除では、先に確認を表示します。
  確認では、「現在」と「切り替え後」（ロールバックでは「ロールバック後」、削除では「削除後」）の世代を表に並べます。
  表の項目はフィンガープリント（先頭 12 桁）、モード、エンジン、検査除外のルート数で、変わる値を太字にします。
  - 選択の「現在」は選択中の世代、「切り替え後」は選択する世代です。
    プロキシが選択中の世代と違う世代を使っているときは、その世代も表示します。
  - ロールバックの「ロールバック後」は、ロールバック先です。
    削除の「削除後」は、どれも「なし」です。
  - 分からない値は「—」になります。
  - プロキシで稼働していないエンジンの確認では、そのエンジンを起動することも表示し、「このエンジンは、プロキシを再起動した後も起動します。稼働中に失敗すると、プロキシ全体が停止します。使わなくなったら、rules deactivate コマンドで選択を解除してください。」を添えます（[運用リファレンス](operator-reference.ja.md) の「エンジンごとの選択中の世代」）。
    これには、そのエンジンに選択中の世代が無いときの最初の選択、選択中の世代での起動、ロールバックを含みます。
  - インポートは確認なしで送信します。
    確認を表示するのは、事前検証のブロックを受け入れてインポートし直すときだけです。
  - 実行中は、ほかの変更を始められません。
- 結果が分からないとき（ボディに `result` が無い 502 と 504、接続が切れたとき）は、次のものを再読み込みして表示します。
  - 世代の選択とロールバック: 行き先のエンジンの状態と履歴
  - インポート: 世代の一覧の新しい方から 3 つ
  - 削除: 世代の一覧

  managed 設定の変更で、変更が始まったかどうか分からないときは、「結果不明」として状態を再読み込みして表示します。
- 画面は時間をおいて自分から再読み込みすることはありません。
  画面から変更したときは、それに関わる表示を再読み込みします。
  最新にするには「再読み込み」を使います（インポートの画面にはありません）。
- 例外は managed 設定の反映の処理です。
  反映の処理が終わるまで、画面は前の応答の 1 秒後に `GET /api/managed/job` を読んで、状態を確認し続けます。
  読めない応答が 3 回続くか、反映の処理にかかる可能性のある時間を過ぎると、確認をやめて、その旨を表示します。
  確認の間はリクエストのたびにセッションが使われたことになるので、セッションは `admin.session_idle_ms` では終了しません。`admin.session_total_ms` では終了します。
  プロキシを通して使っているときは、ログの残し方が `security` でなければ、確認の 1 回ごとにプロキシのログに 1 行が入ります。
- 一覧の表では、並べ替えられる列の名前を押すと、その列で並べ替えます。
  押すたびに昇順と降順が切り替わり、値の無い行は後ろに来ます。
  表の上の欄に語を入力すると、セルに見えている文字がその語をすべて含む行に絞り込みます。
  語は空白で区切り、大文字と小文字は区別しません。
  操作のボタンの列は対象にしません。
  行は 50 行ずつのページに分け、「前へ」と「次へ」で進みます。
  並べ替えと絞り込みは、画面が読み込んだ行の中だけで行います。
  世代に含まれる検査除外のルートの表のように、絞り込みの欄が無い小さな表もあります。
- アクセスログは、`GET /api/records` の 1 回の応答（500 行まで）を 50 行ずつのページで表示します。
  応答に続き（`next`）があれば、最後のページの「次へ」で、続きの古いログを読み込みます。
  最初のページの「前へ」では、前に読み込んだ新しい方に戻ります。
  続きの位置は URL に入らないので、URL を開き直すと最初から読み込みます。
- 画面の場所は、URL の `#` の後に入ります。
  基本の形は `#/<screen>`（`overview`、`generations`、`import`、`history`、`records`、`audit`、`sites`、`upstreams`、`routes`、`policy`、`managed`、`managed-history`、`config`、`account`、`users`）です。
  そのほか、世代の詳細は `#/generations/<fingerprint>`、バージョンの内容は `#/managed/<version>`、ログの 1 件は `#/records/<id>`、ログの検索は `#/records?<key>=<value>` です（条件の名前は `GET /api/records` と同じで、続きの位置は除きます）。
  移動するたびにブラウザーの履歴に入るので、ブラウザーの戻る操作と進む操作で行き来できます。
  URL を開き直しても、同じ画面になります。
- URL の中の値は、使う前に形式を検証します。
  形式の違う値、画面が認識しない条件、余分な部分は使わずに URL から取り除き、「アドレスの正しくない部分を取り除きました。」と表示します。
  未知の画面と、ロールで使えない画面では、概要を開きます。
  ログの 1 件は、読み込んだ行に無ければ、そのリクエスト ID を条件にして読み出します。
  見つからなければ、その旨を表示します。
- 時刻は 1 つの表示方法で表示します。
  初期状態はローカルの時刻で、`2026-11-04 16:33:56（JST）` の形です。
  括弧の中は、ブラウザーが返すタイムゾーンの短い名前で、`JST` や `GMT+8` などになります。
  画面上部の帯の「時刻」で、UTC（`（UTC）`）に切り替えられます。
  表では、タイムゾーンの名前を列の名前に 1 回だけ書き（`時刻（JST）` など）、セルには書きません。
  夏時間などで列の名前と違うタイムゾーンになる時刻だけは、セルにもタイムゾーンを書きます。
  もう一方の表示方法の時刻は、その時刻の `title` 属性（ポインターを重ねると表示される文字）に表示されます。
  ログの検索の `from` と `to` は、この切り替えに関わらず、UTC の RFC 3339（`Z` で終わる）で書きます。
- ログインした後、パスワード変更待ちや二要素認証の設定待ちのときは、その画面だけを表示します。
- 画面はブラウザーの `fetch` で管理 API を呼び出します。
  API の応答の文（`error`）は、画面が言語ごとの文に置き換えます。
- 応答に `error` の文が無い失敗（手前に置いたプロキシがルールでブロックしたリクエストの 403、プロキシが管理プロセスに接続できなかった 502 など）では、画面は失敗の文の後に、応答の `X-Request-ID` にあるリクエスト ID を表示します。
  その ID で「アクセスログ」の画面を検索すると、ブロックしたルールなどが分かります（上の「管理画面の Host での CRS の調整」）。
  ID を表示するのは、プロキシと管理プロセスが付与する形式のときだけです。

managed 設定の画面:

- 管理プロセスが managed 設定なしで起動しているときは、設定のバージョンの画面と編集の画面に、managed 設定でできることと、使い始めるまでの手順の要点を表示します。
  手順は、[運用リファレンス](operator-reference.ja.md) の「managed 設定への移行」に従います。
- 設定のバージョンの画面は、選択中のバージョン、稼働中のバージョン、プロキシの状態（「接続可」「接続不可」「プロキシが処理中」「managed 設定は未使用」「リロード中」）を表示します。
  2 つのバージョンが違うときは、その通知を表示します。
  operator 以上には、「選択中のバージョンをもう一度反映する」と「稼働中のバージョンを選択し直す」の 2 つの操作も表示します。
  前者はプロキシを選択中のバージョンに切り替え、後者は稼働中のバージョンを名前で反映して選択中のバージョンにします。
- 設定ファイルが、稼働中のプロキシが読み込んだ内容と違うとき（`GET /api/config` の `sha256` が `/api/status` の `proxy.config` と違う）は、その旨を表示します。
  この画面から反映すると、設定ファイルの変更も一緒に反映されます。
  設定ファイルにエラーがあると、反映は拒否されます。
- 名前で反映（「このバージョンを反映する」）、ロールバック、2 つのバージョンをそろえる操作、削除（「このバージョンを削除する」）では、先に確認を表示します。
  確認では、「現在」と「反映後」（削除では「削除後」）のバージョンを表に並べます。
  表の項目はサイト数、アップストリーム数、エンジンごとのアップストリーム数、ルート数、デフォルトのアップストリーム、全体のアクセス制御、全体のレート制限、ホストごとの設定数です。
  エンジンごとのアップストリーム数は、「Coraza のアップストリーム数」と「ModSecurity のアップストリーム数」です。
  デフォルトのエンジンが分からないときは、「エンジンを指定したアップストリーム数」の 1 行になります。
  反映では、「各サーバーのダウン判定と、アップストリームの失敗回数はリセットされます。」も表示します。
  名前で反映、ロールバック、2 つのバージョンをそろえる操作では、「反映後」の値にラベル「現在 検知のみ」を添えることがあります。
  添えるのは、検知のみのモードの世代が稼働しているエンジンがあり、反映後のバージョンにそのエンジンのアップストリームがあるときです。
- 変更を送信すると、反映の処理が終わるまで「反映中」と表示します。
  終わると、結果（「反映済み」「拒否」「使用中」など）と、起きたこと、次にすることを表示します。
  プロキシが反映を `fixed` で拒否したときは、「稼働中は変更できない設定キーが変更されているか、アップストリームのエンジンがプロキシで稼働していません。」と表示します。
  次にすることとして、「エンジンが稼働していないときは、ルールの世代の画面でそのエンジンを起動してから、もう一度反映してください。それ以外は、変更できない設定キーを元に戻すか、プロキシを再起動してください。」も表示します。
  名前で反映とロールバックの 409 で、`at` が `upstreams.<name>.engine` のときは、拒否の文の前に、「アップストリーム app:」のようにアップストリームの名前を添えます。
- バージョンの内容（`#/managed/<version>`）は、operator 以上だけが開けます。
  内容は秘密を含む可能性があるので、開いている間だけ画面のメモリに置きます。
  選択中でないバージョンでは、「このバージョンから下書きを作成する」で、そのバージョンから下書きを作成できます。

下書き:

- サイト、アップストリーム、ルート、アクセス制御とレート制限の 4 つの画面は、managed 設定の 1 つの下書きを編集します。
  下書きは選択中のバージョンから作成します。バージョンの内容の画面では、ほかのバージョンからも作成できます。
  ここでの変更は、「保存して反映する」を押すまで有効になりません。
- 下書きはこのページのメモリにだけあり、ブラウザーのストレージ、URL、履歴には入れません。
  ログアウトしたとき、操作がないままセッションが切れたとき、タブを閉じたときに失われます。
  変更のある下書きを残してページを離れようとすると、ブラウザーが確認を表示します。
- 下書きに入力している間は、30 秒に 1 回まで `GET /api/session` を送信して、セッションを延長します（入力はセッションを使ったことになります）。
- 画面上部の帯には、元のバージョンと、「変更あり」か「変更なし」を表示します。
  「変更あり」になるのは、下書きから作成するバージョンが、元のバージョンと違うときだけです。
  入力して元に戻した下書きは「変更なし」になります。
  入力の形式にエラーのある下書きは、「変更あり」になります。
- 帯の「検証する」は `POST /api/managed/check` を送信し、拒否されたら、エラーをその欄に表示します（下の「応答の形式」の `at`）。
  「保存して反映する」は、検証、確認、`POST /api/managed/apply` の順に進みます。
  「変更なし」の下書きは保存できません。検証では「元のバージョンと同じで、変更はありません。」と表示します。
- 「保存して反映する」の確認では、保存する変更（アップストリーム、デフォルトのアップストリーム、アクセス制御、レート制限、ホストごとの設定、サイト、ルートの追加・削除・変更）を名前で並べます。
  値は表示しません（書き換えに秘密を書けるためです）。
  - アップストリームのエンジンが替わるとき（2 つのバージョンの両方にあるアップストリームだけ）は、「アップストリームのエンジン」として並べます。
    エンジンの指定を付けたか外しただけで、検査するエンジンが同じときは、「アップストリームのエンジンの指定」として並べます。
  - 選択中の世代が検知のみのモードであるエンジンで検査するアップストリームがあるときは、「{n} 件のアップストリーム（{names}）は、検知のみの世代のエンジンで検査されます。ルールに一致したリクエストも遮断されません。」を表示します。
    `{n}` は数、`{names}` は名前です。
    名前は 20 件までで、残りは「ほか 3 件」のように件数で表示します。
  - ACME の証明書が新しく必要なサイトがあるときは、「{n} 件のサイトで新しい証明書が必要です。acme renew で発行されるまで（タイマーに任せると最大 1 日あまり）、そのサイトのホストには TLS で接続できません。」を表示します（`{n}` はその数）。
- 下書きの元のバージョンがもう選択中でないとき（ほかのユーザーかコマンドが先に変更した）は、そのままでは保存できません。
- 証明書チェーン、秘密鍵、CA の PEM のファイルは、ブラウザーで読み込みます。
  UTF-8 のテキストで 1 MiB 以下であることを検証し、送信するテキストの SHA-256 で指定します。
  ファイルの内容は表示しません。
  SHA-256 はブラウザーの暗号機能で計算するので、ファイルを選択できるのは、安全な接続（https か localhost）のときだけです。
  読み込んだバイト列は使い終わるとすぐに 0 で埋めますが、テキストはブラウザーの中で 0 で埋められず、どこからも参照されなくなるまでメモリに残ります。

ルートの画面:

- 一覧の「パス」の列には、ルートのパス、または正規表現を表示します。
  パスが正規表現のルートには「正規表現」の印を、`priority` を持つルートには「優先度 {n}」の印（`{n}` は値）を付けます。
  `priority` を書いていないルートには、優先度の印は付きません。`"priority": 0` のルートは「優先度 0」と表示します。
  一覧の上の絞り込みの欄は、この印の文字も対象にします。
- 編集の枠の「パス」は、1 行の入力欄です。
  「パスを正規表現として扱う」を選択すると、入力した文字をルートの `path_regex` に書き、`path` は書きません。
  選択しないときは、入力した文字を `path` に書き、`path_regex` は書きません。
  選択を切り替えても入力した文字は残り、「パス」の下の説明は選択に合わせて替わります。
- 「優先度」は任意です。
  空欄のときは `priority` を書きません（0 は書き足しません）。
  -1000〜1000 の整数を入力します。
  画面が確認するのは、4 桁以内の整数であることだけで、範囲外の値は検証が拒否し、拒否は「優先度」の欄に表示します。
- 正規表現の構文、パスへの一致の仕方、上限、`priority` によるルートの選択、`access` との関係については、[運用リファレンス](operator-reference.ja.md) の「`forward`」の `routes` を参照してください。
- パスが正規表現のルートには、誰かを拒否するアクセス制御と、書き換え後のパスを設定できません。
  誰も拒否しないアクセス制御は、設定しないのと同じで、保存できます。
  画面は、これらの欄を隠したり無効にしたりしません。検証が下書きを拒否し、拒否をアクセス制御の部分か「書き換え後のパス」の欄に表示します。
  正規表現の選択を切り替えると、「パス」、アクセス制御の部分、「書き換え後のパス」に表示していた拒否は消えます。
- ルートの `path_regex` についての検証の拒否は「パス」の欄に、`priority` についての拒否は「優先度」の欄に表示します。
- 「保存して反映する」の確認では、ルートをホストとパスで示します。
  正規表現は、前に `~` を付けて書きます（例: `app.example.com ~ ^/api/`）。
  同じ文字のパスと正規表現は、別のルートです。優先度だけの変更は、そのルートの変更として並べます。

ホストごとの設定の画面:

- アクセス制御とレート制限の画面には、上から順に、「全体の設定とホストごとの設定は、管理画面のルートには適用されません。」の注意、全体のアクセス制御とレート制限の枠、ホストごとの設定の一覧と「ホストごとの設定を追加する」、開いたホストごとの設定を編集する枠を並べます。
- ホストごとの設定の設定キー、ホストの比較の決まり、重ね方については、[運用リファレンス](operator-reference.ja.md) の「ホストごとの設定（`host_policies`）」を参照してください。
- 編集の枠では、名前とホスト（1 行に 1 つ）を書きます。
  アクセス制御とレート制限は、それぞれ次の 3 つから選びます。
  - **「引き継ぐ」**: 全体の設定をこのホストにも適用します。
    レート制限は全体と同じカウンターで数えます。
  - **「このホストの設定」**: 全体の設定の代わりに、この枠の値を適用します。
    全体のアクセス制御は引き継がれません。
    レート制限はこのホスト用のカウンターで数えます。
  - **「使わない」**: このホストには適用しません。
    アクセス制御では、全体の拒否もこのホストには適用されません。

  切り替えても、入力は下書きに残ります。
- 全体のアクセス制御かレート制限を変更する下書きでは、全体の枠と「保存して反映する」の確認に、「全体のアクセス制御を引き継がない {n} 件のホストごとの設定（{names}）には、この変更は効きません。」を表示します（`{n}` は数、`{names}` は名前です。レート制限も同じ形です）。
  「このホストの設定」と「使わない」のホストには、全体の変更（緊急の拒否を含む）が効かないためです。
- 一覧には、「ホストごとの設定は、Host ヘッダーがそのホストであるリクエストにだけ適用されます。別のホストのリクエストが、デフォルトのアップストリーム、ホストのないルート、*. で始まるホストのルートを通って同じアップストリームに届くときは、全体の設定だけが適用されます。ホストごとにルートを書き、デフォルトのアップストリームを「なし」にすることをお勧めします。」と表示します。
- 設定ファイルに `geo` が無いのに国を指定すると、検証の `at` が、そのホストごとの設定のアクセス制御を指します。
  管理画面のルートと同じホストを書くと、検証の `at` が、その行を指します。

## 応答の形式

### 応答

- 応答はどれも JSON で、次のヘッダーを持ちます（管理画面のファイルは別です。上の「管理画面」）: `Content-Type: application/json`、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`、`Referrer-Policy: no-referrer`、`X-Request-ID`（リクエスト ID）。
- `admin.trusted_proxies` に入る相手からのリクエストで、`X-Request-ID` がプロキシの付与する形式（16 桁の小文字の 16 進数、`-`、1〜16 桁の数字）なら、リクエスト ID にその値を使います。
  そうでなければ、管理プロセスが同じ形式の ID を作成します。
  プロキシを通したリクエストでは、プロキシのログの `id` と監査ログの `id` が同じになります。
- 失敗の応答は `{"error": "<sentence>"}` です。
  文はエラーの種類ごとに決まった英語の 1 文で、リクエストの値は含みません。
  入力のファイルの名前だけは、インポートの 400 で、別の項目の `subject` に付きます。
  インポートの 422 には `trial` も、世代の選択とロールバックの失敗には上の表の項目も付きます。
  管理画面はこの文を言語ごとの文に置き換えます。
- `POST /api/managed/check` と `POST /api/managed/apply` の 400 は、`{"error", "at"}` です。
  `at` は、拒否した値がボディの中のどこにあるかを示します。場所が無いときは `null` になります。
  アップストリームのエンジンに選択中の世代が無いために、`POST /api/managed/activate` と `POST /api/managed/rollback` が拒否する 409 も、`{"error", "at"}` です。
  - 場所はリクエストボディ内の設定キーのパスで書きます。
    ファイルが多すぎるときは `files` です。
    大きすぎるファイル、2 回あるファイル、バージョンが指定していないファイルは、`files[k]` です。
    バージョンの中の場所は、`sites[1].hosts[0]`、`upstreams.app.servers[2].address`、`upstreams.app.engine`、`sites[0].certificate.key`、`host_policies[1].rate_limit.keys` の形になります。
  - 配列の番号は 0 から数えます。
  - JSON の形式が違うボディと、64 桁の小文字の 16 進数でない `expect` には、場所がありません（`null`）。
    下の「管理 API の検証の順序」で拒否した 400 には、`at` のキーがありません。
  - 文は場所を含まない決まった文です。
    設定ファイルの拒否（409）も文だけで、場所は持ちません。
- 反映の処理の `detail`（プロキシが拒否した文）では、場所を `at` で持たず、文の中に書きます。
  文の中では、リスナーとアップストリームのサーバーは 1 から数え（`listener 1 cannot be bound`、`(upstream app, server 1)` など）、サイトは名前で書きます（`site app`）。
  検証の `at` とは数え方が違います。

### ステータスコード

| ステータスコード | 場合 | 主な `error` |
|---|---|---|
| 400 | ボディが JSON のオブジェクトでない、その API が認識しないキーがある、クッキーと API トークンの両方がある、入力のエラー | `bad request`、API ごとの文。`/api/managed/check` と `/api/managed/apply` では `at` も付きます |
| 401 | セッションも API トークンも無い、終了した、ユーザーが変更された、無効の API トークン。ログインのエラー | `unauthorized`、`invalid credentials` |
| 403 | `Origin`・CSRF・ロール・状態・API トークンが使えない API による拒否。パスワードや認証コードのエラー。ほかの拒否 | `forbidden`、`second factor required`、`password change required`、`second factor setup required`、`the password is wrong`、`the current password is wrong`、`the code is wrong`、`mfa is required` |
| 404 | 表に無いパス、存在しない世代・managed 設定のバージョン・ユーザー・API トークン、`records` が無い設定 | `not found`、`no such generation`、`records are not configured` |
| 405 | パスにそのメソッドが無いとき。`Allow` を付けます（`GET` があれば `HEAD` も含めます） | `method not allowed` |
| 408 | ボディが 30 秒以内に届かない | `request timeout` |
| 409 | 別の変更と重なった、状態に合わない、数の上限、世代のエンジンが使えない、エンジンごとの状態を返さないプロキシ、アップストリームのエンジンに選択中の世代が無い、managed 設定が無い、設定ファイルが受け付けられない | `conflict`、`the name is taken`、`the store has too many users`、`the user has too many tokens`、`the last enabled owner stays`、`the user was changed since it was read`、世代の操作の文（`the chosen generation is not the one that was expected`、`the proxy does not report its engines` など）、`the configuration has no managed object`、`a change of the managed configuration is under way`、managed 設定の操作の文（`no generation is chosen for the engine of an upstream` など） |
| 413 | ボディが上限を超える | `payload too large` |
| 415 | ボディを読み込む API に、`application/json` でない `Content-Type` | `unsupported media type` |
| 422 | インポートの事前検証の失敗 | `the trial failed` |
| 429 | クライアントの回数の超過 | `too many tries` |
| 500 | 管理プロセスの中の不整合、ルールストアか managed ストアを読めない、選択中の世代の記録が壊れている・食い違っている | `internal error`、ルールストアと managed ストアの文（`the current generation record is broken` と `the current generation records of the engine disagree` を含む） |
| 502 | プロキシが切り替えなかった | `the proxy did not switch` |
| 503 | 保存先や監査ログの行を読み書きできない、時間切れ、プロキシに接続できない、managed 設定の検証が重なった | `unavailable`、`the proxy cannot be reached`、`the proxy is busy`、`the proxy did not say how the switch ended`、`a check of a managed version is under way` |

`the current generation record is broken` または `the current generation records of the engine disagree` の 500 は、管理 API では直せません。
`GET /api/generations` と `GET /api/status` も 500 になるため、管理画面では世代の一覧の表示も切り替えもできません。
`rules activate` でそのエンジンの世代を選択し直してください（[運用リファレンス](operator-reference.ja.md) の「エンジンごとの選択中の世代」）。

managed 設定の変更（「保存して反映」「名前で反映」「ロールバック」）は、受け付けると 202 で応答します。
どう終わったかは、反映の処理（上の「managed 設定の操作」）で確認します。

### 管理 API の検証の順序

次の順に検証し、最初に通らなかった検証で応答します。

1. パス（表に無ければ 404）とメソッド（無ければ 405）
2. 最小のロールがある API では、認証情報（セッションのクッキーか `Authorization: Bearer`）。
   両方あれば 400、どちらも無いか合わなければ 401、API トークンの回数を使い切ったクライアントは 429
3. 変更では `Origin`（403）と、セッションなら `X-CSRF-Token`（403）
4. API トークンが使えない API に、API トークン（403）
5. セッションの状態（403。決まった文）
6. ロール（403）

3 から 6 で拒否したリクエストは、ユーザーが分かっているので、監査ログに書きます。
その後、その API がボディを読み込むなら、`Content-Type`（415）と JSON の形式（400）を検証します。
