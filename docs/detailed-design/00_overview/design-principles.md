# 設計方針・制約

> **状態: 初期草案**
>
> 5つの設計原則を前提とする。原則の適用方法、検査モード、移植・版管理・コード構成の方針は検討中である。実装済みの範囲は [システム概要](system-overview.md) の「現在の状態」を参照。

## この文書の範囲

設計原則とその適用の候補、検査モードと技術障害の区別、fail-closed の適用範囲、記録と管理機能の扱い、移植と前例の扱い、依存・ルール・設定の版の方針、コードの構成の方針を示す。

構成の候補と設計上の義務は [アーキテクチャ概要](architecture.md)、前提と用語は [システム概要](system-overview.md) を参照する。

## 設計原則

迷ったときは、「敵対的な監査に耐えるか」で判断する。

### 1. 権限分離

単一の責務の単位に分け、障害を横へ広げない。各要素の権限を最小にする。

適用（候補）:

- 検査、HTTP の受付と転送、管理を別の責務として扱う。
- プロセスを分けるだけでは権限分離にならない。実行する利用者、アクセスできるファイル、外部との通信、資源の上限、起動と再起動の責任を組で決める（AR-03、AR-04）。
- ルールの機能のうち、外部への問い合わせ（DNS など）、外部コマンドの実行、ファイルへの書き込みは、検査側に要る権限を広げる。残す機能と、要る権限・OS の制限を組にして決める。使える機能の許可リストは候補だが、採否が決まるまで機能を削らない（DP-07、OV-01）。

### 2. 入力を信用しない

外部からのデータはすべて攻撃の経路とみなす。境界で型・長さ・範囲を明示的に検証する。

適用（候補）:

- クライアントの要求、上流の応答、設定、ルール、管理の入口への入力、プロセス間のメッセージ（両方向）を入力として扱う。
- 検査プロセスから返る判定と記録用の情報も、Rust 本体で検証する。
- クライアントが送った識別子（要求 ID など）を、内部の transaction の識別子に使わない。
- クライアントの IP アドレスを示すヘッダーは、信頼すると設定した送り手からのものだけを採用する案（DP-08）。

### 3. 最小主義

コードが少ないほど不具合は減る。依存はすべて恒久的な負債になる。

適用（候補）:

- 依存を加えるときは、理由と、加えない場合の案を記録する。
- 別プロセス案では、検査プロセスを Coraza のルールの構築と検査に限り、ほかの機能を持たせない。
- 必要が確かめられていない機能や抽象化を、先に作らない。
- 最小主義は、確認を減らすことではない。コードを減らしても、境界と異常系の確認は減らさない。

### 4. 資源の決定性

確保と解放を明示する。あふれと境界を考え、プラットフォームの挙動に頼らない。

適用（候補）:

- 本文、伸長（大きさと、伸長に使う CPU・メモリ・ディスク・時間）、引数、同時実行、待ち行列、ディスクへの退避、時間に、明示的な上限を置く。値は未決定（AR-09、AR-14）。
- 検査器の上限（検査エンジンへ渡す本文や引数など）と、Rust 本体の受付・転送の上限は分けて決める。On、DetectionOnly、Off、明示的 bypass のどれを採っても、Rust 本体の受付・転送には資源と時間の境界を持たせる案（AR-09）。
- 上限を超えたときは、黙って切り捨てず、拒否するか、明示した部分検査として扱う。部分検査は、検査を必要とする通信には適用できない（AR-09）。どちらにするかは通信の種類ごとに決める（DP-03）。
- transaction、一時ファイル、接続、同時実行の枠は、正常と異常のすべての経路で、解放の責任者を決める（AR-10、AR-15）。
- 検査エンジンの既定値に頼らず、使う値を設定で明示する。

### 5. 構造的なセキュリティ

セキュリティは後付けの修正ではなく、構造で作る。症状ではなく、脆弱性の種類をなくす。

適用（候補）:

- 検査を必要とする通信（DP-02）の検査不能を、明示的 bypass や Off など、意図した無検査と同じものとして扱わない。転送するか拒否するかは、モードと障害の種類ごとに決める（DP-03）。
- 「判定がない」ことを「許可」と区別する。検査しなかった理由（明示的 bypass か、検査不能か）を分けて記録する。
- 検査、判定、転送の間で、表現の解釈を揃える（AR-07）。
- HTTP のフレーミングの曖昧さを、そのまま受け付けない（AR-06）。

## 検査モードと技術障害の区別

検査のモードは、次の2つの軸に分けて扱う。

| 軸 | 値 |
|---|---|
| ルールの選択 | 既定のルールセット、ルートごとの別のルールセット、明示的 bypass |
| 選んだ検査器の動作 | On、DetectionOnly、Off |

- これらのモードを残すか、どれを残すかは未決定（DP-01、OV-01）。次の表は、残す場合に決める必要がある論点で、モードの採用を決めるものではない。
- 意図した無検査（明示的 bypass、Off）や、破壊的な動作を実行しない検査（DetectionOnly）と、技術的な検査不能は、別のものとして扱う。
- 技術的な検査不能には、準備完了の前、異常終了、応答しない、通信の異常、期限超過、上限超過、構築の失敗などの種類がある。DP-03 は、障害の種類とモードの組ごとに答える。
- Off と明示的 bypass も同じではない。Off でも、記録や資源の管理のために検査器の側が関わる設計がありうる。
- ルールの動作によって、transaction ごとに検査器の動作や本文の扱いを変えられる場合がある。その場合、モードはルールの中からも変わりうるため、採用する版で確かめ、使える機能の範囲（DP-07）とあわせて決める。

| 設定された状態 | 意図した挙動 | 技術障害のときの扱い |
|---|---|---|
| ルールセット（既定またはルートごと）＋ On | ルールの破壊的な動作（拒否、切断、リダイレクトなど）を実行する | 検査を必要とする通信（DP-02）のうち、指定した検査器を使えないものは拒否する案（fail-closed）。別のルールへ切り替えてよい条件は DP-04 |
| ルールセット＋ DetectionOnly | ルールの評価は行うが、破壊的な動作は実行しない。記録が残るかは、ルールと監査記録の設定による（DP-10） | 検知しても遮断しないことと、技術障害は別。技術障害のときに拒否するか、通して記録するか、記録の上でどう区別するかは DP-03。DetectionOnly の通信を検査を必要とする通信に含めるかは DP-02 |
| ルールセット＋ Off | ルールを評価しない | 検査器が要る範囲（記録、資源の管理）と、障害のときに転送するかは DP-03。Rust 本体の受付・転送の上限と期限は Off でも持つ案（AR-09、AR-14） |
| 明示的 bypass（残す場合、DP-01） | 検査プロセスを呼ばない案 | 検査プロセスの障害の影響を受けない案。Rust 本体の受付・転送の上限と期限は持つ案（AR-09）。設定の意図、記録の要件、判定に使う表現は DP-05 |
| 検査の要否やルートを判定できない | — | bypass として扱わない。検査を必要とする通信として扱うか、拒否するかは DP-03（AR-07） |
| ルールセットの構築・選択の失敗 | — | 起動時の構築の失敗、更新の失敗、存在しないルールセットの参照を分けて決める。既定のルールへ切り替えるか、拒否するかは DP-04。検査を必要とする通信で、より弱い設定（DetectionOnly、Off、明示的 bypass）へ切り替えることは、原則 5 の候補と両立しない。切り替える場合の記録と通知の要件も DP-04 で決める |

## fail-closed の適用範囲

- 候補: 「検査を必要とすると定義した通信の検査不能を、意図した無検査へ変換しない」。すべてのモード、すべての通信に一律に当てるものではない。
- 「検査を必要とする通信」の範囲は未決定。たとえば DetectionOnly の通信を含めるかは DP-02。
- 拒否するときにクライアントへ返す応答は未決定（AR-16）。
- すでに転送したデータは取り戻せない。検査の完了前に送ってよい範囲は AR-08。
- 部分検査で未検査の残りを転送することは、検査を必要とする通信の fail-closed と両立しない（AR-09）。
- ルールセットが使えないときの別のルールへの切り替えは、fail-closed とは別に決める（DP-04）。
- 上流の障害は検査不能とは別に扱う（AR-18）。

## 記録と管理機能の扱い

記録（DP-10）:

- 記録には、攻撃者が送った値や、認証情報・個人情報などの機微なデータが入りうる。記録する項目、機微なデータの伏せ方（マスキングなど）、保存と表示での制御文字などの扱い、閲覧の権限、大きさ・保存期間・容量、記録できないときの扱いを決める。
- 記録用の情報は、検査プロセスから返るものも含めて入力として扱い、Rust 本体の境界で検証する（AR-13）。
- 記録の出力が、情報の漏えいや、記録を閲覧・解析する側への入力の注入の入口にならないことを、検証の候補にする。
- 値、保存方式（OV-07）、表示の方法は未決定。

管理機能（採る場合。OV-03、AR-05）:

- 管理UIの再利用と改善を検討することは前提。採る場合は、配置だけでなく、認証、操作ごとの権限の分け方（ルールや bypass の変更と、記録の閲覧など）、変更の履歴、変更が及ぶ範囲を決める。
- 管理の入口への入力も、信用しない入力として扱う（原則 2）。
- 具体的な役割、認証の方式、画面の詳細は未決定。

## 移植と前例の扱い

この節の方針は候補で、前例の扱い全体は DP-06 で決める。

- 移植元とする版（OV-02）と、残す機能の基準（OV-01）は未決定。決まるまで、個々の機能を残す・除く・移すとは決めない。
- 移植元と同じ結果になることだけを受入条件にすると、移植元の挙動を確かめないまま仕様として固定することになる。検査範囲は仕様として明文化し、仕様に対して検証する案。
- 移植元の挙動のうち確認が必要なものは、写す・直す・採否を決める、に分けて記録する案。
- 機能を足す・除くことと、既存の検査範囲を正しく実行するための接続処理とは、分けて扱う。

前例の分け方の候補（DP-06）:

| 対象 | 参考にする前例（候補） |
|---|---|
| 製品のルート、設定、記録、運用 | tukuyomi の実装と設計。残す範囲は OV-01 で決める |
| Coraza への入力、phase、判定、寿命 | 採用する版の Coraza の公式 API と、公式の接続の実装。ただし公式の例のモードや部分検査の設定を、そのまま製品の仕様にしない |
| Rust の所有権、エラー、並行実行 | tukuyomi-core で別に決める |

前例どうしで挙動が違う場合は、根拠と採否を設計の記録に残してから実装に移る。

## 依存・ルール・設定の版

- 採用する時点で、保守されていて既知の修正を含む版であることを確かめ、版を固定する。この文書では特定の版を推奨しない。
- 検査エンジンの版を上げるだけでは足りないことがある。上限への到達や解析エラーを拒否する設定とルールを、エンジンの版と組で確かめる（AR-09）。
- libcoraza 案では、接続ライブラリの版と、その中に含まれる Coraza の版の両方を確かめる。
- 別プロセス案では、Rust 本体と検査プロセスの2つの実行ファイルの版の組み合わせと、通信の契約が合うことを確かめる。合わない組み合わせを検知して受け付けないか、適合する組として配布するかなどは未決定（AR-13、OV-06）。
- ルールセットの版と、検査エンジンの設定も、同じように固定して確かめる。
- 接続方式を比べるときは、Go API を直接使う側の Coraza の版と、libcoraza に含まれる Coraza の版を記録して比較の条件に含め、できれば揃える。揃わない場合は版を含む構成どうしの比較であり、接続方式だけの差とは結論しない。
- 版を更新するたびに、同じ確認を繰り返す。確認の手順は未決定（DP-09）。

## コードの構成

- コードは責務・型・所有者で整理する。過度にファイルを分けない。
- 具体的なモジュールとファイルの構成は、実装の時点で必要に応じて決める。この文書では定めない。
