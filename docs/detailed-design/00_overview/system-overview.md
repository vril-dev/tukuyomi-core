## 製品の目的

tukuyomi-core は、tukuyomi（tukuyomi WAF）から派生し、WAF 機能に特化したシステムを目指す。

- どの機能を残し、どの機能を除くかの基準は未決定（OV-01）。基準が決まるまで、個々の機能を残す・除くとは決めない。
- 移植元とする tukuyomi の版は未決定（OV-02）。

### 初回の検査核（実装済みの範囲）

初回の検査核は、要求の検査を担う部分である。WAF としての完成を意味しない。

- Rust のライブラリ [`kernel/`](../../../kernel/)。標準ライブラリだけを使う。ライブラリ自身はスレッドを作らず、呼び出し側が回す。この中の監督（`Supervisor`）が、検査プロセスの起動、停止、再起動と、起動ごとの一時ディレクトリを所有する。
- Go の検査プロセス [`inspector/`](../../../inspector/)。Coraza の Go API を直接使う。初回の検査核は Coraza v3.8.1 に固定している。これは現在のコードが使う版で、版の推奨や DP-09 の手順の決定ではない。
- 検査プロセスはライブラリが直接起動し、同じホストの中で、引き継いだ Unix domain socket の対（検査プロセスの fd 0）で通信する。ライブラリも検査プロセスも、TCP の待ち受けポートを増やさない。
- 要求ごとの結果は、許可（`Allow`）、遮断（`Block`）、検査不能（`Uninspectable`）の3つ。検査を完了できなかった要求は、許可にならない。検査できないと分かっている入力は、受け付けの時点で呼び出し側に返し（`Refused`）、許可にしない。たとえば、本文があり Content-Type が `application/x-www-form-urlencoded`、`multipart/form-data`、`application/json`、`application/<名前>+json` のどれでもない要求、Content-Encoding を伴う要求、Transfer-Encoding を伴う要求は、この形で返す。ただし、本文の先頭だけを渡す要求で、Transfer-Encoding が `chunked` の1行だけで Content-Length を持たないものは受け付ける（HTTP/1.1 の chunked の本文の先頭を検査するため）。
- 再起動の回数は、直近の一定の時間（設定の窓）の中で上限がある。上限に達したら、窓が空くまで起動し直さず、その間に待っている要求は検査不能にする（HTTP では 503）。ルールの誤りなどの決定的な失敗では起動し直さない。
- 一時ディレクトリは、起動ごとに専用のものを、利用者だけが使える権限で作る。検査プロセスの終了を確かめた後に消す。終了を確かめられないときは消さずに残し、新しい検査プロセスを起動しない。
- 検査プロセスは、ルールセットの世代を読んだ後、Landlock で一時ディレクトリの外のファイルに触れなくし（Linux 6.7 以上では TCP の bind と connect も断る）、capability を捨て、`no_new_privs` を付ける。Landlock が無い Linux では起動を断る。UDP、unix の socket、MPTCP の socket は絞れない。
- 1つの要求で検査に渡せる本文は 1 MiB までである。本文の先頭だけを渡すときは、切ったことを検査プロセスに知らせ、切ったことによる本文の解析の失敗では遮断しない。

### HTTP・HTTPS の受付と転送（実装済みの範囲）

初回の検査核の前に置く受付と転送である。WAF としての完成を意味しない。鍵、命令、記録の詳細は [運用リファレンス](../../operations/operator-reference.md) に書く。

- Rust の実行体 [`proxy/`](../../../proxy/)。tokio、hyper、rustls を使い、初回の検査核をライブラリとして使う。1つの設定ファイル（JSON）で、待ち受け、上流、経路、各段の上限と期限を決める。設定の値に既定値はなく、範囲と関係を起動の時に確かめる。`config check` の命令で、起動の前に同じ確かめを流せる。
- 待ち受けは 1〜8 つ。平文の HTTP、TLS（1.2・1.3、server name で証明書を選ぶ）、https への redirect の3種類がある。HTTP/1.1 と HTTP/1.0 を扱い、TLS の待ち受けでは HTTP/2 も扱える。接続の使い回し（keep-alive と pipelining）を扱う。
- 上流は名前を付けた組で、組の server を重みで選ぶ。失敗の続いた server を一時外し、予備の server を持てる。接続は使い回す。2回送っても害の無い method の要求は、次の server へ回せる。server の名前は起動のときに1回だけ引く。組ごとに TLS でつなげる（上流へは HTTP/1.1）。
- 経路は、要求の Host と path で上流の組を選ぶ。経路ごとに、client の IP と国の制限、要求と応答の書き換え（Host、path、query、field）、本文の上限、長い応答と WebSocket の扱いを決められる。WebSocket の frame は検査しない。
- 要求のヘッダー部は、HTTP の解析の前に厳格に確かめる。たとえば、行の終わりは CRLF だけ、request-target は origin-form だけ、Host はちょうど1つ、Transfer-Encoding と Content-Length の併用は拒否する。違反と上限の超過は、本文のない決まった応答（400、408、413、414、415、417、431）で拒否し、上流へ何も送らない。HTTP/2 の要求も、同じ形に書き直して同じ決まりで確かめる。
- 本文は、先頭の設定したバイト数（1 MiB まで）を検査する。それより長い本文は、許された後に残りを検査せずに上流へ流す。chunked の本文を扱う。Content-Encoding は `gzip` だけを受け、検査する経路では伸長した本文を Content-Encoding なしで検査する（伸長した後が検査する長さを超えるもの、壊れたもの、ほかの符号化は拒否する）。検査する経路では、本文の型は初回の検査核と同じく、`application/x-www-form-urlencoded`、`multipart/form-data`、`application/json`、`application/<名前>+json`（名前は英数字・`.`・`-`）だけで、ほかの型は 415 で拒否する。検査しない経路では、本文の型を問わずに流す。どの経路でも、Content-Type を2つ以上持つ本文は 415 で拒否する。JSON の型の本文は、検査プロセスが Coraza の JSON の処理器を選んで解析させる（運用者の規則では替えられない）。JSON の入れ子は 64 段まで（配列の入れ子は、展開した量の上限のため、短い本文ではそれより浅くても遮断されることがある）で、それを超える本文、RFC 8259 に合わない本文、引数の数の上限を超える本文は遮断する。
- 検査で許可（`Allow`）された要求、検知だけのモードで規則に当たった要求、検査しない経路の要求だけを上流へ転送する。転送の前に、接続に属するヘッダー（Connection とそれが挙げるもの、Keep-Alive、TE、Transfer-Encoding、Upgrade、Expect など）と、名前に `_` を含むヘッダーを除き、X-Forwarded-For、X-Forwarded-Host、X-Forwarded-Proto を付ける。X-Forwarded-For は、設定で信じた proxy からのものだけを残す。遮断はルールの状態コード（200〜599 の外は 500）で、検査不能は 503（プログラムの内部の不整合を示すものは 500）で答え、どちらも転送しない。上流への接続の失敗、期限の超過、不正な応答は 502 で答える。
- ルールセットは、命令 `rules import` で取り込み、試しに通ったものを世代にする。`rules activate` で選んだ世代へ、SIGUSR1 で無停止で切り替える。世代は、遮断するものと、検知だけのもの（規則に当たっても通して記録する）がある。世代には、検査しない経路（Host と path）を持たせられる。CRS は、版と checksum を固定した取得の台本で取得し、同梱しない。
- 証明書は、ファイルを置くか、命令 `acme renew`（ACME の HTTP-01）で発行・更新する。SIGUSR2 で読み直す。
- 記録は、標準エラーに1行1件の JSON で出す。要求ごとの記録は、要求の番号、method・Host・path（query は入れない）、答え、判定したルールの世代、当たった規則の id と重さと anomaly score を持つ。要求の番号は、上流へ送る要求とclient への応答の `X-Request-ID` にも入れる（client が送った値は置き換える）。書けない記録は捨てて数え、要求は止めない。設定すれば、同じ行をディレクトリのファイルにも書く（大きさと本数で回す。ファイルに書けなかった行は標準エラーに出し、数える）。
- 設定で loopback の監視の待ち受けを置くと、`/healthz`・`/readyz`・`/metrics`（Prometheus の text の形）に答える。systemd の `Type=notify` に、準備と停止を知らせる。
- root では動かない。起動もすべての命令も、user id のどれかが 0 なら断る。
- SIGTERM、SIGINT、SIGHUP で新しい受付を止め、進行中の要求を期限まで処理してから、検査プロセスを止めて終わる。

### 要求の前の方針（実装済みの範囲）

経路を引く前に要求を断る方針である。WAF としての完成を意味しない。鍵と数え方の詳細は [運用リファレンス](../../operations/operator-reference.md) の「要求の前の方針」に書く。

- 設定の最上位の `access`、`rate_limit`、`geo` で決める。head の確かめに通った要求のすべてに効く（ACME の challenge と監視の待ち受けは除く）。検査しない経路に当たる要求にも、https への redirect の待ち受けにも効く。値は起動のときに読み、起動し直すまで変わらない。
- `access` は、client の address の network と国の、許可と拒否である。経路ごとの `access` にも、国の一覧を書ける。断るときは 403 で答える。
- 国は、運用者が置いた MaxMind DB の形式のデータベースで引く。データベースは同梱せず、取得もしない。private な address と、データベースが知らない address は、`UNKNOWN` として扱う。
- `rate_limit` は、client ごとの要求の流量を制限する。IPv4 は address ごと、IPv6 は /64 ごとに数える。数える client の数に上限があり、超えると古い client の count から外す。制限を超えた client には、429 と `Retry-After` で答える。
- client の address は、`X-Forwarded-For` を信じる相手（設定の `trusted_proxies`）の申告だけを使って決める。

### 管理のプロセス（実装済みの範囲）

管理 API と管理画面を持つ、proxy とは別のプロセスである。WAF としての完成を意味しない。詳細は [管理リファレンス](../../operations/admin-reference.md) に書く。

- 同じ実行ファイルの `admin` 命令で動く。proxy と同じ利用者で動き、loopback の address で平文の HTTP を待つ。外から使うときは、proxy の TLS の待ち受けの経路を通す。
- 利用者、役割（`viewer`、`operator`、`owner`）、session、API の token、パスワードの変更、MFA（TOTP）、ログインの試行の制限、監査の記録を持つ。利用者と token と履歴はファイルに保存する。
- ルールの世代を、一覧し、取り込み（試し付き）、選び、動いている proxy へ切り替えを依頼し、前の世代へ戻し、消せる。切り替えの履歴を残す。proxy への依頼は Unix domain socket（制御 socket）で行い、proxy はこの socket では、状態の問いと切り替えの依頼にだけ答える。
- 記録のファイルを、時刻、type、class、status、規則、要求の番号、client、世代で絞って引ける。
- 管理画面は、実行ファイルに組み込んだ静的なファイル（[`proxy/admin-ui/`](../../../proxy/admin-ui/)）を管理のプロセスが配る。画面は、状態、ルールの世代、切り替えの履歴、取り込み、記録、監査の記録、アカウント、利用者である。日本語と英語に対応する。

### 実装していないもの・決まっていないこと

実装していないもの:

- HTTP の受付と転送のうち、上の範囲の外（HTTP/3、平文の HTTP/2、上流への HTTP/2、要求の trailer、1xx の応答の中継（WebSocket の 101 を除く）、PROXY protocol、応答のキャッシュ）。対応する範囲は OV-05
- XML の本文、上の形の外の JSON の型（`text/json` など）、`gzip` 以外の内容の符号化の本文の検査（AR-09）
- 応答の検査（OV-04）
- 設定ファイルを管理 API や管理画面で編集すること。動いている proxy が、設定を読み直すこと（世代の切り替えと証明書の読み直しを除く）
- 署名つきの監査の記録と tracing。利用者・token・履歴・記録の、ファイル以外への保存（DP-10、OV-07）
- ビルド済みの実行ファイルと配布物
- 検査プロセスを別の利用者や別のサービスで動かすこと（AR-04）

決まっていないこと:

- 構成の候補の全体としての採用。AR-01 は、初回の検査核に限って、Rust のライブラリと別プロセスの Go の検査プロセスの構成を採った。libcoraza との比較は終えていない。
- 通信方式、監督の担当、再起動の条件、本文の扱いなど、各文書の未決事項は、全体としては未決定のまま。初回の検査核の実装は、これらの決定ではない。たとえば、本文の種類による拒否は、初回の検査核の拒否の規則で、AR-09 の決定ではない。HTTP・HTTPS の受付と転送の拒否の規則、応答の状態コード、上限と期限も、この実装の規則で、AR-06、AR-07、AR-16、AR-18、OV-05 の決定ではない。管理のプロセス、管理 API、管理画面、記録のファイル、要求の前の方針の実装も、OV-03、OV-07、AR-05、DP-10 の決定ではない。
- 全体としての安全性は評価していない。

## 前提・候補・未決定の区別

この文書群では、内容を次の区分で書き分ける。

| 区分 | 意味 |
|---|---|
| 前提 | プロジェクトの方向として示されているもの。変える場合は改めて決める |
| 候補 | 有力な案だが、検証と採用の判断を経ていないもの |
| 未決定 | 候補が絞られていないか、判断を保留しているもの |
| 実装済み | 初回の検査核、HTTP・HTTPS の受付と転送、要求の前の方針、管理のプロセスの範囲だけ（「現在の状態」の各節）。ほかは該当なし |

### 前提

- 主な実装言語は Rust とする。
- tukuyomi から派生した、WAF の機能を中心とする製品にする。WAF 以外の機能は、基準（OV-01）が決まってから除く。
- 設計原則として、権限分離、入力を信用しない、最小主義、資源の決定性、構造的なセキュリティを置く（[設計方針・制約](design-principles.md)）。
- 管理UIは、tukuyomi の管理UIの再利用と改善を検討する。範囲と元にする版は未決定（OV-03）。
- コードは責務・型・所有者で整理し、過度にファイルを分けない。具体的なモジュールとファイルの構成は、実装時に必要に応じて決める。

### 候補

- 検査エンジンには Coraza を使う案で比較している。検査エンジンを独自に作り直す案は候補にしていない。
- 接続方式の第一候補は、Rust 本体と、Coraza の Go API を直接使う小さな Go 検査プロセスに分ける構成（AR-01）。初回の検査核に限っては、この構成のうち、Rust のライブラリと別プロセスの Go 検査プロセスを実装した。HTTP を扱う Rust 本体は、上の「HTTP・HTTPS の受付と転送」の範囲を実装した。
- 比較対象として、Rust 本体から libcoraza（Coraza の C ライブラリ）を呼ぶ構成を残す（AR-01）。

どちらの構成が速い、簡単、安全とは、検証の前には決めない。比較の観点は [アーキテクチャ概要](architecture.md) に書く。

## 関係する外部の要素

| 要素 | 役割 | 扱い |
|---|---|---|
| クライアント | 保護対象のアプリケーションへ HTTP の要求を送る | 送られてくるものはすべて信用しない入力として扱う |
| 上流アプリケーション | tukuyomi-core が要求を転送する保護対象 | 応答も入力として扱う。応答の検査は OV-04 |
| 運用者 | 設定とルールを管理し、記録を確認する | 管理の手段と範囲は OV-03、AR-05。今の実装は「現在の状態」を参照 |
| ルールと設定 | 検査の内容を決める | ルールと設定も入力として検証する。使える機能と権限は DP-07 |

## 検討の対象とする範囲

| ルールと設定の管理 | ルールの検証、反映、世代の切り替え | ルールセットの取り込みと試し、世代の選択と切り替えを、命令と合図、管理 API と管理画面で実装済み（「現在の状態」を参照）。設定ファイルの編集は未実装。全体は設計の検討中（AR-11） |

## 用語

| 用語 | この文書群での意味 |
|---|---|
| Rust 本体 | 候補構成で、HTTP の受付・解釈・転送、設定、記録の保存を担う Rust のプロセス |
| 検査プロセス | 候補構成で、Coraza によるルールの構築と検査だけを担う Go のプロセス |
| 検査器 | ある世代のルールと設定から構築した、検査を行う単位 |
| transaction | 検査エンジンが1つの要求（応答を検査する場合は応答も）を検査する単位。採用した検査範囲で必要な phase を順に処理し、終えるときにログ記録の phase と Close を行う。経路ごとにどの phase を呼ぶかは AR-10 |
| phase | 検査エンジンの評価段階。順序は要求ヘッダー、要求本文、応答ヘッダー、応答本文、ログ記録。早い段階での遮断の後や、応答を検査しない構成では、途中の phase を呼ばないことがあり、常にすべての phase を通るわけではない |
| ルールの世代 | ある時点で有効なルールと設定の組。更新するたびに新しい世代になる |
| 検査を必要とする通信 | 設定上、検査を経ずに転送してはならないと定義した通信。定義は DP-02 |
| 検査不能 | 停止、通信断、期限超過、上限超過などの技術的な理由で、検査を完了できない状態。意図した無検査とは別に扱う |
| 明示的 bypass | 設定によって、意図して検査を行わない経路。残すかどうかは DP-01 |
| On / DetectionOnly / Off | Coraza の検査器の動作。On はルールの破壊的な動作（拒否、切断、リダイレクトなど）を実行する。DetectionOnly はルールの評価は行うが、破壊的な動作は実行しない。記録が残るかは、ルールと監査記録の設定による（DP-10）。Off はルールを評価しない。ルールの一致（検知）と破壊的な動作の実行（遮断）は別に扱う |
| fail-closed | 検査を必要とする通信が検査不能のとき、転送しない扱い。適用範囲は [設計方針・制約](design-principles.md) |
