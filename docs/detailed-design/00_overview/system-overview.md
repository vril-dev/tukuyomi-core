## 製品の目的

tukuyomi-core は、tukuyomi（tukuyomi WAF）から派生し、WAF 機能に特化したシステムを目指す。

- どの機能を残し、どの機能を除くかの基準は未決定（OV-01）。基準が決まるまで、個々の機能を残す・除くとは決めない。
- 移植元とする tukuyomi の版は未決定（OV-02）。

### 初回の検査核（実装済みの範囲）

初回の検査核は、要求の検査を担う部分である。WAF としての完成を意味しない。

- Rust のライブラリ [`kernel/`](../../../kernel/)。標準ライブラリだけを使う。ライブラリ自身はスレッドを作らず、呼び出し側が回す。この中の監督（`Supervisor`）が、検査プロセスの起動、停止、再起動と、起動ごとの一時ディレクトリを所有する。
- Go の検査プロセス [`inspector/`](../../../inspector/)。Coraza の Go API を直接使う。初回の検査核は Coraza v3.8.1 に固定している。これは現在のコードが使う版で、版の推奨や DP-09 の手順の決定ではない。
- ModSecurity の検査プロセス [`inspector-modsecurity/`](../../../inspector-modsecurity/)。Rust と C++ の橋渡しで、libmodsecurity v3.0.17 を静的に結ぶ。ルールセットの世代は、どちらのエンジンで検査するかを持ち、ライブラリは世代のエンジンの検査プロセスを起動する。どちらの検査プロセスも、同じやり取りで話し、下の守りを同じに持つ（[運用リファレンス](../../operations/operator-reference.md) の「ModSecurity の世代」）。
- 検査プロセスはライブラリが直接起動し、同じホストの中で、引き継いだ Unix domain socket の対（検査プロセスの fd 0）で通信する。ライブラリも検査プロセスも、TCP の待ち受けポートを増やさない。
- 要求ごとの結果は、許可（`Allow`）、遮断（`Block`）、検査不能（`Uninspectable`）の3つ。検査を完了できなかった要求は、許可にならない。検査できないと分かっている入力は、受け付けの時点で呼び出し側に返し（`Refused`）、許可にしない。たとえば、本文があり Content-Type が `application/x-www-form-urlencoded`、`multipart/form-data`、`application/json`、`application/<名前>+json` のどれでもない要求、Content-Encoding を伴う要求、Transfer-Encoding を伴う要求は、この形で返す。ただし、本文の先頭だけを渡す要求で、Transfer-Encoding が `chunked` の1行だけで Content-Length を持たないものは受け付ける（HTTP/1.1 の chunked の本文の先頭を検査するため）。
- 再起動の回数は、直近の一定の時間（設定の窓）の中で上限がある。上限に達したら、窓が空くまで起動し直さず、その間に待っている要求は検査不能にする（HTTP では 503）。ルールの誤りなどの決定的な失敗では起動し直さない。
- 一時ディレクトリは、起動ごとに専用のものを、利用者だけが使える権限で作る。検査プロセスの終了を確かめた後に消す。終了を確かめられないときは消さずに残し、新しい検査プロセスを起動しない。
- 検査プロセスは、ルールセットの世代を読んだ後、Landlock で一時ディレクトリの外のファイルに触れなくし（Linux 6.7 以上では TCP の bind と connect も断る）、capability を捨て、`no_new_privs` を付ける。Landlock が無い Linux では起動を断る。UDP、unix の socket、MPTCP の socket は絞れない。
- 1つの要求で検査に渡せる本文は 1 MiB までである。本文の先頭だけを渡すときは、切ったことを検査プロセスに知らせ、切ったことによる本文の解析の失敗では遮断しない。

### HTTP・HTTPS の受付と転送（実装済みの範囲）

初回の検査核の前に置く受付と転送である。WAF としての完成を意味しない。設定キー、コマンド、ログの詳細は [運用リファレンス](../../operations/operator-reference.md) に書く。

- Rust の実行体 [`proxy/`](../../../proxy/)。tokio、hyper、rustls を使い、初回の検査核をライブラリとして使う。1つの設定ファイル（JSON）で、リスナー、アップストリーム、ルート、各段の上限とタイムアウトを決める。managed 設定を使うときは、アップストリーム、ルート、デフォルトのアップストリーム、サイトと証明書、全体のアクセス制御とレート制限、ホストごとの設定を managed 設定のバージョンに置き、設定ファイルにはほかを置く（下の「managed 設定」）。設定の値にデフォルト値はなく、範囲と関係を起動のときに検証する。`config check` のコマンドで、起動の前に同じ検証を流せる。
- リスナーは 1〜8 つ。平文の HTTP、TLS（1.2・1.3、サーバー名で証明書を選ぶ）、https への redirect の3種類がある。HTTP/1.1 と HTTP/1.0 を扱い、TLS のリスナーでは HTTP/2 も扱える。接続の使い回し（keep-alive と pipelining）を扱う。
- アップストリームは名前を付けたサーバーのまとまりで、サーバーを重みで選ぶ。失敗の続いたサーバーを一時除外し（ダウン判定）、バックアップのサーバーを持てる。接続は使い回す。2回送っても害の無い method のリクエストは、次のサーバーへ回せる。サーバーの名前は、起動のときと設定のリロードのときに引く。アップストリームごとに TLS でつなげる（アップストリームへは HTTP/1.1）。
- ルートは、リクエストの Host とパスでアップストリームを選ぶ。ルートごとに、クライアントの IP と国の制限、リクエストとレスポンスの書き換え（Host、パス、クエリ、ヘッダー）、ボディの上限、ストリーミング応答と WebSocket の扱いを決められる。WebSocket の frame は検査しない。
- リクエストのヘッダー部は、HTTP の解析の前に厳格に検証する。たとえば、行の終わりは CRLF だけ、request-target は origin-form だけ、Host はちょうど1つ、Transfer-Encoding と Content-Length の併用は拒否する。違反と上限の超過は、ボディのない決まった応答（400、408、413、414、415、417、431）で拒否し、アップストリームへ何も送らない。HTTP/2 のリクエストも、同じ形に書き直して同じ決まりで検証する。
- ボディは、先頭の設定したバイト数（1 MiB まで）を検査する。それより長いボディは、許可された後に残りを検査せずにアップストリームへ流す。chunked のボディを扱う。Content-Encoding は `gzip` だけを受け、検査するルートでは伸長したボディを Content-Encoding なしで検査する（伸長した後が検査する長さを超えるもの、壊れたもの、ほかの符号化は拒否する）。検査するルートでは、ボディの型は初回の検査核と同じく、`application/x-www-form-urlencoded`、`multipart/form-data`、`application/json`、`application/<name>+json`（名前は英数字・`.`・`-`）だけで、ほかの型は 415 で拒否する。検査除外のルートでは、ボディの型を問わずに流す。どのルートでも、Content-Type を2つ以上持つボディは 415 で拒否する。JSON の型のボディは、検査プロセスが Coraza の JSON の処理器を選んで解析させる（運用者のルールでは変更できない）。JSON の入れ子は 64 段まで（配列の入れ子は、展開した量の上限のため、短いボディではそれより浅くてもブロックされることがある）で、それを超えるボディ、RFC 8259 に合わないボディ、引数の数の上限を超えるボディはブロックする。
- 検査で許可（`Allow`）されたリクエスト、検知のみのモードでルールに当たったリクエスト、検査除外のルートのリクエストだけをアップストリームへ転送する。転送の前に、接続に属するヘッダー（Connection とそれが挙げるもの、Keep-Alive、TE、Transfer-Encoding、Upgrade、Expect など）と、名前に `_` を含むヘッダーを除き、X-Forwarded-For、X-Forwarded-Host、X-Forwarded-Proto を付ける。X-Forwarded-For は、設定で信じたプロキシからのものだけを残す。ブロックはルールの状態コード（200〜599 の外は 500）で、検査不能は 503（プログラムの内部の不整合を示すものは 500）で応答し、どちらも転送しない。アップストリームへの接続の失敗、タイムアウト、不正な応答には 502 で応答する。
- ルールセットは、コマンド `rules import` でインポートし、事前検証に通ったものを世代にする。`rules activate` で選択した世代へ、SIGUSR1 で無停止で切り替える。世代は、ブロックするものと、検知のみのもの（ルールに当たっても通してログに残す）がある。世代には、検査除外のルート（Host とパス）を持たせられる。CRS は、バージョンと checksum を固定した取得のスクリプトで取得し、同梱しない。
- 証明書は、ファイルを置くか、コマンド `acme renew`（ACME の HTTP-01）で発行・更新する。SIGUSR2 で再読み込みする。managed 設定を使うときは、サイトの証明書を managed ストアに置く（下の「managed 設定」）。
- SIGHUP で設定ファイルをリロードし、止まらずに新しい設定に切り替える。managed 設定を使うときは、managed ストアの選択中のバージョンも一緒に読む。管理プロセスは、制御ソケットの `reload` で、バージョンを名指した同じリロードを依頼する。ルートとアップストリーム、ポリシー（国のデータベースを含む）、リスナーの追加と削除、証明書などが切り替わり、切り替えた後に受けた接続から新しい設定を使う。開いている接続は、受けたときの設定でリクエストを終えてから閉じ、リクエストは拒否しない。受け付けない設定（エラー、動いている間に変えられない設定キーの違い、bind できないリスナー）は何も変更しない。
- ログは、標準エラーに1行1件の JSON で出す。リクエストごとのログは、リクエスト ID、method・Host・パス（クエリは入れない）、応答、判定したルールの世代、当たったルールの ID と重さと anomaly score を持つ。リクエスト ID は、アップストリームへ送るリクエストとクライアントへの応答の `X-Request-ID` にも入れる（クライアントが送った値は置き換える）。書けないログは捨てて数え、リクエストは止めない。設定すれば、同じ行をディレクトリのファイルにも書く（サイズと本数でローテーションし、設定すれば決まった間隔でディスクへ同期する。ファイルに書けなかった行は標準エラーに出し、数える）。ルートごとに、ログを残せないときはリクエストを 503 で拒否する形（`required`）と、ルールが判定したリクエストなどの守りのログだけを残す形（`security`）を選べる。
- 設定で loopback の監視のリスナーを置くと、`/healthz`・`/readyz`・`/metrics`（Prometheus の text の形）に応答する。systemd の `Type=notify` に、準備と停止を通知する。
- root では動かない。起動もすべてのコマンドも、user id のどれかが 0 なら拒否する。
- SIGTERM、SIGINT で新しい受付を止め、進行中のリクエストをタイムアウトまで処理してから、検査プロセスを止めて終わる。

### リクエストの前のポリシー（実装済みの範囲）

ルートを引く前にリクエストを拒否するポリシーである。WAF としての完成を意味しない。設定キーと数え方の詳細は [運用リファレンス](../../operations/operator-reference.md) の「リクエストの前のポリシー」に書く。

- 設定の最上位の `access`、`rate_limit`、`host_policies`、`geo` で決める（managed 設定を使うときは、`geo` のほかは managed 設定のバージョンに置く）。head の検証に通ったリクエストのすべてに効く（ACME のチャレンジ、監視のリスナー、managed 設定を使うときの管理画面のルートは除く）。検査除外のルートに当たるリクエストにも、https への redirect のリスナーにも効く。値は、SIGHUP と制御ソケットの `reload` のリロードで切り替わる。
- `access` は、クライアントのアドレスのネットワークと国の、許可と拒否である。ルートごとの `access` にも、国の一覧を書ける。拒否するときは 403 で応答する。
- 国は、運用者が置いた MaxMind DB の形式のデータベースで引く。データベースは同梱せず、取得もしない。private なアドレスと、データベースが知らないアドレスは、`UNKNOWN` として扱う。
- `rate_limit` は、クライアントごとのリクエストのレートを制限する。IPv4 はアドレスごと、IPv6 は /64 ごとに数える。追跡するクライアントの数に上限があり、超えると古いクライアントのカウントから外す。制限を超えたクライアントには、429 と `Retry-After` で応答する。
- `host_policies`（ホストごとの設定）は、Host がそのホストのリクエストに、全体の `access` と `rate_limit` の代わりに掛ける設定である。アクセス制御とレート制限のそれぞれで、全体の設定を引き継ぐか、このホストの設定を掛けるか、使わないかを選べる。ホストの比較の決まりはルートと同じである。Host を読めないリクエストは、どのホストにも当たりうるとして、全体とすべてのホストごとの設定の `access` に通らなければ拒否し、レート制限もそれぞれのカウンターで数える。ホストごとの設定は 64 件まで、ホストは合わせて 1024 個まで書ける。
- クライアントのアドレスは、`X-Forwarded-For` を信じる相手（設定の `trusted_proxies`）の申告だけを使って決める。

### 管理プロセス（実装済みの範囲）

管理 API と管理画面を持つ、プロキシとは別のプロセスである。WAF としての完成を意味しない。詳細は [管理リファレンス](../../operations/admin-reference.md) に書く。

- 同じ実行ファイルの `admin` コマンドで動く。プロキシと同じ OS ユーザーで動き、loopback のアドレスで平文の HTTP を待つ。外から使うときは、プロキシの TLS のリスナーのルート（managed 設定を使うときは、設定ファイルの `admin.route` に書く管理画面のルート）を通す。
- ユーザー、ロール（`viewer`、`operator`、`owner`）、セッション、API トークン、パスワードの変更、MFA（TOTP）、ログインの試行の制限、監査ログを持つ。ユーザーと API トークンと履歴はファイルに保存する。
- ルールの世代を、一覧し、インポート（事前検証付き）し、選択し、動いているプロキシへ切り替えを依頼し、前の世代へロールバックし、削除できる。切り替えの履歴を残す。
- managed 設定のバージョンを、一覧し、検証し、保存して反映し、名前で反映し、前のバージョンへロールバックし、削除できる。設定の変更履歴を残す（下の「managed 設定」）。
- プロキシへの依頼は Unix domain socket（制御ソケット）で行い、プロキシはこのソケットでは、状態の問い合わせ、世代の切り替えの依頼、managed 設定のバージョンでのリロードの依頼にだけ応答する。
- ログファイルを、時刻、type、class、status、ルール、リクエスト ID、クライアント、世代で絞って検索できる。
- 管理画面は、実行ファイルに組み込んだ静的なファイル（[`proxy/admin-ui/`](../../../proxy/admin-ui/)）を管理プロセスが配る。画面の並びは [管理リファレンス](../../operations/admin-reference.md) の「管理画面」に書く。日本語と英語に対応する。

### managed 設定（実装済みの範囲）

設定の一部を設定ファイルから分けて、管理画面と管理 API から変更する形である。WAF としての完成を意味しない。設定キーとコマンドと手順は [運用リファレンス](../../operations/operator-reference.md) の「managed 設定」、管理 API と画面は [管理リファレンス](../../operations/admin-reference.md) の「managed 設定の操作」と「管理画面」に書く。

- 設定ファイルに `managed` を書くと使う。書かなければ、設定ファイルだけで動く。有る無しを変更するときは、プロキシと管理プロセスを再起動する。
- サイトと証明書、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定を、managed ストア（設定の `managed.dir` のディレクトリ）にバージョンとして置く。バージョンの名前は中身の SHA-256 で、一度置いたバージョンの中身は変わらない。証明書チェーン、秘密鍵、CA のファイルも、中身の SHA-256 を名前にして置く。`managed` のある設定ファイルには、バージョンに置く設定キーを書けない。
- プロキシは、起動、`config check`、SIGHUP のときに、managed ストアの選択中のバージョンを設定ファイルと一緒に読む。プロキシは managed ストアに書かない。
- 管理プロセスは、管理画面の下書きから作ったバージョンを検証して保存し、制御ソケットの `reload` でプロキシに反映させる。managed ストアがそのバージョンを選択するのは、プロキシがそのバージョンで設定を切り替えた後だけで、プロキシが拒否したバージョンは選択されない。反映でプロキシは止まらない。
- managed 設定を使うときの管理画面への入口は、設定ファイルの `admin.route` に書く管理画面のルートで、プロキシが自分で作る。全体の設定とホストごとの設定は掛からず、`admin.route.access` のネットワークの一覧で守る。
- コマンド `managed`（`import`、`activate`、`list`、`remove`）で、バージョンを作り、選択し、一覧し、削除できる。ACME のサイトの証明書は、`acme renew` が managed ストアに書く。

### ログ送信プロセス（実装済みの範囲）

プロキシのログファイルを読み、行を DB の表へ送る、プロキシとは別のプロセスである。WAF としての完成を意味しない。詳細は [運用リファレンス](../../operations/operator-reference.md) の「記録の送り手」に書く。

- Rust の実行体 [`records-ship/`](../../../records-ship/)。プロキシと同じ設定ファイルを読み、同じ OS ユーザーで動く。managed 設定のバージョンは読まない。DB につなぐ部品（PostgreSQL は `tokio-postgres`、MySQL は `mysql_async`）は、この実行ファイルにだけ入れ、外からのリクエストを受けるプロキシの実行ファイルには入れない。DB のパスワードは、設定ファイルとは別のファイルに置き、ログ送信プロセスだけが読む。
- 送り先は PostgreSQL か MySQL で、設定で選ぶ。表が無ければ作る。DB への接続は、デフォルトで TLS を使い、証明書と名前を検証する。
- ログファイルを inode と作成された時刻で追い、行と送った位置を1つの transaction で入れる。行の hash を UNIQUE にして、二重に送った行を1つにする。DB に接続できない間は待ち、戻れば続きから送る。
- プロキシは、ログ送信プロセスが書く位置のファイルを読んで遅れを見積もり、`required` のルートでは、送っていないログがローテーションで削除される前にリクエストを拒否する。
- 古い行は、設定した日数で削除する。

### 実装していないもの・決まっていないこと

実装していないもの:

- HTTP の受付と転送のうち、上の範囲の外（HTTP/3、平文の HTTP/2、アップストリームへの HTTP/2、リクエストの trailer、1xx の応答の中継（WebSocket の 101 を除く）、PROXY protocol、応答のキャッシュ）。対応する範囲は OV-05
- XML のボディ、上の形の外の JSON の型（`text/json` など）、`gzip` 以外の内容の符号化のボディの検査（AR-09）
- 応答の検査（OV-04）
- 設定ファイルそのものを管理 API や管理画面で編集すること（管理画面で編集できるのは managed 設定で、設定ファイルは値を見るだけ）。管理プロセスとログ送信プロセスが、動いている間に自分の設定の値を変更すること（管理プロセスは、managed 設定の検証と変更のたびに設定ファイルを再読み込みするが、`admin` などの値は起動のときのまま使う）。実行ファイルを、接続を切らずに入れ替えること
- managed 設定のバージョンを反映する前に、そのバージョンの ACME の証明書を発行すること。ACME のサイトを追加するかホストを変更したバージョンを反映すると、managed ストアにそのホストの組の証明書が無ければ、`acme renew` で発行するまで、そのサイトのホストには TLS で接続できない
- TLS の秘密鍵を、プロキシとは別のプロセスで扱うこと（AR-04）
- 署名つきの監査ログと tracing。ユーザー・API トークン・履歴の、ファイル以外への保存。ログの、PostgreSQL と MySQL のほかへの保存。管理 API と管理画面が、DB からログを検索すること（DP-10、OV-07）
- Linux x86_64 のほかの環境の、ビルド済みの実行ファイル
- 検査プロセスとログ送信プロセスを、別の OS ユーザーや別のサービスで動かすこと（AR-04）

決まっていないこと:

- 構成の候補の全体としての採用。AR-01 は、初回の検査核に限って、Rust のライブラリと別プロセスの Go の検査プロセスの構成を採った。libcoraza との比較は終えていない。
- 通信方式、監督の担当、再起動の条件、ボディの扱いなど、各文書の未決事項は、全体としては未決定のまま。初回の検査核の実装は、これらの決定ではない。たとえば、ボディの種類による拒否は、初回の検査核の拒否の決まりで、AR-09 の決定ではない。HTTP・HTTPS の受付と転送の拒否の決まり、応答の状態コード、上限とタイムアウトも、この実装の決まりで、AR-06、AR-07、AR-16、AR-18、OV-05 の決定ではない。管理プロセス、管理 API、管理画面、ログファイル、ログ送信プロセス、リクエストの前のポリシー、managed 設定の実装も、OV-03、OV-07、AR-05、DP-10 の決定ではない。
- 全体としての安全性は評価していない。

## 前提・候補・未決定の区別

この文書群では、内容を次の区分で書き分ける。

| 区分 | 意味 |
|---|---|
| 前提 | プロジェクトの方向として示されているもの。変える場合は改めて決める |
| 候補 | 有力な案だが、検証と採用の判断を経ていないもの |
| 未決定 | 候補が絞られていないか、判断を保留しているもの |
| 実装済み | 初回の検査核、HTTP・HTTPS の受付と転送、要求の前の方針、管理のプロセス、managed 設定、記録の送り手の範囲だけ（「現在の状態」の各節）。ほかは該当なし |

### 前提

- 主な実装言語は Rust とする。
- tukuyomi から派生した、WAF の機能を中心とする製品にする。WAF 以外の機能は、基準（OV-01）が決まってから除く。
- 設計原則として、権限分離、入力を信用しない、最小主義、資源の決定性、構造的なセキュリティを置く（[設計方針・制約](design-principles.md)）。
- 管理UIは、tukuyomi の管理UIの再利用と改善を検討する。範囲と元にする版は未決定（OV-03）。
- コードは責務・型・所有者で整理し、過度にファイルを分けない。具体的なモジュールとファイルの構成は、実装時に必要に応じて決める。

### 候補

- 検査エンジンには Coraza を使う案で比較している。検査エンジンを独自に作り直す案は候補にしていない。
- 接続方式の第一候補は、Rust 本体と、Coraza の Go API を直接使う小さな Go 検査プロセスに分ける構成（AR-01）。初回の検査核に限っては、この構成のうち、Rust のライブラリと別プロセスの Go 検査プロセスを実装した。HTTP を扱う Rust 本体は、上の「HTTP・HTTPS の受付と転送」の範囲を実装した。
- 比較対象として、Rust 本体から libcoraza（Coraza の C ライブラリ）を呼ぶ構成を残す（AR-01）。

どちらの構成が速い、簡単、安全とは、検証の前には決めない。比較の観点は [アーキテクチャ概要](architecture.md) に書く。

## 用語

| 用語 | この文書群での意味 |
|---|---|
| Rust 本体 | 候補構成で、HTTP の受付・解釈・転送、設定、ログの保存を担う Rust のプロセス |
| 検査プロセス | 候補構成で、Coraza によるルールの構築と検査だけを担う Go のプロセス |
| 検査器 | ある世代のルールと設定から構築した、検査を行う単位 |
| transaction | 検査エンジンが1つのリクエスト（応答を検査する場合は応答も）を検査する単位。採用した検査範囲で必要な phase を順に処理し、終えるときにロギングフェーズ（phase 5）と Close を行う。ルートごとにどの phase を呼ぶかは AR-10 |
| phase | 検査エンジンの評価段階。順序はリクエストヘッダー、リクエストボディ、レスポンスヘッダー、レスポンスボディ、ロギング。早い段階でのブロックの後や、応答を検査しない構成では、途中の phase を呼ばないことがあり、常にすべての phase を通るわけではない |
| ルールの世代 | ある時点で有効なルールと設定の組。更新するたびに新しい世代になる |
| managed 設定 | 設定の一部（サイトと証明書、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定）を設定ファイルから分け、管理画面と管理 API から変更する形。実装済みの範囲は「現在の状態」の「managed 設定」 |
| managed ストア | managed 設定のバージョンと、バージョンが使う証明書などのファイルを置くディレクトリ（設定の `managed.dir`） |
| バージョン（managed 設定の） | managed 設定の、ある時点の中身。名前は中身の SHA-256 で、一度置いたら中身は変わらない。ルールの世代とは別のもの |
| ホストごとの設定 | Host がそのホストのリクエストに、全体のアクセス制御とレート制限の代わりに掛ける設定（`host_policies`） |
| 検査を必要とする通信 | 設定上、検査を経ずに転送してはならないと定義した通信。定義は DP-02 |

| 明示的 bypass | 設定によって、意図して検査を行わないルート（検査除外のルート）。残すかどうかは DP-01 |
| On / DetectionOnly / Off | Coraza の検査器のモード。On はルールの破壊的なアクション（拒否、切断、リダイレクトなど）を実行する。DetectionOnly はルールの評価は行うが、破壊的なアクションは実行しない。ログが残るかは、ルールと監査ログの設定による（DP-10）。Off はルールを評価しない。ルールの一致（検知）と破壊的なアクションの実行（ブロック）は別に扱う |
| fail-closed | 検査を必要とする通信が検査不能のとき、転送しない扱い。適用範囲は [設計方針・制約](design-principles.md) |
