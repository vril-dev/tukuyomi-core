## 製品の目的

tukuyomi-core は tukuyomi（tukuyomi WAF）から派生した製品で、WAF の機能に特化することを目指しています。

- どの機能を残し、どの機能を除くかの基準は未決定です（OV-01）。
  基準が決まるまでは、個々の機能を残すか除くかを決めません。
- 移植元とする tukuyomi のバージョンは未決定です（OV-02）。

### 検査カーネル（実装済みの範囲）

検査カーネルはリクエストの検査を担う部分です。
現在の実装は初期実装で、WAF としての完成を意味しません。

- **Rust のライブラリ [`kernel/`](../../../kernel/)**: 標準ライブラリだけを使い、自身ではスレッドを作らずに、呼び出し側のスレッドで動きます。
  検査プロセスの起動、停止、再起動と、起動ごとの一時ディレクトリは、このライブラリの中のスーパーバイザー（`Supervisor`）が所有します。
- **Go の検査プロセス [`inspector/`](../../../inspector/)**: Coraza の Go API を直接使います。
  検査カーネルの初期実装は Coraza v3.8.1 に固定しています。
  これは現在のコードが使うバージョンで、バージョンを推奨するものでも、DP-09 の手順を決めたものでもありません。
- **ModSecurity の検査プロセス [`inspector-modsecurity/`](../../../inspector-modsecurity/)**: Rust と C++ の橋渡しで、libmodsecurity v3.0.17 を静的にリンクします。
  ルールセットの世代ごとに、どちらのエンジンで検査するかが決まっていて、ライブラリはその世代のエンジンの検査プロセスを起動します。
  プロキシは起動したエンジンごとに検査カーネルを動かし、リクエストは行き先のアップストリームが使うエンジンの検査カーネルだけで検査します。
  どちらの検査プロセスも同じプロトコルで通信し、下の保護の仕組みを同じように持ちます（[運用リファレンス](../../operations/operator-reference.ja.md) の「ModSecurity の世代」）。
- 検査プロセスはライブラリが直接起動し、同じホストの中で、引き継いだ Unix ドメインソケットのペア（検査プロセスの fd 0）で通信します。
  ライブラリも検査プロセスも、TCP で待ち受けるポートを増やしません。
- リクエストごとの結果は、許可（`Allow`）、ブロック（`Block`）、検査不能（`Uninspectable`）の 3 つです。
  検査を完了できなかったリクエストは、許可になりません。
  検査できないと分かっている入力は、受け付けの時点で呼び出し側に返し（`Refused`）、許可にしません。
  たとえば、ボディがあって Content-Type が `application/x-www-form-urlencoded`、`multipart/form-data`、`application/json`、`application/<name>+json` のどれでもないリクエストは、この形で返します。
  Content-Encoding を伴うリクエストと、Transfer-Encoding を伴うリクエストも同じです。
  ただし、ボディの先頭だけを渡すリクエストのうち、Transfer-Encoding が `chunked` の 1 行だけで Content-Length を持たないものは受け付けます（HTTP/1.1 の chunked のボディの先頭を検査するためです）。
- 再起動の回数には、直近の一定の時間（設定のウィンドウ）の中での上限があります。
  上限に達したら、ウィンドウ内の再起動の回数が上限を下回るまで再起動せず、その間に待っているリクエストは検査不能にします（HTTP では 503）。
  ルールのエラーなどの決定的な失敗では、再起動しません。
- 一時ディレクトリは起動ごとに専用のものを、プロセスの OS ユーザーだけが使える権限で作り、検査プロセスの終了を確認した後に削除します。
  終了を確認できないときは削除せずに残し、新しい検査プロセスを起動しません。
- 検査プロセスは、ルールセットの世代を読んだ後に、Landlock で一時ディレクトリの外のファイルに触れられなくします（Linux 6.7 以上では TCP のバインドと接続も禁止します）。
  さらに、ケーパビリティを破棄し、`no_new_privs` を設定します。
  Landlock が無い Linux では起動しません。
  UDP、Unix ドメインソケット、MPTCP のソケットは制限できません。
- 1 つのリクエストで検査に渡せるボディは 1 MiB までです。
  ボディの先頭だけを渡すときは、切り詰めたことを検査プロセスに通知します。
  切り詰めたことが原因でボディの解析に失敗しても、ブロックはしません。

### HTTP／HTTPS の受信と転送（実装済みの範囲）

リクエストの受信と転送を担う部分で、検査カーネルの前に置きます。
WAF としての完成を意味しません。
設定キー、コマンド、ログの詳細は、[運用リファレンス](../../operations/operator-reference.ja.md) を参照してください。

- **Rust の実行ファイル [`proxy/`](../../../proxy/)**: tokio、hyper、rustls を使い、検査カーネルをライブラリとして使います。
  リスナー、アップストリーム、ルート、各段階の上限とタイムアウトは、1 つの設定ファイル（JSON）で決めます。
  managed 設定を使うときは、アップストリーム、ルート、デフォルトのアップストリーム、サイトと証明書、全体のアクセス制御とレート制限、ホストごとの設定を managed 設定のバージョンに置き、それ以外を設定ファイルに置きます（下の「managed 設定」）。
  設定の値にデフォルト値はなく、範囲と値どうしの関係は起動時に検証します。
  `config check` のコマンドを使うと、起動の前に同じ検証を実行できます。
- リスナーは 1〜8 個で、種類は平文の HTTP、TLS（1.2・1.3、サーバー名で証明書を選択）、https へのリダイレクトの 3 つです。
  HTTP/1.1 と HTTP/1.0 を扱い、TLS のリスナーでは HTTP/2 も扱えます。
  接続の再利用（keep-alive とパイプライン処理）に対応しています。
- アップストリームは名前を付けたサーバーのグループで、サーバーは重みで選びます。
  失敗が続いたサーバーは一時的に除外し（ダウン判定）、バックアップのサーバーを持つこともできます。
  接続は再利用します。
  2 回送っても問題の無いメソッドのリクエストは、次のサーバーへ再送できます。
  サーバーの名前は、起動時と設定のリロード時に名前解決します。
  アップストリームごとに TLS で接続できます（アップストリームへは HTTP/1.1）。
- ルートは、リクエストの Host とパスでアップストリームを選びます。
  ルートごとに、クライアントの IP アドレスと国による制限、リクエストとレスポンスの書き換え（Host、パス、クエリ、ヘッダー）、ボディの上限、ストリーミング応答と WebSocket の扱いを決められます。
  WebSocket のフレームは検査しません。
- リクエストのヘッダー部は、HTTP の解析の前に厳格に検証します。
  たとえば、行の終わりは CRLF だけ、request-target は origin-form だけ、Host はちょうど 1 つに限ります。
  Transfer-Encoding と Content-Length の併用は拒否します。
  違反や上限の超過があれば、ボディの無い決まった応答（400、408、413、414、415、417、431）で拒否し、アップストリームへは何も送りません。
  HTTP/2 のリクエストも同じ形に書き直し、同じ決まりで検証します。
- ボディは、先頭から設定したバイト数（1 MiB まで）を検査します。
  それより長いボディは、許可された後、残りを検査せずにアップストリームへ流します。
  chunked のボディに対応しています。
  Content-Encoding は `gzip` だけを受け付け、検査するルートでは、伸長したボディを Content-Encoding なしで検査します（伸長した後に検査する長さを超えるもの、壊れたもの、ほかの符号化方式は拒否します）。
  検査するルートで扱うボディの型は、検査カーネルと同じく `application/x-www-form-urlencoded`、`multipart/form-data`、`application/json`、`application/<name>+json`（名前は英数字・`.`・`-`）だけで、ほかの型は 415 で拒否します。
  検査除外のルートでは、ボディの型を問わずに流します。
  どのルートでも、Content-Type を 2 つ以上持つボディは 415 で拒否します。
  JSON の型のボディは、検査プロセスが Coraza の JSON ボディプロセッサーを選んで解析します（運用者のルールでは変更できません）。
  JSON の入れ子は 64 段までです（配列の入れ子は、展開した量に上限があるため、短いボディではそれより浅くてもブロックされることがあります）。
  64 段を超えるボディ、RFC 8259 に合わないボディ、引数の数の上限を超えるボディはブロックします。
- アップストリームへ転送するのは、検査で許可（`Allow`）されたリクエスト、検知のみのモードでルールに一致したリクエスト、検査除外のルートのリクエストだけです。
  転送の前に、接続ごとのヘッダー（hop-by-hop ヘッダー。Connection とそれが挙げるもの、Keep-Alive、TE、Transfer-Encoding、Upgrade、Expect など）と、名前に `_` を含むヘッダーを除き、X-Forwarded-For、X-Forwarded-Host、X-Forwarded-Proto を付けます。
  X-Forwarded-For は、設定で信頼したプロキシからのものだけを残します。
  ブロックしたリクエストにはルールのステータスコード（200〜599 の範囲外は 500）で、検査不能のリクエストには 503（プログラムの内部の不整合を示すものは 500）で応答し、どちらも転送しません。
  アップストリームへの接続の失敗、タイムアウト、不正な応答などには、502 で応答します。
- ルールセットはコマンド `rules import` でインポートし、事前検証に通ったものを世代にします。
  世代は `rules activate` でエンジンごとに選択し、SIGUSR1 で、選択した世代へ無停止で切り替えます。
  検査するエンジンは、アップストリームごとに選べます（[運用リファレンス](../../operations/operator-reference.ja.md) の「検査エンジンの選択」）。
  世代にはブロックするものと検知のみのもの（ルールに一致しても通してログに残す）があり、検査除外のルート（Host とパス）も持たせられます。
  CRS は同梱せず、バージョンとチェックサムを固定したスクリプトでダウンロードします。
- 証明書は、ファイルを置くか、コマンド `acme renew`（ACME の HTTP-01）で発行・更新します。
  再読み込みは SIGUSR2 で行います。
  managed 設定を使うときは、サイトの証明書を managed ストアに置きます（下の「managed 設定」）。
- SIGHUP を受けると、設定ファイルをリロードし、停止せずに新しい設定に切り替えます。
  managed 設定を使うときは、managed ストアの選択中のバージョンも一緒に読みます。
  管理プロセスは、制御ソケットの `reload` で、バージョンを指定した同じリロードを依頼します。
  切り替わるのは、ルートとアップストリーム、アクセス制御とレート制限（国のデータベースを含みます）、リスナーの追加と削除、証明書などです。
  新しい設定を使うのは、切り替えた後に受け付けた接続からです。
  開いている接続は、受け付けたときの設定でリクエストを終えてから閉じ、リクエストは拒否しません。
  受け付けない設定（エラーのあるもの、動作中に変更できない設定キーの違い、稼働していないエンジンを参照するアップストリーム、バインドできないリスナー）では、何も変更しません。
- ログは、標準エラーに 1 行 1 件の JSON で出します。
  リクエストごとのログは、リクエスト ID、メソッド・Host・パス（クエリは含めません）、応答、判定したルールの世代、一致したルールの ID と重大度と anomaly score を持ちます。
  リクエスト ID は、アップストリームへ送るリクエストとクライアントへの応答の `X-Request-ID` にも入れます（クライアントが送った値は置き換えます）。
  書けないログは破棄してその件数を数え、リクエストは止めません。
  設定すれば、同じ行をディレクトリのファイルにも書きます。
  ファイルはサイズと本数でローテーションし、設定すれば一定の間隔でディスクへ同期します。
  ファイルに書けなかった行は、標準エラーに出して件数を数えます。
  ルートごとに、ログを残せないときはリクエストを 503 で拒否する形（`required`）と、ルールが判定したリクエストなどのセキュリティのログだけを残す形（`security`）を選べます。
- 設定でループバックアドレスに監視用のリスナーを置くと、`/healthz`・`/readyz`・`/metrics`（Prometheus のテキスト形式）に応答します。
  systemd には、`Type=notify` で準備の完了と停止を通知します。
- root では動かず、起動もすべてのコマンドも、ユーザー ID のどれかが 0 なら拒否します。
- SIGTERM か SIGINT を受けると、新しい接続とリクエストの受け付けを止めます。
  処理中のリクエストはタイムアウトまで処理し、その後、検査プロセスを停止して終了します。

### アクセス制御とレート制限（実装済みの範囲）

アクセス制御とレート制限は、ルートを選ぶ前にリクエストを拒否する仕組みです。
WAF としての完成を意味しません。
設定キーとカウントの方法の詳細は、[運用リファレンス](../../operations/operator-reference.ja.md) の「アクセス制御とレート制限」を参照してください。

- 設定は最上位の `access`、`rate_limit`、`host_policies`、`geo` で決めます（managed 設定を使うときは、`geo` のほかは managed 設定のバージョンに置きます）。
  ヘッダー部の検証に通ったすべてのリクエストに適用します（ACME のチャレンジ、監視用のリスナー、managed 設定を使うときの管理画面のルートは除きます）。
  検査除外のルートに一致するリクエストにも、https へのリダイレクトのリスナーにも適用します。
  値は SIGHUP や制御ソケットの `reload` によるリロードで切り替わります。
- `access` は、クライアントのアドレスが属するネットワークと、国による許可と拒否です。
  ルートごとの `access` にも、国を指定できます。
  拒否するときは 403 で応答します。
- 国は運用者が置いた MaxMind DB 形式のデータベースで判定します。
  データベースは同梱しておらず、ダウンロードもしません。
  プライベートアドレスと、データベースに無いアドレスは、`UNKNOWN` として扱います。
- `rate_limit` はクライアントごとのリクエストのレートを制限し、IPv4 はアドレスごと、IPv6 は /64 ごとに数えます。
  追跡するクライアントの数には上限があり、上限を超えると、古いクライアントをカウントの対象から外します。
  制限を超えたクライアントには、429 と `Retry-After` で応答します。
- `host_policies`（ホストごとの設定）は、Host がそのホストであるリクエストに、全体の `access` と `rate_limit` の代わりに適用する設定です。
  アクセス制御とレート制限のそれぞれについて、全体の設定を引き継ぐか、このホストの設定を適用するか、使わないかを選べます。
  ホストを比べる決まりは、ルートと同じです。
  Host を読めないリクエストは、どのホストにも一致しうるものとして扱い、全体の設定と、すべてのホストごとの設定の `access` に通らなければ拒否します。
  レート制限も、それぞれのカウンターで数えます。
  ホストごとの設定は 64 件まで、ホストは合わせて 1024 個まで書けます。
- クライアントのアドレスは、信頼する相手（設定の `trusted_proxies`）から受けた `X-Forwarded-For` の値だけを使って決めます。

### 管理プロセス（実装済みの範囲）

プロキシとは別のプロセスで、管理 API と管理画面を提供します。
WAF としての完成を意味しません。
詳細は、[管理リファレンス](../../operations/admin-reference.ja.md) を参照してください。

- プロキシと同じ実行ファイルの `admin` コマンドで動きます。
  プロキシと同じ OS ユーザーで動き、ループバックアドレスで平文の HTTP の接続を待ち受けます。
  外部から使うときは、プロキシの TLS リスナーのルートを通します（managed 設定を使うときは、設定ファイルの `admin.route` に書く管理画面のルート）。
- ユーザー、ロール（`viewer`、`operator`、`owner`）、セッション、API トークン、パスワードの変更、MFA（TOTP）、ログインの試行回数の制限、監査ログを持ちます。
  ユーザー、API トークン、履歴は、ファイルに保存します。
- ルールの世代について、一覧表示、インポート（事前検証付き）、選択、動作中のプロキシへの切り替え依頼、前の世代へのロールバック、削除ができます。
  選択、切り替え依頼、ロールバックは、エンジンごとに行います。
  切り替えの履歴を残します。
- managed 設定のバージョンについて、一覧表示、検証、保存と反映、名前を指定した反映、前のバージョンへのロールバック、削除ができます。
  設定の変更履歴を残します（下の「managed 設定」）。
- プロキシへの依頼には、Unix ドメインソケット（制御ソケット）を使います。
  このソケットでプロキシが応答するのは、状態の問い合わせ、世代の切り替えの依頼（切り替えるエンジンを指定します）、managed 設定のバージョンを指定したリロードの依頼だけです。
- ログファイルを、時刻、type、class、status、ルール、リクエスト ID、クライアント、世代、エンジンで絞り込んで検索できます。
- 管理画面は、実行ファイルに組み込んだ静的なファイル（[`proxy/admin-ui/`](../../../proxy/admin-ui/)）で、管理プロセスが提供します。
  画面の構成は、[管理リファレンス](../../operations/admin-reference.ja.md) の「管理画面」を参照してください。
  画面は日本語と英語に対応しています。

### managed 設定（実装済みの範囲）

managed 設定は、設定の一部を設定ファイルから分けて、管理画面と管理 API から変更する仕組みです。
WAF としての完成を意味しません。
設定キー、コマンド、手順については、[運用リファレンス](../../operations/operator-reference.ja.md) の「managed 設定」を参照してください。
管理 API と画面については、[管理リファレンス](../../operations/admin-reference.ja.md) の「managed 設定の操作」と「管理画面」を参照してください。

- 設定ファイルに `managed` を書くと managed 設定を使い、書かなければ設定ファイルだけで動きます。
  使うかどうかを切り替えるときは、プロキシと管理プロセスを再起動します。
- サイトと証明書、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定を、managed ストア（設定の `managed.dir` のディレクトリ）にバージョンとして保存します。
  バージョンの名前は内容の SHA-256 で、一度保存したバージョンの内容は変わりません。
  証明書チェーン、秘密鍵、CA のファイルも、内容の SHA-256 を名前にして保存します。
  `managed` のある設定ファイルには、バージョンに含める設定キーは書けません。
- プロキシは、起動時、`config check` の実行時、SIGHUP の受信時に、managed ストアの選択中のバージョンを設定ファイルと一緒に読みます。
  プロキシは managed ストアに書き込みません。
- 管理プロセスは、管理画面の下書きから作ったバージョンを検証して保存し、制御ソケットの `reload` でプロキシに反映させます。
  managed ストアがそのバージョンを選択するのは、プロキシがそのバージョンで設定を切り替えた後だけで、プロキシが拒否したバージョンは選択されません。
  反映してもプロキシは停止しません。
- managed 設定を使うときの管理画面の入口は、設定ファイルの `admin.route` に書く管理画面のルートで、プロキシが自分で作ります。
  このルートには全体の設定とホストごとの設定は適用されず、`admin.route.access` のネットワークの一覧で保護します。
- コマンド `managed`（`import`、`activate`、`list`、`remove`）で、バージョンの作成、選択、一覧の表示、削除ができます。
  ACME のサイトの証明書は、`acme renew` が managed ストアに書きます。

### ログ送信プロセス（実装済みの範囲）

プロキシとは別のプロセスで、プロキシのログファイルを読み、行を DB のテーブルへ送ります。
WAF としての完成を意味しません。
詳細は、[運用リファレンス](../../operations/operator-reference.ja.md) の「ログ送信プロセス」を参照してください。

- **Rust の実行ファイル [`records-ship/`](../../../records-ship/)**: プロキシと同じ設定ファイルを読み、同じ OS ユーザーで動きます。
  managed 設定のバージョンは読みません。
  DB に接続するライブラリ（PostgreSQL は `tokio-postgres`、MySQL は `mysql_async`）は、この実行ファイルにだけ入れ、外部からのリクエストを受けるプロキシの実行ファイルには入れません。
  DB のパスワードは、設定ファイルとは別のファイルに置き、ログ送信プロセスだけが読みます。
- 送信先は PostgreSQL か MySQL で、設定で選びます。
  テーブルが無ければ作ります。
  DB への接続にはデフォルトで TLS を使い、証明書とホスト名を検証します。
- ログファイルは inode と作成時刻で追跡し、行と送信済みの位置は 1 つのトランザクションで書き込みます。
  行のハッシュを UNIQUE にしてあるため、二重に送った行は 1 つにまとまります。
  DB に接続できない間は待ち、接続が戻ったら続きから送ります。
- プロキシはログ送信プロセスが送信済みの位置を書くファイルを読んで、遅れを見積もります。
  `required` のルートでは、未送信のログがローテーションで削除される前に、リクエストを拒否します。
- 古い行は、設定した日数が過ぎたら削除します。

### 実装していないもの・決まっていないこと

実装していないもの:

- HTTP の受信と転送のうち、上の範囲外のもの（HTTP/3、平文の HTTP/2、アップストリームへの HTTP/2、リクエストのトレーラー、1xx の応答の中継（WebSocket の 101 を除きます）、PROXY protocol、応答のキャッシュ）。
  対応する範囲は OV-05
- XML のボディ、上の形以外の JSON の型（`text/json` など）、`gzip` 以外の Content-Encoding を持つボディの検査（AR-09）
- 応答の検査（OV-04）
- 設定ファイルそのものを、管理 API や管理画面で編集すること（管理画面で編集できるのは managed 設定で、設定ファイルは値を表示するだけです）。
  管理プロセスとログ送信プロセスが、動作中に自分の設定の値を変更すること（管理プロセスは、managed 設定の検証と変更のたびに設定ファイルを再読み込みしますが、`admin` などの値は起動時の値のまま使います）。
  実行ファイルを、接続を切らずに入れ替えること
- managed 設定のバージョンを反映する前に、そのバージョンの ACME の証明書を発行すること。
  ACME のサイトを追加したバージョンや、ホストを変更したバージョンを反映したときに、そのホストの組み合わせの証明書が managed ストアに無ければ、`acme renew` で発行するまで、そのサイトのホストには TLS で接続できません
- TLS の秘密鍵を、プロキシとは別のプロセスで扱うこと（AR-04）
- 署名付きの監査ログとトレーシング。
  ユーザー・API トークン・履歴を、ファイル以外へ保存すること。
  ログを、PostgreSQL と MySQL 以外へ保存すること。
  管理 API と管理画面で、DB からログを検索すること（DP-10、OV-07）
- Linux x86_64 以外の環境用の、ビルド済みの実行ファイル
- 検査プロセスとログ送信プロセスを、別の OS ユーザーや別のサービスで動かすこと（AR-04）

決まっていないこと:

- 構成の候補を、全体として採用するかどうか。
  AR-01 では、検査カーネルの初期実装に限って、Rust のライブラリと、別プロセスで動く Go の検査プロセスという構成を採りました。
  libcoraza との比較は終えていません。
- 通信方式、スーパーバイザーの担当、再起動の条件、ボディの扱いなど、各文書の未決事項は、全体としては未決定のままです。
  現在の検査カーネルの実装は、これらを決めたものではありません。
  たとえば、ボディの種類による拒否は、検査カーネルの初期実装が採っている拒否の決まりで、AR-09 を決めたものではありません。
  HTTP／HTTPS の受信と転送での拒否の規則、応答のステータスコード、上限とタイムアウトも、この実装が採っている決まりで、AR-06、AR-07、AR-16、AR-18、OV-05 を決めたものではありません。
  管理プロセス、管理 API、管理画面、ログファイル、ログ送信プロセス、アクセス制御とレート制限、managed 設定の実装も、OV-03、OV-07、AR-05、DP-10 を決めたものではありません。
- 全体としての安全性は評価していません。

## 前提・候補・未決定の区別

この文書群では、内容を次の区分で書き分けます。

| 区分 | 意味 |
|---|---|
| 前提 | プロジェクトの方向として示されているもの。変える場合は、改めて決めます |
| 候補 | 有力な案ですが、検証と採用の判断を経ていないもの |
| 未決定 | 候補が絞られていないか、判断を保留しているもの |
| 実装済み | 検査カーネル、HTTP／HTTPS の受信と転送、アクセス制御とレート制限、管理プロセス、managed 設定、ログ送信プロセスの範囲だけ（「現在の状態」の各節）。ほかは該当しません |

### 前提

- 主な実装言語は Rust とします。
- tukuyomi から派生した、WAF の機能を中心とする製品にします。
  WAF 以外の機能は、基準（OV-01）が決まってから除きます。
- 設計原則として、権限分離、入力を信用しない、最小主義、資源の決定性、構造的なセキュリティを置きます（[設計方針・制約](design-principles.ja.md)）。
- 管理 UI については、tukuyomi の管理 UI を再利用し、改善することを検討します。
  範囲と元にするバージョンは未決定です（OV-03）。
- コードは責務・型・所有者で整理し、ファイルは過度に分けません。
  具体的なモジュールとファイルの構成は、実装時に必要に応じて決めます。

### 候補

- 検査エンジンには Coraza を使う案で比較しており、独自に作り直す案は候補にしていません。
- 接続方式の第一候補は、Rust のプロキシと、Coraza の Go API を直接使う小さな Go の検査プロセスに分ける構成です（AR-01）。
  検査カーネルの初期実装に限っては、この構成のうち、Rust のライブラリと、別プロセスで動く Go の検査プロセスを実装しました。
  HTTP を扱う Rust のプロキシは、上の「HTTP／HTTPS の受信と転送」の範囲を実装しました。
- 比較の対象として、Rust のプロキシから libcoraza（Coraza の C ライブラリ）を呼び出す構成を残します（AR-01）。

どちらの構成が速いか、簡単か、安全かは、検証の前には決めません。
比較の観点は、[アーキテクチャ概要](architecture.ja.md) を参照してください。

## 用語

| 用語 | この文書群での意味 |
|---|---|
| Rust のプロキシ | 候補の構成で、HTTP の受信・解釈・転送、設定、ログの保存を担う Rust のプロセス |
| 検査カーネル | リクエストの検査を担う部分。Rust のライブラリ（`kernel/`）と Go の検査プロセス（`inspector/`）からなります。ModSecurity の世代では、ライブラリが ModSecurity の検査プロセス（`inspector-modsecurity/`）を起動します |
| 検査プロセス | 候補の構成で、Coraza によるルールの構築と検査だけを担う Go のプロセス |
| WAF インスタンス | ある世代のルールと設定から構築した、検査を行う単位 |
| トランザクション | 検査エンジンが 1 つのリクエスト（応答を検査する場合は応答も）を検査する単位。採用した検査範囲で必要なフェーズを順に処理し、終えるときにロギングフェーズ（phase 5）と Close を行います。ルートごとにどのフェーズを呼ぶかは AR-10 |
| フェーズ（phase） | 検査エンジンの評価の段階。順序は、リクエストヘッダー、リクエストボディ、レスポンスヘッダー、レスポンスボディ、ロギングです。早い段階でブロックした後や、応答を検査しない構成では、途中のフェーズを呼ばないことがあり、常にすべてのフェーズを通るわけではありません |
| ルールの世代 | ある時点で有効なルールと設定の組み合わせ。更新するたびに、新しい世代になります。エンジンごとに 1 つ選択します |
| managed 設定 | 設定の一部（サイトと証明書、アップストリーム、ルート、デフォルトのアップストリーム、全体のアクセス制御とレート制限、ホストごとの設定）を設定ファイルから分け、管理画面と管理 API から変更する仕組み。実装済みの範囲は「現在の状態」の「managed 設定」 |
| managed ストア | managed 設定のバージョンと、バージョンが使う証明書などのファイルを置くディレクトリ（設定の `managed.dir`） |
| バージョン（managed 設定の） | managed 設定の、ある時点の内容。名前は内容の SHA-256 で、一度保存したら内容は変わりません。ルールの世代とは別のものです |
| ホストごとの設定 | Host がそのホストであるリクエストに、全体のアクセス制御とレート制限の代わりに適用する設定（`host_policies`） |
| 検査を必要とする通信 | 設定上、検査を経ずに転送してはならないと定義した通信。定義は DP-02 |
| 検査不能 | 停止、通信の切断、タイムアウト、上限の超過などの技術的な理由で、検査を完了できない状態。意図して検査しない場合とは区別して扱います |
| 明示的なバイパス | 設定によって、意図して検査を行わないルート（検査除外のルート）。残すかどうかは DP-01 |
| On / DetectionOnly / Off | Coraza の WAF インスタンスのモード。On は、ルールの破壊的なアクション（拒否、切断、リダイレクトなど）を実行します。DetectionOnly は、ルールの評価は行いますが、破壊的なアクションは実行しません。ログが残るかどうかは、ルールと監査ログの設定によります（DP-10）。Off はルールを評価しません。ルールの一致（検知）と、破壊的なアクションの実行（ブロック）は、区別して扱います |
| fail-closed | 検査を必要とする通信が検査不能のときに、転送しない扱い。適用範囲は [設計方針・制約](design-principles.ja.md) を参照してください |

## 未決事項

未決事項には文書をまたいで重複しない ID を付け、この文書では OV- を使います。
構成に関するものは AR-（[アーキテクチャ概要](architecture.ja.md)）に、原則と方針に関するものは DP-（[設計方針・制約](design-principles.ja.md)）に置きます。

| ID | 事項 | 現在の扱い | 影響する範囲 |
|---|---|---|---|
| OV-01 | 残す機能・除く機能の基準 | 未決定。決まるまで、機能を残すか除くかは決めません | 機能要件、AR-07、DP-01、DP-07、DP-08 |
| OV-02 | 移植元とする tukuyomi のバージョン | 未決定 | 移植の前例、上流の動作の確認 |
| OV-03 | 管理 UI の再利用・改善の範囲と、元にするバージョン | 再利用と改善を検討することは前提。範囲とバージョンは未決定 | UI 設計、AR-05、DP-10 |
| OV-04 | 応答の検査を行うか、行う場合の範囲 | 未決定 | AR-08、AR-10、状態 × 操作の「応答の返却」 |
| OV-05 | 対応する HTTP のバージョンと通信の種類（HTTP/1.1、HTTP/2、HTTP/3、Upgrade、逐次送信など） | 未決定 | AR-06、AR-08 |
| OV-06 | 配布形態（単一の実行ファイルが必須かを含みます）、対応する環境、デプロイ構成 | 未決定 | AR-01、AR-03、AR-04、AR-13、AR-17、DP-09 |
| OV-07 | 設定・ルール・ログの保存方式 | 未決定 | AR-05、AR-11、DP-10 |
